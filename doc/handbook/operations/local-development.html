Before starting

Prerequisites

  • Python 3.11+ and repository virtual environment
  • Node/npm compatible with the frontend lockfile
  • Docker, and the Supabase CLI at the version every workflow pins (2.116.0), installed with npm as CI installs it: npm install -g supabase@2.116.0. The CLI version decides which Postgres, PostgREST and GoTrue images supabase start boots, so preflight fails on any other (scripts/check_supabase_cli.py, WFSETUP.03). The same gate fails when an extension in LOCAL’s database differs from the one the image ships, older or pointing at a library file the image lacks (WFSETUP.04): CI starts from an empty database, while LOCAL keeps its database, extensions included, when the CLI changes. The local mail catcher is off: [local_smtp] in supabase/config.toml has enabled = false
  • Ruff and BasedPyright through development dependencies/tooling
  • Postgrestools for SQL semantic/safety checks (configuration postgres-language-server.jsonc; LOCAL gets the pgTAP and plpgsql_check extensions it relies on from supabase/seed_dev_tooling.sql, which ./scripts/reset-dev.sh loads and CERT and PROD never receive)
  • Graphify for architecture/impact analysis

First run

Install and start

source .venv/bin/activate
pip install -e ".[dev]"

cd frontend
npm ci
cd ..

supabase start
./scripts/reset-dev.sh

cd frontend
npm run dev
Never run bare supabase db reset. Use ./scripts/reset-dev.sh; it resets LOCAL and recreates the expected admin account.

Validation loops

It first runs three canary files to prove type checking and plpgsql_check reached the database, because postgrestools skips both silently and exits 0 when it cannot connect. A finding the checker cannot avoid (an object the test file creates itself, a psql \gset line, migration lock rules in a test) carries an inline -- pgt-ignore…: <reason>; an unused suppression is itself a warning.

Run the smallest relevant test first. Before completion, run all suites applicable to the changed behavior. Record anything intentionally not run.

Implementation discipline

TDD order

  1. Define acceptance assertions and plan-test IDs.
  2. Write tests.
  3. Run and prove RED.
  4. Implement the minimum behavior.
  5. Run and prove GREEN.
  6. Refactor while remaining green.

Troubleshooting

  • Database semantic checks require the configured LOCAL instance on port 54322. If it is down, scripts/check-postgrestools.sh fails on its canaries instead of passing.
  • If postgrestools reports pgTAP calls such as plan() or is() as 42883 “function does not exist”, LOCAL is missing the tooling extensions: run ./scripts/reset-dev.sh.
  • After a Supabase CLI change, python scripts/check_supabase_cli.py names every extension that differs from the new image and the command that brings it back, run as supabase_admin (the extensions’ owner; as postgres, ALTER EXTENSION fails with “pgaudit stack is not empty”): an update where the image has a path and the library is present, otherwise a drop and a create in the same schema. ./scripts/reset-dev.sh also brings it back, and replaces LOCAL’s data with the seed.
  • Svelte files are checked through svelte-check; generic TypeScript LSP alone is insufficient.
  • Integration tests may require live external APIs; distinguish them from deterministic unit tests.
  • Do not install Python packages into the system interpreter; use the virtual environment.
