Environments and release

Keep development, certification and production responsibilities distinct; move software and approved data through explicit contracts.

LOCAL → CERT → PRODWorkflow controlledVerified 4 October 2026

Environment roles

Environment contract

LOCAL

Development, schema iteration, test execution and operator preparation. Safe to rebuild through repository scripts; never a source for production credentials.

CERT

Certification and review surface. Receives release candidates and curated data, supports parity checks and becomes the approved source for production promotion.

PROD

Published system. Changes are deliberate, auditable and protected from experimental/manual shortcuts.

Each host serves one environment (ADR-109). github.io is CERT: the application opens on CERT only, under a yellow TEST ribbon that links to weteraniszermierki.pl, with no environment switch; it keeps the PROD pair only to read which seasons PROD already holds for promotion. weteraniszermierki.pl is PROD: its pages hold the PROD pair only. On the file host, register.html and the embed/ documents the WordPress pages frame are PROD-only too.

Software delivery

Release flow

  1. Run local tests, format/type gates, documentation checks and coherence.
  2. Push the intended commit with unrelated work excluded.
  3. CI validates database, Python, frontend and generated documentation.
  4. The release workflow’s gate job (ADR-094) resolves the diff since CI last completed on main and runs scripts/release-gate.sh; if every changed path is documentation-only (doc/, or a root CLAUDE.md/AGENTS.md/README.md), the run stops here — no build, no deploy. Any deployable path, a manual dispatch, or an unresolvable diff range deploys.
  5. When the gate passes, the workflow builds/deploys schema, functions and frontend artifacts to the intended environment.
  6. Frontend artifacts reach both hosts from one build. GitHub Pages serves the application, register.html, the published calculator and annex with their embed/ copies, and the custom-element bundle. The build injects the CERT pair into index.html and the github.io calculator and annex; the PROD pair into register.html, the embed/ copies, and index.html for the promotion read. The step “Verify the WordPress embed copies are PROD-only” then fails the release if an embed/ copy is missing, carries a CERT pair or lacks the PROD URL.
  7. Every WordPress page on weteraniszermierki.pl loads the bundle’s stable entry assets/main.ce.js by that exact URL. A release therefore updates the association’s site with no upload and no WordPress change, and reaches every visitor within ten minutes, because Pages serves the bundle with max-age=600. A rename of that file breaks the site silently, which is why the build guards the name. A page body changes only after the bundle it needs has shipped.
  8. Verify CERT before allowing production continuation.
  9. Pages does not wait for the production approval, so the github.io application and every WordPress page run the new code while PROD’s database may still wait. Hence the rule (ADR-109): code that needs a new database object ships one release after the migration that creates it, and PROD is approved within minutes of CERT.
  10. Verify production health and update release tracking/seed artifacts where required.

Recovery

Failure boundaries

  • A CI failure blocks release; fix or prove transient before rerun.
  • A CERT verification failure blocks PROD.
  • A wrong WordPress page body is republished from its reference copy, or set to draft at once (operator runbooks); the page is never deleted, because the menu names its id.
  • A reconciliation transaction failure rolls back the unit of work; inspect the generated report/log.
  • A protected deletion becomes reported divergence, not a forced erase.
  • Do not edit deployed migrations; add a corrective migration.
  • A from-scratch bootstrap (CI's supabase start, any full db reset) applies migrations before the seed dump loads, so a data migration that resolves pre-existing rows by name runs against empty tables there even though every row exists on the long-running tiers. Guard such lookups and skip with a NOTICE rather than calling a fail-loud RPC. Rationale and rules: ADR-036 amendment (2026-07-14); worked example: fencer birth-year master-list reconciliation.
  • The seed carries PROD’s fencer ids. Its fencer section is one call of fn_seed_load_fencers with PROD’s roster and id sequence.
    • The call moves the fencers that data migrations created to their PROD ids, creates everyone else at PROD’s id and sets the sequence.
    • It refuses, by name, a fencer the roster lacks or describes twice, and it fails unless the roster then equals PROD’s.
    • Every result in the seed names its fencer by id.
    scripts/mirror-prod-local.sh then checks LOCAL against live PROD, id for id (python -m python.pipeline.promotion.refresh --target local --mode verify), and stops on any difference (ADR-036 §1). It then loads PROD’s registrations with the CERT refresh’s own copy, for every PROD event with entries (python -m python.pipeline.promotion.refresh --target local --mode registrations): the columns the ingestion reads, never the e-mail hash, edit token or consent stamp. The step fails unless each event’s registrations part of the input fingerprint then equals PROD’s, so a LOCAL promote rehearsal starts from PROD’s inputs (ADR-036 §3).
  • Use documented mirror/export/snapshot scripts before risky data operations.
  • Tracking/reconcile-log commit steps (release.yml deploy-cert/deploy-prod, evf-sync.yml promote jobs) retry on a rejected push by fetching and rebasing onto origin/main, since concurrent runs commit to the same auto-generated files; a failure here after 5 attempts is a real conflict needing investigation, not routine contention.

Security

Secrets and delivery gates

GitHub environment secrets and Supabase deployment credentials are environment-scoped. Browser code receives public configuration only. Workflow dispatch uses trusted server-side infrastructure. Rotate any credential exposed in source, logs or chat.

Names and locations only: documentation and agent memory may name paths and variables, but must never copy their values. There is no FTL e-mail delivery on any environment — it was never commissioned and the project cannot send e-mail; the organizer downloads their own files from a capability-gated page. See ADR-080 amendment 2026-09-25.

Definition of done

Release verification

  • All required jobs concluded successfully.
  • Expected schema migration set is deployed.
  • Frontend artifact/version/environment is correct.
  • Public ranklist/calendar and protected admin authentication load: on github.io under the TEST ribbon with no switch, and on the WordPress pages with the new bundle.
  • Promotion/reconciliation report shows expected convergence.
  • No unrelated local files were staged or pushed.
  • Tracking and documentation reflect the shipped state.
