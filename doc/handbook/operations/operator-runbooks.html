Before any command

Operating principles

  • Confirm environment, season and event code before mutation.
  • Prefer event-scoped actions over bulk operations.
  • Review generated reports and divergences, not only exit status.
  • Do not advance to the next event without required human sign-off.
  • Do not force-delete results-bearing data to make parity “green.”
  • Capture workflow/run id and final outcome for handoff.

Runbook

Ingest or review one event

  1. Verify the recorded source URL/file and event identity.
  2. Run the event-scoped ingest/review command or ingest-event.yml (Telegram ingest <exact code> <url>). It runs on CERT only: a domestic event reaches PROD through promote.
  3. Inspect parse counts, pool/category handling, identity outcomes and URL/data validation.
  4. Review draft/source/CERT-reference differences where the review path is used.
  5. Resolve ambiguity with an override or identity action; rerun the same event.
  6. Commit only after the report is accepted.
  7. Verify post-commit count, score/parity and notification output.

PPW and MPW from 2026/2027. A joined listing that repeats a place is refused before anything is written, with the places named: ask the organiser for the fenced order and ingest again. A listing with a fencer who has no category — a pending match, or no birth year — is refused until the match or the birth year is resolved. So is a listing with a fencer the birth year cannot identify: namesakes on the roster whom the birth year does not tell apart, or the only fencer of that name two or more categories from the bracket, which is a data error. Nothing of that listing is written, and the error names the fencer and the namesakes with their birth years. Correct the birth year, or add an identity entry with the fencer’s birth year to doc/overrides/<event code>.yaml, and run the ingest again. At the end of the run a Telegram message such as PPW2-2026-2027 szabla M: fenced V2+V3 (10); § 2: V2 (5) | V3 (5). Scored as fenced. means the organiser joined the categories otherwise than the scoring table’s § 2 gives. The results are scored as fenced and nothing waits for anyone; take it up with the organiser for the next event. A later message saying the brackets now follow § 2 closes it; the current verdicts are in tbl_joining_check.

International events (PEW, MEW, MSW, PSW). The staging summary’s international section lists, per bracket, the rows stored, the PENDING rows and the rejected rows (ADR-106). A PENDING row was printed POL but is not an exact identity of a fencer with an SPWS start; sign-off refuses while one remains. Resolve each one in doc/overrides/<event code>.yaml: an identity entry naming the scraped name and the id_fencer when the candidate is that person, or a match_method entry EXCLUDED when they are not ours; then re-stage the event and sign off. A rejected row needs nothing. A fencer of ours rejected because their birth year does not fit the bracket’s category is fixed by correcting the birth year, then re-staging. Conflicting federations within a season are listed in vw_fencer_nationality_conflict.

Runbook

Synchronize EVF

  1. Run scheduled/manual EVF sync for the intended environment. The workflow reconciles calendar CERT→PROD both before and after the scrape step — the pre-scrape reconcile runs regardless of whether the scrape itself later fails, so PROD never falls further behind CERT than it already was.
  2. Review created/updated/reused event identity and duplicate warnings.
  3. Review result parity for events eligible for import/promotion.
  4. For each calendar promotion (pre- and post-scrape), inspect create/update/delete/skipped sets in its reconcile report.
  5. If a promote step refuses with an active-season mismatch, do not override it — it means CERT and PROD's bool_active seasons disagree (e.g. an admin edited a season's dt_start/dt_end on one environment but not the other). Fix the season row divergence directly, then rerun; the reconciler will pick up correctly once seasons agree.
  6. An EVF event carries no tournament children until it has results (ADR-096): populate-urls.yml and scrape-tournament.yml act on brackets that already exist, so they have nothing to do for an event still in PLANNED. Its first ingest goes through phase5-event-runner.yml on the organiser’s results at the event-level url_event (ADR-105; ingest-event.yml refuses an international event), or the EVF sync’s own results mode for the active season. The url_event is the organiser’s event page, never the EVF calendar page (EVF reuses those addresses for later editions): an FTL event schedule, an Engarde tournament, a 4fence results folder, an Ophardt (fencingworldwide) /tournament/ page or a d’Artagnan index.html. Write it with set_event_source_urls, which refuses a page whose date, name or weapons are not the event’s.
  7. The results mode stores only the rows the international admission stores (an exact identity of a fencer with an SPWS start). It reports PENDING rows, printed POL without one, in its log and Telegram message and stores nothing for them; resolve them by re-ingesting the event through phase5-event-runner.yml with the override file.

Runbook

Add a missing past event

  1. After a season’s EVF events close, run python -m python.tools.evf_event_completeness --season <season code>. It lists every EVF event with results at EVF that has no PEW, MEW or MSW event row within two days of it, and exits 1 when there is one. It only reads.
  2. Create the event row on LOCAL with one guarded INSERT (code, name, season, organiser, place, dates, weapons, the organiser’s results URL, status COMPLETED), checked against the source page; keep the statement, since CERT and PROD run the same one.
  3. Stage it with phase5_runner, review the summary against EVF’s record, get the event’s sign-off and commit with --commit-run-id <run> --event-code <code> --replace-event. Check the stored rows through what the drilldown reads, then python -m python.tools.compare_evf_points --event-code <code> --evf-event-id <id>.
  4. Release the code the staging needed. Then, with approval for each environment, run the same INSERT on CERT and on PROD through scripts/cloud-sql.sh, stage with phase5-event-runner.yml, compare the staged rows with LOCAL and EVF, and commit with commit_run_id. promote.yml reaches the active season only, so it cannot carry a past-season event.
  5. A result of the previous season counts in the active season’s rolling score for the season’s carry-over window: directly while the event’s next edition has no row, then through that row’s prior link until it is held. Do not create a placeholder row for the next edition (ADR-091). For an EVF event the calendar sync sets the link when EVF publishes the next edition, by matching the city of the prior season’s event; create the past event on PROD before that edition is mirrored there.

Runbook

Repair after identity/master-data change

  1. Complete the fencer/alias/birth-year correction through the governed admin/RPC path.
  2. Confirm affected events were enqueued.
  3. Drain or observe the recompute worker: CERT and PROD both drain automatically every 15 minutes (recompute-drain.yml / recompute-drain-prod.yml, ADR-072 amendment 2026-07-14) or via manual workflow_dispatch with debounce: 0 to force an immediate check; run the documented LOCAL worker manually where appropriate.
  4. Verify affected tournament categories/counts and public ranking components.
  5. Escalate queue poison/repeated abort rather than deleting queue state blindly.

Runbook

Promote to production

  1. Confirm CI/release and CERT verification are green.
  2. Select the correct season/event/calendar promotion contract. For one domestic event’s results it is promote, which replays the verified CERT run on PROD (ADR-108 §6).
  3. Before an event’s promote: CERT refreshed from PROD (python -m python.pipeline.promotion.refresh --target cert --mode apply --event <code>), then the event ingested on CERT, then the gate passed (python -m python.pipeline.promotion.gate --event <code>).
  4. Send promote <exact code> on Telegram, or run promote.yml with event_code; tick dry_run to see the outcome without writing. A prefix is answered with the matching codes.
  5. A refusal names what to do and writes nothing: the gate’s finding, a listing changed since the CERT run (re-ingest CERT), PROD holding results no CERT run produced (find their source first), or a dry run that did not end on the CERT run’s fingerprint.
  6. Read the Telegram result and the PROD staging report, and verify PROD public/admin behavior. A message that an event differs from CERT after the drain needs investigating: the apply has committed and is not rolled back.
  7. The seed job refreshes the seed export; record any remaining divergence.

The apply needs the repository secret SUPABASE_PROD_DB_URL (a direct connection to PROD’s database); without it promote refuses before reading anything.

Runbook

Close a finished event

  1. A domestic event stays IN_PROGRESS until every listing is final and its end date has passed. Nothing is needed when the daily close (event-close.yml, 04:00 UTC) reports it COMPLETED on CERT and PROD.
  2. When it reports the event still open, follow the message: not final yet — wait; the schedule changed since the CERT run — ingest CERT and promote again; PROD does not hold the CERT run’s result — promote it; a listing is dated after the end date — correct the event’s dates.
  3. To see what it would do, run event-close.yml manually with dry run ticked (the default).
  4. To close an event by hand, send complete <exact code> on Telegram, for example complete PPW1-2026-2027. A prefix is refused with the matching codes; the end date is not checked.

Runbook

Send an FTL seed bundle

Withdrawn — there is no send. E-mail delivery of seed bundles was never commissioned and never ran: the association holds no registered sending identity, so the project cannot send e-mail. ftl-seed.yml has never been dispatched, every scheduled run was skipped, and no event on CERT or PROD carries ts_ftl_sent. Do not attempt to enable it, and do not set ENABLE_FTL_DEADLINE_SEND.

The organizer collects their own files instead, and nothing needs to be run to make that happen. Send them the capability link for the event; the page lists every event with entries that has not yet taken place, and builds the files at the moment of download from the entry list read at that moment. A link that is absent, unknown or withdrawn yields an empty page rather than an error. Confirm the organizer can open the page and import the ZIP; there is no timestamp to verify, because nothing is sent.

Recorded in ADR-080 amendment 2026-09-25.

Runbook

Find or rotate the FTL export organizer link

  1. The current link is not recorded anywhere except tbl_ftl_export_token — query it via scripts/cloud-sql.sh <cert|prod> "SELECT uuid_token, txt_label, ts_created, ts_revoked FROM tbl_ftl_export_token WHERE ts_revoked IS NULL;" and build the link from the returned uuid_token.
  2. To mint a token for a new organizer, or to rotate/revoke one (a link leaked, or an organizer no longer needs it), follow ADR-095 in full — the canonical, self-contained procedure, composed by .claude/skills/ftl-token-rotate/SKILL.md through scripts/cloud-sql.sh.
  3. Rotating a token never requires editing register.html or the WordPress page at weteraniszermierki.pl/pliki-zasilajace-xml-ftl/ — the token travels only in the URL's ?k= parameter, never in page markup.
