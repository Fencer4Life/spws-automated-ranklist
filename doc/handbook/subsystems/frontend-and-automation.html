Why it exists

Purpose

Give users a coherent bilingual interface and give operators controlled automation without exposing credentials or embedding domain policy in presentation code.

Ownership

Scope and boundaries

Owns

  • Public/admin interaction and state
  • SPA/custom-element builds
  • Auth/MFA UX
  • API adaptation and diagnostics
  • Workflow definitions and triggers
  • Operational notification adapters

Does not own

  • Authoritative scoring
  • Database authorization policy
  • External provider availability
  • Secret values in client code
  • Manual domain approval decisions

Present tense

Current flow

  1. App.svelte selects ranklist, calendar or authenticated admin surfaces.
  2. lib/api.ts centralizes Supabase read/RPC calls and environment behavior.
  3. Admin auth establishes Supabase session and TOTP challenge/enrollment state.
  4. Vite builds SPA and custom-element targets from separate entrypoints. The custom-element entry publishes at the stable name assets/main.ce.js, because the WordPress page that embeds it names that URL.
  5. The same application serves two hosts. On GitHub Pages it renders with its full chrome (chrome="full"). On weteraniszermierki.pl each public page body is a <style> block that hides the theme’s own header, navigation, side tabs and footer on that page only, then one element from the custom-element bundle: <spws-ranklist chrome="site" view="ranklist" admin-entry> for /ranking/, <spws-calendar chrome="site"> for /znajdz-zawody/, and <spws-document> for /kalkulator-punktow/ and /tabela-punktacji/. The bodies’ reference copies live in doc/wordpress/. In chrome="site" the element draws the SPWS bar — ☰, the logo as the link home, the page’s title (a short one below 430 px) and the PL/EN switch — and a drawer whose entries are same-tab links to the addresses the body passes in as href-home, href-ranking, href-calendar, href-calculator and href-table. chrome="none" — one row with the page name, the language toggle and fullscreen, and no drawer — is what <spws-calendar> renders without a chrome attribute, so a calendar body published before site existed keeps working. /pliki-zasilajace-xml-ftl/ carries <spws-ftl-export>, a capability link outside the drawer.
  6. The navigation drawer carries four entries: the ranklist, the calendar, the points calculator and the scoring-table annex (Załącznik nr 1). In every mode it floats over the page, opens only on ☰, closes on a choice, a tap outside or Esc, and holds no sign-in entry. On github.io the first two switch application views and the last two are links to standalone static pages that are not part of the bundle. Those pages live in frontend/public/, which Vite copies into dist/ unchanged, so they ride the Pages artifact without a build step and without type checking. Each is one self-contained file carrying the generated scoring module (ADR-102). frontend/scripts/build-scoring-pages.mjs also writes a PROD copy of each under frontend/public/embed/, without the TEST ribbon, the page’s own language bar and its banner. On the association’s site <spws-document doc="…"> frames that copy under the SPWS bar. The frame takes the height the document reports, and a framed calculator’s link to the rules opens the site’s annex page in the same tab; the element accepts both messages only from the asset base’s origin. The drawer and the element pass the active locale as ?lang=, which the pages treat as a hint rather than a precondition: the annex holds both languages in its markup and switches them with CSS alone, so it stays readable and switchable where no script runs, such as a messenger or iOS Files preview. Publishing a further page this way is an exception requiring its own decision, not a routine option.
  7. Each host serves one environment (ADR-109). A surface runs on the CERT pair whenever it holds one — github.io and LOCAL — and on PROD otherwise: the WordPress pages, their framed embed/ documents and register.html are given only the PROD pair. There is no CT/PD switch. github.io shows a yellow TEST ribbon, linked to weteraniszermierki.pl and pinned to the top while the page scrolls, and keeps the PROD pair only to read which seasons PROD already holds for promotion. Every read, write and dispatch goes through the client of the surface’s own environment.
  8. Static image assets resolve through lib/assetBase.ts. It is empty by default, so the Pages build emits bare file names; the WordPress page bodies set asset-base to the Pages origin, where the organizer marks, the framed documents and register.html deploy. Registration links are built from it, never from the page address.
  9. The calendar reads every season. Its dataset has one owner, reloadCalendar(); the season-scoped event query serves the admin list and the prior-season pickers and never the calendar.
  10. A failure inside the calendar stays inside the calendar. It renders within an error boundary, because a throw from a $derived tears down the component tree and would otherwise stop the header, the navigation and the hamburger along with it — a live page with nothing listening, recoverable only by reloading.
  11. Trusted operational actions dispatch allowlisted workflows through server-side infrastructure.
  12. GitHub Actions install dependencies, execute domain commands and use environment-scoped secrets.
  13. The Apps Script bot is a Telegram command surface: it starts workflows, reads CERT and PROD through the Supabase Management API and replies in the admin chat. Its help is the command list (operator runbooks).
  14. The organizer takes their own seed files from a capability-gated page; nothing is sent to them. The EventManager seed button and the Telegram send <EVENT-CODE> participants command dispatch ftl-seed.yml, which was built to e-mail the bundle and was abandoned before it ever ran — the project has no registered sending identity and cannot send e-mail. Both triggers therefore lead nowhere and are retained unused.

Must remain true

Invariants

No GitHub PAT/service-role/Gmail secret is bundled or stored in browser-visible configuration.
Web components remain Shadow-DOM isolated and usable on the host site.
English/Polish locale state is reactive across public surfaces.
Admin UI availability follows authenticated authority, not query-string presence alone.
?admin=1 opens the sign-in at load on github.io and, on the association’s site, only on an element that carries admin-entry — /ranking/. The calendar, the documents and chrome="none" ignore it. Authority still comes from the password, TOTP and the server-side aal2 check (ADR-083), never from the parameter.
The application’s view, chrome and asset-base default to the GitHub Pages behaviour, and <spws-calendar> defaults to chrome="none", so adding a publication target never changes an existing one.
The embed/ documents hold only the PROD pair; release.yml fails the release if one carries CERT. The WordPress page bodies hold the PROD anon key, and their reference copies hold a placeholder instead, which scripts/wp_publish_page.py fills without printing the key.
The custom-element entry keeps the file name assets/main.ce.js. A rename does not fail in CI — it fails silently on a live page on the association’s website — so release.yml guards it.
Operational failures are visible in UI/report/Telegram surfaces, not console-only.
Workflow dispatch requires a signed-in admin session that has completed TOTP (aal2). The allowlist is the second gate, not the first: verify_jwt = true is satisfied by the public anon key that ships in this bundle (Security posture).
Workflow allowlists, Telegram help and documentation stay synchronized.
The send button is disabled until the persisted organizer address matches the current draft.

Run and observe

Operations

Run Vitest and Svelte check after frontend changes; use Playwright for browser journeys. Inspect workflow job logs at the failing step and rerun only when evidence supports a transient failure. For FTL delivery, verify the chosen target and event code, save the organizer address before dispatch, and treat a failed stamp after SMTP acceptance as a possible duplicate-on-retry. Update dispatch allowlists, secrets reference and operator help whenever adding a workflow/command.

Evidence

Tests

Vitest covers components, state and API integration; Svelte check enforces type/template correctness; Playwright covers critical browser paths, including the bar at 320–390 px, the calculator’s layout and the framed documents (frontend/e2e/site-chrome.spec.ts). Workflow YAML is validated through CI execution and targeted configuration checks.
