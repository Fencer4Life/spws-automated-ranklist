Subsystem · Ingestion

Ingestion

Normalize heterogeneous fencing sources, apply SPWS domain policy and commit one trusted event result set with traceable provenance.

Plugin/rule orchestrationDraft + automated pathsVerified 3 October 2026

Why it exists

Purpose

Result providers disagree on files, fields, categories and identity. Ingestion creates one source-neutral contract and applies domain decisions after parsing, so provider quirks cannot silently become ranking policy.

Ownership

Scope and boundaries

Owns

  • Source parsing and IR
  • Event/tournament resolution
  • Identity dispatch
  • Pool/category/count validation
  • Draft/review artifacts and commit orchestration
  • Ingest trace, faults and report fragments
  • The PZSz senior match review queue (tbl_pzsz_match_review) — an uncertain candidate held for an administrator's approve/reject decision, never auto-linked or auto-created

Does not own

  • Authoritative scoring formulas
  • Admin event/URL policy decisions
  • CERT→PROD release authorization
  • External provider correctness
  • Frontend navigation

Smallest useful explanation

Mental model

Source adapter → ParsedTournament IR → Rule plan → Ordered plugins
      → faults/remediation + report fragments → Commit → Post-commit flow

Plugins declare reads, writes, kind and effects. The rulebook orders them into scenarios. Context moves forward; plugins do not call one another. Recoverable domain faults remain data in the context. Infrastructure failure is an abort.

Present tense

Current flow

  1. ingest_cli.py constructs services and selects a flow — INGEST_DOMESTIC for SPWS PPW/MPW, or INGEST_PZSZ_SENIOR for a PZSz PPS/MPS senior bracket.
  2. ParseSource invokes the selected parser and creates the shared context — the same parser and IR for every flow; only the plugin sequence after it differs.
  3. Validation, event resolution, identity, pool split, count, pool-round and category plugins run in declared order for INGEST_DOMESTIC. INGEST_PZSZ_SENIOR drops the pool-splitting steps — a PZSz field is never split into several tournaments — and its identity step (ResolveFencers with a PZSZ_SENIOR intake) matches by exact name/alias only, queuing an uncertain candidate for admin review rather than linking or auto-creating one. In INGEST_DOMESTIC, ResolveFencers settles each row by exact name or alias first, telling namesakes apart by birth year, then by the fuzzy matcher. A row the birth year cannot decide, or whose only fencer of that name is two or more categories from the bracket, is PENDING and creates nothing (Identity and recompute). It reads the birth years declared at registration for the event: a new fencer takes the declared year, confirmed, when it fits the bracket, and a move of a known fencer’s year uses the declaration, as Stage 0 does.
  4. For an international event, meaning a PEW, MEW, MSW or PSW type including the IMEW and IMSW alternation codes, each source row is decided once by one admission module, python/pipeline/international_admission.py, on every path: s6_resolve_identity and ResolveFencers through stages._admit_international_rows, the Admin per-tournament scrape and the legacy orchestrator through resolve_tournament_results, and the daily EVF sync. A row is stored when it is exactly one roster fencer by surname, first given name and a birth year that fits the bracket’s category, and that fencer has a PPW or MPW result in any season (fn_spws_starter_ids()), whatever country the source prints. The comparison is exact: Polish letters are folded and a second given name in the source is dropped, but a typo or another first name is not the same person, and an unknown birth year cannot confirm the category. Otherwise a row printed POL is PENDING: it carries a candidate when there is one and is never stored automatically. Every other row is rejected, listed in PipelineContext.rejected, and never becomes PENDING. No fencer is created for an international event. The count check adds the rejected rows to the matched ones, so a parse still accounts for the whole bracket. Each stored result keeps the federation its source printed in tbl_result.txt_entered_for (three letters, PL folded to POL, or none). Stage 0 never creates or recalibrates a fencer for an international event, and team brackets are skipped when an FTL schedule is read (ADR-105, ADR-106).
  5. Some plugins use plugins/bridge.py to call proven functions in stages.py; mapped legacy halts become faults or aborts.
  6. Commit (or, for the PZSz flow, CommitPzszSenior) persists accepted live state through the database boundary — one SENIOR-labeled tournament per weapon/gender, at the full source field size, each result carrying the fencer's own veteran category.
  7. Before writing, Commit asks the database which engine the tournament type uses this season (fn_get_type_engine) and files the listing through the joined-bracket module paired with it. PER_CATEGORY_RENUMBER (EVF classic) splits a joined listing per category, renumbers places 1…K and stores the category’s own count as N. JOINED_BRACKET_CATEGORY_PLACE (the 2026/2027 SPWS engine) keeps the joined place, stores the joined N on every sibling tournament, and sends every one of them the listing’s category order, one digit per place, built from every listed fencer with a category, matched or not. Before anything is written it refuses a joined listing that repeats a place — nothing then says which fencer fenced ahead, so the operator asks the organiser for the fenced order — and a listing with a fencer who has no category (a pending match or no birth year) until that is resolved; a tie inside one category is accepted. A domestic listing holding a PENDING row is refused before anything is written, under either engine; the error names each fencer, why he waits and the roster’s namesakes with their birth years. An unknown engine fails the commit, and an international type is never given the joined module. SOURCE_FIELD_PLACE files every international bracket (PEW, MEW, MSW, PSW), whatever the type’s engine. SPWS stores only the rows it admits, so N is the whole source bracket the parser recorded (raw_pool_size), never the number of rows kept, and each fencer keeps their published place. fn_ingest_tournament_results refuses an international write that carries no count or a place above it, before it deletes anything, and fn_commit_event_draft recounts a joint-pool sibling only for PPW and MPW (ADR-105). The PZSz flow does not split and needs no module; PPS and MPS are scored by EVF classic.
  8. POST_COMMIT validates participant count, notifies and formats staging output.
  9. The Phase 5 draft writer (review_cli.py) files an international bracket as one draft tournament in its source category. N is the parser's whole-bracket size and every admitted fencer keeps their source place. A bracket without a single source category is refused, and so are two source brackets that map to one tournament code; the duplicate-code merge never recounts an international N. The Phase 5 staging summary lists each international bracket's source N, highest place, rows stored, rows stored that the source did not print POL for, PENDING rows and rejected rows. It flags an N equal to the rows printed POL, and a bracket whose source prints no country. A PENDING row is written to the draft without a match method and listed below the table with its candidate. Sign-off refuses while one remains: the event's override file, doc/overrides/<event code>.yaml, resolves it with an identity entry or a match_method entry EXCLUDED, and the event is re-staged. An identity entry names the fencer, fencer: {surname, first_name, birth_year}, and each run resolves it against its own roster to exactly one fencer, because fencer ids differ between LOCAL, CERT and PROD; a name that resolves to no fencer, or to two, halts the run. An identity entry also links a rejected row whose first name is printed in another form (“LYNCH Patrick” for LYNCH Pat), and at sign-off it confirms its alias pair, which never blocks as a suspected wrong match. The Admin scrape, the legacy orchestrator and the EVF sync report a PENDING row and store nothing for it. scrape_tournament ingests an international tournament whole, at the scraped bracket size. The new pipeline's event URL path (ingest_event_from_url) refuses international events and names the Phase 5 runner (ADR-105).
  10. The Phase 5 runner (phase5_runner.py) expands each event URL into brackets: an FTL event schedule through its schedule page (a tournament named for two categories, “Cat 3 and 4”, “Category 3 & 4” or “Cat 3/4”, spans both and is skipped like any bracket without one category), an Engarde tournament through Engarde’s competition list. An Engarde bracket is an individual, completed final of one category; its weapon, gender and category come from the published title and its date from the competition; a title naming two categories (“Cat 3+4”, “3 -4”) makes the final combined, whatever one category its slug names. Pool rounds, team events, open competitions and competitions without one category are skipped and listed in the staging summary, and an Engarde bracket’s N is the number of placed fencers. As on every platform, a fencer listed without a place — DNS (did not start), DNF (did not finish) or DNQ (did not qualify) — is not in N, although Engarde’s classification header counts him. An Engarde fencer’s nationality comes from the column headed as one (Country, Nation, Nación and the equivalents in other languages); a page that prints a Club column there has no nationality, its fencers carry none, and only an identity match stores one of them. A 4fence event expands into its category brackets; each is read from its final classification (the place is the column CLASS, not the pool ranking “Cla Gir”; the country is the federation code, EEPOL → POL) and its last-four tableau, which names the second bronze medallist the classification prints without a place, whether the tableau prints names as links or as plain text: he is 3rd and in N. Any other fencer without a place left during the direct elimination; he is not in N and the places below him close up. An Ophardt (fencingworldwide) tournament page expands into its individual competitions of one weapon, gender and EVF age band (O40–O70 → V1–V4), each read from its results page; a team or mixed event, or an age band outside EVF’s, is skipped with a reason. The page prints a competition’s day and month only, and the number in its URL is Ophardt’s season, not the year (Chania, 2 May 2026, is 32819-2025): a bracket’s date is the latest day of that day and month on or before its results page’s last transmission. A d’Artagnan event index expands into its single-category competitions, each read from its rankings page; the combined pool rounds (“V1/V2 Runde”) are skipped, and the index itself is never read as a bracket. Each draft tournament is typed from the event code’s family; the database refuses a tournament whose type disagrees with its code. For an international event the stage-time alias flush writes pairs of automatically linked rows only, never a ❌ pair. Sign-off (--commit-run-id) refuses a run holding an unresolved PENDING row or a ❌ pair. With --replace-event it replaces the event’s stored tournaments by the run’s in one transaction (fn_replace_event_from_draft: rollback by the exact code, then commit). phase5-event-runner.yml stages on CERT or PROD and, given commit_run_id, commits a staged run there through the same replace path.
  11. Once every listing of the event is committed, ingest_cli._after_event_run runs the joining check (python/pipeline/joined_brackets/joining_check.py): per weapon and gender it reads the stored category orders, computes the scoring table’s § 2 grouping for the same category sizes with plan_brackets, stores the verdict in tbl_joining_check, and sends one Telegram message through TelegramNotifier when the verdict changes — to a mismatch, or back. A repeat run and a first match are silent. It never fails the run: every listing is already scored as fenced.
  12. With --record-run, which ingest-event.yml passes for target cert, a URL ingestion records its run in tbl_ingest_run for promote. fn_ingest_run_open writes the row before the first write: the commit, the event URL, the season end year, the input fingerprint and the roster as the run found it. The run adds a hash of the schedule and of every listing as parsed, with the keep-rule’s verdict and what its commit did. It closes FINISHED, or FAILED with the error. The database records the master-data changes since the row opened: fencers created, birth years moved, aliases added (ADR-108 §4).

The review CLI can instead write run-scoped draft tables, compare source/CERT-reference/draft state and call fn_commit_event_draft after operator review.

Must remain true

Invariants

Every parser emits the same ParsedTournament/ParsedResult contract and stable source-row identity.
Parser facts do not override admin-canonical metadata without explicit validation.
Plugin public writes are declared and checked; order satisfies the context-key DAG.
One event commit is transactional—partial live replacement is not an acceptable result.
Draft, ingest-history and run-record tables are reachable only by service_role: RLS is enabled with no policy, and all grants are revoked from anon and authenticated. The pipeline reaches them because service_role bypasses RLS inherently, not because a policy admits it (Security posture).
Combined categories, joint pools, gender routing and participant counts retain their distinct meanings.
How a joined listing is filed is decided by the engine assigned to the tournament type, never by the listing; each engine has exactly one joined-bracket module.
Source URLs are validated against parsed data on writes where policy requires it.

Run and observe

Operations

Use event-scoped CLI/workflow inputs and review the generated staging report before advancing. Failures should identify parser, plugin and fault/abort boundary. LOCAL database changes use the safe reset script, never a bare reset. Do not advance through batches without required event sign-off.

Re-ingesting an international event goes through the Phase 5 runner. Two limits apply. A bracket whose source prints no nationality has every row dismissed unless the event’s override file names a fencer’s federation: the summary flags it with the number named, and the Admin per-tournament scrape, which reads no override file, cannot repair it. A past event is re-ingested with --replace-event: fn_rollback_event_by_code takes the exact code in any season, while fn_rollback_event resolves a prefix in the active season only. promote.yml also reaches the active season only, so a past-season event reaches CERT and PROD through phase5-event-runner.yml: stage, review, then commit with commit_run_id.

Three tools support a repair. set_event_source_urls writes an event’s result URLs only when every source’s date, name and weapons match the event; it reads FTL, 4fence and d’Artagnan pages; an Engarde tournament through the competition list its page loads, which gives each competition’s date, weapon and city; and an Ophardt tournament through its first competition’s results page, which gives the year. An Engarde or Ophardt page alone has no date and is refused. compare_evf_points checks each committed Polish result of an EVF event against EVF’s N and points. evf_event_completeness lists the EVF events of a season that have results at EVF and no event row. The last two only read.

Operational commands and workflow selection are documented in operator runbooks.
