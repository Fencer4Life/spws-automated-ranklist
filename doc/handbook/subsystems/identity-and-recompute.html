Identity and recompute

Resolve unstable source names to durable fencer identities, preserve human decisions as aliases and repair affected rankings when master data changes.

FK identityAlias memorySelf-healing recompute

Why it exists

Purpose

Source names vary by spelling, diacritics, ordering and provider. Rankings need a stable person identity, while operators need a safe path to confirm ambiguity and correct mistakes without re-scraping unrelated events.

Ownership

Scope and boundaries

Owns

  • Canonical fencer identity
  • Name folding and fuzzy candidates
  • Alias memory and match provenance
  • Estimated birth-year review
  • Merge/split identity correction
  • Affected-event recompute

Does not own

  • Raw source parsing
  • Ranking formulas
  • Registration consent policy
  • Event lifecycle
  • Foreign federation master records

Smallest useful explanation

Mental model

scraped name → exact alias / canonical comparison → fuzzy candidate
     → auto match | human confirmation | domestic auto-create | international skip
     → result stores fencer FK + original source name + match provenance

A later identity correction does not rewrite source evidence. It changes canonical links/data, queues affected events and recomputes derived category/count/score state from committed FK-linked results.

Most stored results on CERT and PROD carry the fencer id as their scraped name (2,610 and 2,661 of 2,811 on 1 October 2026), and neither holds a USER_CONFIRMED or AUTO_CREATED result. Recomputes before 1 October 2026 overwrote them (ADR-072 amendment of that date). Identity links and scores are intact. The original names come back only when an event is re-ingested from its source.

Present tense

Current flow

  1. Identity resolution receives parsed rows and intake policy. For an international event every row is first decided by the shared admission (python/pipeline/international_admission.py): it is stored on an exact identity, meaning surname, first given name and a birth year fitting the bracket’s category, to a fencer with a PPW or MPW result, whatever country is printed; it is PENDING when printed POL without one; otherwise it is rejected before matching. No international row creates a fencer, and none links to a fencer who has never started at SPWS (ADR-106).
  2. A stored international result keeps the federation its source printed (tbl_result.txt_entered_for). tbl_fencer_nationality holds one federation per fencer and season: that of the season’s earliest-dated result carrying one. The trigger trg_result_season_nationality on tbl_result recomputes it whenever such a result is stored, moved or deleted, so the order of ingestion does not matter. A later start in the same season that prints another federation does not change it and is listed in vw_fencer_nationality_conflict. An administrator’s entry (enum_source ADMIN) is kept as entered. Neither the admission, the scoring nor the ranking reads it, and it enqueues no recompute; tbl_fencer.txt_nationality, which Stage 0’s deduplication reads, is a separate single value.
  3. Known aliases provide deterministic matches before fuzzy scoring.
  4. Thresholds and organizer context decide automatic, review, auto-create or skip outcomes.
  5. An automatic link needs the same surname, the same first given name and a confirmed birth year that fits the bracket’s category. A second given name on either side is dropped, the year before the season’s end year is accepted for an autumn EVF category, and an unknown or estimated birth year does not veto. A contradicting birth year, a near-match without a fitting birth year, or two namesakes who both fit leave the row PENDING: software never chooses between two people. A source word written without Polish letters matches the roster word once folded, one point below an exact spelling; a word written with them is compared as written. The alias checker marks a pair as a wrong match when the first given names differ or the surnames are further apart than a typo: one letter in a surname of up to six letters, two in a longer one.
  6. Committed results retain original source names, confidence and method.
  7. Admin identity actions update aliases/fencer data through controlled RPCs.
  8. Database change hooks enqueue affected events; the recompute worker drains/debounces work.
  9. RECOMPUTE_DOMESTIC reloads committed rows, recalculates category/counts and commits derived state through the joined-bracket module paired with the tournament type’s engine. Under the 2026/2027 SPWS engine a category’s rows must come from one joined listing; N and the listing’s category order are read back as stored, because both count fencers who were never stored, and the order’s digit at every stored place is rewritten to that fencer’s current category, so a birth-year correction that moves a fencer between categories moves their digit too. Places never stored keep theirs. An international result (PEW, MEW, MSW, PSW) is never moved: it stays in the tournament it is stored in, with its stored N and place, and is written with that bracket as its source category, so the V-category guard trusts the bracket the fencer fenced (ADR-105). Every recomputed row is written with its stored scraped name, confidence and match method unchanged, empty values included.
  10. After the recompute, recompute/worker.py runs the event’s joining check again (joined_brackets/joining_check.py), because a moved fencer changes the category sizes § 2 is computed from. It reports a change of verdict on Telegram and never fails the recompute.

Must remain true

Invariants

Results identify fencers by foreign key, never by mutable display name.
Original scraped names and match provenance remain auditable after correction.
Human-confirmed aliases become reusable cross-event memory.
Domestic and international low-confidence outcomes follow different business policy.
An international result is stored only for a fencer with an SPWS start, by exact identity; a fencer has one federation per season, fixed by the season’s earliest-dated start.
Birth-year or merge corrections recompute all affected events, not only the currently viewed ranking.
The recompute queue and watermark are service_role-only. An admin edit still enqueues because the eight fencer-mutation RPCs are SECURITY DEFINER and fn_enqueue_affected_events is too, so the queue INSERT runs as the definer — the admin never needs a grant on the queue (Security posture).
fn_merge_fencers is not callable by an anonymous browser. It deletes a fencer row and re-points its results.
Recompute uses committed results and FKs; it does not repeat source scraping/fuzzy matching.

Run and observe

Operations

Review ambiguous identity in admin/staging reports. Prefer confirming/transferring aliases over manually editing result names. After master-data changes, monitor recompute queue/workflow and verify affected event rankings. A merge is a high-impact operation and must preserve result/registration references.

Evidence

Tests

Matcher (MATCH.ID, MATCH.FOLD), international admission (ADM.ID), season nationality (NAT.SEASON, NAT.EVID), alias checker (NAME.CLS), dedup, birth-year, identity UI and recompute tests cover normalization, threshold outcomes, provenance, FK repointing, queue debounce and cross-event repair. Database tests protect alias uniqueness and merge behavior.
