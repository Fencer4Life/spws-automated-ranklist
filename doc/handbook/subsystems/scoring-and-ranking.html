Scoring and ranking

PostgreSQL owns the authoritative transformation from committed results and season configuration to published segmented rankings.

Database-owned policySeason configurationRolling carry-overVerified 19 September 2026

Why it exists

Purpose

Produce reproducible domestic and extended rankings, expose component scores for explanation and support season-specific policy without forking frontend or Python formulas.

Ownership

Scope and boundaries

Owns

  • Age-category lookup
  • Points and ranking functions
  • Season scoring configuration
  • Domestic/international inclusion
  • Rolling carry-over engine dispatch
  • Public ranking/score read models

Does not own

  • Source parsing
  • Fencer identity decisions
  • Event URL selection
  • UI filter state
  • Promotion authorization

Smallest useful explanation

Mental model

committed result + tournament slot + fencer + event + season config
         → effective category / eligible pool / points
         → ranking rows + score drilldown + optional carried rows

Present tense

Current flow

  1. Ingestion commits result placements to category/gender/weapon tournament slots.
  2. Ranking functions select eligible current-season results for the requested dimensions.
  3. The configured engine determines prior-event carry-over behavior.
  4. Current results and stopping rules suppress replaced carry-over where applicable.
  5. Public ranking and drilldown APIs return ordered totals and components.
  6. The Svelte frontend formats/filters the result without recalculating authoritative points.

Must remain true

Invariants

One authoritative SQL implementation owns scoring and age-category semantics.
Weapon, gender and V-category segmentation is preserved even after combined physical pools.
A historical event merge never guesses sporting facts: original-provider/full-field evidence fixes place and field size before affected tournaments are recomputed.
Season configuration is exportable/importable and round-trips without silent field loss.
Carry-over engine selection is per season; existing seasons are not silently rewritten by a new default.
A prior-event link is nullable and must not be inferred from the PEW number.
Admin edits to scoring configuration are explicit, authenticated and test-covered.
A tournament type with no configured multiplier or threshold raises rather than silently writing a NULL score or admitting a bracket ungated.
Once a season's first result is scored, ordinary Admin edits to its scoring configuration (base value, podium coefficients, all type multipliers, participant thresholds, ranking rules, scoring engine) are rejected database-side, field by field, regardless of season dates; the carry-over engine and the two EVF/Kadra toggles remain always editable.

Run and observe

Operations

Change scoring through the admin configuration contract, export the JSON before risky changes and compare affected rankings. Engine changes require parity comparison and explicit season selection. Never patch calculated output rows to “fix” a formula. Once a season shows as locked (a scored result exists), the Admin editor stays open for reading and export but every save attempt is rejected with an explanation; there is currently no in-product path to change a locked season's configuration.

Evidence

Tests

pgTAP suites cover base ranking, rolling, engine dispatch/FK carry-over, cross-gender segmentation, joint pools, thresholds and configuration round-trip. 55_evf_historical_event_fragment_repair.sql pins the corrected 2025–2026 physical-event ownership and source facts. 56_evf_predecessor_event_fragment_repair.sql proves that consolidating the six predecessor-season clusters preserves all 157 in-scope results and each stored score field, retains the distinct prior Guildford event and its 20 results, and clears only the three reviewed unrelated rolling links. Frontend tests verify filters and drilldown presentation; they do not replace SQL correctness tests. 80_season_scoring_contract.sql (SS26.* acceptance IDs) pins the versioned engine dispatcher, the normalized per-type policy and its PPS/MPS extension end to end, including a config write reaching the normalized table and a tournament scoring with its configured multiplier, and the governance lock (all governed fields stay editable unlocked and are rejected uniformly once locked, tracking scoring rather than season dates, with role-based trigger backstops on direct table writes). ScoringConfigEditor.test.ts, SeasonManager.test.ts and SeasonManagerWizard.test.ts cover the same lock at the UI layer: every field disabled and the Polish explanation shown on a guarded save click with no RPC fired, and readonly deriving from the server-reported lock state rather than a season date.
