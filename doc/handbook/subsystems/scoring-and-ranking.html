Subsystem · Scoring

Scoring and ranking

PostgreSQL owns the authoritative transformation from committed results and season configuration to published segmented rankings.

Database-owned policySeason configurationRolling carry-overVerified 28 September 2026

Why it exists

Purpose

Produce reproducible domestic and extended rankings, expose component scores for explanation and support season-specific policy without forking frontend or Python formulas.

Ownership

Scope and boundaries

Owns

  • Age-category lookup
  • Points and ranking functions
  • Scoring engines and their assignment per tournament type
  • Season scoring configuration
  • Domestic/international inclusion
  • Rolling carry-over engine dispatch
  • Public ranking/score read models

Does not own

  • Source parsing
  • Fencer identity decisions
  • Event URL selection
  • UI filter state
  • Promotion authorization

Smallest useful explanation

Mental model

committed result + tournament slot + fencer + event + season config
         → engine of the tournament type → components + method + final score
         → effective category / eligible pool / ranking entry
         → ranking rows + score drilldown + optional carried rows

Present tense

Current flow

  1. Ingestion commits result placements to category/gender/weapon tournament slots.
  2. fn_calc_tournament_scores resolves the engine of the tournament’s type — the type row’s engine, or the season’s when the row names none — and passes each result’s place, the stored field size and the stored K, m and b to the dispatcher fn_score_by_engine. It stores every component rounded to two decimals, −1 where the scoring method does not use it, the method itself, and the final score rounded once from the unrounded sum times the type’s coefficient.
  3. Ranking functions select eligible current-season results for the requested dimensions. When the Season Scoring Rules name entry_types, fn_ranking_full admits only a fencer with a result of one of those types in the ranking’s window — the ranked season, plus the previous season when the ranking is rolling — in any weapon; what the fencer scores still comes from every type the rules’ buckets name.
  4. The configured engine determines prior-event carry-over behavior.
  5. Current results and stopping rules suppress replaced carry-over where applicable.
  6. Public ranking and drilldown APIs return ordered totals and components.
  7. The Svelte frontend formats/filters the result without recalculating authoritative points.

Must remain true

Invariants

One authoritative SQL implementation owns scoring and age-category semantics.
Weapon, gender and V-category segmentation is preserved even after combined physical pools.
A historical event merge never guesses sporting facts: original-provider/full-field evidence fixes place and field size before affected tournaments are recomputed.
Season configuration is exportable/importable and round-trips without silent field loss.
A released scoring strategy is immutable; a formula change is a new engine version. The dispatcher is a static CASE that raises on an unknown engine code, and the engine registry is metadata only — it never names a function to call.
Every scored result records its method (TABLE, PLACE_MEDAL or EVF_CLASSIC). A component the method does not use is stored as −1, never NULL or NaN; CHECK constraints hold each component to a real value or −1, and to exactly the set its method uses.
The engine assigned to each tournament type is governed like every scoring field: exported, imported, snapshotted in revisions and frozen once the season scores its first result.
Carry-over engine selection is per season; existing seasons are not silently rewritten by a new default.
A prior-event link is nullable and must not be inferred from the PEW number.
Admin edits to scoring configuration are explicit, authenticated and test-covered.
A tournament type with no configured multiplier or threshold raises rather than silently writing a NULL score or admitting a bracket ungated.
Once a season's first result is scored, ordinary Admin edits to its scoring configuration (base value, podium coefficients, all type multipliers, participant thresholds, ranking rules, default ranking mode, scoring engine) are rejected database-side, field by field, regardless of season dates; the carry-over engine and the two EVF/Ranking toggles remain always editable.
Season Scoring Rules read as either schema (the original domestic/international shape, or the versioned schema_version: 2 shape of three sections aggregating into two display groups) through one canonicalization function; the original functions and shape are never rewritten in place, and a season is cut over to the new shape only together with its consuming code.
A privileged, audited revision that corrects a locked season's configuration either rescores every already-scored tournament under the new revision and activates it, or (on any failure) leaves the prior revision active and every score at its pre-revision value — never a partially rescored season.
A season's ranking publication capability (PPW_ONLY or FULL) is set at season creation and is permanently immutable thereafter, for every role, with no exemption; it is a migration/season-creation policy fact, never an Admin-editable field. A PPW_ONLY season's own PPW ranking and its underlying EVF/FIE result data remain fully readable everywhere — only the combined SPWS+EVF+ ranking RPC is refused for it.

Run and observe

Operations

Change scoring through the admin configuration contract, export the JSON before risky changes and compare affected rankings. Engine changes require parity comparison and explicit season selection. Never patch calculated output rows to “fix” a formula. Once a season shows as locked (a scored result exists), the Admin editor stays open for reading and export but every save attempt is rejected with an explanation. Correcting a locked season's configuration is a privileged operator procedure, fn_revise_and_rescore_season, run outside the Admin session entirely — docker exec -i supabase_db_SPWSranklist psql on LOCAL, scripts/cloud-sql.sh <cert|prod> on CERT/PROD — never through the web session, which cannot call it at all. It applies the new configuration, records an audited revision (actor, reason, optional board reference), rescores every already-scored tournament in the season, and rolls back the whole call atomically if any tournament fails to rescore.

Evidence

Tests

pgTAP suites cover base ranking, rolling, engine dispatch/FK carry-over, cross-gender segmentation, joint pools, thresholds and configuration round-trip. 55_evf_historical_event_fragment_repair.sql pins the corrected 2025–2026 physical-event ownership and source facts. 56_evf_predecessor_event_fragment_repair.sql proves that consolidating the six predecessor-season clusters preserves all 157 in-scope results and each stored score field, retains the distinct prior Guildford event and its 20 results, and clears only the three reviewed unrelated rolling links. Frontend tests verify filters and drilldown presentation; they do not replace SQL correctness tests. 80_season_scoring_contract.sql (SS26.* acceptance IDs) pins the versioned engine dispatcher, the normalized per-type policy and its PPS/MPS extension end to end, including a config write reaching the normalized table and a tournament scoring with its configured multiplier, and the governance lock (all governed fields stay editable unlocked and are rejected uniformly once locked, tracking scoring rather than season dates, with role-based trigger backstops on direct table writes) and its privileged revision exception (revoked from authenticated; empty reason/actor rejected before any write; the prior revision survives deactivated with its snapshot intact; an engine identical to the current one is a data-only revision with no new engine row; a multiplier-only revision rescores and the change is visible in the stored score; every result ends up stamped with the new revision id; an injected mid-rescore failure rolls back the whole call, prior revision and scores untouched; a successful call flips the season pointer, revision activation and every result's stamp together). 83_spws_place_medal_engine.sql (SE27.* IDs) pins the place-and-medal strategy against the signed-off points table — its three ranges and the boundaries at 3/4 and 31/32, the medal only while K exceeds the place, the exact cube root, and the refusal of a 4–31 bracket without K, m and b — together with the engine per type and its lock, the component columns and their CHECK constraints, the backfill of history to −1 and EVF_CLASSIC, and the ranking-entry gate. 82_published_page_params.sql pins the per-type public parameter rows. 84_admin_ranking_rules_validation.sql (ADM27.* IDs) pins the write-time refusals, the acceptance of the 2026/2027 rules and of an unchanged older-shape resend, the validator's missing grant and the absence of any stub-tournament helper; ranking-rules.test.ts and the ADM27 cases of ScoringConfigEditor.test.ts pin the editor's mirror of the same checks: each pool's picker, a used type disabled, the warning under a faulty bucket and the refused save. frontend/tests/scoring.test.ts pins the browser module to values derived from fn_score_by_engine. ScoringConfigEditor.test.ts SE27.UI.02–07 pins the per-type engine selectors, their modules, the two read-only panels, the type_engines payload, the EVF hint and the lock on every selector; export.test.ts SE27.UI.08 the export’s columns, languages and „nie dotyczy”; AdminScoringEngines.test.ts SE27.UI.09 the engine list loading at sign-in and never for an anonymous visitor. ScoringConfigEditor.test.ts, SeasonManager.test.ts and SeasonManagerWizard.test.ts cover the same lock at the UI layer: every field disabled and the Polish explanation shown on a guarded save click with no RPC fired, and readonly deriving from the server-reported lock state rather than a season date. The same file's SS26.RANK IDs pin fn_ranking_rules_canonical's validation (unknown type, malformed best/always selector, non-positive best, conflicting display-group assignment, cross-section double-counting), best/always bucket aggregation, EVF/FIE and PZSz combining into one evf_plus_total with no third column, V0 not short-circuited (unlike fn_ranking_kadra), byte-exact parity against fn_ranking_ppw/fn_ranking_kadra for the original Season Scoring Rules shape, and PZSz carry-over staying disabled by default even with rolling enabled and the type declared in the current season's rules.
