Events and registration

Maintain a trustworthy season calendar, create scoring slots only when needed, reconcile approved event identity across environments and accept privacy-aware registrations.

Event lifecycleCERT→PROD reconciliationConsent-aware registrationVerified 28 August 2026

Why it exists

Purpose

Events connect public planning, result ingestion, promotion and registration. The subsystem keeps calendar identity stable while separating future event existence from tournament/result state.

Ownership

Scope and boundaries

Owns

  • Season/event/tournament lifecycle
  • Calendar identity and organizer
  • Prior-event linkage
  • Event URL/registration fields
  • Season skeleton and calendar reconciliation
  • Registration, consent and public entry list

Does not own

  • Result source correctness
  • Scoring formula
  • Fencer master identity policy
  • Email provider delivery guarantees
  • Host-site content outside components

Present tense

Current flow

  1. Admin creates/initializes a season and future events without manufacturing tournament children.
  2. Calendar sync drops case-insensitive whole-word CAMP entries before validation, then validates and records the retained in-season competition count.
  3. Weapons come from evidence, never from a default: the calendar post’s weapon categories, then the event page’s categories, then its description line, then the linked invitation letter, and last an approved manual override — so real EVF data always outranks a hand-entered fact. An entry whose weapons cannot be established anywhere is one EVF has not finished announcing: it is held back, the rest of the season syncs normally, and it enters on a later run once EVF publishes them. An entry already imported is never held back, so losing its categories upstream cannot withdraw a live event.
  4. The EVF calendar post id is primary calendar identity; the results-database id remains secondary.
  5. Retained competitions receive PEW bases chronologically by (dt_start, EVF calendar id); weapon letters are alphabetical and nullable id_prior_event independently preserves only approved geographic rolling linkage.
  6. An event already cancelled at first import receives base zero and consumes no positive ordinal. A later cancellation keeps its positive base and never frees its slot, but may shift with the sequence when a newly announced event moves the chronology — only while nothing is anchored to the old code, meaning the event is still ahead, carries no registrations and holds no results; a results-free cancellation remains publicly visible through seven days after its original end.
  7. An EVF event whose code carries no weapon letters cannot leave PLANNED, so tournaments and results never attach to an event whose weapons were never established; cancelling such an event is still permitted. Every event status, who may set it, and which automation carries it between environments is catalogued in Event status lifecycle. The code suffix is the authoritative weapon record; the stored weapon array defaults to all three and cannot express “unknown”.
  8. Ingestion creates/fetches tournament slots when actual results require them. One physical weekend at one venue owns one event row.
  9. Original scoring-provider facts and URLs are authoritative; the EVF results database is secondary. A scored identity conflict stops automation and requires a reviewed, source-verified repair.
  10. CERT calendar promotion applies the guarded whole-set difference to PROD, including calendar identity and every event-level field. It also carries the planning half of the lifecycle — a skeleton becoming dated, and a cancellation — while the results half stays with per-event promotion, so PROD never reports an event as finished while holding none of its results. The boundary is set out in Event status lifecycle.
  11. Public registration is enabled per event and records consent/version evidence through a constrained RPC.
  12. Registration identity matching is an exact (surname, first name, birth year) lookup. A match links the fencer; a miss is still accepted and stored with a null fencer link, so newcomers and fencers whose stored birth year was estimated can enter. The fencer record itself is created later, at result ingestion.
  13. The public entry list is reachable from inside the registration flow without leaving it: the form keeps its state, and both a back affordance and a close control return to the transfer details. Where the roster is hosted in a dialog, closing dismisses the dialog instead — the control means “leave this list” on both surfaces, and the destination follows the host. An entrant who spots a mistake corrects the entry they already submitted rather than submitting a second one: the browser holds a capability token issued at registration, and the correction is applied to the existing row by identifier, so the declared name and birth year can change — which the create path cannot do, since it treats those as the identity of an unlinked entrant. The capability lasts only as long as the page: an entrant returning later, on any device, re-enters the identity they declared, which reopens their own entry rather than adding a second one. A shared entry-list link opens the roster on its own; it carries no back affordance, because it never passed through the form, but it does offer a close control that leads to the registration form for the same event, so the shared link is not a dead end. Registration identity matching and entry-list views expose the appropriate public/admin projections.
  14. Admin or Telegram dispatch generates a fresh mix-all FTL ZIP, Gmail accepts it, and only then does the service-role RPC stamp the event; a gated daily sweep handles due unstamped events.

Organizer handoff

FTL seed delivery

The first delivery release contains the validated mix-all files only. It is generate-at-send and at-least-once: manual runs are explicit re-sends, while the sweep selects only unstamped live events after cutoff and skips empty bundles. Exact-once behavior would require a durable attempt/lease model.

Must remain true

Invariants

An event may exist without tournament children; a scored tournament belongs to exactly one physical event weekend.
One EVF calendar post id owns at most one row per season; repeat scrapes update it rather than incrementing its code.
For complete count N, no numeric PEWn may have n > N; cancelled and non-scoring retained entries count toward N, while CAMP entries are excluded.
A boundary-spanning EVF entry is a configuration error and blocks the scrape.
Event codes and external identity keys remain stable; environment-local ids are resolved, not copied.
id_prior_event is nullable and never inferred from the PEW number; at most one event in a season may claim one non-null prior event.
Original scoring-provider facts outrank the secondary EVF results DB; unverified scored conflicts fail closed.
Source-owned identity may refresh, but admin-owned URLs/fees/registration settings are never silently clobbered.
An event's scraped EVF link is recorded as its results pointer (url_event) only after the event has ended (dt_end in the past); future or in-progress events carry no url_event, while their invitation and registration URLs are still captured. Once concluded, the fill-blank refresh populates it and never overwrites a later manual edit.
PROD deletion is limited to safe planned, results-free events; protected divergence is reported.
CERT and PROD active seasons must match before whole-set reconciliation.
Registration consent evidence is captured with the version presented to the user.
Registration writes only tbl_registration; it never creates or mutates a fencer record.
One entrant holds at most one registration per event, whether or not they are linked to a fencer record, and whichever path writes it: the matched and unmatched write branches absorb each other's row for the same declared identity rather than standing beside it.
  • Declared registration names are stored whitespace-normalised, whichever path writes them — the public RPC, the admin projection or a future caller.
  • A registration cannot be enabled on an event with no payment account resolving from the event or its organizer.
  • A stored IBAN is always a valid IBAN; blank, empty and whitespace-only are one and the same state.
  • The entry fee is quoted in the currency the event states, and every surface that shows or copies it agrees: the fee on the first registration step, the amount row, its copy button and copy everything. PLN is the fallback for an event that states no currency, never a fixed label.
  • A registration carries an edit capability that no public projection returns. The published row identifier authorises nothing on its own.
  • Correcting a declaration never creates a second entry, and never restamps consent.
    • The public registration page addresses exactly one environment, fixed at build time; it exposes no environment toggle.
    FTL delivery never stamps before SMTP acceptance; SMTP errors leave ts_ftl_sent unchanged.

    Run and observe

    Operations

    Review calendar reconciliation reports before trusting convergence. Investigate skipped deletions rather than forcing them. Validate URLs against the event they claim to represent. For organizer delivery, pilot one event on CERT, inspect the manifest/recipient and timestamp, then use manual PROD dispatch. Keep ENABLE_FTL_DEADLINE_SEND unset until that pilot is signed off. Gmail credentials stay only in GitHub Actions secrets; an App Password is independently revocable but must still be treated as a high-value credential.
