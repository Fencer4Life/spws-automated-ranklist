Product surfaces

One Svelte application serves public ranking and calendar journeys, event registration and authenticated administration; selected views are also packaged as embeddable web components.

Public experience

Ranklist

Filter by season, weapon, gender and age category; switch ranking mode where configured; open a fencer drilldown to understand score composition. The controls keep one fixed place on the list and in the drilldown: the language flags (round images, not emoji) in the top-right corner, and at the right end of the line below the title the Ranking | PPW switch (Ranking first, where the season shows it) followed by the ODS download of the view on screen. The drilldown’s header shows the fencer’s name with category, season and birth year, the close button beside the flags (Esc also closes), and under the name a headline with the fencer’s place and total for the view shown; the SPWS and EVF+ parts appear only in the chart headings. Its Ranking | PPW switch switches the ranklist behind it too, so the place in the headline always matches the list. On a phone the drilldown is full screen and its header stays at the top while the results scroll. Both result tables, their phone cards and both bar charts run by points, highest first, newer first on equal points. Every result that counts in the ranking carries ★; a result that does not count is greyed out (grey background and grey text in the tables and cards, a faded bar in the chart). The counted set is the ranking’s own — the season’s ranking buckets decide it, and the printed totals are its sums. Each table and its phone cards sit in a framed panel. A row is named by event and season („PPW1 · 2026/27“), or by an EVF circuit tournament’s own name, with the full tournament code as its tooltip; a joined-bracket result carries a note with its premium and any cap reduction. On a rolling ranking each result carried over from the previous season keeps its grey-text, striped-bar look and is marked with the season it comes from; the legend reads „★ wliczany“ and „↩ Wynik z poprzedniego sezonu“, and the type legend explains only the tournament types shown. The drilldown’s ODS export lists every result with its bracket size N, the fencer’s category K, place m and fencers below b, the method that scored it and each stored component, named as the calculator names them and in the page’s language; a component the method does not use reads „nie dotyczy”.

A pill, „ⓘ Reguły rankingu na sezon 2026/2027“, sits in the middle of the bottom of the screen and stays there while the list scrolls. It is pinned to the viewport, above an iPhone’s home bar, and under the drawer and every modal. It names the season chosen in the dropdown, appears once that season’s own ranking rules have loaded, and is absent for a season that stores none. While it shows, the list ends with room for it, so the last row is never hidden. It opens a modal drawn from that season’s definition alone: the sum in the table’s own column names (SPWS + EVF+ = Razem, or one „Punkty“ box for a PPW-only season); one card per pool, with each bucket’s types, its rule and one ★ per counted result (an always-counted type such as MPW gets one ★); who is ranked, from the season’s entry types; the rolling-ranking note for the active season; and the coefficients of the types shown, read from fn_public_scoring_params when the modal opens and left out if they fail to load. Its footer links the scoring-table annex. It closes with ✕, Esc or a click outside, and on a phone it is a full-screen sheet with its title pinned at the top.

Calendar

Navigate events through a rotating monthly barrel that drives a single full-detail event card. The drum is a true cylinder carrying seven rows; quiet months are shown but never rested on. The barrel spans every season with no season clamp — its seams carry the season code — and the card shows dates, location and flag, fee tiers, registration deadline, registration, entry-list, result links (from the first published result: IN_PROGRESS or COMPLETED) and announcement links, and weapons. Where the season configuration enables it, a SPWS / EVF+ control narrows the calendar to domestic events, and three weapon chips narrow it by weapon.

Registration

Submit identity and consent information for an event that has registration enabled, then follow verification/matching behavior.

Entry list

View registered participants through the event’s public entry-list surface without exposing private administrative fields.

Organizer start files

Download the event’s Fencing Time seed files — one mixed-pool competition per weapon and one direct-elimination table per gender and age category present — together with a list stating each file’s name, the title Fencing Time will display, how many fencers it holds and whether it is imported as a competition or used as a pick-list. One control bundles the whole set, because a single event produces dozens of files. The page reads a projection that publishes no birth year and no database identity, and it is the only public surface with a language of its own: organizers of European-circuit events may not read Polish.

Published alongside the app

The published static pages

Two pages that ship from frontend/public/ to the GitHub Pages origin beside the application are linked from its navigation drawer: the points calculator (/kalkulator-punktow.html) and Załącznik nr 1, the scoring-table annex (/tabela-punktacji.html). The ranklist’s season-rules modal links the annex as well; that link resolves through the embed’s asset base, so it also opens from the WordPress page. Both are plain files that Vite copies verbatim, and both hold no credential beyond the anon key.

Neither carries its own copy of the scoring formula. Both compute from one shared module generated into them, and read fn_public_scoring_params, which returns one row per tournament type: the engine assigned to that type, its coefficient, and the season's base value, DE-round points and podium coefficients. Each page takes its row by type. An administrator who changes scoring configuration before a season's first scored result therefore sees that change on both pages; once the season locks, the parameters stop moving and the pages freeze with the scorer. The database lock is the only lock.

The calculator follows the active season. It carries the annex’s tools with the same texts — „W skrócie”, the result calculator (a field of up to 300, a joined-bracket mode for the fencer’s own and the youngest category, the rank coefficient with a chip per type on the joined engine), the premium table and the joined-bracket simulator — and links to the annex for the rules: relatively inside the ranklist, and by its full GitHub Pages address in the WordPress copy, which is uploaded alone. It has no engine toggle. The annex shows „W skrócie”, the same tools, the 64 × 64 table (rows 1–3 meetings, 4–15 EVF with a premium for older categories in a joined bracket, 16–64 EVF), and the rules §§ 1–6, including the coefficient of every tournament type. Both compute only with SPWS_EVF_JOINED_V1_2026_2027 and show a message instead of numbers if the PPW row names another engine. The annex stays pinned to SPWS-2026-2027 by season code, because a regulation annex that silently re-rendered under the same title at a season roll-over would no longer be the document it declares itself to be.

Both require network access. Offline, each still renders and reads, and shows a parameters-unavailable message in place of a figure rather than a number computed from stale constants. See ADR-102, ADR-085 and ADR-092 and ADR-103 §7.

Authenticated

Administration

Admin mode is requested through the application route/query context, but access is established through Supabase Auth and TOTP MFA. Merely adding ?admin=1 does not grant data authority.

Season administration

Create and manage seasons, initialize season structure, select scoring/carry-over configuration and operate environment-aware promotion. The scoring editor gives each tournament type a card with its coefficient, its engine and the joined-bracket module that engine implies; the season engine is the default for a type without its own. Two read-only panels list what each engine fixes and no field can change: EVF classic’s place scale, 10 points per elimination round and podium × 3 × ∛N, and the 2026/2027 engine’s three ranges and constants. The EVF base value’s hint names the types it feeds. The ranking rules offer each pool only its own types — PPW and MPW domestically; PEW, MEW, MSW, PSW, PPS and MPS internationally — and a type already in a bucket cannot be picked for another. A loaded bucket the ranking cannot use as written (a type outside its pool, a type in two buckets, or not exactly one of „najlepsze N” with N ≥ 1 or „wszystkie”) carries a warning under it; changed rules that still break one of these are not saved, while unchanged rules save as they are. In the season edit card the wizard’s skeleton inventory is one collapsed line with its count until the administrator opens it, and the season’s own Zapisz / Anuluj are always the last element — below the inventory, and below the scoring editor’s own footer when Punktacja is open. That Zapisz saves everything the card shows: when Punktacja is open with unsaved changes it saves the scoring configuration first, through the same checks as the editor’s own „Zapisz i przelicz”, and then the season; a refused scoring save keeps the card open, saves no season field, and shows the reason in the card, as a refused „Zapisz i przelicz” does. A season's scoring configuration locks itself the moment its first result is scored — the editor stays open for reading and export, but every field is disabled and a save attempt is refused with an explanation; correcting a locked season requires an audited operator procedure outside this surface, not a repeated save.

Event administration

Maintain events, tournament slots, result URLs, registration settings and ingestion actions.

Fencer and identity administration

Review identity candidates, aliases, estimated birth years, duplicate identities and master-data corrections.

Operational feedback

Trigger trusted workflows through server-side dispatch and surface progress/errors in the interface rather than requiring browser-console debugging.

Host integration

SPA and web components

The SPA entrypoint supports the certification/admin application. A separate custom-element build produces Shadow-DOM-isolated ranklist, calendar, registration and entry-list elements for embedding by the SPWS website.

Embedding invariant: web components must not leak styles into the host page or depend on the host page’s CSS to remain usable.

Canonical journeys

From user action to data

  1. A public visitor selects a ranking context, or rotates the calendar barrel to a month and selects an event.
  2. The frontend reads stable Supabase views/RPCs through its API layer.
  3. For registration, a dedicated RPC validates event availability, consent and identity input.
  4. For administration, the auth layer establishes an MFA-backed session before protected operations are available.
  5. Admin writes use controlled RPCs or trusted workflow dispatch rather than direct anonymous table mutation.

Product responsibility

What the frontend does not own

  • It does not decide scoring policy independently from PostgreSQL.
  • It does not store GitHub credentials in the browser.
  • It does not treat visual event status as permission to mutate lifecycle state — see Event status lifecycle for who may set each status.
  • It does not make console output the operator’s only diagnostic surface.
