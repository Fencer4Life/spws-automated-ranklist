python/pipeline/promotion/gate.pyThe CERT gate (ADR-108 §5): reads the latest run record, fn_promote_gate_checks on the target and PROD read-only, blocks on identity, scoring and joined-bracket issues and unmet preconditions, and records its outcome on the run row; CLI --event --target cert|local [--no-record]
python/pipeline/promotion/plan.pyPlan mode (ADR-108 §6, ADR-119 §3): the RecordingConnector reads the database it plans for (PROD for promote, CERT or LOCAL for a recorded ingest) and records every write of the ingestion, answers reads of its own writes from the record, and gives a new fencer the CERT run’s id on PROD, or an id reserved with fn_reserve_fencer_id on CERT, or, for the XML dry run (reserve=False), a placeholder id below zero that reserves nothing; plan_event runs the URL driver with it and without the after-run steps; apply_plan is the reference apply. plan_check.py is the LOCAL acceptance check: plan, then apply, equals a live run, and so does the recorded CERT ingest (recorded)
python/pipeline/promotion/cert_apply.pyThe recorded CERT ingest (ADR-119 §3), which ingest_cli --record-run runs: read every final listing, save a given link, open the run with its prior, plan against CERT with reserved ids, one fn_promote_event_apply, close the run, then the drain, the gate (findings to Telegram, counts to the log), the staging report and the joining check. Nothing final writes nothing; an apply without an answer is settled by reading CERT again. In the results sync’s mode (--quiet) it sends nothing to Telegram; the step outputs its run, whether it finished and its gate, and a finished run lifts the event’s results-sync pause. Its seams are replaced in python/tests/cert_apply_fakes.py
python/pipeline/promotion/lifecycle.pyThe event lifecycle rule (ADR-108 §7, ADR-119 §1): a skip whose reason starts “not final” (is_not_final) keeps the event open, whichever engine gave it; COMPLETED once every listing is final and read and the end date has passed in Warsaw, otherwise IN_PROGRESS; status writes through the validator’s pairs
python/pipeline/promotion/close.pyThe daily close behind event-close.yml: completes an event of any organizer on CERT then PROD once the schedule, the CERT run and both result fingerprints agree, or reports on Telegram what to do; --dry-run
python/pipeline/promotion/results_sync.pyThe hourly results sync behind results-sync.yml (ADR-119 §4): select takes the active-season events in their window (first day to the day after the end date in Warsaw, by the moment the cron was due) that have a results link and no pause, honours RESULTS_SYNC=off, lifts a named event’s pause and sends the morning line; a scheduled select (GitHub's cron, or the Telegram bot's hourly dispatch with --scheduled, whose slot is the UTC hour it runs in: bot_slot) records its start on CERT first (fn_results_sync_begin), ends within 20 minutes of the last one and sends the morning line once a day (ADR-119 G47); compare hashes the schedule and the final listings as the run record does and compares them with the latest finished CERT run and PROD’s fingerprint, writing no result: its read is the ingest’s (ingest_cli.read_event), so it stores only a sighting of a bracket from an engine without a finished signal and a captured PZSz start list; outcome records the cycle’s verdict in tbl_results_sync_event, pauses the event on any failure and sends the cycle’s one line. public_error is what may pass between jobs: a step’s environment is printed in its log, so no fencer is named
python/pipeline/promotion/run_record.pyThe record of a CERT ingestion that promote replays: the schedule and listing hashes, the commit and the run, opened with the prior the CERT plan starts from and closed through fn_ingest_run_open, fn_ingest_run_finish and fn_ingest_run_fail (ADR-108 §4, ADR-119 G17)

Database contracts

Migrations are the authoritative evolution record, but current behavior is the result of the full ordered migration set. Search the latest definition of an object rather than assuming the first migration remains current. Never edit a deployed migration; add a corrective migration.

Views and RPCs are application contracts. When adding an event field, review every reconstructed view and round-trip function that owns the projection.
