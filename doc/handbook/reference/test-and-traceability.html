Fixture discipline

Fixtures own their data

A pgTAP fixture must not depend on which rows the seed happens to contain, nor on the date the suite runs. Three rules follow, and all are load-bearing:

  • Create fixture rows; do not borrow seed rows. Looking a fencer up by surname binds the test to seed contents and is ambiguous whenever production holds two fencers sharing a surname — the defect the seed’s own name lookup once had. The seed now carries PROD’s fencer ids (ADR-036 §1), and a fixture names its own rows.
  • Derive age-dependent values from the active season, never from literals. fn_age_category buckets on season end year − birth year, so a hardcoded birth year silently changes category at a season rollover. Fixtures set birth years as <active season end year> − <target age> and place each fencer mid-band (V1 at 45, V2 at 55, V3 at 65) rather than near a boundary.
  • Choose the active season by setting today. s.bool_active is computed from the season dates on every read (ADR-031, amended 2026-10-06), so it cannot be set. A fixture that needs a season active sets the day the rules read: PERFORM set_config('spws.today', '<a date inside the season>', false), and clears it with '' when later assertions need the real date. fn_today() returns that setting when it is set, and CURRENT_DATE otherwise.

The same rules hold for a Python test that writes to LOCAL. test_pipeline_integration.py creates its own SPWS event on a free date of LOCAL’s active season and synthetic fencers no real person carries, then removes every row it made, puts the fencer and event sequences back, and fails unless LOCAL’s counts and sequences are as it found them (P3.INT.5).

No Python test writes into the repository. The 3-way diff and the staging report fall back to the repository’s own doc/staging when they are given no folder; an autouse fixture in python/tests/conftest.py points both fallbacks at each test’s temporary folder, and P3.D13 proves it.

Mutating statements in a test are scoped to the fixture's own season. A statement that mirrors a migration backfill must carry an explicit scope even when the unscoped form appears to work against today's seed.

A test that must guard live rules resolves the active season rather than naming a season literally — but pairs that with a config contract: one assertion pinning the exact configuration values the rest of the file's arithmetic assumes. Scoring configuration is per-season, so a literal season pin silently guards retired rules, while a bare config-following test silently changes meaning when an admin edits config. The contract assertion resolves both: a rule change produces one named failure that says which expectations to recompute. Assertions about whether the engine applies configuration compare against the configured value, not a literal, so they never drift; the literals live in the contract, in one place.

Requirement chain

Traceability chain

FR / NFR → RTM row → plan test ID → test-code marker → implementation evidence

Use stable IDs in plans and tests. If requirements or test IDs change, update the RTM, the explicit roster sentinel in scripts/check-spec-sync.sh and documented suite totals in the same change. The current pgTAP total is in spec Appendix D, which moves with every change and which CI checks against the suite; this page states the shape of the discipline, not a running total. For example, 79_no_bracket_stubs.sql proves that a calendar-discovered event stays childless until results exist (ADR-096) and that two consecutive renumbering syncs both live. The HTML requirements traceability matrix remains governance/reference, not newcomer reading.

Change workflow

Mandatory TDD

  1. Define acceptance tests and IDs before implementation.
  2. Write the test.
  3. Run it and prove RED for the intended reason.
  4. Implement the minimum change.
  5. Run and prove GREEN.
  6. Refactor while preserving GREEN.
  7. Run applicable full suites and coherence/documentation gates.

Repository gates

Coherence checks

  • Python/frontend versions remain synchronized when released.
  • ADR source count matches the governance registry.
  • pgTAP planned assertions match the documented total.
  • A migration change ships with a specification, ADR, governance or handbook change in the same push or pull request; CI fails otherwise (python/tests/test_coherence_migration_gate.py).
  • Generated ADR and root HTML match retained Markdown sources.
  • Canonical handbook metadata, links, map coverage and ownership are valid.
  • The deny-by-default authorization posture holds — asserted twice, deliberately: pgTAP 52.1–52.12 prove what LOCAL looks like after migrations replay, and scripts/check-security-posture.sh proves what CERT and PROD actually look like, from inside the release deploy jobs where a manual dispatch cannot route around it. See Security posture.
  • Every CI run’s Summary page shows each job’s results: each check as a pass or fail line, the counts and time, and each failing pytest test or pgTAP file with its first error line or failed tests (scripts/ci_summary.py, Vitest’s own reporter for the frontend; RTM NFR-17). Read it first on a red run.
  • A pgTAP file that ran a different number of assertions than it planned fails CI and preflight (scripts/check_pgtap_plans.py, CISUM.08), because pg_prove itself still calls that file ok. On 18 Oct 2026 19_phase3_wizard.sql planned 25 and ran 5, and CI stayed green.

Handoff

Completion report

Report exact commands, outcomes, skipped checks and remaining risks. Never say “tests pass” when only a narrow test ran. Do not fix unrelated pre-existing failures silently; distinguish them from changes introduced by the task.
