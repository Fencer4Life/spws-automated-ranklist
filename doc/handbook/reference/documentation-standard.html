Canonical page contract

Required metadata and structure

Every handbook page declares doc-id, doc-status, doc-type, doc-owner, last-verified, source globs and review triggers. Subsystem pages additionally contain purpose, boundaries, mental model, current flow, invariants, implementation map, operations, tests, related decisions and change triggers.

Every page links two stylesheets, in this order: doc/adr/assets/adr.css (the shared design) and then doc/handbook/assets/handbook.css (the handbook additions); doc/handbook/PAGE_TEMPLATE.html shows the form. A stylesheet never uses @import: the README opens pages through html-preview.github.io, which loads linked stylesheets from GitHub but cannot resolve an import, so the page would open unstyled. python/tests/test_docs_stylesheets.py (DOCSTYLE.01–03) enforces both.

Every page wears the ADR page frame, and the frame is generated: scripts/render_handbook_frame.py writes the facts card beside the title from the page’s doc-status, doc-owner, doc-type, last-verified and doc-id, and the contents column from its <section id> headings. Change the metadata or the section heading, never the frame, and run the script. A page states when it was verified only through last-verified, never in a hand-written chip. render_handbook_frame.py --check runs in preflight and CI, and python/tests/test_render_handbook_frame.py (HBFRAME.01–07) pins the frame.

Present tense rule: handbook pages describe the post-change system. Do not append implementation diaries, milestone close-outs or superseded behavior.

Authority

Link, do not duplicate

  • Link to ADRs for rationale.
  • Link to formal rules for exact business statements.
  • Link to the workflow catalog for inventory and to runbooks for procedures.
  • Link to source paths/tests as evidence.
  • Do not link legacy narrative as the canonical explanation.
  • Do not maintain volatile counts in README or orientation pages unless generated.
  • The system chart has one source, doc/handbook/assets/system-architecture.svg. A page shows it as an image inside <figure class="system-map"> and never copies or redraws it; when the system changes, that file changes, and every page follows. Its colours repeat the shared tokens of doc/adr/assets/adr.css, because an image cannot read the page’s stylesheet.

The box is binary: it cannot be checked until every field is resolved and the validator passes.

Per change

Maintenance workflow

  1. Classify documentation impact during planning.
  2. Name owning pages through the documentation map.
  3. Update current-system prose and source references in the same change.
  4. Update/add/supersede ADRs when the change is a decision.
  5. Update runbooks/catalogs for operational impact.
  6. Move superseded prose to archive/evidence.
  7. Run renderers, check_docs.py and coherence gates.
  8. Report docs changed and checks run.

Automation

Validation

python scripts/render_adrs.py --check
python scripts/render_docs.py --check
python scripts/render_handbook_frame.py --check
python scripts/check_docs.py
python scripts/check_docs.py --changed-from origin/main

Ownership warnings remain advisory until mappings have completed two development cycles without unacceptable false positives. Structural metadata, links, map coverage and required sections are hard failures immediately.

History discipline

Archive policy

Archive only after replacement coverage is proven. Preserve files and Git history, create an archive index and leave redirects at high-value old HTML paths. Evidence remains exact and searchable but is not part of the newcomer navigation.
