How to read this page

What GitHub runs for the system

GitHub hosts the repository and runs every automated job of the system as a GitHub Actions workflow: the quality gate on every change, the release to CERT, GitHub Pages and PROD, the intake of results, the daily calendar synchronizations, the movement of verified data to PROD, and the self-healing recompute. Each workflow is one file in .github/workflows/ and has exactly one block on this page, grouped by the process it serves.

  • First row: the workflow’s name as GitHub shows it and its file, the process it serves, how often it runs and who starts it, and what it depends on: a workflow that triggers or calls it, data another workflow must have produced first, and the lane it shares.
  • Second row: what it does, step by step, and what a red run usually means, with the first thing to check.
  • Red, cancelled, skipped. A run is red when a step exits non-zero. Most workflows also report a failure on Telegram. A cancelled run was stopped by hand or dropped while it waited in a shared lane; a skipped job had a condition that was false, such as a release after a red CI run.
  • Times. GitHub schedules in UTC. Warsaw is UTC+2 in summer time and UTC+1 in winter time; the clocks go back on 25 October 2026.

The clock

Daily schedule

Scheduled runs start from the workflow file on main, and the cron is the earliest a run can start, not when it starts. GitHub delays scheduled runs under load, most at the start of an hour, and drops some, so no cron here fires at minute 0 (python/tests/test_workflow_schedules.py, WFCRON.01). Measured 10–24 Oct 2026, when every cron was on the hour: the daily runs started once a day, 4–9 hours after their cron; the 15-minute drains started 5–6 times a day; the start-list captures started 0.2–3.5 hours late. Process · quality and delivery

Quality gate and release

Every change to main passes CI, then Release delivers it.

WorkflowProcessHow oftenDepends on
What it doesA red run usually means
CIci.ymlThe quality gate for every change to main

On every push to main and every pull request into main. No schedule and no manual start.

A commit whose message carries [skip ci] does not run it: the seed, tracking and reconcile-log commits the workflows push themselves.

Nothing has to run first. When it completes on main it triggers release.yml.

It boots LOCAL from the committed seed supabase/seed_prod_latest.sql, which export-seed.yml, promote.yml and promote-season.yml keep current. No lane.

What it does

Four jobs run side by side on a GitHub runner with a read-only token (ADR-083); they write nothing and need no approval.

  • pgTAP (database) boots LOCAL Supabase in Docker (every migration, then the committed seeds), runs the postgrestools semantic gate, where any finding fails, and runs every pgTAP test.
  • pytest (Python) runs Ruff lint and format, BasedPyright, the three generated-HTML checks (ADR pages, rendered docs, the handbook page frame), check_docs.py and pytest.
  • Frontend runs svelte-check, where a warning fails, and Vitest.
  • Coherence Checks runs scripts/check-coherence.sh: version sync, the ADR count and the pgTAP total against the specification, and that a migration changed by the push or pull request comes with a documentation change in the same range.

scripts/preflight.sh runs the same gates on a developer machine.

A red run usually means

A gate found a real problem in the change. Nearly always one of: a type or lint error, a failing pgTAP assertion, a count in the specification that no longer matches (pgTAP total, ADR count), a migration pushed without its documentation, a stale generated page, or a migration the committed seed no longer satisfies. Runner trouble (a Docker pull, a pip or npm install) is rare.

First check: the failing step; then run scripts/preflight.sh, which reproduces it. A red CI on main makes the Release after it skip.

Releaserelease.ymlDelivery of main to GitHub Pages, CERT and PROD

After every CI run that completes on main, and on a manual start from the Actions page, which always deploys. Telegram and the admin screens cannot start it.

The PROD job waits for an approval in the production environment.

Triggered by ci.yml completing on main; it goes on only if CI succeeded.

Lane release: one release at a time, and a newer release replaces one that is still waiting. Every workflow that writes CERT or PROD relies on the schema it deploys.

What it does

  • gate lists the paths changed since the commit PROD last deployed, recorded in deployed_migrations.json (scripts/release-gate.sh). If every one is documentation (doc/, a root README, AGENTS or CLAUDE file, a tracking file), the run ends green without deploying; anything else deploys (ADR-094). So a change whose release never ran (red CI, or cancelled while waiting) stays in the range until it is deployed, and a base that is not an ancestor of the new commit deploys.
  • build computes the LOCAL schema fingerprint, puts each host’s public keys into its own files (ADR-109): the CERT pair into github.io’s index.html, calculator and annex; the PROD pair into register.html, the embed/ copies the WordPress pages frame, and index.html’s promotion read, builds the app and the web components, and checks that the bundle holds no secret, that the embed copies are PROD-only and that the bundle keeps its stable name assets/main.ce.js.
  • deploy-pages publishes GitHub Pages at once, without waiting for the PROD approval.
  • deploy-cert checks out the commit build fingerprinted, applies its pending migrations through the Supabase Management API, compares CERT’s schema fingerprint with LOCAL’s, deploys the dispatch-workflow Edge Function, runs the security posture check (ADR-083) and records the deploy on top of main with scripts/commit-tracking.sh, a [skip ci] commit on every deploy, migrations or not: the deployed commit in deployed_migrations.json, which the next gate measures from, and release-manifest.json for this release (build’s copy of the manifest is a dry run).
  • deploy-prod waits for the approval, then does the same on PROD, for the same commit however far main moved meanwhile (ADR-011).

A failed build or deploy job ends with a Telegram message naming it; a failed posture check sends its own SECURITY POSTURE REGRESSION message instead.

A red run usually means

CERT’s or PROD’s live schema disagrees with what CI built: a migration fails on the cloud database, the fingerprint differs after the migrations, or the security posture check finds a function or grant outside its allowlist. A build guard (a secret in the bundle, a CERT key in a PROD embed copy, a renamed bundle) is the other designed stop.

First check: which deploy job failed, the LOCAL and CLOUD fingerprints it printed, and the line “Applied before failure”. Tracking moves only after success, so the next run applies the same files again. Skipped means CI was red; cancelled means a newer release replaced this one while it waited.

Export Seed from PRODexport-seed.ymlThe committed copy of PROD’s data that LOCAL and CI load

On demand: Telegram export-seed, and as a side effect of the Telegram complete and rollback commands; or by hand. Telegram always exports PROD.

Nothing has to run first. Every supabase start loads its file: ci.yml, the Release build and LOCAL.

promote.yml and promote-season.yml run the same exporter in their own jobs. No lane.

What it does

Reads all of PROD’s data (or CERT’s, when source is set to cert by hand) through the Supabase Management API with python/pipeline/export_seed.py. It writes supabase/seed_prod_<date>.sql and points seed_prod_latest.sql at it; a CERT export writes supabase/seed_cert_<date>.sql and leaves seed_prod_latest.sql alone (SEEDNAME.01–04). It commits and pushes the file to main with [skip ci], or reports that nothing changed (ADR-036).

It writes no database. It sends a Telegram message on success and on failure. Its commit runs no CI, but the next Release counts the seed file as a deployable change.

A red run usually means

It has never been red. From the code, red means the Management API kept failing (401, 429, 503 or time-outs through every retry), or the push failed three times. It rebases onto a main that moved and retries, so what is left is a conflict: another export of the same day’s seed file landed first.

First check: the failed step in the run linked from Telegram: export (the API) or commit (the push: start it again).

Process · results intake

Results intake

A current-season event of any organizer reaches CERT through ingest-event.yml and PROD only through promote.yml. The other four are tools: one tournament, result links, past seasons and the review report.

WorkflowProcessHow oftenDepends on
What it doesA red run usually means
Ingest event (NEW pipeline, from URL)ingest-event.ymlResults of one current-season event, of any organizer, into CERT, ahead of promote

On demand: Telegram ingest <EVENT-CODE>, the usual route (EVF sync and the PZSz digest suggest the command), or by hand.

No admin screen starts it, although the dispatch-workflow allowlist accepts it.

Lane cert-write with recompute-drain.yml, so CERT’s results never mix two states (ADR-108 §9).

Needs the event on CERT (an SPWS or PZSz event also its url_event: an FTL event schedule, set in Admin or given as the url_event input, which saves it; anything else is refused before the first write); a PZSz event needs a stored start list from pzsz-start-lists.yml. promote.yml replays the run it records.

What it does

Validates the inputs and refuses any target but cert. Refreshes CERT’s master data (fencers, aliases) from PROD with --auto: a refresh that renumbers nobody and leaves nobody unpaired is applied; any other stops the job before its first write (ADR-113 §7). An applied refresh then copies the event’s results links from PROD when PROD holds one (fn_copy_event_result_links), so a link set in PROD’s Admin reaches the ingest; the url_event input is saved after it and wins (ADR-117).

Then runs the rule-driven ingest (python -m python.pipeline.ingest_cli): SPWS and PZSz from FTL (PZSz with the newest stored start list, ADR-111), EVF and FIE from every result-URL slot or EVF’s results, one tournament per source bracket (ADR-105, ADR-113). It opens a tbl_ingest_run row before any write and closes it FINISHED or FAILED, replaces the event’s results on CERT, sets the event status by the lifecycle rule, uploads the staging report to Storage and sends it to Telegram with a promote hint.

A red run usually means

A data guard stopped the ingest, and nothing reached PROD: the master-data refresh would renumber or unpair a fencer (Telegram ⏸ with the counts), a fencer’s birth year conflicts with the bracket (ListingRefused names the fencer and the fix), the event or its URL is missing, or a PZSz event has no stored start list while pzszerm.pl shows its JavaScript check. The run row is FAILED.

First check: the Telegram ❌ or ⏸ text and the last line of the traceback. An expired SUPABASE_ACCESS_TOKEN or an FTL login failure is the environment case.

Scrape Tournament Resultsscrape-tournament.ymlOne tournament’s results scraped into CERT

On demand: Telegram t-scrape <tournament code>, the ⬇ “Import results from URL” button on a tournament row in Admin → Events, or by hand. Rarely used.

Needs the tournament’s url_results, usually filled by populate-urls.yml.

It records no run, so promote.yml never carries its result to PROD. No lane.

What it does

Refuses any target but cert and a malformed code as its first step, and holds no PROD secret: PROD gets results only through promote (ADR-113). Reads the tournament’s url_results and its sibling tournaments, and stops if any sibling already holds results: it never replaces.

It parses the page (FTL, Engarde, 4Fence, Dartagnan), splits a domestic result by birth year into the age categories (an international tournament stays one whole bracket, ADR-105), removes empty siblings and writes through fn_ingest_tournament_results. It writes no drafts and no run record. A Telegram message carries the last ten lines of its output, escaped so that Telegram’s HTML mode accepts them.

A red run usually means

The scrape stopped or failed: a sibling tournament already holds results (it never replaces), the tournament or its url_results is missing, the page could not be read or parsed, or the database refused the write. Or the input was refused: a target other than cert (the button pressed on the PROD admin page) or a malformed code.

First check: the last lines of output in the Telegram message, which carries the run’s status.

Populate Tournament URLspopulate-urls.ymlFinding each tournament’s result link from the event’s pages

On demand: Telegram populate-urls <event> (CERT) and populate-urls-prod <event> (PROD), the event-row ⬇ button in Admin → Events (shown when the event has a url_event), or by hand.

Needs the event’s URL slots, url_event to url_event_5. scrape-tournament.yml uses the links it fills. No lane.

What it does

Refuses a malformed event code or a target other than cert or prod. On the target, reads the event’s five URL slots (FTL, Engarde, 4Fence, Dartagnan), finds each competition’s results page and writes tbl_tournament.url_results only where a tournament has none: it never overwrites a link and never creates a tournament.

It imports no results. A Telegram message carries the last twenty lines of its output, escaped for Telegram’s HTML mode, with an “Updated n/m” count and a MISS line for each tournament it could not match.

A red run usually means

The script failed: the event was not found or has no URL slots, a site could not be read, or a slot points to a platform it cannot read (Ophardt). A tournament it could not match is not red but a MISS line, and a link it could not write is a FAIL line.

First check: the “Updated n/m”, MISS and FAIL lines in the Telegram message, which carries the run’s status.

Stage or replace one event's results (past-season repair)phase5-event-runner.ymlRepair of a past-season event, and LOCAL work

By hand only, from the Actions page or gh workflow run. No Telegram command or admin screen starts it. Each run is titled with its event, target and mode.

Needs the event’s url_event slots; commit mode needs an earlier staged run of this workflow.

A Phase 5 commit on PROD makes promote.yml refuse that event, so a current-season event goes through ingest-event.yml. No lane.

What it does

Stage mode runs the Phase 5 pipeline (python -m python.tools.phase5_runner) on CERT or PROD: it reads the event’s URL slots, keeps each bracket’s whole source N and the fencers’ own places (ADR-105), writes draft rows (tbl_*_draft), uploads the review report staging-reports/<event>/full.md to Storage (ADR-058) and sends it to Telegram.

Commit mode (commit_run_id) runs the sign-off checks on that staged run and replaces the event’s results with it through fn_replace_event_from_draft, rollback and commit in one transaction: the way a past-season event reaches CERT and PROD. It writes no tbl_ingest_run row.

A red run usually means

An input or sign-off gate: an unknown event code, an event with no URL slot, or, in commit mode, rows still PENDING or alias pairs marked blocking (exit 2, listed in the log with ⛔).

First check: the ⛔ lines in the log, then the Telegram ❌ message, which names the mode.

Regen Verdict Report (.md)regen-report.ymlRefreshing an event’s review report after alias triage

On demand: in Admin → Fencers → Aliases, “+ Create new fencer” on an alias that owned results starts one run per affected event, on that admin page’s environment; or by hand. Rarely needed.

Needs the event on the target. It renders from the newest draft run of phase5-event-runner.yml, or from committed rows when there is none. No lane.

What it does

Validates the inputs, then re-renders staging-reports/<event>/full.md from the database as it is now (python -m python.tools.phase5_report) on CERT or PROD, without reading any source again. It uploads the report to Storage and sends it to Telegram (ADR-058, ADR-061). It changes no result.

When GitHub accepts the start, the admin screen says “regeneration started · the report arrives on Telegram”; the report follows when the run finishes, or its failure message if it fails.

A red run usually means

An unknown event code (it shows as a traceback rather than a message) or a Storage or database error. There is no run history yet.

First check: the event code and target in the run inputs, and the last line of the log.

Process · calendar and start lists

Calendar and start-list synchronization

These keep CERT’s calendar current from EVF and PZSz, mirror it to PROD, and capture the PZSz start lists.

WorkflowProcessHow oftenDepends on
What it doesA red run usually means
EVF Calendar + Results Syncevf-sync.ymlEVF calendar intake, and the EVF-versus-CERT results report

Daily, cron 23 6 * * *: 06:23 UTC, 08:23 Warsaw in summer, 07:23 in winter. Measured 10–24 Oct 2026, when the cron was on the hour: once a day, 4–9 hours late.

On demand: Telegram evf-cal-import (calendar half) and evf-results-import <event> (results half, no mirror), or by hand with mode, event_code and filter_stale.

Calls promote-calendar.yml after it writes CERT (not in results-only mode), which waits in the prod-write lane.

Needs an active season on CERT. Scheduled for the same minute as pzsz-sync.yml; the two scrapes run side by side.

What it does

Calendar half, on CERT: scrapes EVF’s season calendar, records the scrape, enters future events and updates their fields and the organizer’s letter (fn_ingest_evf_calendar, fn_sync_evf_event_fields, fn_refresh_evf_event_urls), writing no results link (ADR-117), and repairs an event marked COMPLETED with a future date. An entry whose weapons EVF has not published, or a championship it must not guess about (a championship that is not a European Championship, a second candidate for the season’s IMEW or DMEW, or an unexpected singleton), is held back, named on Telegram and counted in the digest (pending_weapons, held_championships) instead of failing the run.

Results half: reads EVF’s results API, decides EVF’s rows by the international admission (ADR-106), compares them with CERT and reports the gap on Telegram with the commands to send, ingest <code> then promote <code>, and reports PENDING rows (printed POL, with no exact identity of a fencer with an SPWS start) in the log and on Telegram. It writes no result (ADR-113 §8), but creates the CERT event when an EVF event in scope has none. If the calendar half fails, the results half still runs and the run ends red. Then promote-calendar.yml mirrors the calendar to PROD, even after a failed sync. End to end: EVF calendar sync explainer.

A red run usually means

The calendar half failed: EVF’s calendar or results API unreachable or answering with a bot challenge, the Management API failing through its retries, or the database refusing the calendar plan (a code collision on CERT). The red runs of recent months were code defects since fixed; it has been green daily since mid-September 2026.

First check: the Telegram “EVF Calendar FAILED” or “HALT” message, then ERROR: calendar sync failed in the log. Missing CERT credentials end the run red with exit 2 and the workflow’s “EVF sync FAILED” message; no active season ends it green having done nothing.

PZSz Senior Calendar Syncpzsz-sync.ymlPZSz senior calendar intake (PPS and MPS)

Daily, cron 23 6 * * *: 06:23 UTC, 08:23 / 07:23 Warsaw. Measured 10–24 Oct 2026, when the cron was on the hour: once a day, 4–8 hours late.

On demand from the Actions page, with dry_run (the script’s --dry-run, no write). No Telegram command.

Calls promote-calendar.yml after the sync (not on a dry run), which waits in the prod-write lane. Needs an active season on CERT.

Creates the events whose start lists pzsz-start-lists.yml captures; its digest names the ingest command (ADR-112 §5) once an administrator has set the event’s results link on CERT or PROD (PROD read only, SUPABASE_PROD_REF; ADR-117) and a stored start list is ready for ingest-event.yml.

What it does

Reads our CERT list of PZSz events, then pzszerm.pl’s listing and home page in headless Chromium, which runs the site’s own JavaScript check the way a person’s browser does (no cookie forged, no CAPTCHA solved; ADR-116). It creates new future events, then decides six fields of each future event on its own: the invitation link and the fee while blank, the city, venue address and dates every run, reading the organizer’s letter in four passes that abstain when unsure.

Every write is compare-and-set through fn_pzsz_apply_event, so an admin’s hand correction is never overwritten. It never stops part-way, sends one Telegram digest when there is something to report, and sets its exit status last. A dry run writes nothing. Then promote-calendar.yml mirrors the calendar to PROD, even after a failed sync.

A red run usually means

A fatal, not a warning: an ended event with no stored start list, no finished CERT run and no way to get one (red once, then recorded), a create or event write the database rejected, or the run itself failing (no active season, CERT unreachable, Chromium not starting). A listing not served, the JavaScript check, a listing at its 70-row cap and an unreadable letter are warnings in the digest.

First check: the ❌ lines in the “PZSz Calendar” digest. A setup failure (the pip or Chromium install) sends its own short Telegram message, since the sync never ran to send one.

Promote calendar → PROD (reusable)promote-calendar.ymlThe CERT → PROD calendar mirror

Never on its own: it runs as a job inside evf-sync.yml and pzsz-sync.yml, right after each sync, so its runs appear under theirs, not under its own name.

Called with uses: by evf-sync.yml and pzsz-sync.yml. Lane prod-write: it waits behind any other PROD writer. Needs the same active season on CERT and PROD.

What it does

The one definition of the calendar mirror. python -m python.pipeline.promote --mode calendar checks that CERT and PROD have the same active season, then reconciles every event of that season on PROD with CERT through fn_mirror_events_to_prod, creating, updating and deleting rows by event code, for every organizer (ADR-081). It carries no results link, and a calendar page in PROD’s URL komunikatu gives way to CERT’s letter (ADR-117). That carries the planning half of the event lifecycle to PROD, a skeleton becoming dated and a cancellation (Event status lifecycle), and each PZSz event’s id_pzsz_event and venue address. It converges the whole season, not only what the calling sync scraped, so the EVF and PZSz mirrors cover each other.

It writes the reconcile report to doc/staging/reconcile/, commits and pushes it with [skip ci] (rebasing and retrying up to five times) and reports the created, updated and deleted events on Telegram. Start lists do not travel this way; promote.yml replays them.

A red run usually means

The active seasons on CERT and PROD differ, PROD refused a row (a unique-key collision; last seen in August 2026, fixed), the Management API failed (no retry here), or the log push failed five times.

First check: the Telegram “Calendar reconcile → PROD FAILED” message. Each mirror converges the whole season, so the next sync’s mirror repairs a missed one.

PZSz Start Lists → CERTpzsz-start-lists.ymlCapturing PZSz start lists, whose birth years the PZSz result ingest needs

Five crons: 11 5 * * *, 11 9 * * *, 11 13 * * *, 11 17 * * * and 11 19 * * *; Warsaw 07:11, 11:11, 15:11, 19:11, 21:11 in summer and an hour earlier in winter. The 05:11 UTC run is the day’s first. On an event’s last day the 09:11 UTC run (10:11 Warsaw in winter, 11:11 in summer) is the window’s last attempt, passed --last-attempt.

Measured 22–24 Oct 2026, when the crons were on the hour: 0.2–3.5 hours late, so a run can start hours after its time, even after midnight Warsaw time; it still works on the moment it was due. On demand from the Actions page, no inputs.

Own lane pzsz-start-lists: one capture at a time. Needs the PZSz events pzsz-sync.yml creates.

ingest-event.yml reads what it stores; promote.yml replays it to PROD.

What it does

A PZSz start list appears four days before an event’s first day, and pzszerm.pl still serves it during the event, so the window runs from D−4 to noon (Warsaw) on the event’s last day. Each run purges stored lists outside the active season, selects the events in that window by the Warsaw moment the run was due (the cron that fired, passed as --cron; a manual run uses the clock), which also decides the first-run and last-attempt messages (PZSZ.SL.10–13), reads each event’s start lists with headless Chromium (the same JavaScript check as the calendar run) and stores every new version through fn_pzsz_start_list_store.

Two independent checks compute the window, the selection and the reader, so a single bug cannot widen it. It writes CERT only and promotes nothing; PROD receives the lists only through promote.yml, which replays them by hash (ADR-112 and its amendment of 25 October 2026, ADR-116 §7). One Telegram digest per run when there is news.

A red run usually means

The window’s last attempt, the run due before noon on the event’s last day, found a tournament the event is known to have with nothing stored in the whole window (from D−1 until then it is a warning); or the run itself failed: no active season, a CERT query or store failure, Chromium not starting. A page that does not render is a warning. A setup failure (the pip or Chromium install) sends its own short Telegram message.

First check: the ❌ line naming the event and the weapon and gender pairs; then store that list from a saved page before the ingest. A fencer who entered at the venue is on no list at any time.

EVF Parity Sweepevf-parity-sweep.ymlEVF score parity: checking that PROD holds the N and points EVF published, read only

Daily, cron 17 4 * * *: 04:17 UTC, 06:17 / 05:17 Warsaw. Measured 10–24 Oct 2026, when the cron was on the hour: once a day, 4–8 hours late.

On demand with max_age_days (60) and evf_empty_stop_days (30).

Lane prod-write, scheduled for the same minute as event-close.yml, so one waits for the other.

Checks the results ingest and promote put on PROD; reads EVF’s results API as evf-sync.yml does.

What it does

Reads PROD (python -m python.pipeline.evf_parity_sweep, ADR-053 as amended on 25 October 2026). For every EVF event at ENGINE_COMPUTED whose end date is within max_age_days (future events included) and that holds results on PROD, it pairs the event with the EVF event of EVF’s results API dated from three days before its start to three days after its end (EVF dates a championship by its last day), keeping, when two fit, the ones sharing a weapon with the results PROD holds, and compares every PROD result with EVF’s row of the same weapon, gender, category, place and surname: the field size N and the points (python/tools/compare_evf_points.py).

Each event with a difference gets a Telegram message naming every difference; one summary follows every run, naming any event with nothing from EVF evf_empty_stop_days after its end, any event with two EVF events in reach that share its weapons, and any event that differs only because EVF counts a fencer it lists without a place (place 9999), whom N, counting placed fencers only, leaves out. It writes nothing: a difference is corrected through ingest and promote (EVFCHK.01–10).

A red run usually means

A read failed: EVF’s results API (listing the events or one event’s results) or PROD, for one event or all; the summary’s “Read failed” lines name each. Missing PROD secrets also turn it red: every red run up to October 2026, in May 2026, was a missing PROD URL secret. A difference is reported, not red.

First check: the “Read failed” lines of the Telegram summary, then the secrets.

Process · production movement

Promotion to PROD and event close

These move verified data from CERT to PROD and close events after their end date.

WorkflowProcessHow oftenDepends on
What it doesA red run usually means
Promote Event to PRODpromote.ymlEvent results from CERT to PROD

On demand: Telegram promote <exact code>, or by hand, where dry_run writes nothing.

Needs a finished, recorded CERT run of the event from ingest-event.yml that passes the gate, CERT’s recompute queue drained by recompute-drain.yml, the event row on PROD (made by promote-calendar.yml) and PROD’s inputs unchanged since the CERT run.

Its promote job waits in the prod-write lane.

What it does

  • resolve (read only; promotion/replay.py, ADR-108 §6) checks the code, refuses a prefix or an unknown code by listing the matching codes, and finds the latest CERT run and the commit it ran on, which must be on main.
  • promote checks that commit out, re-runs the gate against CERT and PROD, checks what PROD already holds, plans the ingestion against PROD, refuses if a source or the master data changed since the CERT run, and calls fn_promote_event_apply through PROD’s service-role API twice: a dry run, then the apply in one transaction, in which an international run’s result URLs also fill PROD’s blank slots (ADR-113). It then sends the staging report, drains PROD’s recompute queue itself (a queued drain would wait behind it in the lane) and compares the drained events with CERT.
  • seed exports PROD’s seed and pushes it with [skip ci], rebasing and retrying.

A dry run stops after the dry apply and prints the fingerprint PROD would end on.

A red run usually means

A refusal by design, with nothing written: the code was not exact (a word after it, for example), there is no recorded CERT run, the gate blocks, PROD holds something no CERT run produced, or a source changed since the CERT run (re-ingest CERT, then promote again). After the commit, a difference between CERT and PROD or an undrained queue ends the run red with exit 2 although the result is on PROD.

First check: the failed step. “Validate input” or “Find the latest CERT run”: resend promote <code> with the code alone. “Replay on PROD”: the Telegram “refused:” text names the fix.

The season’s events reach PROD afterwards through promote-calendar.yml.

What it does

Promote checks the code (SPWS-YYYY-YYYY), reads the season from CERT, refuses if CERT’s season already has tournaments (unless force_late_bootstrap) or PROD already has the season, and creates the season row and its scoring configuration on PROD through fn_promote_season_skeleton, never events (ADR-077).

Delete removes a skeleton from PROD or CERT and refuses an active season or one with tournaments. Then it exports PROD’s seed and pushes it, rebasing onto a main that moved and retrying. A success sends a Telegram message, and so does a failure, from the job’s last step.

A red run usually means

A refusal by design: the season already has tournaments on CERT or already exists on PROD (both runs so far, in July 2026, were these), the season is active or has tournaments (delete), or the code is malformed. A push that fails three times after the export turns the run red although PROD has the season.

First check: the last RuntimeError line in the log, and whether Admin → Seasons already shows the season on PROD. The Telegram failure message links the run.

Dependencies

How the workflows connect

Chains

  • Code: a push to main → ci.yml → release.yml, which goes on only after a green CI.
  • Calendar: evf-sync.yml and pzsz-sync.yml write CERT → each calls promote-calendar.yml, which mirrors the whole season to PROD.
  • PZSz results: pzsz-sync.yml creates the event → pzsz-start-lists.yml stores its start lists from D−4 to the morning of its last day → ingest-event.yml ingests it on CERT → promote.yml replays it on PROD → event-close.yml completes it after the end date.
  • Other results: evf-sync.yml reports which events have results to load and names the commands → ingest-event.yml → promote.yml → event-close.yml. evf-parity-sweep.yml then probes EVF events at ENGINE_COMPUTED.
  • Master data: a correction queues the affected events → recompute-drain.yml (CERT) and recompute-drain-prod.yml (PROD) re-score them; promote’s gate needs CERT’s queue drained.
  • Seed: export-seed.yml, promote.yml and promote-season.yml push PROD’s seed → ci.yml and the Release build load it.
  • Past seasons: phase5-event-runner.yml stages an event, regen-report.yml refreshes its report after alias triage, and a second phase5-event-runner.yml run with commit_run_id commits it.
  • Result links: populate-urls.yml fills a tournament’s url_results → scrape-tournament.yml scrapes it.

Shared lanes

A concurrency group is a lane: GitHub runs one job of a lane at a time, and every lane here waits for a running job to finish rather than cancel it. A lane is how two workflows that write the same database avoid writing it at the same moment.

Maintenance

Keeping this page current

  • Same commit. Adding, removing or renaming a workflow, or changing its schedule, a workflow it calls or is triggered by, or its lane, changes this page in the same commit. python/tests/test_github_workflows_page.py (GHWF.01–06) fails otherwise, in preflight and in CI: one block per workflow file, the workflow’s own name, every field filled, every cron, every called or triggering workflow and every lane.
  • The release skill says so. Both copies of the release skill (.claude/skills/release/SKILL.md and .agents/skills/release/SKILL.md) name this page as the step for a workflow change.
  • Rules every workflow keeps, checked in CI: a job installs every package its Python imports (python/tests/test_workflow_python_deps.py, WFDEPS.01); a step that pipes a command into tee sets shell: bash, so a failed command fails the step (WFPIPE.01); an input reaches a script only through env:, never as ${{ inputs.… }} inside the script (WFINJ.01); no value holds an empty ${{ }}, which GitHub refuses even in a # line of a script, so the whole workflow does not start (WFEXPR.01); contents: write stands at the top of a workflow only when a job that inherits it pushes (WFPERM.01). The last four are in python/tests/test_workflow_shell_safety.py. The Supabase CLI comes from supabase/setup-cli@v3, which needs no Node runtime, at one pinned version in every job (WFSETUP.01), and every job names runs-on: ubuntu-24.04 instead of ubuntu-latest, whose image GitHub moves without notice; a move to a newer image is made on a pull request (WFRUN.01). Every setup-node step runs Node 24, and every action is at a release that runs on the Node 24 runtime; an action not yet checked, or an older release, fails CI until its runtime has been read (WFNODE.01). actions/setup-node runs at v7 or later, whose own code prints no Node deprecation; v5 printed DEP0040 and DEP0169 in every job that sets up Node (WFNODE.02; all four in python/tests/test_workflow_runners.py). actions/deploy-pages@v5, the newest release, still prints DEP0040 from its own bundle.
  • What the test cannot see. A new failure condition, a changed dispatch route or a different meaning of a red run is a review trigger for this page; update the block by hand.
  • Dispatch from the admin screens. A workflow an admin screen starts must also be on the allowlist of the dispatch-workflow Edge Function, which first requires a signed-in admin with TOTP (aal2): verify_jwt = true alone is not an authorization control, because the public anon key satisfies it. See Security posture.
  • Names. A workflow’s name says what it does, not only a phase label.
  • Dispatch from Telegram. A new Telegram command needs a handler and a help entry in scripts/gas_telegram_bot.js; python/tests/test_gas_bot.py fails until they agree.
  • New inputs and secrets are documented with the operations they serve: Operator runbooks and Environments and release.
