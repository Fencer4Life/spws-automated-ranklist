context

Context

SQL migrations were being applied manually via curl to the Supabase Management API. Frontend deploys were decoupled from database deploys. PROD had no migration tracking, and there was no proof that PROD schema matched CERT or LOCAL. The team needed a build-once-deploy-twice promotion pipeline with auditable tracking.

decision

Decision

Implement a three-tier promotion pipeline: LOCAL (Docker) → CERT (Supabase cloud) → PROD (Supabase cloud). The same SQL migration files, same git SHA, and same schema fingerprint flow through all tiers.

Key mechanisms:

  • Schema fingerprint: MD5 hash of function definitions + table/column structure in the public schema. Computed locally after pgTAP passes, then verified on CERT and PROD after migration apply. Hard fail on mismatch.
  • deployed_migrations.json: Repo-committed tracking file recording which migrations are applied to each cloud environment, updated via [skip ci] commits after each deploy.
  • release-manifest.json: Audit trail with version, SHA, schema fingerprint, test counts, and per-environment deployment timestamps.
  • release.yml workflow: Triggered by CI success on main. Four jobs: build (frontend + fingerprint), deploy-pages, deploy-cert (auto), deploy-prod (manual approval via GitHub environment protection).
  • Coherence checks: CI gate verifying version sync (pyproject.toml ↔ package.json), ADR file/spec parity, pgTAP assertion count, and migration↔documentation sync.

alternatives

Alternatives Considered

  1. supabase db push — requires direct PostgreSQL port 5432, which is firewalled on Supabase cloud. Not viable.
  2. GitHub Actions artifacts only — expire after 90 days, no permanent audit trail. Tracking would be lost.
  3. Separate branches per environment (cert/prod branches) — splits commit history, creates merge conflicts, loses single-SHA traceability.
  4. Database-stored migration tracking table — creates a chicken-and-egg problem: need migrations applied to track migrations. Also unreachable without Management API.
  5. Docker image promotion — Supabase cloud is managed, cannot receive Docker containers. Only SQL can be applied remotely.

consequences

Consequences

  • Every release is traceable by git SHA — deployed_migrations.json shows exactly what's on each environment.
  • PROD only receives CERT-validated migrations — the same SQL files that passed pgTAP locally and were applied to CERT.
  • Schema fingerprint proves structural parity across all three tiers.
  • Rollback is forward-only: push a new corrective migration through the full pipeline.
  • [skip ci] commits from tracking updates do not trigger infinite pipeline loops.
  • Frontend is built once in CI and deployed to GitHub Pages — not promoted from local dev builds (local uses 127.0.0.1:54321).
  • PROD deployment requires manual approval from the Fencer4Life reviewer in the GitHub production environment.

Amendment (2026-10-25) — every deploy job applies the commit build fingerprinted

The Decision says the same git SHA flows through all tiers. The jobs had drifted from it: build checked out main when it started, deploy-cert the commit that triggered the run, and deploy-prod main again, pulled after its approval wait. A commit carrying a migration that landed in between was applied without having been fingerprinted. PROD failed "Fingerprint mismatch after applying migrations" on 28 August 2026 (run 33143154193) and 5 September 2026 (run 33985677430): build fingerprinted b7ca0235 and 4a2cdcff, deploy-prod applied 340d2ca0 and e5ccb327, and each time the migration stayed applied while the tracking stayed behind. It was found while correcting the comment that claimed both deploy jobs pull main (doc/plans/github-actions-workflows-page-2026-10-24.html, W2 #10).

Decision: build records the commit it checked out (outputs.sha), and deploy-cert and deploy-prod check out exactly that commit; neither pulls. A commit that lands on main meanwhile is deployed by its own release, which the release lane runs next. The record of a deploy is written by scripts/commit-tracking.sh on top of origin/main as it is when the deploy finishes, in a separate worktree, so the job's tree stays the deployed one; on a rejected push it fetches main and writes the record again. It names the deployed commit (.<env>.last_sha), which ADR-094's gate measures from, and the CERT record carries the release manifest of the deployed tree.

Tests: python/tests/test_release_tracking_commit.py RELTRACK.01 (the wiring) and RELTRACK.02–05 (the script against a temporary origin whose main moved: the record lands on top, the CERT manifest counts the deployed tree, a rejected push is written again once, and the last failed attempt ends red).

Amendment (2026-11-01) — each Release run's Summary page says what it carries and deployed

Since 31 October 2026 each Release run is titled by the merge it releases (RTM NFR-16), but GitHub shows only a merge commit's first line: a Release run's page held its job boxes and nothing else, and a documentation-only run's reason sat in the gate's log.

Decision (signed 1 Nov 2026, R1, R3 and R4 A in doc/plans/release-notes-on-every-release-run-2026-11-01.html): every Release run whose gate ran writes its notes onto its own Summary page, GitHub's job summary.

  • A notes job (needs: [gate, build], it runs whenever the gate ran, with contents: read only) runs scripts/release_notes.py over the gate's range (ADR-094 amendment 2026-11-01) up to the commit build fingerprinted. It lists every first-parent commit since PROD last deployed: each merge with its title, explanation and Branch: line, a commit pushed straight to main with its subject and body, and the workflows' own [skip ci] commits counted by kind, with a compare link. Text is escaped so that GitHub makes no tag, mention or issue link of it; past 900 KB the list gives titles only, since GitHub takes at most 1 MiB per step. No deploy job needs it, so its failure never stops a deploy: it turns its own job red and sends a Telegram line.
  • deploy-pages, deploy-cert and deploy-prod each write their own section: the Pages URL; for CERT and PROD (scripts/release-section.sh, the step just before the Telegram alert, which stays last) the deployed commit, the migrations applied or none, the fingerprint check, the Edge Function, the posture check (ADR-083) and the record on main, or the first step that failed.
  • After a red CI every job stays skipped, as before: a notes job there would turn a grey run green.
  • No GitHub Release object or tag is created (R1 B, rejected): it would cover only finished PROD deploys and add a public, notified object per deploy.

This does not revisit Alternative 2. The Summary page lives as long as the run's logs, 90 days, the most a public repository allows, so it is a view and not the audit trail. The record that lasts stays deployed_migrations.json, release-manifest.json and the merges in git, from which python3 scripts/release_notes.py --base <sha> --head <sha> prints the same notes for any past range. Tests: python/tests/test_release_notes.py RELNOTES.01–11.
