context

Context

The design's ranking model (§06) needs three independently-configured Season Scoring Rules — SPWS, EVF/FIE, and the not-yet-built PZSz — aggregating into exactly two publicly displayed groups (SPWS, EVF+). The existing json_ranking_rules schema (ADR-006) has only two implicit groups (domestic, international) and no version marker, so a third rule family cannot be added without either overloading international further or inventing a second, disconnected mechanism. Separately, the design's governance-lock table (ADR-097) lists "default ranking mode" as a governed field, but no column for it existed anywhere — deferred explicitly by the governance-lock plan's own Flags section to this step.

decision

Decision

1 · schema_version: 2 for json_ranking_rules, read by one new canonicalization function

fn_ranking_rules_canonical(v_rules JSONB) reads either shape: schema v1 (domestic/international, or the pure-NULL legacy season) or schema v2 (season_scoring_rules — three named sections, each declaring a group, types and buckets — plus display_groups mapping group to sections, plus views mapping mode to groups). It returns one row per bucket (section, grp, types, best, always_include, bucket_idx) and validates as it goes: an unknown tournament type, a bucket declaring both or neither of best/always, a non-positive best, a section's own group field disagreeing with its display_groups placement, or the same tournament type reachable through two sections feeding one view all RAISE before anything is returned — a PL/pgSQL set-returning function's tuplestore is only handed to the caller once the function completes without error, so no partial, half-validated result can ever surface.

2 · The legacy adapter accounts for a discovery made while implementing it: international is a superset, not international-only

Verified against the real stored json_ranking_rules for SPWS-2024-2025 through SPWS-2026-2027 while writing this migration: schema v1's international array duplicates domestic's own PPW/MPW buckets verbatim, alongside the genuinely-international one. fn_ranking_kadra's existing JSONB path reads international alone and splits its own ppw_total/pew_total afterward by ARRAY['PEW','MEW','MSW','PSW'] membership — which only produces the correct ppw_total because international already carries the domestic buckets too. The canonicalization adapter therefore drops any international bucket whose types are already wholly covered by domestic before emitting it as an evf_fie-section bucket; without this, evf_plus_total would silently double-count every PPW/MPW score. This is exactly the class of gap the design's own scenario-walkthrough discipline exists to catch, and it changes an implementation detail, not the approved architecture.

3 · fn_ranking_full — a fourth instance of the existing per-engine dispatch pattern, not six new functions

fn_ranking_full(p_weapon, p_gender, p_category, p_season, p_rolling) is a thin dispatcher on the season's carry-over engine, following the exact CASE ... ELSE RAISE EXCEPTION 'Unknown carryover engine' pattern fn_ranking_ppw/fn_ranking_kadra/fn_fencer_scores_rolling already use three times over (ADR-042/045). Each body (fn_ranking_full_event_code_matching, fn_ranking_full_event_fk_matching) generalizes the existing bucket_results/selected/totals pattern those functions' own JSONB paths already use, replacing a hardcoded ARRAY['PEW','MEW','MSW','PSW'] group-membership test with the data-driven grp column from fn_ranking_rules_canonical. One generic loop now covers all three rule sections per engine, rather than needing six functions (two engines × three sections) mirroring today's six (two engines × two groups). PZSz (PPS/MPS) is explicitly excluded from both engines' carried-over eligibility regardless of section membership — design §07's "future PPS/MPS carry-over... begins disabled."

4 · Neither fn_ranking_ppw, fn_ranking_kadra, fn_fencer_scores_rolling, nor any of their four per-engine bodies is touched

They keep serving the live frontend exactly as today, against whichever season's json_ranking_rules they are pointed at. The real SPWS-2026-2027 season's json_ranking_rules is not migrated to schema v2 by this change — the live frontend still calls the untouched old functions against the active season, and they do not understand the new shape. That cutover is deliberately deferred to design step 7, together with the frontend migration onto fn_ranking_full, so there is never a moment where the live season's stored JSON and the function reading it disagree about its shape.

5 · default_ranking_mode joins the existing governance lock, in the same migration

tbl_scoring_config.enum_default_ranking_mode (PPW | RANKING, default PPW) is added and immediately folded into the same four places every other governed field already touches: fn_export_scoring_config (read), fn_import_scoring_config (field-level guard), fn_guard_scoring_config_write (direct-write trigger backstop), fn_apply_scoring_config_write (the privileged revision's unconditional write path). SPWS-2026-2027 is set to RANKING in the same migration, per design §06's season matrix — an ordinary pre-lock write, since that season is still unscored and unlocked.

6 · A newly-created function needs its own explicit REVOKE, independent of ADR-083

Verified live during implementation: fn_ranking_rules_canonical, a brand-new function name, was granted EXECUTE to PUBLIC by Postgres on creation despite ADR-083's Block 6 default-privilege change — that change only removed a stale custom default-ACL entry granting anon/authenticated specifically; it never touched Postgres's own standard implicit PUBLIC grant on new objects. Caught by 52.7's allowlist-equality assertion, not assumed away. This is precisely why every other new internal helper in the governance-lock migrations (fn_raise_scoring_locked, fn_guard_scoring_config_write, fn_backfill_scoring_lock, fn_apply_scoring_config_write) already carries its own explicit REVOKE EXECUTE ... FROM PUBLIC, anon, authenticated — fn_ranking_rules_canonical now does too, and the finding is recorded here so it is not silently re-discovered.

alternatives

Alternatives considered

  1. A legacy-shape translation shim inserted into all six existing duplicated ranking functions, instead of one new RPC. Rejected: it multiplies the surface that must agree with the new validation rules, and this codebase already has one documented instance of exactly this drift class (ADR-096, two independently-drifting copies of the tournament-code formula).
  2. Cutting the real SPWS-2026-2027 row over to schema v2 immediately. Rejected: the live frontend still calls the untouched old functions against the active season, and they cannot read the new shape — this would silently break the deployed ranklist for the currently active season.
  3. Six new functions mirroring today's six (one per engine × group). Rejected as unneeded duplication now that a generic loop, parameterized by the canonical structure, covers all three rule sections at once.
  4. Validating season_scoring_rules shape inside fn_import_scoring_config at save time. Deferred, not rejected: no Admin UI exists yet to author schema v2 JSON (design step 7), so validating where it can actually be exercised and tested today — read time, inside fn_ranking_rules_canonical — is what this step delivers; save-time validation is added when the editor UI lands.
  5. Reading international wholesale as the evf_fie section's type set. Tried first and rejected after live verification showed it double-counts PPW/MPW into evf_plus_total — see Decision §2.

consequences

Consequences

fn_ranking_full becomes the only code that understands schema v2, and the only code that understands both schemas at once; the four frozen schema-v1-only functions and this one new function coexist for a bounded, documented interval ending at design step 7. The default-ranking-mode column joins the governance lock's field list immediately, closing the flag the governance-lock plan left open.

fn_ranking_full deliberately does not reproduce fn_ranking_kadra's IF p_category = 'V0' THEN RETURN; early exit — V0 has no EVF/FIE equivalent, but SPWS and (eventually) PZSz results can still contribute, per design §06. The live parity check against real SPWS-2024-2025/SPWS-2025-2026 data confirms spws_total matches fn_ranking_ppw's total_score in every case with zero exceptions, and evf_plus_total matches fn_ranking_kadra's pew_total in every non-V0 case; the V0 rows where fn_ranking_kadra returns no row at all (hence a NULL to compare against) while fn_ranking_full correctly returns evf_plus_total = 0 are exactly the fixed behavior SS26.RANK.10 exists to pin, not an unexplained discrepancy.

A later step must still: build the Admin UI for authoring season_scoring_rules; migrate the live frontend from fn_ranking_kadra/fn_ranking_ppw to fn_ranking_full; and cut SPWS-2026-2027's json_ranking_rules over to schema v2 as part of that same change — not before.

Test impact. pgTAP 1086 → 1100 assertions (14 new, all passing on a database rebuilt from scratch via ./scripts/reset-dev.sh). postgrestools check on 20260919000008_ranking_full.sql: 0 findings. 20260919000007_ranking_schema_v2.sql carries the same runningStatementWhileHoldingAccessExclusive/lockTimeoutWarning advisories already present, unaddressed, in the immediately-preceding governance-lock migration (20260919000005) — a pre-existing, accepted pattern for this codebase's single-transaction schema+function migrations, not a new regression.

The real, active SPWS-2026-2027 season carries zero tournaments in the persistent LOCAL seed (its own PPW1 fixture lives only inside a pgTAP test transaction), so fn_ranking_full was confirmed to run against it without error, returning an empty result — the correct behavior for an unscored season, and the full extent of what a season with no data to disagree over can verify.
