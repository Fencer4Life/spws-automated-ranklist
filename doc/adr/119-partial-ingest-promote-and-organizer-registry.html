context

Context

The user wants a multi-day event ingested several times while it runs: each run takes the tournaments that have finished, and the next run takes the rest. Promote follows each ingest. A failed ingest must not reach PROD, and the end state is a GitHub Actions workflow that ingests and promotes by itself. New organizers are coming: USA Fencing and the French veterans federation were named.

Part of this already worked on 31 Oct 2026. A domestic or PZSz ingest kept only the listings whose FTL schedule row said Finished (ADR-108 §7). PPS1e-2026-2027 had been ingested and promoted twice: run 7 with one listing final, run 8 with both, and CERT and PROD both hold run 8's fingerprint fecaf3f0174b. The plan found nine gaps; release 1 closes four of them, and the audit during the build found four more.

  • G3. A running Engarde final completed its event. The Engarde reader skips a competition that is not completed (python/scrapers/engarde.py), a signal as good as FTL's. The lifecycle treated a listing as not final only when its skip reason was FTL's exact text, so the day after the end date an event with a final still running was COMPLETED. Error 7 of doc/plans/ingestion-source-errors-findings-2026-10-31.html shows it.
  • G5. Four engines say nothing. 4fence, Ophardt, d'Artagnan and EVF's results API were read as final once published. Ophardt transmits live, so a provisional ranking would have reached PROD.
  • G6. Every run had the same title. Neither ingest-event.yml nor promote.yml set a run name; the Actions list read "Ingest event (NEW pipeline, from URL)" twenty times.
  • G9. Five places guessed the organizer from the code. stages._organizer_for_event, the twelve-prefix type table, FIE_TYPES, the daily close's ROUTE_CODES and _is_international_intake each matched prefixes. decision

Decision

1 · A run takes only final brackets, and every engine answers when a bracket is final (D1 A, D2 B, D14 A)

  • Partial in what it reads, whole in what it writes. A run reads every listing and takes the final ones; the event is written as one replace. The next run holds everything the last one held plus what has finished since. §3 makes that write one transaction on CERT, as it already is on PROD.
  • The engine contract. ENGINES in python/pipeline/international_sources.py lists every results engine and whether it says when a bracket is final. FTL does: its schedule row says Finished. Engarde does: the competition's state is completed. 4fence, Ophardt, d'Artagnan, EVF's results API and a single results page do not.
  • Not final is one reason. A bracket that is not final is skipped with a reason starting "not final": FTL's unchanged text, "not final (Engarde shows it )", or "not final (no finished signal; its content is not yet 60 minutes old)". lifecycle.is_not_final reads the prefix, so any such skip keeps the event IN_PROGRESS and the daily close leaves it open, through the day after the end date (amended 2026-11-01, G44 A: after it the event completes without the listing and names it; Engarde's empty and a competition the reader would never take are never "not final").
  • For an engine that says nothing, the reader that asks decides:
Who reads A bracket is final when Implementation
The live ingest on CERT its exact content was first seen at least 60 minutes ago, or today in Warsaw is past the event's end date Sightings, sightings_for
Promote's plan on PROD the CERT run took exactly this content of it TakenByRun, from the run's recorded rounds
The daily close it is published (the close runs after the end date) SETTLED
  • The sightings store. tbl_listing_sighting holds one row per event code, listing key and content hash, with the first and last time it was seen; a new hash is a new row, so a changed bracket starts its hour again. fn_listing_sighting_record inserts or touches the row and returns the first time. RLS is on, nothing is granted to anon or authenticated, service_role may select, insert and update, and nothing deletes a sighting (migration 20261031000003_listing_sighting.sql). Only the live ingest writes sightings, so they live on CERT (and LOCAL); promote's plan never writes one, and the PROD seed export never carries the table (FINAL.08).
  • One hash everywhere. Ingest, promote's plan and the daily close read an event's sources in the same order and classify them source by source, so its schedule hashes the same in all three. FTL's not-final text is unchanged, because recorded runs hash it (FINAL.06).

2 · One organizer registry (D13 A)

python/pipeline/organizers.py holds every organizer on the results route, its route class and the code families of its events. No other module matches an event-code prefix.

  • Route classes. domestic (SPWS: every row, the keep-rule and the birth-year split), roster (PZSz: a row only when a stored start list confirms it, ADR-111) and international (EVF, FIE and every federation to come: one tournament per source bracket, our fencers admitted by identity). fie_like marks the organizers admitted under ADR-106's FIE amendment.
  • Families. A family is the code's first segment, matched whole, with its tournament type and organizer: PPW, MPW (SPWS); PPS, MPS (PZSz); PEW, MEW, IMEW (EVF); MSW, IMSW, PSW (FIE). Two families are registered and never ingested: DMEW, EVF's team championship, and GP, the 2023/24 Grand Prix rounds, which PROD stores under SPWS and the historical seed tools still read.
  • Unregistered. VFC-2023-2024 is the one stored code of no family: an event row with no bracket, whose type nothing stored records. The registry names nothing for it, so code that asks gets UNKNOWN. The old spreadsheets' "PS" sheet is unregistered too; ADR-008 records it as the EVF Criterium, stored as PEW10.
  • Readers. The organizer, the tournament type, the international check, the FIE flag, the daily close's selection (route_code_regex), the matcher's domestic and international sets, the post-commit hooks, the PEW rename exception and the historical tools all ask the registry. require_route refuses an event of no family, or of a family not ingested, by name before anything is read or recorded.
  • A new organizer is one Organizer, its Family entries, its tbl_organizer row, its tournament type with its scoring configuration (an ADR of its own), and its calendar scraper (its own plan, under ADR-118). A results reader is needed only for an engine not yet in ENGINES. The drivers, promote, the daily close and the run record do not change. doc/handbook/reference/organizers-and-engines.html carries both registries and the checklist.
  • Not registry facts. ADR-066's minimum routing sends PSW to the domestic minimum while the route calls PSW international; the database holds it per type (pgTAP SS26.TYPE.02) and scrapers/base.check_min_participants agrees with it. The types EVF's results API scores (PEW, MEW, MSW) are EVF's calendar, not the route (ADR-028). ROUTE.ORG.06 names both as the only sets of their kind outside the registry.
  • The calendar card keeps panelType, a code-prefix heuristic for the tile colour (ADR-089 §5). It shows an unknown code in the PPW style, so a new organizer's card colour is decided with that organizer's calendar plan.

3 · One apply on both sides (D3 A, D4 A, D10 A, R2.1 C, B1–B10, G15–G18 A, G19 B, G20 A, G21 B, G22 A, G23 A, G24 A, G25 A, G26 A, G27 A; release 2)

A recorded ingest on CERT (ingest_cli --record-run cert, as ingest-event.yml runs it; local for the rehearsal) takes promote's own path against its own database (python/pipeline/promotion/cert_apply.py). Ingest and promote write through one function, fn_promote_event_apply, so a failed ingest writes nothing.

  • The order (B1). The route's reader reads the schedule and every final listing with its rows and hashes, the keep-rule's verdicts, and the PZSz start lists or the international sources; it records sightings and stores a captured start list, and writes nothing else. A read failure opens no run. Then a link given with the command is saved (B2), the prior is read (B3), the run opens, the plan is made, the one apply runs, the run closes FINISHED, CERT's recompute queue drains, the gate runs, and the staging report, Telegram and the joining check follow.
  • The prior (B3, G17). The apply's prior is what CERT holds: its own result fingerprint, or none when it holds no result. fn_ingest_run_open records it on the run row (txt_prior_fingerprint).
  • The plan (B6). plan_event runs against CERT through the recording connector. A new fencer takes an id reserved from CERT's sequence (fn_reserve_fencer_id, service role only); the apply inserts with it and moves the sequence, as on PROD. A refused listing closes the run FAILED with its kind and every listing read, and nothing is written.
  • Nothing final (R2.1 C). A plan with no listing to commit writes nothing. The run closes FINISHED while the event holds no result, and FAILED while it does: "No listing of is final now, but CERT holds the results of an earlier run; nothing was deleted. Look at the source, then ingest again." The apply itself refuses a plan that names no tournament while the event holds results (PROMOTE_PLAN_EMPTY): it never empties an event.
  • The apply. One call: no expected fingerprint, the prior, the run's input parts, the plan's status, dry run off.
    • (a) With no expected fingerprint the apply never skips; it makes every write and returns the fingerprint it reached, which the run records.
    • (b) D4: before the operations, the event's tournaments the plan does not name (weapon, gender, category) are deleted with their results and match candidates; their ingest history and PZSz review rows go by cascade. A named tournament keeps its id and its results are replaced.
    • (c) G16: when the target already holds the expected result, fencers and results are skipped, but the event's record still moves: the result slots 2–5 under their fill-blank tier, and the record of the listings read. url_event is part of the result document, so a skip already holds it. The fingerprint is compared after a skip too.
  • An apply without an answer (B5). CERT is read again. A fingerprint that moved from the prior means the apply committed (only the apply writes the event inside cert-write), and the run is FINISHED; an unchanged one gives FAILED, "run the ingest again".
  • The drain and the gate (B7). After the run closes, CERT's recompute queue drains to empty inside the job, and the gate runs with CERT writable and PROD read-only; its outcome lands on the run row. The ingest step therefore needs the access token and refuses to start without it. The findings go to Telegram with the staging report; the job log carries the verdict and the counts and never a name. A blocked gate ends the job red, and the generic failure line is skipped once the step has reported. Promote still runs its own gate, since PROD may change in between.
  • The ledger (D10, B8). Every attempt of promote on PROD that reached a CERT run is recorded on that run's row (jsonb_promote, written by fn_ingest_run_promote, service role only): applied, skipped or refused, the fingerprint, the reason, the Actions run and the database's time; the latest attempt replaces the entry. A dry run and --prod-target local record nothing. A failed ledger write is logged and changes nothing in the promote. The daily close quotes the entry, "promote refused at 2026-11-07 14:08: " in Warsaw time; its public line says the reason is in Telegram and on the CERT run's row instead.
  • What promote accepts PROD holding (G17). Nothing; an earlier FINISHED CERT run's result; the run's recorded prior, which is what CERT held when the run began; or the run's own result, which the apply skips. Anything else still refuses. From the same start the apply makes on PROD the change it made on CERT, and the fingerprint check guards the end state.
  • One reader per route, one committer (B9). Three readers return every listing with its rows, flow, label and keep-rule verdict; one committer runs them. The run log takes every listing read before the commit starts and each outcome after it, so a FAILED run lists them all. The joining check runs after every route; a PZSz event has no joined listing, so it finds nothing there.

4 · The results sync (D5–D9 A, D12 A, R3.1–R3.4 A, S1–S12; release 3)

A scheduled results-sync.yml runs hourly from 08:13 to 20:13 UTC: 09:13 to 21:13 in Warsaw in winter, 10:13 to 22:13 in summer (R3.4 A: the hours shift with the clock change, as every cron here does; written as two cron lines, 13 8 * * * for the morning cycle and 13 9-20 * * *, so a morning run GitHub starts late is still known as the morning cycle, G28 A). It takes each active-season event on the route from its first day to the day after its end date, by the moment the cron was due, neither COMPLETED nor CANCELLED, one at a time, but only an event with a results link on CERT or PROD (or an EVF id): the link is the switch. Each cycle is ingest-event.yml called in mode sync, in the cert-write lane:

  • Compare (R3.3 A): the schedule and every final listing are read as the ingest reads them and hashed as the run record hashes them (the schedule, each listing, each PZSz start list, the result slots), against the latest FINISHED CERT run and PROD's fingerprint. Nothing changed and PROD current: the cycle ends. The same hashes, PROD behind: promote only. The compare writes no result; it stores only what the ingest's read stores: the first sighting of a bracket from an engine without a finished signal, which the 60-minute rule counts from, and a PZSz start list it captured (G35 A).
  • Refresh, ingest, promote, only when something changed: the refresh of CERT from PROD (--auto), the recorded ingest with --quiet, and promote.yml called with quiet when the run finished and its gate passed, or when PROD is behind. The called promote keeps the prod-write lane and hands back its write count (G30 A).
  • Outcome (R3.2 A): one job records the cycle's verdict on the event's row, pauses the event on any failure with its reason and the Actions run (D8), and sends the one line of the cycle; a quiet cycle sends nothing. Its log carries the verdict and the reason, never the line. A dry run refreshes, ingests and promotes nothing, so it has no run to judge: its outcome says what the cycle would do from the compare alone (unchanged, would promote, would refresh, ingest and promote with the new listings) and a failed read as a real cycle reports it (G36 A).

The schedule is two cron lines, so the morning cycle is known by the line that fired even when GitHub starts it late (G28 A); the select job sends the morning line, naming every event in window, syncing, paused or without a link (G29 A). sync [<code>] in Telegram dispatches the workflow; with a code it syncs that one event in or out of its window, after lifting its pause, and refuses an event without a link, or a closed one, with one line. A manual ingest whose run finishes lifts the pause too. The repository variable RESULTS_SYNC=off ends every scheduled cycle at the select; a manual run ignores it. No public log line names a fencer or a birth year (D12): a recorded run's refusal is logged by its kind and listing, a promote's refusal by where its reason is, and an error that opened no run passes between jobs as its type only, unless its text is the pipeline's own.

  • The pause store (release 3a). tbl_results_sync_event holds one row per event code: when the sync paused it (ts_paused_at), why (txt_paused_reason: the failure's kind and listing, never a person, since the morning line and the Actions log show it), the Actions run that failed (url_paused_by_run), and the time and verdict of its last cycle (ts_last_cycle_at, txt_last_verdict: unchanged, promoted, nothing_final, failed, blocked, refused or stopped). A pause is whole: a time and a reason, or neither. fn_results_sync_pause(code, reason, run_url) writes it, fn_results_sync_resume(code) lifts it and says whether there was one, and fn_results_sync_cycle(code, verdict) records a cycle; the database sets every time. Row-level security is on, anon and authenticated have no grant, and service_role reads, inserts and updates but never deletes. The rows are CERT's (and LOCAL's): the PROD seed export never names the table (SYNC.SEED.01).

ingest-event.yml runs as "Ingest · " and promote.yml as "Promote · ", with " · dry run" for a dry run. alternatives

Alternatives considered

  1. Tournament-level incremental writes (D1 B). Rejected: a run record and a promote per tournament would double the comparison paths; one atomic replace per event keeps one invariant.
  2. Final once published for engines without a signal (D2 A). Rejected: Ophardt transmits live, so a provisional ranking would reach PROD for an hour before being replaced.
  3. The 60-minute rule for every engine (D2 C). Rejected: FTL and Engarde say when a bracket is final, and waiting an hour on them delays every Saturday final for nothing.
  4. The registry as a database table, editable in Admin (D13 B). Rejected: a new organizer needs a release for its calendar scraper anyway; a module is tested like code, and a table adds schema and a cache for no operational gain.
  5. Leave the prefixes and add each organizer by hand (D13 C). Rejected: five places disagreed already, and a new federation was refused before its first read.
  6. Keep FTL's flag and Engarde's skip text as two special cases (D14 B). Rejected: that is how G3 arose, a signal that existed and was ignored.
  7. A type-to-organizer map for the historical tools. Rejected during the build: a federation added later may reuse an existing type (ROUTE.ORG.04's fixture does), so a type cannot name its organizer. The tools ask the registry with the event code.

Amendment (2026-11-01, plan G37 A, G38 A, G44 A, G48 A) — one refusal contract, no message in a recorded run's log, and a competition stuck at the source never holds an event

Signed by the user in chat on 2026-11-01 ("All as recommended", G37–G46). G41, the reading of a name the source repeats in both name cells, amends ADR-106 and ships with this amendment.

Context

PEW Madrid 2026's first live cycle (2026-11-01) stopped in women's épée V2 on one PENDING row. The international commit refused it with a plain ValueError whose text named the fencer, so the traceback printed the name into the public Actions log (D12 broken), the pause reason was "ValueError", and its advice named the Phase 5 runner, which ADR-113 no longer uses for a current event. A recorded run printed the message of any other error too. Re-reading the ten Engarde events of the last 30 months the same day found five competitions left at the source in state empty or poules for good. §1 kept such an event IN_PROGRESS for ever, and checked the state before the category, so even a joined competition held its event; Madrid 2026 (TABLE FOIL MALE 4, empty) could never be completed.

Decision

  1. One refusal contract (G37 A). An international listing with a PENDING row is refused with ListingRefused("identity", …), as a domestic one is. Its message names each row and the fix: an identity entry in the event's override file, or match_method: EXCLUDED with a note; at an FIE event, a Pole missing from the roster is added first. A recorded run logs it by its kind and listing, and the pause reason is "identity, ".
  2. No message in a recorded run's log (G38 A). Any other error of a recorded run leaves the log with its type and the frames it was raised through (file, line, function), and the run exits 1. The message stays on the run row and goes to Telegram. In a quiet (sync) run, a failure before the run opens passes on its type only, unless its text is the pipeline's own and names no one: an FTL session refused, the gate unavailable, a stored start list missing, or a bracket not understood (SourceNotUnderstood).
  3. §1 amended: a competition stuck at the source never holds an event (G44 A).
    • The Engarde reader decides what a competition is before its state: a team event, a pool round, one without a category and one spanning categories are skipped as such, whatever their state, so none reads "not final".
    • Engarde's empty is a competition nobody fenced: skipped as "nobody fenced (Engarde shows it empty)", never "not final".
    • A listing still not final holds its event IN_PROGRESS through the day after the end date, the results sync's last day (lifecycle.holds_open). From the next day the lifecycle completes the event without it and names it (Verdict.left_out); the daily close's COMPLETED message says "completed without …; a manual ingest takes their results if they appear". The cycle's line names every listing not final, so on the last day of the window it says what the close will leave out.
  4. The refresh names no one in a public log (G48 A, signed "Both as recommended" the same day). Madrid's live cycle after push 1 printed 21 fencers with their birth years into its public log: the PROD→CERT refresh that runs before each ingest printed its whole report, a line per changed fencer. Inside a GitHub Actions job (GITHUB_ACTIONS) the refresh now prints its head only (status, counts, database, registrations, results links, and where the report is stored) and the number of its named lines; the lines go to the report file and, with --report-storage, to CERT's private staging-reports bucket at <code>/refresh/<time>.md (StorageMdHandler.upload_refresh). A refusal is printed by its kind, which names no one (refusal_kind): the database's marker (the align function's ALIGN_VCAT names a fencer), found inside the Management API's "Failed to run sql query: ERROR: P0001: …" too; else a database error's SQLSTATE ("database error 23505"); else the refresh's own message up to its first colon. Its whole text is kept in the report file and stored as a report is. A failure to store is said and never fails the refresh. A stopped or refused refresh's Telegram message carries the named lines and the stored place. The results sync's line names the place: ⏸ for a stop; for a refusal ❌ "the PROD→CERT refresh refused ()", the event paused with the reason "refresh refused: ". The administrator's terminal still shows the whole report.

Amendment (2026-11-01, plan G43 A, G47 A, G50 A, G52 A) — the bot starts the hourly cycle, override entries name the roster, only linked rows are written, and an event is read for its own weapons

Status: Signed by the user in chat on 2026-11-01: G47 A ("I sign off"), G43 A with G37–G46 ("All as recommended"), G50–G54 ("All as recommended"). Built test-first, and released on 2026-11-01 in push 2a (main af30c76d; G57 A, "Yes, push 2a").

Context

GitHub ran this repository's crons hours late or not at all on 1 November: the 15-minute recompute drains every 3–4 hours, the 04:17 daily close at 11:19, and the sync's first three hourly slots never. An override file's identity entry pinned LEAHEY John to 1976 after the roster had corrected him to 1969, and every re-ingest of his events stopped before it read anything; the gate's first run found four such entries, not the three the audit had named. Re-planning his events read-only found two defects of the read and the write: an EXCLUDED row kept its fuzzy candidate's id and reached fn_ingest_tournament_results, whose cast to enum_match_status (which has no EXCLUDED) failed the whole apply; and the reader took every bracket the organiser published, so Jabłonna 2025, two EVF events on one FTL schedule (PEW7es-2024-2025 and PEW8f-2024-2025), would have stored each other's results. The Phase 5 runner had kept to the event's weapons since 2 October (INTL.WPN.01, decision F A); the recorded ingest of ADR-113 never inherited it.

Decision

  1. The bot starts the hourly cycle (G47 A). The Telegram bot's hourly time trigger (dispatchScheduledSync, scripts/gas_telegram_bot.js) dispatches results-sync.yml with scheduled in the UTC hours 08 to 20. The select runs it as a scheduled cycle whose slot is the UTC hour it runs in (bot_slot: 08 is the morning cycle) and whose moment is now; it obeys RESULTS_SYNC=off; outside those hours it runs nothing. GitHub's two cron lines stay as a backstop. Every scheduled select records its start on CERT first (fn_results_sync_begin, tbl_results_sync_cycle): a start within 20 minutes of the last one ends its cycle at the select, and the day's ☀ line goes to the first morning cycle only. A manual or dry run records nothing. A dispatch the bot cannot make is told in the chat.
  2. Override entries name the roster (G43 A). A gate (python -m python.pipeline.override_drift) checks every identity entry of every doc/overrides/*.yaml against the roster the run will meet: LOCAL's in preflight, CERT's in CI (read only, in a job of its own that alone holds the token and tells Telegram when it fails). A fencer key names exactly one fencer, by the rule the ingest resolves it with (overrides.roster_matches); an id_fencer is on the roster; a create_fencer names nobody the roster holds. A line names the file, the line and the entry, never a fencer or a birth year.
  3. Only rows a rule or a person linked are written (G50 A). Both commits (plugins/ingest.py, plugins/pzsz_commit.py) write only AUTO_MATCHED, AUTO_CREATED and USER_CONFIRMED rows. An EXCLUDED row, whatever candidate it carries, is dropped as a PENDING one is; the staging report lists it as before.
  4. An international event is read for its own weapons (G52 A). Every reader of the international route (international_sources.read_brackets, and read_schedule for the daily close) keeps to the event's weapons by the rule the Phase 5 runner keeps (weapons_of: arr_weapons, else a PEW code's letters, ADR-046). A bracket of another weapon is skipped before it is fetched, refused or asked whether it is final, with the reason "not a weapon of this event", so it never holds the event open and is never stored. A code without letters names no weapon, and every weapon is the event's.

Changed: results_sync.py (bot_slot, SyncSql.begin, --scheduled), results-sync.yml (the scheduled input, its run name, its validation), gas_telegram_bot.js (dispatchScheduledSync, createTimeTrigger starting both timers); overrides.py (roster_matches); plugins/ingest.py, plugins/pzsz_commit.py; international_sources.py (weapons_of, OTHER_WEAPON), promotion/close.py (the event row passed to the re-read).

Amendment (2026-11-01, plan G42 A, G45 A) — what a source states twice is reported, and every international source is re-read each week

Status: Signed by the user in chat on 2026-11-01 with G37–G46 ("All as recommended"); built test-first in push 2b on "Yes, build 2b", to the build sheet's readings 2b.1–2b.12 (plan, push 2b build sheet), and G58 A ("G58 A, then push") the same day; released on 2026-11-01 in push 2b (main 9fc4cbc1).

Context

Madrid gave two data-entry slips in two days: a weapon declared as sabre under an épée title (31 October), and a name keyed into both name cells (1 November). The readers also decide other labels silently: Engarde takes the title's gender over sexe (Budapest 2025 declared women under "Men's Epee V4 (70)", Madrid 2024 men under two women's sabre finals) and the title's category over the slug; FencingTime XML takes AltName's gender word over Sexe; d'Artagnan searches its declared line and its title as one text. Decision

  1. What a source states twice is compared and reported, and the choice is unchanged (G42 A). A bracket's disagreements go on ParsedTournament.source_disagreements, each a kind and a detail naming no fencer (python/pipeline/source_consistency.py): Engarde's gender (sexe against the title) and category (the slug against the title), and the count its classification prints against the rows it lists, placed or not; d'Artagnan's gender (the declared line against the <h3>); FencingTime XML's gender (Sexe against AltName); and each row of EVF's results API against its competition: a known weapon_abbr naming another weapon wins, as before, and is counted, and an unknown one keeps the competition's weapon and its gender is guessed (G58 A: the reader once let such a row keep the previous row's weapon). FTL states a label once; Ophardt's and 4fence's headings are generated from the declared setting (ADR-105's amendment); a file import has nothing to compare. Every bracket a reader holds whole is checked for places that are not 1..N with ties; on the international route, a bracket in which no row has a country is reported, since the admission then decides every row by identity alone. No reader keeps a second country column today, so a row's country is never compared with a federation's. The reader computes the list once (checked), prints one disagree line per item in the read's log (so the ingest, the sync's compare and a dry run show it), and the staging report's Detected automation gaps (which Telegram receives) and the run record list it. Nothing is held, refused or chosen differently, and the list is not part of a listing's hash.
  2. Every international source is re-read each week (G45 A). .github/workflows/source-regression.yml (python -m python.pipeline.source_regression) reads and plans, against CERT and with nothing written, every international event whose start lies in the last 30 months, as the recorded ingest reads and plans it; each tournament's planned fencers, places and N are compared with CERT's stored ones, and CERT's result fingerprint with PROD's, after CERT's roster is compared with PROD's. It runs on Mondays, the day before an international event starts, and on demand; every day it names the international events starting within 14 days and dry-reads, through results-sync.yml, those with a results link (G42 A (2)). Amendment (2026-11-01, plan G59 A, G60 A) — a fencer found twice is one fit, and every refusal says what it means

Status: Signed by the user in chat on 2026-11-01 ("All as recommended": G59 A, G60 A, G61 A); built test-first in push 3 and released on 2026-11-01 (main b65deadb). The source re-read run by hand after it (run 41354506817) reads both events equal, nothing written.

Context

The first source re-read, run by hand on 2026-11-01 (run 41345143021), refused Tbilisi 2026 (MSW-2026-2027) and IMSW 2025 (IMSW-2025-2026) by identity, and its log said only "ListingRefused (identity)", which read as an FTL sign-in failure. Its message names no fencer, so results_sync.public_error passes it with its meaning.
    • The recorded run's log line, the run row's refusal (public) and the results sync's pause reason ("identity, : ") say it. A run recorded before this falls back to its kind's meaning. This amends point 1 of the first amendment of 2026-11-01 and §4's pause store, whose reason was the kind and listing alone.
    • The source re-read prints for each event "read from , then refused (): ", "refused before anything was written: ", or "failed: ", with the text of the pipeline's own errors, such as an FTL sign-in refused.
