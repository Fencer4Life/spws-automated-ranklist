context

Context

PZSz national senior competitions (PPS, MPS) already exist on the calendar (PR #7, merged before this ADR) as childless events. Veterans enter them alongside much younger fencers in one undivided senior field — unlike every existing source this pipeline ingests, which already carries either a single V-category or a small number of them per physical pool. Design §07 requires the stored tournament to preserve the field's full size and each veteran's original place (the "34-of-107 invariant"), reuse the existing FTL parser rather than build a second one, and match conservatively: only an existing canonical fencer or an approved exact alias auto-links; anything else needs a human decision, and nothing is ever auto-created.

decision

Decision

1 · SENIOR is a tournament-level label; a CHECK constraint keeps it out of results

enum_age_category gains SENIOR (its own migration — a new enum value cannot be used in the transaction that adds it, the same split PPS/MPS's own enum values already needed). tbl_result.enum_source_age_category gets CHECK (enum_source_age_category IS NULL OR enum_source_age_category <> 'SENIOR'): the one column that already carries a per-row category override (ADR-056) cannot be used to publish a non-veteran category by mistake.

2 · Flow.INGEST_PZSZ_SENIOR — built from the same plugins, minus the ones that split a pool

ParseSource → ValidateIR → ResolveEvent → ResolveFencers(intake="PZSZ_SENIOR") → ValidateCounts → CommitPzszSenior. DetectCombinedPool/SplitByAge/DetectJointPool/AssignFinalVcat are dropped: nothing to split — a PZSz field never becomes several tournaments, it stays one SENIOR tournament per weapon/gender, and each row carries its own V-cat instead. ValidateCounts is reused unchanged — it already does the URL→data validation §07 item 2 requires, plus the now-fail-closed min-participants gate.

3 · ResolveFencers activates its dormant intake param for the first time

rulebook.py had passed params={"intake": "DOMESTIC"} into INGEST_DOMESTIC's own ResolveFencers step since ADR-070, but nothing ever read it — only ctx.params.get("scope") was read (the dedup-sweep branch). intake="PZSZ_SENIOR" is the first real consumer: Phase A (exact/alias) is unchanged, since it is already exactly "an existing canonical fencer or an approved exact alias" (§07 item 4's own wording). Phase B changes: a fuzzy candidate below the auto-match threshold is tagged PENDING (a value StageMatchResult.method's own docstring already anticipated but that no code path had ever produced) with the candidate riding along in alternatives, instead of being linked (domestic's own policy) or silently excluded (international's deferred policy). A genuine non-match (best.id_fencer is None) is EXCLUDED, same as elsewhere — a true non-match is not "uncertain," it is simply absent from this competition's veteran data.

4 · CommitPzszSenior — one tournament per (weapon, gender), full field size, original places

Groups matched rows by nothing (there is only one group): one SENIOR tournament per weapon/gender, int_participant_count set directly and unconditionally from len(parsed.results) — the full source field, known at parse time regardless of how matching turns out — via a new db.set_tournament_participant_count, not solely fn_ingest_tournament_results's own p_participant_count override (which refuses an empty results array, and a bracket with zero initially auto-matched rows must still record its full size). _row's existing default (place=None ⇒ the match's own m.place) already preserves original placement; _rerank_places — a per-V-cat-split concept — is never called. Each written row's enum_source_age_category is computed fresh from the matched fencer's own governed birth year and the season end year (vcat_for_age, the same helper AssignFinalVcat already uses elsewhere), independent of the tournament's SENIOR label. A PENDING match writes no tbl_result row — id_fencer is a real, NOT NULL foreign key, and a still-uncertain candidate is not yet known to be that person — it is queued via a new db.queue_pzsz_match_review instead.

5 · The review queue: a new table modeled on tbl_registration_identity_override, not tbl_match_candidate

tbl_match_candidate requires an already-committed id_result (NOT NULL) — it is a post-write correction/audit table, not a pre-write hold, and cannot represent "a candidate exists but nothing has been written yet." tbl_pzsz_match_review copies tbl_registration_identity_override's already-proven shape instead: dedicated table, nullable candidate FK, CHECK-constrained enum_status (PENDING/APPROVED/REJECTED), decision timestamp, admin-only RLS, no anon policy. fn_approve_pzsz_match_review writes the ONE held row directly — never a call to fn_ingest_tournament_results, which deletes and rewrites the WHOLE tournament and would erase every already-committed row while re-deriving int_participant_count from the row count instead of leaving the full field size untouched. This step ships the table and its two decision RPCs, not a review screen — the same backend-first sequencing steps 4/5 already used for fn_ranking_full; an administrator resolves a pending row via direct RPC call today.

6 · derive_tourn_type_from_event_code and _organizer_for_event gain PPS/MPS recognition

derive_tourn_type_from_event_code parses the real PZSz code shape (pzsz_calendar.py's own plan_event_codes: PPS{round}[W|M]{efs}*, round mandatory; MPS[W|M]{efs}*, no round) — mirroring the existing PEW branch's digit/suffix parsing. _organizer_for_event (stages.py) gains the same two prefixes → "PZSz", closing a real gap: without it, a PZSz event fell through to "UNKNOWN", which is not "domestic", so ResolveFencers's existing (pre-this-ADR) fallback would have silently taken the EXCLUDED branch for every row — the wrong one, since EXCLUDED drops a row with no review trail, and PZSz needs a genuine third outcome.

7 · Dispatch: organizer-based, and CLI scope deliberately narrower than ingest_event_from_url

ingest_event_from_url's own round-discovery path (parse_tournament_name) decodes a bracket's weapon/gender/V-cat from its FTL name — a convention specific to how SPWS/EVF name brackets (e.g. "Weterani M V2"). A PZSz senior field carries no V-cat at all, and this session has no verified sample of PZSz's own FTL bracket-naming convention to decode instead of guessing at one. Rather than fabricate an unverified parser, a new, narrower entry point — ingest_pzsz_senior_bracket_from_url(event_code, weapon, gender, url, season_end_year, db) — takes weapon/gender as the caller's own (an admin action naming the specific bracket, the same shape the existing N15 Telegram ingest command already uses for a URL), reuses ftl.parse_json unchanged, and routes through Flow.INGEST_PZSZ_SENIOR via _run_parsed_through_flow, which gained an optional flow parameter (default INGEST_DOMESTIC, unchanged for every existing caller).

alternatives

Alternatives considered

  1. A second FTL parser specifically for PZSz. Rejected: §07 item 1 requires reuse, and nothing about PZSz's FTL export differs from any other organizer's — the difference is entirely in what the pipeline does with the parsed IR afterward.
  2. Treating a PZSz event as "domestic" (auto-create unmatched) or "international" (silently exclude unmatched). Rejected: both are real, tested behaviors for real reasons elsewhere, and neither matches §07's explicit "never auto-create... skip unmatched... uncertain enters review."
  3. Splitting a PZSz field into per-V-cat tournaments, matching every other ingestion path. Rejected: this is precisely the case that would break the 34-of-107 invariant — a per-V-cat tournament can only report its own slice's N and would need _rerank_places, both explicitly against §07.
  4. Writing an uncertain match into tbl_result under a placeholder/best-guess id_fencer, tagged for later review. Rejected: tbl_result.id_fencer is a real FK to a real person; a still-uncertain candidate is not yet known to be that person, and publishing it (even provisionally) into a ranking is a bigger, harder-to-undo mistake than the read simply not showing that competitor's row for a few days.
  5. Guessing PZSz's FTL bracket-naming convention to reuse ingest_event_from_url's full round-discovery path. Rejected as unverifiable: this session has no live PZSz FTL sample to confirm a naming pattern against, and the planning gate's own "verify before claim" rule forbids inventing one. Deferred, not designed around.

consequences

Consequences

fn_ranking_ppw, fn_ranking_kadra, fn_ranking_full, Flow.INGEST_DOMESTIC's own Rule, and every other existing ingestion path are untouched. A review-queue row with no UI to act on it is inert but visible via direct query/RPC. PZSz bracket discovery (turning an FTL event schedule into a list of weapon/gender rounds without guessing at V-cat) is left for whoever wires an operator-facing trigger onto ingest_pzsz_senior_bracket_from_url — a real, verified sample of a PZSz FTL bracket name is a prerequisite that did not exist this session. A future carry-over engine for PPS/MPS (explicitly deferred, begins disabled per ADR-098) will need its own ADR when it lands, since a SENIOR-to-SENIOR prior-event link crosses a different kind of tournament than every existing carry-over matcher assumes.

Two corrections made during implementation, not assumed at plan time:

  • fn_ingest_tournament_results refuses an empty results array, so a bracket with zero initially auto-matched rows (everyone queued for review) would never get its int_participant_count set through that RPC's own override alone. Fixed by a new db.set_tournament_participant_count, called unconditionally before any row is written — live-verified: a synthetic 107-competitor bracket with only 1 exact match and 8 queued reviews correctly recorded int_participant_count=107 from the start.
  • "No historical scoring" (§07) is not an ingestion-time fail-closed gate — verified live that fn_sync_scoring_type_config (step 4) already projects PPS/MPS onto EVERY season, including the three real historical ones, at multiplier 1.0/threshold 1 (no season can even be constructed without it, since the projection fires from tbl_scoring_config's own column default). The actual boundary is one layer up: a historical season's json_ranking_rules never names PPS/MPS in any bucket, so fn_ranking_ppw/fn_ranking_kadra's legacy JSONB walk can never select a PZSz result into any published total even if one existed. supabase/tests/81_pzsz_senior_ingestion.sql's SS26.PZSZ.09 was rewritten during implementation to pin this actual fact against the real SPWS-2023-2024 season rather than a synthetic "unconfigured" fixture that cannot be built.
