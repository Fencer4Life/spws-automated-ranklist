Frontend · register.html · Plan · issue I6 from the entry-list release

Correct the comment on which database the public page reads

A comment in frontend/register.html says the release fills both the CERT and PROD addresses and that the page picks CERT first. The release fills only PROD, on purpose. The comment misled the live check of the entry-list release on 17 Nov. This plan corrects four comment lines and nothing else.

01 · Verified in the source

What is wrong, and what is true

✗ frontend/register.html, lines 28–31 today

<!-- local: cert points to local Supabase, prod empty (mirrors index.html).
     cloud: GH Actions sed fills both cert+prod with cloud credentials —
     RegistrationElement/EntryListElement pick cert first, else prod (no
     runtime env toggle is exposed on this public page, ADR-079 §6). -->
  • The release fills only PROD. .github/workflows/release.yml lines 147–150 blank supabase-cert-url and supabase-cert-key and write PROD's pair, under a comment (lines 135–146) that explains why: the elements resolve (certUrl || prodUrl), so a filled CERT pair would send every real registration to CERT.

03 · Test-first, honestly

Why there is no new test, and what proves no harm

An HTML comment has no behaviour to put under test, so there is no red to see first. A test that greps for the comment's wording would pin prose, not behaviour; the behaviour itself (PROD only on the deployed page) is already fixed by the release step and was observed live on 17 Nov. What this plan proves instead:

  1. The built page does not change: the CE build (vite build --config vite.config.ce.ts) of the branch start and of the change, compared file by file. Expected: the bundle assets/main.ce.js and index.ce.html byte-identical; register.html differing only inside the comment, if the build keeps comments at all.
  2. scripts/preflight.sh exits 0.

No pixel sheet: a comment is never drawn, and step 1 proves the shipped files are unchanged.
