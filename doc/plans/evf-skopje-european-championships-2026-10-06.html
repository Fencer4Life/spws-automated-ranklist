This page shows the evidence for each one, proposes one fix that repairs all three environments through the existing sync, and lists the five decisions it needs from you.

2 · Root cause

Four defects, each proven against live data

The two symptoms you saw come from two separate defects (1 and 2). Tracing them exposed two more that touch the same row (3 and 4). The probes ran the repository's own scraper functions against EVF's live pages; nothing was written anywhere.

1 × The code planner turns every calendar entry into a PEW

plan_calendar_codes (python/scrapers/evf_calendar.py:169–233) gives every retained entry the next chronological PEW{n}{weapons} code (line 231). There is no championship branch. The database re-checks that plan in fn_ingest_evf_calendar_identity_v1 (latest definition supabase/migrations/20260913000002_no_bracket_stubs.sql:258), whose expected code is also PEW-only (lines 434–448). Any other code is refused as code plan mismatch (line 450).

The classifier still exists: fn_classify_evf_event returns IMEW for this name (20260427000001_event_code_allocator.sql:107–123; pgTAP evf.28 checks exactly that). The insert branch even calls it (line 518), but uses the result only to look up a previous-season link. The row is then inserted under the PEW code (line 533). The previous-season lookup finds nothing, because 2025/26 held the team championship (DMEW), not an individual one.

How it got this way: the 7 Aug 2026 amendment to ADR-043 replaced the allocator with complete-snapshot numbering: "every remaining competition receives a positive chronological PEW code". The championship case was never carried into the new design. On 6 Sep, ADR-091 removed the IMEW-2026-2027 season skeleton because the sync would discover the event. It did discover it, on 15 Sep, but numbered it as a circuit event.

2 × "épée" with accents is not read as a weapon

EVF's list-page post for Skopje carries no weapon categories, and the detail page names no weapon. The evidence ladder (ADR-086, repair_missing_weapons, lines 849–916) therefore falls through to the schedule PDF. That PDF writes "Women's épée V3", "Men's foil V1", "Men's sabre V2". The matcher _DETAIL_WEAPON_RE = \b(EPEE|FOIL|SABRE)\b (line 93) does not fold accents, so épée never matches.

_weapons_from_pdf_bytes(SCHEDULES-SKOPJE-2027-V3.pdf) → ['FOIL', 'SABRE']
_weapons_from_text("Women's épée V3")             → []

The resulting fs suffix became part of the code, and arr_weapons was filled with foil and sabre. A _diacritic_fold helper already exists in the same module (line 1539) but is used only for name matching.

3 × Every 2027 event lost its end date — found while tracing the one-day span

For events in a different calendar year, EVF's list writes full dates: 05/05/2027 - 09/05/2027. For the current year it writes 31 October - 1 November. _tribe_event_end_date (lines 387–412) tries only the day-and-month-name formats (line 404) and otherwise falls back to the start date.

Run against today's live list, 13 of the 17 upcoming entries come back with end = start. That is every entry dated 2027: Guildford, Tampere, Levi, Fâches-Thumesnil, Lausanne, Naples, Stockholm, Athens, Salzburg, Liège, Skopje, Dublin and Toronto (18–20 June stored as 18–18). The identity sync (fn_sync_evf_event_fields, evf_sync.py:585–617) writes the wrong date to CERT, and the reconciler carries it to PROD.

4 ~ The weapons column does not follow the code

When EVF changes an event's weapons, the ingest renames the code (new suffix) but leaves arr_weapons alone. The rename's UPDATE (20260913000002:507–516) has no weapons column, and the URL refresh fills the column only when it is blank (20260904000001:12–14). Madrid shows it today. EVF lists épée, foil and sabre, and the code is PEW2efs, but CERT and PROD hold {EPEE,SABRE}; the 3 Oct review flagged this and left it unchanged. This breaks the invariant on the events handbook page: "where an event code carries a weapon suffix, the suffix is authoritative and this column agrees with it."

It matters here because Skopje's corrected code, IMEW-2026-2027, has no suffix. Without this fix its arr_weapons would stay foil and sabre. ADR-089 already records this as open item 1: "fold it in when that function is next edited".

Why no test caught it

  • The planner tests contain no championship entry. The only championship fixture, Cognac 2026, is used for city resolution (evf.66). The classifier's own pgTAP tests (evf.27–29) pass, because the classifier is correct; its result just never reaches the code.
  • The list-page fixture has only the 22 August end-date shape (test_evf_calendar.py:102). The EVF markup for another calendar year never appears.
  • No weapon fixture contains an accented épée.

3 · Consequences

What it would have done when the results arrive

  • Scored as a circuit event. A tournament's type is derived from its event code. Skopje's results would be typed PEW and scored and ranked as a circuit event, not as the European Championships (MEW).
  • No series link. With no id_prior_event, the FK engine sees no previous edition. (No ranking effect today; §11 explains why.)
  • Wrong on the public calendar now. The card shows it in the circuit colour, with two weapon pills and a one-day date. Every 2027 event shows as a single day.
  • Nothing scored, nothing entered. No tournaments and no registrations exist on any environment. Skopje, Dublin and Toronto can therefore still be renamed safely (the _is_safe_to_renumber conditions: future, no registrations, no results).

5 · Design

The fix, layer by layer

This plan adds no data migration. The corrected sync rewrites the rows the same way it writes any EVF change, so CERT, PROD and LOCAL reach the same state through one path, the reflow logic that already exists (ADR-086 §4b). The one SQL migration changes only functions.

PYTHONpython/scrapers/evf_calendar.py
  • Accents. _weapons_from_text matches against _diacritic_fold(text), so épée, ÉPÉE and Epee all read as EPEE. Whole-word matching is unchanged, so prose still cannot invent a weapon.
  • Dates. _tribe_event_end_date also accepts dd/mm/yyyy. That form already carries the year, so it is used as is, with no year roll.
  • Classification. A new classify_calendar_entry(event) returns PEW, IMEW, DMEW or HOLD, using the Q1 rule. HOLD entries leave the snapshot before validation, exactly as partition_unweaponed holds back weaponless entries, and are counted in the digest.
  • Planning. plan_calendar_codes gives singletons IMEW-{season} / DMEW-{season} outside the PEW sequence. The positive PEW numbers stay exactly {1..N} over circuit entries only. A second singleton of the same kind follows Q2.
PYTHONpython/scrapers/evf_sync.py
  • The payload's desired_code comes from the new plan; no new field is needed. Held-back championships are listed beside pending_weapons in the scrape-run record and in the Telegram digest.
MIGRATIONsupabase/migrations/2026100600000N_evf_singleton_championships.sql
  • fn_classify_evf_event: tightened to the Q1 rule (both words). evf.27–29 keep passing; their names already follow it.
  • fn_ingest_evf_calendar_identity_v1: the expected code classifies first. A singleton must be IMEW-/DMEW-{season} and does not advance the PEW counter. Everything else is unchanged, including the cancellation rules and the guard against renumbering scored events.
  • Rename/update branch: also writes arr_weapons from the payload's weapons (defect 4; closes ADR-089 open item 1).
  • Insert branch: inserts under the planned code, which is now correct for singletons, and writes arr_weapons at creation.
  • The three-argument wrapper fn_ingest_evf_calendar(jsonb, int, int) owns id_prior_event. After the delegate runs, it writes every event's link from a series key. That key carries the year ("europeanchampionships2027"), so it can never find a previous edition, and a link set anywhere else would be wiped on the same run. The singleton link (Q3 A) is therefore resolved there: the latest earlier event of the same kind, by season end, unless the target already has a link.
  • Both functions are reproduced from their live definitions (LOCAL pg_get_functiondef, identical to 20260913000002 and 20260808000002). The edits are applied by exact-match replacement, so nothing else in them changes.
NO CHANGEreconciler, frontend
  • promote --mode calendar already matches on id_evf_calendar_event when a code has moved, so the rename reaches PROD as an UPDATE (ADR-086 §4b). It carries code, weapons, dates and the prior link, resolved by business code.
  • The calendar card takes its colour group from the code prefix (IMEW → int), its organiser from the row and its weapon pills from arr_weapons. All three are correct once the data is.

ADR-043 · Amendment (2026-10-06) — a European Championship is a singleton in the snapshot plan

Context. The 2026-08-07 amendment numbered every retained calendar entry chronologically as PEW{n}. The 2027 Individual European Championships (Skopje, calendar post 5407) therefore became PEW16fs-2026-2027, and Dublin and Toronto moved down to make room. fn_classify_evf_event still returned IMEW, but the insert branch used that answer only for a prior-season lookup.

Decision. (1) An entry whose name carries both whole words European and Championship(s), accents folded, is its season's singleton: DMEW-{season} for the team championship, IMEW-{season} otherwise. The team flag alone no longer makes a DMEW. (2) A singleton takes no PEW number, so the positive bases are exactly {1..N} over circuit entries. The RPC re-checks the plan: a PEW code for a European Championship is a code plan mismatch. (3) Held back and reported, never guessed: any other championship; every new candidate when a singleton has more than one; and a singleton of the kind tbl_season.enum_european_event_type does not expect. An entry already imported is never withdrawn, and two imported candidates for one singleton are an integrity error. (4) An unlinked singleton links to the latest earlier edition of its kind (ADR-021's biennial series); a link already present is kept.

Consequences. The next calendar run renames PEW16fs-2026-2027 to IMEW-2026-2027 and closes the gap (Dublin PEW16efs, Toronto PEW17efs). Nothing is anchored to the old codes. Skopje's results, in May 2027, will be typed MEW. Migration 20261006000002; pgTAP 107.1–107.9; pytest evf.79–evf.83.

ADR-086 · Amendment (2026-10-06) — accents and full-date ends

Decision. The ladder matches weapon names with accents folded: Skopje's schedule writes "épée", which the unfolded whole-word pattern skipped, so the event was coded foil and sabre. The list page's end date is also read as a full dd/mm/yyyy date, the form EVF prints for another calendar year. Without that, every 2027 event's end fell back to its start.

Consequences. Thirteen 2027 entries get their real end dates on the next run. Prose still cannot invent a weapon. pytest evf.76–evf.78.

ADR-089 · Amendment (2026-10-06) — open item 1 closed

Decision. The calendar ingest writes arr_weapons from the scraped weapons whenever it writes the code, on insert and on rename. When EVF changed Madrid's weapons, the suffix moved to efs while the column kept {EPEE,SABRE} on CERT and PROD.

Consequences. Madrid self-heals on the next run. A singleton's code carries no suffix, and its weapons live in the column alone. pgTAP 107.3.

ADR-091 · Amendment (2026-10-06) — the European singleton is discovered and coded

Decision. No change to the rule. The prune of IMEW-2026-2027 relied on the sync discovering the event. It did (15 Sep 2026), but coded it as a circuit event until the ADR-043 amendment of the same date. Season skeletons stay limited to events nobody discovers for us.

11 · Out of scope

Found on the way, not part of this fix

The 2025 Individual Europeans do not carry into 2026/27

The 1 Oct repair plan says "the 2026/27 ranking reads the 2025/26 editions plus the biennial IMEW 2024/25". On PROD, vw_eligible_event carries nothing from IMEW-2024-2025 into 2026/27. It ended on 1 Jun 2025, and the 366-day window closed on 2 Jun 2026, before the season began. Whether a biennial championship should carry for two years is a domain rule (ADR-021). This fix neither depends on it nor changes it. It is a separate question for you.

Closed seasons hold the same collapsed end dates

Example: DMEW-2025-2026 holds 14 May 2026; EVF lists 14–17 May. The sync only touches the active season, and closed seasons are never re-ingested, so these stay as they are unless you want a scoped date correction.

Session worktrees have no .env

scripts/cloud-sql.sh reads .env next to itself. Run from a session worktree, it sends no token and gets HTTP 401. For this analysis, the primary checkout's copy ran the read-only queries. The session-start protocol could link .env into each worktree.
