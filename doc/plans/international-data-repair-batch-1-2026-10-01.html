! 2 October: the four repaired events were stored as PPW. Found by you in the drilldown; fixed on LOCAL

The Phase 5 draft builder wrote every tournament with a fixed type, PPW (python/pipeline/review_cli.py, since May 2026). Domestic ingests never showed it. The international re-ingest did: Jabłonna 2025 (PEW7es-2024-2025), Plovdiv, Manama and Guildford, 51 tournaments, were committed as PPW. So:

  • the drilldown listed Manama and Guildford under Zawody krajowe, and the ranking counted them in the domestic (SPWS) total;
  • Plovdiv and Manama were scored with the PPW multiplier 1.0 instead of the championship's 1.2: their points were about 20% too low;
  • a fencer with no domestic result entered the ranking through a Guildford row typed PPW (6 such fencers, PRZYSTAJKO Daniel shown 1st in V1 men's foil);
  • the release-1 guards and INTL.INV.01 check only international types, so they did not see these rows. My “INTL.INV.01 = 0” after each event was true and proved nothing about them.

The ranking tables on the four review pages were computed in this wrong state and are void. The rows you signed off are unchanged: the same fencers, places and N. Only the type, the points of Plovdiv and Manama, and the ranking effect were wrong.

CERT and PROD were never affected: a read-only check finds every tournament's type in agreement with its code in both. The repair batch has not run there.

Decided 2 October · R1–R4 = A

Four decisions

R1 · What happens to the damaged international results that have no organiser source?

29 events have none: 8 of 2024/25 (25 damaged brackets) and 21 of 2023/24 (46). Those seasons are published PPW-only (ADR-099), so their international results appear in no published ranking. They also feed no 2026/27 carry-over, because the 2026/27 ranking reads the 2025/26 editions plus the biennial IMEW 2024/25.

  • A (recommended): leave them as stored, and list them. The invariant report from release 2 names every one, and a later batch can repair any event once a source turns up. Nothing published changes.
  • B: repair them from EVF results. You allow EVF as the exception when no other source exists, and here none does. Whether EVF gives the whole bracket size for every category of these events has not been checked, so N may stay uncertain. It is 29 events of review for no visible effect.
  • C: delete their international results. Clean, but it destroys data that can still be repaired. I recommend against it.

R2 · Re-ingest all 16 events, or only the 9 whose N is visibly wrong?

  • A (recommended): all 16. The "N equals the Polish count" check misses renumbered places (Napoli V1 men's épée: places 1–4 of 59). It also misses every scraped name a recompute overwrote, and PEW61s Liège was never ingested at all. One uniform pass leaves no event half-trusted.
  • B: only the 9 with a wrong N. That is 100 brackets instead of 150, and the other 7 events keep unverified places and numeric scraped names.

R3 · How do CERT and PROD follow?

  • A (recommended): sign off per event on LOCAL, then one go per environment for the batch. Your per-event sign-off happens where the review is: on LOCAL, against the source. CERT then re-runs exactly the signed-off events, and each must reproduce its LOCAL result bracket for bracket. PROD then follows by promote.yml, one event at a time, after CERT matches. Any difference stops the batch.
  • B: a separate go for each event in each environment. 32 more approvals for runs that must reproduce a result you already signed off.

R4 · Napoli (PEW4efs-2025-2026): its source gives no country

The 4fence parser records no nationality (fencer_country=None). Release 2 keeps only rows whose country is POL, and treats a missing country as not POL (ADR-038 point 4). So staging Napoli from 4fence would dismiss every row, and the staging summary flags it ("every row dismissed: the source has no country"). The 4fence results pages are script-driven, so whether they show a nationality is not yet known.

  • A (recommended): extend the 4fence parser to read the nationality, if the classification pages show it, test-first. Napoli is then staged like every other event. If 4fence shows no nationality, fall back to B for Napoli alone.
  • B: stage Napoli from EVF's results, as the exception you allow when no other source works. EVF's rows carry a country.
  • C: for a source without countries, keep only rows that exactly match a Polish fencer in the roster. This relaxes ADR-038's fail-closed rule for every such source, not just Napoli. I recommend against it.

Before the first event

What must be in place

  1. Release 1 is deployed to CERT and PROD. Until then, every fencer edit lets the recompute drains renumber and recount international brackets, and they would undo a repair within the hour.
  2. Release 2 is built and on LOCAL. The Phase 5 path must drop foreign rows before matching, write the source N in the draft, and keep the source places. Today it writes each category's row count as N. CERT and PROD runs wait until release 2 is released too.
  3. A rollback by exact event code. fn_rollback_event resolves a prefix in the active season only, so it cannot reach a 2025/26 event. The draft commit only inserts and never replaces, and tournament codes are unique, so the old tournaments must go first. A small RPC, fn_rollback_event_by_code(p_code), will:
    • take an exact code, with no LIKE, so PEW1efs can never match a 2026/27 event;
    • delete the event's tournaments through the existing fn_delete_tournament_cascade;
    • leave the event row and its status as they are;
    • be service_role only (ADR-083).
    pgTAP REPAIR.RB.01–04: the exact code only; another season untouched; the event row kept; no anon or authenticated grant.
  4. Source URLs written to the event. Your URLs go into the event's result URL slots (FR-98), replacing an EVF link where one is stored. Each write is checked against the source first: the event name, the date and the weapons must match (the URL-identity rule).

Per event, on LOCAL · nothing is committed without your word

The procedure

  1. Snapshot the event as stored: N, places, scraped names, match method and points per bracket.
  2. Stage the event with the Phase 5 runner from the organiser URL(s). This writes drafts only.
  3. Review page (doc/staging/<code>.review.html). For every bracket it shows the stored N and places against the source's: the whole bracket size, each Pole's published place, foreign rows dismissed, and any Pole the matcher could not link. International events never auto-create a fencer. It also shows the points before and after, and the effect on the 2026/27 ranking for each fencer. I send you the page's path and link.
  4. Your sign-off on that event. If anything looks wrong, the event stays as stored and the drafts are discarded.
  5. Roll back and commit in one session: fn_rollback_event_by_code, then fn_commit_event_draft.
  6. Verify what was committed. N equals the source bracket, every place equals the source place, and no place is above N (INTL.INV.01). Every tournament's type agrees with its code (TT.CODE.06), and the drilldown data of one affected fencer lists the event as international. Scraped names are real names again, and the match method is recorded.

The next event starts only after the previous one is verified.

After the batch is signed off on LOCAL

CERT and PROD

  • CERT: the same rollback and staged re-ingest per event (phase5-event-runner.yml, target CERT). Each event must reproduce its LOCAL result: the same N, places, fencers and points per bracket. A difference stops the batch and gets its own review.
  • PROD: promote.yml per event, once CERT matches. Promotion copies the stored N and places, which are right by then. PROD is read back afterwards and compared with CERT.
  • Seed: the PROD seed is refreshed after the batch, so a LOCAL reset reproduces the repaired data. A seed refresh is a change to the test inputs, so the full pgTAP suite must pass first (ADR-036 amendment).
