EVF calendar sync · tbl_tournament · Implementation Plan

Stop predicting brackets for events with no results

EVF Sync has failed since 2026-09-10 on a duplicate tournament code. The rows colliding are fictional — a "PLANNED" or "CREATED" event should carry event-level facts only. This plan deletes the one live function that still invents brackets, hardens the code rebuild it exposed, and repairs 154 stub rows on CERT / 82 on PROD.

Implemented, deployed & verified — 2026-09-13 retired the stub loop in fn_ingest_evf_calendar repaired 154 CERT + 82 PROD rows ADR-096 (amends ADR-028, ADR-046) — Accepted

Why

A future event should not hold a scoring bracket

The EVF Sync GitHub Actions job has failed since 2026-09-10:

ERROR: calendar sync failed: Management API error (400):
  23505: duplicate key value violates unique constraint "idx_tournament_code"
  DETAIL:  Key (txt_code)=(PEW13es-2026-2027-V2-M-EPEE) already exists.

The scrape itself is healthy — 18 competitions found, 0 new, 18 already in CERT. Two other log lines in the same run are benign and out of scope: the Critérium de Paris weapon hold-back is explicitly "not an error — awaiting EVF announcement," and Found 0 events in EVF API is the results-side discovery finding nothing scored yet this season.

It fired because EVF moved Athens (calendar id 3438) from 2027-05-22 to 2027-03-27. PEW numbers are chronological position, so three events shift:

EventCERT todayWanted
Athens (cal 3438)PEW15es-2026-2027PEW13es-2026-2027
Liège (cal 890)PEW13s-2026-2027PEW14s-2026-2027
Salzburg (cal 4523)PEW14ef-2026-2027PEW15ef-2026-2027

Athens holds 8 child tournament rows where the current design expects 4 — four duplicate pairs. The rebuild tries to collapse each pair onto one code and collides with itself.

✕ The decision this plan implements

A CREATED or PLANNED event carries event-level facts only. Child tournaments come into existence when results are scraped from results URLs — never when a calendar entry is merely discovered. Decided 2026-09-12. This makes the collision a symptom: the rows being fought over should never have been created.

Root cause

Why the rows exist at all — and why every reason for them has expired

fn_import_evf_events (ADR-028, April 2026) inserted one stub tournament per weapon × gender at calendar-import time — hardcoded enum_age_category = 'V2', int_participant_count = 0, enum_import_status = 'PLANNED'. That block was copied forward through nine rewrites of the calendar ingest. Querying every live plpgsql function's definition on CERT for the stub-code pattern found exactly one survivor: the 2-arg delegate fn_ingest_evf_calendar(p_events jsonb, p_id_season integer) in 20260711000001_prod_event_reconciler.sql. Everything else that once minted -M-/-F- stubs is gone.

EXPIREDthe dedup marker

ADR-028 §Calendar Scraping: the old dedup matcher was BETWEEN ±3 days AND EXISTS(tournament) — a child row was the only signal an event had been imported. That matcher is gone, replaced by Python's _find_existing_match id→slug→fuzzy ladder.

EXPIREDthe only home for weapon/type facts

tbl_event had no weapon or type column when the stub loop was written, so a child row was the only place the weapon set and PEW/MEW type could live. arr_weapons is now maintained for every family, derived from the event code (migration 20260904000001, test 71), and the frontend calendar reads weapons from arr_weapons, never from children.

EXPIREDthe international flag

vw_calendar.bool_has_international is computed from children (enum_type IN ('PEW','MEW','MSW','PSW')), but the frontend's own isInternationalEvent() already falls back to the code prefix. The column becomes redundant, not broken.

And the predicted shape was always wrong, not merely premature. A real EVF weekend ends with 10–23 brackets spanning V1–V4 — PROD 2025-2026: PEW6efs 23 brackets, PEW4efs 10 brackets with 389 participants. The stub set is weapons × 2 genders at V2 only; when results land, fn_find_or_create_tournament reuses the V2 stub and mints V1/V3/V4 fresh regardless. This is the same defect class ADR-091 ruled on eleven days ago one level up — "a skeleton is a PREDICTION of a row that is going to arrive anyway" — applied one layer down, to brackets instead of events.

▸ The rule is already the norm everywhere else

On PROD, the only non-terminal events holding tournaments are EVF ones: 17 PLANNED PEW (66 rows), 2 CANCELLED PEW (10), 1 PLANNED DMEW (6). Every PPW, MPS, MPW and MSW planned event holds zero, and CERT agrees. Test 51 already asserts this for the PROD reconciler: "51.1b: CREATE is childless — no tournament rows created." EVF is the outlier, not the pattern.

Audit evidence

How the duplicates were actually produced

trg_audit_tournament fires on UPDATE and DELETE but not INSERT, which separates the two halves of every pair in the log. ts_updated proves nothing here — the reflow rebuild never sets it. Athens, tournament row 1921, the exact bracket the failing run died on:

07-14 05:41  INSERT  PEW79-2026-2027-M-EPEE            <- 2-arg delegate, stub
08-08 06:55  UPDATE  PEW79-2026-2027-M-EPEE      -> __evfcal_1921
08-08 06:55  UPDATE  __evfcal_1921               -> PEW14es-2026-2027-V2-M-EPEE
08-28 16:43  UPDATE  PEW14es-2026-2027-V2-M-EPEE -> __evfcal_1921
08-28 16:43  UPDATE  __evfcal_1921               -> PEW15es-2026-2027-V2-M-EPEE
08-28 16:43  (no audit rows)  id 2065 = PEW15es-2026-2027-M-EPEE   <- the duplicate
  1. The reflow rebuild in fn_ingest_evf_calendar_identity_v1 (migration 20260828000007) writes <event-code-with-season>-<Vcat>-<gender>-<weapon> — a third dialect used nowhere else. Canonical is <base>-<Vcat>-<gender>-<weapon>-<season> (fn_find_or_create_tournament, fn_pew_recompute_event_code, ADR-046); the stub shape is <event-code-with-season>-<gender>-<weapon>.
  2. The delegate guards its insert with NOT EXISTS (txt_code = code || '-M-' || weapon) — a string test. After step 1 that exact string is gone, so it inserts a second row for the same (id_event, V2, gender, weapon), in the same transaction as the rename that caused the miss.
  3. A manual cleanup deleted 62 such rows at 2026-08-28 15:50; the 16:43 sync recreated 68. This is generation three. A data-only repair does not hold — the function that creates the collision is still live.
  4. PROD is clean only because it never renumbers — the mirror copies event fields and never rebuilds child codes, so PROD still carries generation two under stale numbers (PEW7efs-* beneath event PEW7es). Noted, not fixed here.

The three EVF events with no duplicate pair confirm the mechanism by absence: PEW1f and PEW7es have never been renumbered since their stubs were created, so the rebuild never ran on them; PEW0efs (Samorin) was renumbered but is CANCELLED, and the delegate only receives pre-terminal events, so nothing re-inserted behind it.

ADR draft — sign-off needed before disk (planning rule 6)

ADR-096: a bracket is created by results ingestion, never by calendar discovery

Status: Proposed — awaiting sign-off

Amends: ADR-028 §Calendar Scraping (drops the weapon × gender stub loop from calendar import). Relates to: ADR-046 (canonical tournament code formula — now has exactly one implementation), ADR-091 (the same "a skeleton is a prediction" ruling, one layer up, for events instead of brackets), ADR-081 (the CERT→PROD reconciler, whose CREATE path is already childless and needs no change).

Context

The EVF calendar ingest has created one stub tournament per weapon × gender at calendar-import time since ADR-028 (April 2026), at a hardcoded V2 age category. Every original justification has expired (dedup marker, weapon/type storage — see the root-cause section above), the predicted shape is provably wrong (a real event ends with 10–23 brackets across V1–V4, not 2–6 at V2 only), and the mechanism now actively produces duplicate-key failures in production sync: idx_tournament_code violations on 2026-09-10, traced to a code-rebuild dialect mismatch that only matters because these rows exist to be renumbered.

Decision

A tbl_event row in CREATED or PLANNED status carries event-level facts only (name, dates, location, weapons via arr_weapons, URLs). No tbl_tournament child is created by calendar discovery. A bracket comes into existence only when results are found for it — through fn_find_or_create_tournament, called from the results-ingest paths (fn_ingest_tournament_results, the commit pipeline). The calendar's two-arg fn_ingest_evf_calendar delegate loses its weapon-loop insert entirely. The canonical tournament-code formula (<base>-<Vcat>-<gender>-<weapon>-<season>, ADR-046) gains a single shared implementation, fn_rebuild_tournament_codes, used by both the admin rename path (fn_update_event) and the calendar reflow path (fn_ingest_evf_calendar_identity_v1), which previously duplicated the logic and had drifted into three dialects.

Alternatives considered

  • Fix the collision only, keep the stubs. Correct the rebuild's code format and the delegate's guard, add a uniqueness index, leave stub creation in place. Rejected: every future EVF event still acquires 4–6 fictional V2 rows, carrying forward a prediction that is provably the wrong shape and that ADR-091 already ruled against one layer up.
  • Canonicalize the placeholder dialect everywhere instead of removing it. Rejected: PROD's entire current season is placeholder-shaped and every settled season is canonical; rewriting 82 live PROD rows to fix a bug in the rebuild formula is disproportionate, and the dual shape was itself only ever meant to be transitional.

Consequences

  • Positive: the duplicate-key failure class cannot recur — there is nothing to duplicate before results exist. populate-urls.yml and scrape-tournament.yml become exactly what they already are for domestic events. One tournament-code formula instead of three.
  • Negative / accepted: vw_calendar.bool_has_international loses its only remaining input for a childless event; the frontend fallback already covers it, plus the one-line DMEW fix this plan lands. An operator opening EventManager for a future EVF event now sees zero tournaments where they used to see 2–6 — expected, and consistent with every domestic event already shown there.
  • Repair required: 154 CERT rows / 82 PROD rows are pruned as part of the same migration (idempotent, guarded — see the migration section).

Source (once accepted): doc/adr/096-no-bracket-stubs-before-results.md, generated to HTML via python scripts/render_adrs.py, registered in spec Appendix C.
