03The three defects worth remembering

Each was invisible to the test suite and to inspection of the rendered page. All three were found only by comparing a live environment against what the code claimed.

1 · The public page wrote to CERT

RegistrationElement resolves its client as (certUrl || prodUrl), and release.yml injected both pairs into register.html. CERT silently won. Every registration through the shared link would have landed in the wrong database while the page looked perfectly healthy to the fencer.

Only caught by registering once for real and then querying both databases. Now register.html receives the PROD pair only; index.html keeps both because it has a runtime admin toggle.

2 · Every non-exact match was refused

ADR-079's Model B routed non-exact matches through a magic-link email. Phases 4/5 were never built, so the form rendered a "coming soon" panel and wrote nothing at all — turning away every newcomer and everyone whose stored birth year was an ingestion estimate. That is the population the subsystem exists to collect birth years from.

A miss now writes with id_fencer NULL. Nothing downstream needed changing: tbl_registration already carried the full declaration, vw_registration_entry_list does not join tbl_fencer, and the FTL exporter already typed id_fencer: int | None. Several of the fourteen live entries would have been refused under the old behaviour.

3 · The release gate was the only thing diverging

The subtlest of the three schema-fingerprint.sh hashed information_schema.routines with ORDER BY routine_name. That column is not unique — the view returns one row per overload, and fn_ingest_evf_calendar has two with different bodies. With no tiebreaker, their order fell back to physical row order, which differs per database. Two environments with byte-identical schemas produced different fingerprints at random.

CERT passed and PROD failed on the same release, on a schema that was never out of sync. Diffing all 297 routines showed the same name at the same md5, one line apart — and identical output once sorted deterministically.

Fixed by ordering on (routine_name, routine_definition). The tiebreaker is deliberately not specific_name: that column embeds the function's OID, which differs per database, so ordering by it would have made the fingerprint environment-specific and defeated the comparison entirely — a worse bug wearing the same clothes.

Worth internalising: the migration had already applied cleanly when this fired. A red deploy-prod does not mean PROD is broken — read which step failed before concluding anything.

05Known noise — do not chase

  • Telegram "SECURITY POSTURE REGRESSION on PROD". Fired twice (17 and 28 Aug) without the posture check ever running — it is gated on job-level failure, so any earlier step failing sends it. Both were false. Worth re-gating on the posture step's own outcome.
  • 19_phase3_wizard.sql plans 25 assertions but runs 5. Pre-existing, unrelated, suite still passes.
  • CI failure on efc0dca. test_live_dartagnan_reachable hits a live external site and timed out. Network flake on a docs-only commit.
  • A second Release run queues itself after each push (CI completion re-triggers it). Harmless, but it holds the concurrency lock — if a deploy seems stuck, look for a run parked on the deploy-prod gate.

06If you pick this up cold

  1. Read the Wave 1 handover for what changed in the form, then ADR-079's 2026-08-17 amendment for why.
  2. Before touching CERT or PROD, the cloud-db-ops skill applies. Its first rule exists because it was broken on 17 August: never write test data to a live environment until you have proven, in the same session, that you can delete it. A test row sat on the public roster for hours because that was skipped.
  3. Queries: scripts/cloud-sql.sh <cert|prod> "SELECT …". Non-SELECT needs CLOUD_SQL_CONFIRM=yes and echoes the statement and target first.
  4. An HTTP 401 from the Management API is not proof of an expired token — check for a shadowing shell export first. That misdiagnosis cost most of an afternoon.
  5. Adding a fencer by hand: the add-fencer skill. A shared given name and birth year is a coincidence, not evidence — ask once, record the answer, move on.
The one habit that paid All three defects survived a green test suite and looked fine on screen. Each was caught by performing the real action against the real environment and then querying the database directly. On anything user-facing, budget for that step even when everything appears to work.
