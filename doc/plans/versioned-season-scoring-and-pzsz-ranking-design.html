01 · Outcome

Historical scores stay explainable; new rules stop rewriting old seasons

  • The current algorithm becomes the frozen EVF_CLASSIC_V1_2025_2026 engine.
  • The published calculator formula becomes SPWS_FIELD_SCALED_V1_2026_2027.
  • A season is assigned an engine; nothing chooses an algorithm at calculation time. An engine name is descriptive, versioned, and suffixed with its introduction/reference season; a later season reuses it by pointing at it, which is a season-row update and no code change at all.
  • Real scoring and read-only preview use one dispatcher and the same immutable strategy.
  • Once the first result in a season is scored, the entire Admin scoring editor becomes read-only — including ranking buckets. A board-authorized, audited database operation may still replace the active configuration revision and rescore the whole season.
  • The published calculator and scoring table stop carrying their own copies of the formula. One season-agnostic shared module serves both — the calculator bound to the active season, the annex pinned to 2026/2027 — so a pre-lock Admin edit is reflected in all three surfaces and the lock freezes all three at once.
  • PPS and MPS become distinct first-class tournament types beginning with 2026/2027.
  • The full Ranking exposes only two totals: SPWS and EVF+. EVF+ combines EVF/FIE and PZSz scores governed by independent Season Scoring Rules.
  • The official full Ranking begins permanently with 2026/2027; the three earlier spreadsheet-derived seasons remain public in PPW mode only.

Deliberately out of scope

No Admin whole-season rescore workflow; no calculator restyle; no PZSz results before 2026/2027; no guessed PPS/MPS multipliers or result-counting buckets; no automatic creation of fencers from senior results.

03 · Architecture

Stable orchestration, immutable strategies, one component contract

Bulk or preview callerTournament writer or public calculator
Stable dispatcherResolves explicit season engine
Static CASEOne branch per released formula
Immutable strategyReturns the common score components
BoundaryBulk persists; preview only returns

fn_calc_tournament_scores(p_tournament_id) remains the stable transactional writer. It validates the tournament and season, resolves the authoritative multiplier, dispatches each result through the selected strategy, writes all four score columns, stamps ts_points_calc, marks the tournament SCORED, and records the ordinary Admin configuration-lock boundary in the same transaction.

fn_preview_tournament_score(...) is a public, read-only facade over the same dispatcher. It returns the engine label, base, place points, DE bonus, podium bonus, coefficient and final score. It cannot update a tournament or result.

Follow the dispatcher this repository already has

ADR-042 and ADR-045 established per-season engine selection here: tbl_season names the engine and a static CASE resolves it to a separate function, closing with ELSE RAISE EXCEPTION 'Unknown … engine'. Scoring adopts that pattern rather than a second mechanism. tbl_season.id_scoring_engine names the engine; the dispatcher's CASE resolves it; tbl_scoring_engine survives as a metadata table only — display label, immutable-constants documentation, active/retired — so the Admin dropdown and the published pages can show a human label instead of a raw code.

The rejected “growing IF tree” is today's situation, where one function holds all the arithmetic inline. A thin dispatcher calling separate immutable functions is the opposite of that, and it satisfies the property that actually matters: adding a branch edits the dispatcher, never a strategy.

Dispatching on a function reference stored in a table was considered and rejected. It requires dynamic EXECUTE inside a SECURITY DEFINER function, so a writable registry row becomes an execution path; Postgres tracks no dependency, meaning DROP FUNCTION on a live strategy would succeed and break a closed season at runtime instead of at migration time; and postgrestools and the knowledge graph cannot see the call edge.

Engines are assigned, never branched to

Nothing chooses an algorithm at calculation time. A season is assigned exactly one engine, and once any result in that season is scored the assignment cannot change. Reuse is free and costs no code: a later season that wants an existing formula points at it, which is a season-row update. The dispatcher grows one branch per distinct formula ever released, never one per season — three seasons sharing a formula is one branch. This is already how ADR-042's two carry-over engines serve every season in the system.

The public calculator's EVF/SPWS toggle is a human comparison control on a page and is not this mechanism. Both hold at once.

Naming convention

DESCRIPTIVE_FAMILY_V<contract-version>_<reference-season>

EVF_CLASSIC_V1_2025_2026
SPWS_FIELD_SCALED_V1_2026_2027
SPWS_FIELD_SCALED_V2_2027_2028

04 · Formula

The calculator is the 2026/2027 contract

B(N) = min(mpValue, baseSlope × log₂(max(2, N))) ← the field-scaled engine
B(N) = mpValue ← the classic engine

place = B(N), when N = 1
place = B(N) − (B(N) − 1) × ln(place) / ln(N), otherwise
DE = deRound × max(0, floor(log₂N) − ceil(log₂place) + powerOfTwoAdjustment)
podium = coefficient × 3 × ∛N, where coefficient is podiumGold / Silver / Bronze for places 1 / 2 / 3
final = round((place + DE + podium) × tournamentMultiplier, 2)

place > N, place < 1 or N < 1 is invalid input and is rejected, not scored.

powerOfTwoAdjustment is +1 when N is not an exact power of two, and 0 when it is. The plan previously left the term undefined.

Reversed — the numbers are season configuration, not engine constants

An earlier version of this document stated that 10, 50 and the podium coefficients 3/2/1 are engine constants rather than season knobs. That is no longer true. mpValue and the podium coefficients remain the existing tbl_scoring_config columns int_mp_value and int_podium_gold/silver/bronze, editable in Admin until the season's first result is scored — which is what makes a pre-lock edit visible in the calculator and the scoring table.

The engine owns only what cannot be expressed as a number: the shape of the base — flat mpValue for EVF_CLASSIC_V1_2025_2026 against min(mpValue, baseSlope × log₂(max(2, N))) for SPWS_FIELD_SCALED_V1_2026_2027. That difference is what distinguishes the two engines and it is the only thing frozen by the engine version.

Two unrelated tens. baseSlope is base points per bracket round and appears only in the field-scaled engine; deRound is points per DE round won and appears in both. They coincide at 10 today and are not the same quantity. They must carry separate names in schema, code and tests.

At N ≥ 32 the field-scaled base reaches mpValue and the result is identical to the classic engine for the same placement and multiplier, because 10 × log₂(32) = 50. The entire difference between the two engines is confined to fields smaller than 32.

N = 1 re-prices walkovers, deliberately

The max(2, N) guard exists to stop log₂(1) = 0 producing a base of zero, so a one-competitor bracket inherits the N = 2 base of 10. Against the classic engine's base of 50 this moves a walkover from 59 points to 19 before the type multiplier: 50 + 0 + 9 becomes 10 + 0 + 9.

This is a live case, not a hypothetical. ADR-066 records that in PPW2-2025-2026 six of seven FOIL brackets had a single competitor, and that an operator confirmed on 2026-05-10 that the lone competitor in such a bracket does earn ranklist points by walkover. The reduction is accepted as a deliberate consequence of a curve whose stated purpose is that small fields are worth less — a walkover outscoring a fought four-person bracket would be the stranger outcome. It is recorded here rather than left to fall out of a division-by-zero guard, and SS26.NEW pins N = 1 explicitly.

A place greater than the field is invalid data, not a zero

The two present implementations disagree. fn_calc_tournament_scores scores it — WHEN r.int_place > v_n THEN 0 — while the calculator refuses it, returning null from parts(). Byte-equivalent preview and persistence is unachievable until one wins.

Rejection wins. A place greater than the field size is corrupt data, and zero is the one value that hides it: it sorts to the bottom and reads as an ordinary weak result. Scoring raises, ingestion validates, and the calculator's existing null surfaces through the in-page validation error §08 already requires. A CHECK constraint lands only after a preflight proves no existing tbl_result row violates it.

This also closes a live leak: num_podium_bonus carries no place > N guard, only WHEN r.int_place = 1/2/3, so N = 2 with place = 3 awards a bronze podium bonus for a place that does not exist in the bracket while its place points correctly collapse to zero.

The historical engine reproduces the classic flat base. Every pre-2026/2027 season is assigned it only after a preflight proves its scored configuration used the values it actually used; because those values are season configuration, the preflight reads them per season rather than assuming 50 and 3/2/1. Any deviation aborts migration and requires its own frozen engine rather than silent coercion.

Ordinary configuration writes go through one server-side RPC, fn_import_scoring_config. Because that function is a single flat-JSONB upsert covering every field at once, the lock must be implemented as field-level authorization inside it rather than as a guard on the whole function. Trigger guards cover direct browser/Admin table writes as defense in depth, including INSERT, UPDATE and DELETE on normalized type settings. One existing write path must be deliberately exempted: saving configuration also issues updateSeasonCarryoverEngine, a direct PostgREST PATCH on tbl_season.enum_carryover_engine, which is carry-over policy and not governed by the scoring lock. A browser-side disabled state is presentation, never enforcement. Existing scored or published seasons are backfilled as administratively locked; where available, the earliest surviving ts_points_calc supplies the initial lock timestamp. That timestamp is audit evidence, not a prohibition on repair and not the sole proof that a historical season was scored.

Repairable results; revisable rules

The lock applies only to ordinary Admin editing of scoring configuration. Tournament source URLs and imported results remain correctable: an operator may fix an FTL URL, replace an invalid import and rescore that tournament under the same active revision. Separately, a board-authorized rule change uses a privileged database procedure outside the Admin UI. It appends an audited configuration revision, creates a new immutable engine version when the formula itself changes, recalculates every applicable result in the season, verifies that no mixed revision remains, and activates the revision only if the complete operation succeeds. Failure leaves the previous configuration and scores authoritative.

Admin behavior after locking

The action still reads Zapisz konfigurację, but every section and the save affordance are visibly and accessibly guarded. Activation explains: “Konfiguracja punktacji jest zablokowana, ponieważ sezon zawiera już obliczone wyniki. Zmiana wymaga zatwierdzonej aktualizacji konfiguracji i ponownego przeliczenia całego sezonu poza panelem administracyjnym.” A native disabled button alone is insufficient because it cannot communicate on click.

Reversed — the lock is total, not partial

An earlier version of this document kept ranking buckets and the default ranking mode editable after the first score. They lock with everything else. The whole Admin scoring editor goes read-only on the season's first scored result, and the trigger is that result — not the season's start or end date.

This keeps readonly a single boolean, re-sourced from the server rather than split into per-section flags: the change is replacing today's client-side readonly={isSeasonPast(season)} with the server's scoring_admin_locked. There is no partial-lock UI to design.

The season/config API returns explicit server authority fields such as scoring_admin_locked and scoring_locked_at. All three editor mount points — SeasonManager.svelte:146, SeasonManagerWizard.svelte:104 and ScoringConfigEditor itself — use those fields, not season dates, client-side result counts or inference. fn_copy_prior_scoring_config, which the wizard's step 2 calls to pre-fill a new season, must not silently carry a prior season's engine assignment forward: assigning an engine is a deliberate act. The guarded Zapisz konfigurację action remains visible and keyboard-reachable through an explanatory affordance; the current implementation’s practice of hiding the save action when readonly must be replaced.

07 · PPS and MPS

One senior field, only known veterans, original place and original N

PPS and MPS are added to enum_tournament_type. A tournament-level SENIOR category represents the source bracket. Result rows continue to hold the fencer’s season-derived V0–V4 category; a constraint prevents SENIOR from becoming a published veteran category.

The 34-of-107 invariant

If a source field contains 107 competitors and a known veteran finishes 34th, the stored tournament count is 107 and the stored place is 34. The importer does not shrink the field to known veterans and does not rerank their placements.

  1. Reuse the existing FTL parser and orchestration contracts; add a PZSz senior flow/policy, not a second FTL parser.
  2. Validate the result URL against the event’s date, identity, weapon, gender and senior category before writing.
  3. Create one SENIOR tournament per actual weapon/gender bracket, with full source participant count. Its minimum-participant gate compares against that full field size, not the count of matched veterans.
  4. Auto-match only an existing canonical fencer or an approved exact alias. Uncertain matches enter Admin review.
  5. Skip unmatched competitors and never auto-create a fencer from PPS/MPS.
  6. Assign each imported veteran’s V0–V4 result category from birth year and the SPWS season end year.
  7. Score the imported rows through the season dispatcher using the PPS or MPS multiplier.

No scoring type configuration is created for PPS/MPS in 2025/2026 or earlier. That absence does not fail closed today and the gate must be built. get_min_participants (python/pipeline/db_connector.py:597–620) returns a threshold of 1 for any unrecognised tournament type, and derive_tourn_type_from_event_code returns None for an unmatched event code, which lands on the same fallback — so a missing configuration currently lets everything through rather than stopping it. Ingestion must raise on a tournament type with no configured settings, and SS26.PZSZ pins that explicitly. Calendar rows may exist historically, but no PZSz tournament/result backfill is performed. Future PPS/MPS carry-over is supported only through explicit prior-event links and begins disabled.

08 · Public calculator

Two published pages, three copies of the formula, one module

Reversed — there are three implementations, and the table is not a printed page

An earlier version of this document treated the calculator as the only duplicate. The formula is in fact written three times in browser JavaScript: kalkulator-punktow-za-wynik-spws.v2.html as fN/rundy/parts/total; its byte-identical WordPress copy; and Tabela-punktacji-SPWS_2026-2027.html as firstPlaceBase/wonRounds/scoreParts/totalScore. The scoring-table annex computes a live 300 × 300 grid in the browser with its own constants and a CSV export — it is a calculator, not a printed table. The three already disagree: the annex floors at MIN_PARTICIPANTS = 4 while the calculator accepts N = 1.

  • Preserve both published URLs — /kalkulator-punktow.html and /tabela-punktacji.html — and their present visual design. Both ship from frontend/public/ to GitHub Pages via release.yml.
  • Collapse all three JavaScript implementations into one shared TypeScript module, frontend/src/lib/scoring.ts. Neither page keeps local arithmetic of its own.
  • Corrected during implementation (20 September 2026): the module is generated into each page by frontend/scripts/build-scoring-pages.mjs between fixed markers, not imported at runtime. The pages are plain files under frontend/public/, which Vite copies verbatim; making them Vite entry points would change their published paths, and emitting a separate .js beside them would turn the hand-carried WordPress calculator into two files that must travel together. --check fails when a page is stale, the same contract render_docs.py --check provides, and it is a scripts/preflight.sh gate.
  • Corrected during implementation: §08 originally required building through Vite “without embedding deployment values into an unprocessed public file”. That is reversed. Both pages carry a hidden #spws-env element whose attributes .github/workflows/release.yml rewrites from GitHub Secrets at build time — exactly as it already does for index.html and register.html. Nothing secret is committed: the repository holds LOCAL placeholders, the anon key is a public credential protected by RLS and the 52.7 allowlist rather than by secrecy, and the existing “no localhost in dist” guard fails the build if the rewrite is ever skipped.
  • Corrected during implementation: the anon grant is fn_public_scoring_params, not fn_preview_tournament_score. The preview function takes an id_tournament, which neither published page has — both take N and place as user input — so publishing it would widen the anon surface to per-tournament previews for no gain. It stays revoked. §08's invariant was always that whatever the pages call is granted in both allowlist copies at once, and that holds.
  • The module takes a season's configuration values — base, podium coefficients, and the assigned engine's base shape — through one anon-executable RPC, then computes locally. It is season-agnostic; each page names the season it wants, the calculator the active one and the annex its pinned SPWS-2026-2027. A pre-lock Admin edit is therefore reflected in the engine, the calculator and the table alike, and the database lock freezes all three at once. The DB lock is the only lock; neither page needs a freezing mechanism of its own.
  • Render validation and network errors in the page. Never fall back to stale JavaScript arithmetic or require DevTools.

Reversed — scope reduced; the pages keep their controls

An earlier version removed the competition-rank coefficient control and added season and tournament-type selectors. None of that happens. The rank coefficient stays a free input. There is no tournament-type selector, so neither page reads per-type multipliers. There is no season selector on either page; each binds to one season by construction — the calculator to the active season, the annex to its pinned SPWS-2026-2027. The EVF/SPWS toggle stays — it is a human comparison control on a public page, which is a different thing from the system assigning exactly one engine per season, and both hold at once.

The only change to these pages is the collapse to one shared module. Their controls, layout and output are otherwise untouched.

Two reconciliations fall out of one module serving both pages. The annex's MIN_PARTICIPANTS = 4 and the calculator's N ≥ 1 cannot both stand once they share code, and with N = 1 now a pinned case (§04) the floor of 4 needs a stated reason or must go. And total() returns an unrounded value today while fn_calc_tournament_scores applies ROUND(…, 2): the formula comes from the page, the two-decimal rounding stays the database's, and the published pages will show rounded values where they previously did not.

Where a server round trip is used, the RPC is STABLE, has a fixed search_path, validates N ≥ 1 and 1 ≤ place ≤ N, performs no write, and exposes no mutable engine metadata. Per-cell or whole-grid RPCs were rejected for the annex: a 300 × 300 grid refetched on every coefficient change is not viable, which is why the shared module computes client-side from server-supplied parameters. The formula consequently lives in exactly two places — the TypeScript module and the SQL strategy — pinned to each other by SS26.PARITY over fixtures, which is a smaller surface than three unpinned copies drifting.

The anon grant is a two-file gate that blocks the PROD deploy job

Granting anon execution is not one edit. The allowlist is asserted as a set equality in supabase/tests/52_security_posture.sql (52.7) and duplicated in scripts/check-security-posture.sh, which the deploy job runs against the real CERT/PROD database. scripts/check-anon-allowlist-sync.sh exists because the two drifted on 2026-09-12: pgTAP stayed green through the whole of CI and the disagreement surfaced at deploy, failing CERT's posture check and blocking PROD. Both files must be updated together. One function serves both published pages from the GitHub Pages origin.

doc/tools/WP-kalkulator-punktow-za-wynik-spws.html and WP-instrukcja-wgrania.txt are retained unchanged, and frontend/tests/assets.test.ts keeps its three-way byte-identity assertion. ADR-085's exit clause — recorded in that test's header as “the page and this test are removed once the formula becomes the live SPWS scoring” — is triggered by this cutover, but the page is kept: §12 supersedes ADR-085 by making the temporary page permanent rather than removing it.

The two pages bind to different seasons, deliberately

The calculator follows the active season. The scoring-table annex is pinned to 2026/2027 and stays pinned. ADR-092 defines it as Załącznik nr 1 to that season's regulation, its source filename encodes that, and a regulation annex that silently re-rendered itself when the season rolled over would no longer be the document it claims to be. ADR-092's season identity therefore stands unchanged; only the source of its numbers changes.

The pin is expressed as an explicit season code — the annex asks for SPWS-2026-2027 — never as “the active season” and never as hardcoded numbers copied into the page. Before that season's first result is scored the annex still tracks Admin edits, because it is asking the live configuration for that season. Once the season locks, its parameters stop moving and the annex is frozen for good, while remaining provably derived from the engine rather than hand-maintained.

This costs nothing architecturally: the shared module is season-agnostic and takes parameters as input, so each page simply supplies a different season. A future season wanting its own annex gets its own file pinned to its own season code.

09 · Walkthroughs

Concrete behavior at the boundaries

A. First 2026/2027 PPW result

  1. Admin selects SPWS_FIELD_SCALED_V1_2026_2027, completes all normalized type settings, and saves.
  2. Ingestion commits placements and invokes fn_calc_tournament_scores.
  3. The dispatcher resolves the selected engine and PPW multiplier; the strategy returns components.
  4. The writer stores components, marks the tournament scored and sets the Admin configuration-lock timestamp atomically.
  5. Later Admin attempts to change anything in the scoring editor — engine, base, podium, multiplier, threshold or ranking bucket — are rejected by the ordinary database API and explained in the UI. Controlled result repair remains available.

A2. A pre-lock edit reaches all three surfaces

  1. Before any 2026/2027 result is scored, an admin lowers the base value in the Admin editor and saves.
  2. The next scoring run uses the new base, because fn_calc_tournament_scores reads it from the season's configuration.
  3. The public calculator and the scoring-table annex both show the new base on their next load, because the shared module reads the same season configuration.
  4. The season's first result is then scored. The configuration locks, and all three surfaces are frozen together by that one lock.

A3. A one-competitor bracket

  1. A PPW bracket is ingested with a single competitor, which ADR-066 admits deliberately.
  2. Under 2025/2026's classic engine the lone entrant scored base 50 + 0 + podium 9 = 59 before the multiplier.
  3. Under 2026/2027's field-scaled engine the max(2, N) guard gives base 10, so the same walkover scores 10 + 0 + 9 = 19.
  4. This is the intended shape of the curve, it is stated in §04, and SS26.NEW asserts it so it cannot regress silently.

A4. A place larger than the field

  1. An import proposes place 120 in a field of 107 — a parse slip, not a result.
  2. Ingestion validation rejects the row rather than storing it.
  3. Had it reached scoring, the dispatcher raises instead of writing the silent zero the present function would produce.
  4. The same input in the published calculator renders the in-page validation error rather than a number.

B. PZSz veteran finishes 34th of 107

  1. The PZSz calendar event already exists childless.
  2. FTL ingestion validates the source and creates the appropriate PPS/MPS SENIOR tournament with N=107.
  3. The existing veteran is matched; the other 106 source competitors need not exist in tbl_fencer.
  4. The result stores place 34, full N remains 107, and the fencer receives their season V-category.
  5. The 2026/2027 engine scores 34/107; the PZSz Season Scoring Rules determine whether it counts toward the one EVF+ total, while PPW excludes it. Its drilldown bar is red to mark its voluntary senior-bonus provenance.

C. New 2027/2028 rules

  1. A developer adds a new immutable strategy and registry entry with a new descriptive season-suffixed code.
  2. The new season selects it before any result is scored.
  3. No 2025/2026 or 2026/2027 strategy is edited; golden tests continue to pin both.

D. Partial failure or concurrent Admin edit

Scoring, score writes, tournament status and first Admin-lock timestamp share one database transaction. Row locking serializes ordinary configuration save against first scoring. Either the pre-score configuration write wins completely, or scoring closes ordinary Admin editing and the configuration write fails completely—never a tournament scored under half of each configuration. The separate privileged revision procedure has its own whole-season atomicity and audit contract.

E. Moving between official and spreadsheet-derived seasons

  1. A visitor views 2026/2027 in Ranking mode and selects 2025/2026.
  2. The season policy is read before a ranking request is issued; client state is normalized to PPW immediately.
  3. The Ranking / PPW switch disappears, the PPW RPC loads, and the drilldown/export inherit PPW.
  4. A late response from the abandoned 2026/2027 Ranking request is ignored because it no longer matches the selected season/request generation.
  5. When the visitor returns to 2026/2027—even years later—the permanent FULL capability restores Ranking / PPW and applies that season’s configured default.

F. Correcting an invalid FTL source

  1. An operator discovers that a tournament was scored from an incorrect FTL URL.
  2. The URL is corrected and the invalid imported result set is replaced through the normal repair/reimport path.
  3. The tournament is scored again using the unchanged active season configuration revision.
  4. The season remains administratively locked, but the repaired scores replace the invalid scores; no configuration unlock is needed.

G. Board-authorized scoring-rule change

  1. The board authorizes a change and supplies a durable decision reference and reason.
  2. An operator invokes the privileged database procedure outside the Admin UI. A formula change selects a newly named immutable engine version; a multiplier or threshold change creates a new configuration revision without rewriting the engine.
  3. The operation retains the old revision, recalculates the whole season and checks that every applicable stored score uses the candidate revision.
  4. Only a complete successful rescore makes the candidate active. Any error rolls back to the previously authoritative revision and scores.

Adding the PPS/MPS enum values needs two migrations

A new enum value cannot be used in the transaction that adds it. The existing precedent is misleading: ALTER TYPE enum_tournament_type ADD VALUE IF NOT EXISTS 'PSW' in 20250305000002 appears to use 'PSW' immediately, but only inside a function body, which Postgres parses at runtime and never evaluates during that transaction. A migration that adds 'PPS' and 'MPS' and then inserts normalized type-configuration rows for them will fail. Split it: one migration adds the enum values, a later one populates their settings.

Deployment preflight is a hard gate

If 2026/2027 already contains a scored tournament when the migration reaches an environment, deployment must stop unless that season already points at the intended new engine and its type settings are complete. The migration must never silently switch an already-scored season.

12 · Proposed decisions

ADR drafts for explicit sign-off before ADR files are created

Proposed ADR A — Versioned season scoring strategies and governed configuration revision

Context: one mutable function cannot preserve old seasons while introducing new formulas, while the board must retain authority to correct a season’s rules and rescore it coherently. Decision: the season is assigned an engine and a static CASE dispatcher resolves it, extending the pattern ADR-042 and ADR-045 already established for carry-over; immutable released strategies behind that dispatcher; tbl_scoring_engine as metadata only; shared preview/persistence contract; normalized revisioned type policy; base value and podium coefficients remaining season configuration rather than engine constants; database-enforced closure of the whole Admin scoring editor after first scoring; unrestricted source/result repair under the active revision; and a privileged audited whole-season revision/rescore procedure. Alternatives rejected: one growing IF tree holding the arithmetic inline; dispatch through a function reference stored in a table, which needs dynamic EXECUTE inside SECURITY DEFINER, defeats Postgres dependency tracking and hides the call edge from static analysis; a partial lock that leaves ranking buckets editable while they silently reorder the published ranklist; wholesale copies of the bulk writer; season-code inference; UI-only enforcement; permanently forbidding authorized corrections; overwriting released engine bodies or configuration history. Consequences: historical golden tests and configuration audit history become mandatory; formula changes create a new engine version; exceptional revision remains an operator procedure outside Admin and cannot publish a partially rescored season.

Proposed ADR B — PZSz senior results as full-field PPS/MPS tournaments

Context: ADR-087 intentionally stopped at the calendar. Decision: distinct PPS/MPS types, one SENIOR source tournament per weapon/gender field, full N and original placement, existing-veteran-only matching, V0–V4 result categorization, and no pre-2026/2027 scoring. Alternatives rejected: five duplicated V-category tournaments; shrinking N to imported veterans; automatic fencer creation; historical backfill. Consequences: ranking rules can treat PPS and MPS independently while source truth remains intact.

Proposed ADR C — Official full-Ranking publication begins with 2026/2027

Context: the three earlier seasons reproduce spreadsheet-era PPW material and never represented an official combined ranking. Decision: store immutable PPW_ONLY/FULL publication policy per season; permanently mark only the first three seasons PPW_ONLY; make 2026/2027 and later FULL; enforce the restriction in database and UI while retaining source results. Alternatives rejected: “older than active season” logic, a duplicated hardcoded date cutoff, scoring-engine inference, and hiding only the toggle. Consequences: 2026/2027 keeps full Ranking after becoming historical; old EVF/FIE data remains usable for audit/carry-over but cannot be presented as an official historical Ranking.

ADR-085 is superseded when the published-page cutover lands — by making its “temporary” page permanent rather than removing it, against the exit clause recorded in assets.test.ts. ADR-042 and ADR-045 are the decisions Proposed ADR A most directly extends and must carry relationship notes; an earlier version of this document omitted both. ADR-092 is amended only in that the annex stops carrying its own copy of the formula; its season identity is unchanged — the annex stays pinned to 2026/2027, as §08 records. ADR-001, ADR-002, ADR-006, ADR-017, ADR-018, ADR-066 and ADR-087 require amendments or relationship notes; ADR-066 in particular is amended by the N = 1 re-pricing in §04 and the fail-closed gate in §07. Proposed ADR C directly supersedes ADR-017’s historical PPW/+EVF presentation rule. The highest ADR on origin/main a108de4d is 096, so the next free numbers are 097–099; confirm with a fresh collision scan before the files are created.
