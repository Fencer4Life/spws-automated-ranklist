The domestic place drift is planned separately

D3 · A domestic recompute does not restore places when a fencer moves out of a category and back

Found during the LOCAL recompute proof (details below). In GP3 2023/24 men's épée, V4 placed 250, 101, SCHOLZ, 325 as 1–4. A birth-year edit moved SCHOLZ to V3, and the recompute renumbered 325 to 3rd. Restoring the birth year moved SCHOLZ back with his stored 3rd place, so 325 and SCHOLZ now tie at 3rd. 325's 4th place is lost, and so are its points (1.00 became 15.93).

The cause: under EVF classic, a domestic category stores places renumbered within that category, 1 to K. When a fencer moves, the recompute only has that renumbered place, not the fencer's place in the pool all categories were fenced in. So it cannot put the fencer in the right position in the other category. International results are not affected (they never move, see below).

  • A (chosen 1 October): keep it out of release 1 and plan it separately. It needs a design choice about what the recompute keeps. Store the pool place next to the category place, or keep the category order as the 2026/27 joined module already does. It only matters when a birth-year correction moves a fencer across a category boundary in a split pool. Release 1 does not make it worse.
  • B: fix it inside release 1. This adds a column, a migration and a backfill from source to a release whose job is to stop the live PEW/MEW damage. It would delay that.

The rule, as you stated it

One rule for every international result

  1. Only Polish fencers are ingested (ADR-038). Non-POL rows are dismissed before matching, so no foreign name can ever be matched to a Polish fencer.
  2. N is the whole source bracket: every fencer who fenced it, Polish or not.
  3. The place is the fencer's own place in that bracket, as published. It is never renumbered among the Poles.
  4. Neither is ever recounted afterwards: not at commit, not in recompute, not on promotion to PROD.
  5. The source is the organiser's results (FTL, Engarde, 4fence, d'Artagnan, Ophardt, FencingWorldwide). EVF results are a secondary source, used only when nothing else exists.

It applies to PEW, MEW, MSW and PSW. PZSz senior brackets already follow points 2–3 (ADR-100). The rule becomes ADR-105, a draft for your sign-off. It amends ADR-038 (adds points 1–4 for every path) and ADR-049 (the 4 June per-V-category count is domestic only). It also amends ADR-072 (recompute keeps an international N and place) and ADR-103/104 (which module an international bracket uses).

Root causes

Four defects, one shared mistake

The shared mistake is counting the rows we keep instead of the bracket that was fenced. For a domestic event the two are the same, because everyone is kept. For an international event we keep only the Poles.

  1. RC1 · N recounted from kept rows. The Phase 5 draft writer, the commit RPC's joint-sibling recount, the ingest RPC's silent fallback, PerCategoryRenumber and scrape_tournament.
  2. RC2 · Places renumbered among kept rows. PerCategoryRenumber dense-ranks, in ingest and in recompute.
  3. RC3 · Recompute re-applies RC1 and RC2 to international events. This happens on CERT and PROD whenever a fencer row changes. A repaired event would be damaged again.
  4. RC4 · Foreign rows reach the matcher in both pipelines. A foreign name that matches a Polish fencer gets a result (KUZMICHOVA). ADR-038 says they are dismissed first, and only the deprecated legacy path still does that.

Found during development · 1 October

Two more recompute defects, and one change to step 2

RC5 · Every recompute overwrote each result's scraped name and match provenance

When RECOMPUTE_DOMESTIC rewrites a result, it deletes and re-inserts the row. It rebuilt each row from the fencer id alone. So every recompute stored the fencer id as txt_scraped_name, reset enum_match_method to AUTO_MATCH and set the confidence to 100. Test N9.6 had pinned that shape. This affects domestic and international events alike.

Read-only, 1 OctResultsScraped name = own fencer idNo scraped nameUSER_CONFIRMEDAUTO_CREATED
CERT2,8112,61018300
PROD2,8112,66113200

What it costs: no score, place or identity link changes, because id_fencer is intact. What is lost is the audit trail. The admin Identity Manager shows numbers where scraped names belong, and every manual identity confirmation is now recorded as an automatic match. Alias write-back is not affected, because it reads drafts at sign-off. The original names exist only in the sources, so they come back only through re-ingestion. The data-repair plan restores them for every event it re-ingests.

Fixed in release 1 (built, GREEN):

  • fetch_event_results reads each row's stored scraped name, confidence and match method. LoadCommitted carries them, and the recompute writes them back verbatim, NULLs included. It no longer sends a forced AUTO_MATCHED status, so the match candidate's status follows the stored method.
  • Migration 20261001000003_recompute_keeps_provenance.sql: the ingest RPC keeps an explicit null confidence as NULL instead of 100. An absent key still means 100, and no source write sends an explicit null. A row with no scraped name gets no match candidate, because the candidate's name is NOT NULL. The 183 early EVF rows stored that way have none today, and the recompute used to fail on them.
  • Tests RECOMP.PROV.01–05 (pytest) and RECOMP.PROV.RPC.01–05 (pgTAP 87). N9.6 is amended to the corrected row shape.

Step 2 changed: an international result stays in its stored tournament

Step 2 said a recompute "may still move" an international result to the fencer's re-derived category. It does not move it any more. A moved result would carry its place from one source bracket under another bracket's N (31st of 60 in Vet-50 filed as 31st of 74 in Vet-60). The stored tournament is the bracket the fencer fenced, and a birth-year correction in our roster does not change that.

The LOCAL proof then failed on fn_assert_result_vcat. That guard requires every result to sit in the category its birth year implies, unless the row carries a source bracket label (ADR-056 revision, "bracket-label wins"). No international result had one. The recompute now writes the stored bracket's category as enum_source_age_category, so the guard trusts the bracket. Test INTL.RECOMP.04. ADR-105 records this choice for your sign-off.

Steps

Release 1 · stop the damage and close the database traps

  1. A source-field module for international brackets. In python/pipeline/joined_brackets/, an international intake (organiser EVF or FIE, or types PEW/MEW/MSW/PSW) always uses the module that keeps the source place and N = field.size. That is the existing JoinedBracketCategoryPlace behaviour, selected by intake rather than by engine; domestic selection is unchanged. field.size is parsed.raw_pool_size at ingest and the stored N at recompute. Tests INTL.MOD.01–04: an EVF bracket of 60 with 2 Poles at 31 and 48 stores N 60 and places 31 and 48; a domestic split still renumbers; selection does not depend on the engine.
  2. Recompute keeps an international N and place. RECOMPUTE_DOMESTIC goes through step 1, keeps each international result in the tournament it is stored in (changed during development), writes that bracket's category as its source label, re-scores it, and never recounts. Tests INTL.RECOMP.01–04: an international event recomputed after a fencer's birth year changes keeps every N and place; a domestic event recomputes exactly as before.
  3. Commit RPC: the joint-sibling recount is domestic only. A migration replaces fn_commit_event_draft. The recount UPDATE gains AND t.enum_type IN ('PPW','MPW'). pgTAP INTL.RPC.01–02.
  4. Ingest RPC: no silent fallback for international types. In the same migration, fn_ingest_tournament_results raises when p_participant_count is NULL for PEW/MEW/MSW/PSW, and when N is smaller than the highest place written. pgTAP INTL.RPC.03–05. Callers are checked: the orchestrator, PZSz and the new pipeline already pass a count, and step 8 fixes scrape_tournament.

Release 2 · every ingestion path ingests international results correctly

  1. POL filter before matching, in both pipelines. stages.py S6 and plugins/resolve_fencers.py drop non-POL rows of an EVF/FIE event before the matcher runs. They reuse the fold in stages.py:83 (PL → POL) and match the legacy rule in matcher/pipeline.py:204. Tests INTL.POL.01–03: a foreign row whose name exactly matches a Pole is dismissed, writes no result and joins no review queue; a POL row matches as before.
  2. Phase 5 draft writer. review_cli.py:899 writes N = parsed.raw_pool_size for an international bracket, places stay as scraped, and no V-category is invented from a matched birth year. Tests INTL.DRAFT.01–03.
  3. The new pipeline's event URL path refuses EVF/FIE events with a clear message naming the Phase 5 runner, until the international flow exists (D2 = A). Test INTL.URL.01.
  4. scrape_tournament passes the source bracket size for an international tournament. Test INTL.SCRAPE.01.
  5. A standing check. A pgTAP invariant (no international result has a place above its tournament's N) and a post-commit line in the staging summary: N, the highest place and the POL count, per international bracket.
  6. Replay MSW Manama on LOCAL through the fixed Phase 5 path (drafts only). Expect 30 POL results in 14 brackets with the FTL places and field sizes shown above, no V0 bracket, no pool-round halt and no foreign match. The output goes on a review page for you; nothing is committed.
