Rotating the FencingTimeLive login

Since 2 Nov FencingTimeLive refuses the pipeline’s login (“please contact customer support”), and you think it hit a usage limit. Below: how you record a new login (you type it; I never see it), and what to decide so the new login does not hit the same wall.

The guide · about five minutes · you do it

How to record the next login

One piece of code reads the login, python/scrapers/ftl_auth.py, from two names: FTL_USERNAME (the account’s e-mail) and FTL_PASSWORD. They live in two places, and both must change.

  1. Create the login, then check it in your own browser. Your choice (L3, 4 Nov): an account at fencingtimelive.com under a “+” alias of the association’s Gmail, for example mailbox+ftl@gmail.com. FTL treats it as a new address; its confirmation mail arrives in the same inbox. You create the account: I cannot create one for you. Then sign in once with it. If it is refused there, stop: no file needs changing yet.
  2. LOCAL: your .env. Open /Users/aleks/coding/SPWSranklist/.env in your editor (every worktree links to this one file). Change the two lines, keeping their names: 
    FTL_USERNAME='the-account@e-mail'
FTL_PASSWORD='the password'
    No spaces around =. Keep the single quotes when the password holds a space, $, # or a quote mark. Save.
  3. CI: the two repository secrets. In a terminal in the repository, run each line on its own; each asks for the value and hides what you paste: 
    gh secret set FTL_USERNAME
gh secret set FTL_PASSWORD
    Never pass the value on the command line (--body): it would stay in your shell’s history. The same works on github.com: Settings → Secrets and variables → Actions → Repository secrets → the pencil beside each name. Eight workflows read these two names (ingest-event, promote, event-close, source-regression, evf-sync, populate-urls, scrape-tournament, phase5-event-runner); the hourly results sync reaches FTL through ingest-event. Nothing else changes.
  4. Keep the old login out of both places, in your password manager only, until FTL’s support has answered (L4).
  5. Tell me “login rotated”. I then make one read-only check on LOCAL: a re-read of one FTL event (IMSW-2025-2026) against LOCAL, nothing written, the result in one line. If FTL refuses, the run stops at that one attempt (G71) and I tell you. CI’s next FTL read proves the secrets.

What I never do

See, print, store or log the values; open .env; ask you to paste them in chat. Documentation and memory name the two variables and where they live, never their values (handbook, Environments and Release).

Why the next login could fail the same way

What we know about the limit

  • FTL’s session lasts 10 days from sign-in and is not extended by use (ADR-068). Our code keeps it only inside one process, so every run signs in again. ADR-068 deferred keeping it across runs.
  • 1 Nov: about twelve sign-ins (CI’s two source re-reads, about ten of my read-only runs), all accepted. 2 Nov, 07:00 UTC onward: refused on this machine and on GitHub’s alike, with nothing of ours signing in during the hours it changed (G63).
  • What is coming. Since 1 Nov the hourly results sync runs by itself. An FTL event in progress costs two or three sign-ins per hourly cycle (its read and ingest on CERT, then promote): roughly 50 to 70 a day, against twelve on 1 Nov. All but one sign-in in ten days could be avoided.
  • Not known: FTL’s rule. I have not read FTL’s terms, and the refusal names no limit. If FTL limits an account on purpose, a second account used to get past that limit may break its terms and lose that account too; only FTL can say (L4).

Decide this first

Five decisions, each with a recommendation

C The pipeline switches to the second login by itself when the first is refused.		A: one active login, changed by you. C would spend the second login the same way within hours, and to FTL it looks like getting round its limit.
4 Nov, your proposal: four “+” aliases of the association’s Gmail with one password, used in turn. I will not build that rotation: four accounts on one mailbox, signing in from the same machines, taken in turn because each is cut off, is a way round FTL’s limit rather than within it, and FTL can link them and block all of them, the first login included. One shared password would also lose all four at once if it leaked. What I will help with: one alias as the replacement login (A), L2 so it lasts, and L4.
L2Sign in less often.A Keep the 10-day session across runs (ADR-068’s deferred follow-up): one sign-in per ~10 days. CI keeps it in a CERT database row only the pipeline’s service role reads (deny-by-default, ADR-083); LOCAL in a file in your user’s cache folder, readable by you only. Never GitHub’s Actions cache: in a public repository a pull request’s workflow can restore it. Its own build sheet, test-first.
B Keep one sign-in per run (as now, with G71).		A: without it the hourly sync signs in some 50 times a day during an FTL event, whichever login it uses.
L3Whose login?A An account in the association’s name (its own mailbox), kept in its password manager, so it outlives any one person.

An alias is one more account on the same mailbox, which FTL can link to the first: use it as the one replacement login (L1 A), not as a pool to move through each time one is refused (L1 C), which FTL would most likely treat as getting round its limit.

B They wait until L2 is built.		A: a handful of sign-ins, one per run, now G71 stops a refused run at its first attempt.

Boundaries

What this does not touch

  • The guide needs no code: the names stay FTL_USERNAME and FTL_PASSWORD. Code changes only with L1 B or L2 A, each test-first after your sign-off.
  • The FTL export organizer link (tbl_ftl_export_token, ADR-095) is a different thing and is not rotated here.
  • No other secret, and no other provider’s login.
