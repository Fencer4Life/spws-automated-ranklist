02Where yesterday's report was wrong

It blamed the Python dedup ladder. The Python ladder is not the layer that decides.

Yesterday I wrote that _find_existing_match in evf_calendar.py eliminates every skeleton at its date gate, so the scrape falls through to "no match" and inserts a fresh row. The first half is true. The second half is not — because that Python function is not what creates the row.

The insert happens in SQL, in fn_ingest_evf_calendar (20260711000001_prod_event_reconciler.sql:215), which asks fn_allocate_evf_event_code (20260429000001_phase4_pew_split.sql:55) whether this scraped event should reuse an existing slot or mint a new code. That allocator already has an adopt-the-skeleton rung. It is Step A, and it was written for exactly this case:

-- Step A: current-season CREATED slot reuse (matches PEW{N} or PEW{N}{letters})
IF v_loc_key <> '' THEN
  SELECT COUNT(*)::INT, MAX(e.txt_code), MAX(e.id_prior_event)
    INTO v_match_count, v_match_code, v_match_prior
    FROM tbl_event e,
         LATERAL fn_normalize_city_key(e.txt_location, e.txt_country) n
   WHERE e.id_season = p_id_season
     AND e.enum_status = 'CREATED'
     AND e.txt_code ~ '^PEW\d+[efs]*-'
     AND n.loc_key     = v_loc_key
     AND n.country_key = v_ctry_key;

So yesterday's recommendation — "add a new rung that adopts the skeleton" — was proposing something the codebase already had. Fixing the Python matcher would have changed nothing, and neither would adding a rung beside one that already exists.

03The real root cause

Step A adopts a skeleton by city. The skeletons had no city.

Every one of the six surviving skeletons has an empty location and an empty country, so fn_normalize_city_key returns an empty loc_key for all of them:

Skeletontxt_locationtxt_countryloc_key
IMEW-2026-2027(empty)(empty)""
MPW-2026-2027(empty)(empty)""
PPW2–PPW5-2026-2027(empty)(empty)""

A scraped EVF event always has a city. An empty skeleton key can never equal a non-empty scraped key, so Step A matches nothing, and the allocator falls through to Step C — next-free PEW{N+1} — which mints a brand-new code beside the skeleton. Every run. That is the duplicate.

Why the skeletons were placeless, which is the part that makes this a trap. fn_init_season does copy the prior season's city onto each PEW skeleton (20260429000001_phase4_pew_split.sql, the live definition — note the older one at 20260428000003 is superseded and its ^PEW\d+- regex would have matched none of the real suffixed codes anyway). The skeletons were created on 28 June 2026. The work that made txt_location reliably hold a city — ADR-088's one location contract — was accepted on 4 September 2026, more than two months later. So at bootstrap time the prior season's cities were largely unpopulated, the skeletons inherited nothing, and Step A was dead on arrival for all of them.

This matters for what you decide next: a season bootstrapped today would inherit real cities and Step A would mostly work. The defect is partly self-healing. Only partly — Step A needs an exact city match, and EVF moves its circuit between cities from season to season. Every event that moves is a skeleton that cannot be adopted, and a duplicate.

04Why removing EVF skeletons is the right fix

A PEW skeleton is a guess at what an external body will publish. EVF publishes the truth within the same season.

The distinction that decides which skeletons earn their place is not who organises the event — it is whether anything automated will independently create the row:

SkeletonOrganizerCreated independently by a scraper?Can duplicate?
PPW1–NSPWSno — SPWS schedules these by handno

MSWFIEno — there is no FIE scraper in python/scrapers/no
PEW1–NEVFyes — evf_calendar.py / evf_sync.pyyes

A skeleton exists to hold a slot for something the association knows it will run but has not yet scheduled. For PPW and MPW that is real: SPWS commits to the event, and an administrator fills in the date and venue later. For PEW it is not. SPWS does not schedule the European circuit; EVF does, and the scraper discovers it. The skeleton contributes no information that will not arrive authoritatively within the season — and it contributes three problems:

  • it carries none of the four identities the dedup ladder can use — no date, no EVF calendar id, no EVF results id, no slug;
  • its only remaining handle is a guessed city, which is wrong whenever EVF moves the event;
  • it guesses the weapon suffix, and got it wrong in 8 of 8 observed cases.

Fencers never saw any of it: the calendar hides CREATED events twice over (calendarMonths.ts:258 drops rows with no dt_start, and visibleEvents at :545 filters enum_status !== 'CREATED', per ADR-077). The cost was to administrators and to the season's event count.

05The decision I need — which skeletons survive

You said "remove the EVF skeletons", then "leave only the SPWS skeletons". Those two sentences draw the line in different places, and the difference is MSW.

MSW is the World Veterans Championships and its organizer is FIE, not SPWS (fn_init_season assigns it v_fie_org). Read literally, "only the SPWS skeletons" removes it. Read as "remove what duplicates", it stays — because no FIE scraper exists, so an MSW skeleton cannot be duplicated by anything.

 OptionSkeletons keptSkeletons dropped
D1
recommended		 Drop the skeletons that a scraper will create anyway PPW1–N, MPW, MSW PEW1–N, IMEW, DMEW
D2 Drop everything not organised by SPWS — your second sentence, read strictly PPW1–N, MPW PEW1–N, IMEW, DMEW, MSW

My recommendation is D1. The rule that survives contact with the next scraper you add is "a skeleton is for an event nobody will discover for us", not "a skeleton is for an SPWS event". MSW is the case that separates them: it is somebody else's competition, but nothing automated creates it, so its skeleton is the only thing holding that slot in the season — and dropping it would silently remove a real event from the season structure and its six V2 child tournaments. If you would rather keep the rule blunt and organiser-based, say D2 and I will build that instead.

06What I will build once you choose

Four changes, TDD order, plus an ADR amendment. Nothing here is started.

  1. A migration redefining fn_init_season so it no longer creates the dropped kinds, and no longer emits their six V2 child tournaments each. The by_kind return value keeps its keys and reports zero, so nothing reading it breaks.
  2. A data migration removing the one EVF skeleton still live — IMEW-2026-2027 — and its children, guarded so it only ever touches a CREATED row with no date, no results and no tournament children with scores.
  3. pgTAP tests first, failing before the change: that a freshly initialised season contains no PEW/IMEW/DMEW skeleton, that it still contains the kept kinds with their children, and that an EVF scrape into a season with no skeletons allocates each event exactly once.
  4. The wizard's own count is wrong and gets fixed with it. App.svelte:1170 predicts the skeleton breakdown with /^PEW\d+[efs]*-/ and shows the user "5 PPW + 9 PEW" before they commit. Once PEW skeletons are gone that number is a lie, so the breakdown drops the EVF kinds too.

ADR-077 has to be amended, not just edited around. It is the record that says a season is bootstrapped with skeletons for its expected events. Narrowing that to "expected events nobody else will publish for us" is a change to the decision, and it needs to be written down as one — with the reason, so nobody restores EVF skeletons in a year wondering why they were missing. I will draft the amendment for your sign-off rather than marking it accepted myself.

One thing I am deliberately not doing. The allocator's Step A stays exactly as it is. It is correct for what remains — an administrator who creates a skeleton and types a city should have it adopted rather than duplicated — and with EVF out of the picture nothing reaches it with a guessed city any more. Removing a working rung because it failed on inputs that will no longer exist would be the wrong lesson.
