01 · Outcome and scope

What exists after this lands

  • The public ranking switch reads PPW / Ranking (not SPWS/EVF+, not Kadra). Ranking calls the new fn_ranking_full RPC (schema v2, ADR-098) instead of the legacy fn_ranking_kadra; PPW is unchanged (fn_ranking_ppw).
  • The ranklist table and export show exactly Zawodnik | SPWS | EVF+ | Razem in Ranking mode, from fn_ranking_full's own spws_total/evf_plus_total/total_score columns. PPW mode keeps its existing single-column shape unchanged.
  • The drilldown shows two top-level sections — blue SPWS, EVF+ — simultaneously in Ranking mode, with individual result bars inside the EVF+ section colored by their own tournament type: orange for EVF/FIE (PEW/MEW/MSW/PSW), red for PZSz (PPS/MPS). No color-specific subtotal is added.
  • V0 can select Ranking. The three duplicated category === 'V0' guards (FilterBar, App's EVF-toggle refresh, the drilldown's inherited kadraDisabled) are removed.
  • The three spreadsheet-derived seasons (2023/2024–2025/2026) force PPW, hide the switch entirely, and the drilldown/export inherit PPW — driven by tbl_season.enum_ranking_publication, read for the first time by the frontend. 2026/2027 defaults to Ranking (from the season's own default_ranking_mode) and keeps the switch.
  • Season, mode, filter and drilldown loads carry a request-generation id so a slow, abandoned fetch can never overwrite state a faster, later one already set.
  • ScoringConfig.engine (the last ambiguous carry-over alias in the frontend) is renamed to ScoringConfig.carryover_engine, finishing the separation from engine_code (the scoring engine) that ADR-097 already established in the database and the Admin selector.

Deliberately out of scope

No change to fn_ranking_kadra/fn_ranking_ppw/fn_ranking_full or any other database function — this step is a pure frontend consumer change. No dynamic-from-data rendering of per-type multiplier fields (§14's "dynamic tournament-type rendering" reading) — the eight hardcoded multiplier cards in ScoringConfigEditor.svelte (PPW/MPW/PEW/MEW/MSW/PSW/PPS/MPS) already cover every configured type today; making that list data-driven is a refactor with no acceptance test behind it and is deferred (see §13 Flags). No URL/deep-link persistence for season/mode/filters — none exists today (verified: only ?admin=1 is read from the URL anywhere in App.svelte), so "constrains deep links" (§10) has no current surface to build against; see §13 Flags. No PZSz match-review Admin screen (still backend-only per step 6's own scope note).

03 · Proposed ADR-101 — sign-off requested

ADR-101: the ranking switch is Ranking / PPW; publication capability is read, not re-decided, by the UI

Status: Proposed

Context. Design steps 4/5/6 (ADR-098/099/100) built the schema-v2 ranking RPC, the immutable per-season publication capability, and PZSz senior ingestion — all backend-only, all deliberately deferring frontend consumption ("compatibility wrappers... before changing frontend consumers", §11 step 4). The frontend still calls the legacy fn_ranking_kadra, has never read enum_ranking_publication, and still calls its combined ranking mode KADRA with button labels "SPWS"/"EVF+". Separately, the Admin scoring-lock UI that the original design's §05 prose assumed step 7 would build shipped early, in step 3, ahead of schedule (confirmed live, §02 above) — so this ADR's scope is narrower than the design doc's own step-7 description: it covers the public ranking UI, publication enforcement, staleness handling and the last carry-over-engine naming cleanup, not the Admin lock UI.

Decision.

  1. Rename the combined mode, not just its label. RankingMode becomes 'PPW' | 'RANKING' (was 'PPW' | 'KADRA') everywhere — type, component props, locale keys, test fixtures. The RANKING mode calls fn_ranking_full (new); PPW keeps calling fn_ranking_ppw (unchanged). fn_ranking_kadra is not called by the frontend after this lands, but is not removed from the database (pgTAP's own parity tests still need it as the independent oracle).
  2. Publication capability is read from tbl_season directly; default mode is read by reusing fn_export_scoring_config. fetchSeasons()'s column list gains enum_ranking_publication (same table, same query, no new round-trip). The season's default_ranking_mode is read by calling the already-anon-executable fn_export_scoring_config(id_season) once per season selection on the public page too — reusing the existing, Admin-shaped RPC rather than adding a second, narrower one, accepting a heavier-than-strictly-needed payload for a public page that will call this once per season change, not per keystroke.
  3. The UI normalizes and hides; it does not additionally gate. When the selected season's enum_ranking_publication = 'PPW_ONLY', App.svelte forces filters.mode = 'PPW' before issuing any ranking fetch and does not render the switch at all (not disabled — absent). This is presentation of a capability the backend already enforces (fn_ranking_full's own exception) and explanation of it, never the sole authority — matching ADR-099's own rejected alternative ("UI-only enforcement") by construction: removing the JS entirely would still leave the RPC refusing the request.
  4. V0's three duplicated guards are deleted, not consolidated into one. There is no remaining reason to disable Ranking for V0 (§06: "V0 can use Ranking. Its EVF/FIE subsection is naturally empty, while SPWS and PZSz can contribute") and a PZSz senior field admits any age including V0 fencers, so the guard is actively wrong now, not merely redundant. Deleting all three (FilterBar, App.svelte's refreshEvfToggle, the inherited kadraDisabled) removes the only place V0 was special-cased in ranking-mode logic; showEvfToggle (publication + config-driven) remains the sole gate on whether the switch renders at all.
  5. A monotonic request-generation counter guards every async ranking/drilldown load. One counter on the root component, incremented at the start of each load, captured by closure, compared against the current value when the response resolves; a mismatch discards the response silently. Chosen over AbortController because Supabase's JS client does not expose per-call cancellation cleanly through the existing api.ts wrapper functions, and a discard-on-arrival counter needs no change to those wrappers' signatures.
  6. EVF+ bar coloring is provenance-only, computed from the existing enum_type per result — no new subtotal. INTL_TYPES in DrilldownModal.svelte splits into EVF_TYPES (orange) and PZSZ_TYPES (red); both still sum into the one evf_plus_total/international column total. Matches §06 exactly: "Color communicates provenance only; it does not create separate orange or red subtotals."
  7. ScoringConfig.engine is renamed to ScoringConfig.carryover_engine. This is the last frontend site using the bare, ambiguous engine name for the carry-over matcher (the database column, the CarryoverEngine type and the Admin selector's variable names are already unambiguous per §02 above) — renaming it closes the naming gap ADR-045/097 opened for the database and the selector but never finished for this one field.
  8. The seed's SPWS-2026-2027 row gains an explicit enum_default_ranking_mode value. Same fix shape as ADR-099's own seed amendment for enum_ranking_publication: migrations run before the seed dump, so a plain re-INSERT silently regresses any column the migration set but the seed doesn't also set.

Alternatives rejected. A new, narrower public RPC/view exposing only enum_ranking_publication + default_ranking_mode together — rejected as premature surface addition when the existing anon-executable fn_export_scoring_config already carries the one field needed and this codebase's own established pattern (steps 4-6) is to reuse an existing RPC over adding a new one when the existing one is already public and already correct. AbortController-based cancellation — rejected per point 5 above (wrapper-signature churn for no behavioral gain over a counter). Keeping KADRA as the internal value and renaming only the display label — rejected: the design's own definition-of-done explicitly treats the mode name itself, not just its label, as part of the "Ranking/PPW" contract, and a display-only rename would leave test fixtures and code asserting a name (KADRA) that no longer means what it says.

Consequences. fn_ranking_kadra becomes dead code from the frontend's perspective but stays in the database, still tested, still the parity oracle for fn_ranking_full — a deliberate compatibility retention, not an oversight. Every test file listed in §09 that currently asserts 'KADRA'/"EVF+ button" gets rewritten, not extended — a mechanical but wide-surface diff. The public ranklist page now makes one additional RPC call per season change (fn_export_scoring_config) that it never made before; this is accepted per point 2 above.

06 · Publication boundary and staleness

App.svelte: the one place that normalizes

  • Season-change handler reads the newly-selected season's enum_ranking_publication (already in the Season object from fetchSeasons()) synchronously, before issuing any ranking fetch: if 'PPW_ONLY', sets filters.mode = 'PPW' immediately and sets a rankingSwitchAvailable = false flag (replacing/augmenting today's showEvfToggleRanklist, which stays config-driven but is now AND-ed with publication capability). If 'FULL', calls fetchScoringConfig(seasonId) (already anon-executable) to read default_ranking_mode and sets filters.mode to it.
  • Request-generation counter — one let requestGen = $state(0) at the top of App.svelte. loadRanking() captures const gen = ++requestGen before its await, and on resolution checks if (gen !== requestGen) return before applying the result to state. The same pattern wraps the drilldown's own load function. This single counter covers season, mode, filter and drilldown changes uniformly, since all of them ultimately call through loadRanking() or the drilldown loader.
  • Historical-season walkthrough (design §09 scenario E) becomes: select 2025/2026 → publication read as PPW_ONLY before fetch → mode forced to PPW, switch hidden → PPW RPC loads → drilldown/export inherit PPW (no RANKING path reachable while that season is selected, since the switch that would set it is absent) → returning to 2026/2027 re-reads FULL + that season's own default_ranking_mode, restoring the switch and Ranking.

07 · Finishing the carryover_engine separation

SS26.CARRY: mostly already true, now named correctly and tested

The database column (enum_carryover_engine), the CarryoverEngine type, the Admin selector's own variable names and the scoring-engine field (engine_code) are already correctly separated (§02). The only remaining ambiguous name is ScoringConfig.engine itself. This step renames that one field to carryover_engine across types.ts, ScoringConfigEditor.svelte's save-payload construction, and App.svelte:1420-1422's read site — then adds the dedicated SS26.CARRY.01-04 test coverage that pins the two fields as independently settable (changing engine_code in a save payload must never touch carryover_engine and vice versa) and confirms the renamed field round-trips through fn_export_scoring_config/fn_import_scoring_config unchanged (those RPCs already read/write tbl_season.enum_carryover_engine directly via the existing PATCH path, not through the JSONB config blob, so no backend change is needed here — only the frontend key naming).

08 · Scenario walkthroughs

Concrete paths, happy and adjacent

A. A visitor opens the ranklist cold on 2026/2027

fetchSeasons() returns 2026/2027 with enum_ranking_publication='FULL'; fetchScoringConfig reads default_ranking_mode='RANKING' (once the seed fix in §13 Delivery lands); the switch renders PPW/Ranking with Ranking active; fetchRankingFull loads; V2 M EPEE shows SPWS/EVF+/Razem columns with orange EVF/FIE and red PZSz bars in the drilldown.

B. The same visitor selects V0

No guard fires. fetchRankingFull is called with p_category='V0'; the EVF+ section may show €0 (no EVF/FIE V0 events exist) plus any PZSz senior contribution; evf_plus_total is whatever fn_ranking_full computes — not short-circuited by the frontend.

C. The visitor switches to 2025/2026 mid-session

Season-change handler reads PPW_ONLY before any fetch; mode is forced to PPW; the switch disappears; the in-flight 2026/2027 Ranking request (if any was still pending) resolves later but is discarded by the generation counter, since requestGen has already advanced.

D. An operator flips the category filter twice in under 300ms

Two fetchRankingFull calls are in flight; whichever resolves second under normal network conditions wins by the counter regardless of which was issued first in wall-clock terms — the counter guards against the LAST issued request's own gen being stale by the time the FIRST one resolves late, not against ordering by issue time. This is the exact race SS26.UIHIST's "ignores stale responses" targets.

E. An Admin edits the scoring engine on an unlocked season, leaving the carry-over engine untouched

Saving the config payload includes the renamed carryover_engine field unchanged from what was loaded; engine_code reflects the new selection; App.svelte's save handler calls updateSeasonCarryoverEngine only if config.carryover_engine is present and, per SS26.CARRY, this never depends on what engine_code was set to.

13 · Flags

Open decisions — sign-off requested alongside ADR-101

1. The FilterBar's static prefix label above the toggle

Today it reads "Ranking" (t('ranking')) sitting above a switch whose combined option will now ALSO read "Ranking" — redundant/confusing side by side. Recommendation: reword the prefix to something scope-neutral ("Widok"/"View") rather than removing it (removing it would leave the two buttons with no group label at all, worse for accessibility). Awaiting confirmation before implementation.

2. Reusing fn_export_scoring_config from the public page

§03 decision 2 accepts a heavier-than-strictly-needed Admin-shaped payload for a public read of one field (default_ranking_mode). The alternative (a new slim public RPC/view) was rejected as premature surface addition, but it is a real tradeoff, not a forced move — flagging for explicit agreement rather than assuming it silently.

3. "Constrains deep links" (design §10) has no current feature to constrain

No season/mode/filter state is ever written to the URL today (verified: only ?admin=1 is read anywhere in App.svelte). This plan treats that clause as vacuously satisfied and does not add URL persistence as a side effect of this step. If deep-linking is wanted, it is a separate, explicitly-scoped feature with its own plan — confirm this descoping is acceptable.

4. Dynamic-from-data rendering of per-type multiplier fields

Step 7's original prose ("dynamic tournament-type... rendering") could be read as requiring ScoringConfigEditor's eight hardcoded multiplier cards to become data-driven (iterate tbl_scoring_type_config rather than one field per known type). No acceptance test in SS26.UI/SS26.LOCK requires this, and every currently-configured type already has its own card. Recommendation: defer as a separate refactor with its own plan if a new tournament type is added in the future and the hardcoded-card pattern becomes a real maintenance cost — not blocking this step.

5. Exact internationalChart item shape for bar coloring

§05 flags that the precise data-flow point where each chart item's enum_type is retained (or needs threading through) was not traced to the statement level during planning — the surrounding code (badges, filters) already keys off enum_type per row, so this is expected to be a small addition, but it is called out here rather than asserted with false confidence, per this repo's verify-before-claim rule.
