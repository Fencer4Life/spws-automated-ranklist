Decision note · frontend · database · daily workflow · 6 Oct 2026

Every public page load asks for a write it is not allowed to make

Each public page load, on the github.io app and on every WordPress page, sends POST /rest/v1/rpc/fn_refresh_active_season as anon. It gets 401 and the browser logs it. Since 23 July (ADR-083) that call does nothing. As a result, no scheduled process moves the active season when its dates pass.

Superseded 6 Oct — V (computed on read) chosen instead branch claude/active-season-401 from origin/main ae2a7a1b CERT 401 · PROD 401 · LOCAL anon EXECUTE = false

Superseded on 6 Oct 2026: option V, not D

After this note, the user asked for a better design. The decision is active-season-computed-on-read-2026-10-06.html: the database computes the active season on every read, so no daily refresh is built. The stored flag, its trigger and fn_refresh_active_season() are removed, and tests set today with spws.today. ADR-031 carries the amendment (2026-10-06). This page stays as the incident record: the observations, the grant history and the call sites below are still accurate. Its recommendation (D), its TDD plan and its draft amendment are not.

01 · Decide this first

Two defects, one call site

1 × The visible defect: a 401 on every public page load

App.svelte:697 calls refreshActiveSeason() in init(), which runs on every non-demo mount. Both shells run it: the github.io index.html, and <spws-calendar>, because CalendarElement.svelte imports App.svelte. Anon lost EXECUTE on 23 July (20260723000001_adr083_deny_by_default_grants.sql L186). The JavaScript discards the failure, but the browser still logs Failed to load resource … 401. JavaScript cannot suppress that line.

2 ~ The latent defect: nothing moves the active season when the date passes

The trigger trg_season_refresh_active fires only on INSERT, DELETE or a change of dt_start/dt_end on tbl_season. Nothing else calls the function: no workflow, no Python, no pg_cron. The only remaining date-driven path is an App mount whose supabase-js client already holds an authenticated session (unverified how often that happens; see 07). CERT and PROD are both on SPWS-2026-2027 (13 Jul 2026 to 15 Jul 2027), and no later season exists yet. Suppose SPWS-2027-2028 is created in advance, as 2026-2027 was (seeded 28 Jun 2026). Then on 16 Jul 2027 nothing moves the flag on either environment.

✓ Recommendation: D

Since 23 July the browser call has done nothing, so removing it changes no behaviour and removes the 401. That fixes only defect 1. Defect 2 is the one with consequences. The active season sets the ranklist's default season, rolling carry-over (ADR-018), the calculator's season (fn_public_scoring_params with a NULL season), the Telegram and ingestion scope, promote.yml, the daily close, and promote_calendar's same-season guard. That state should not depend on who happens to visit or sign in. Option C would fix it by making a public SECURITY DEFINER write part of the design, which is exactly what ADR-083 §4 forbids. Option B fixes it only with a human remembering to sign in, on two environments. Option D keeps ADR-083 intact and makes ADR-031's promise true again: create the season with correct dates, and activation is automatic.

Q2 · Where does the daily refresh run?

VariantWhat it means
D1 (recommended)A new step at the end of .github/workflows/event-close.yml ("Daily Event Close", cron 0 4 * * *, concurrency group prod-write). It runs after "Close events" with if: ${{ !cancelled() }}, so a failed close does not block it, and the existing "Notify failure" step still alerts. It calls a small module that uses the ManagementTransport close.py already uses (SUPABASE_ACCESS_TOKEN), so no new secret is needed. It honours the workflow's DRY_RUN. Running it after the close lets the close treat the old season's last events one final time before the flag moves.
D2pg_cron in a migration. Rejected. The project has no pg_cron today (available but not installed on LOCAL; not checked on CERT/PROD). It would start a job on LOCAL, which breaks planning rule 4, and its effect on the posture gate on hosted Supabase is unverified.
D3A new dedicated workflow that calls the RPC over PostgREST with each environment's service-role key. Viable. It costs a new workflow, a catalog row and secret wiring, for one statement a day.

Recommendation: D1. It adds the fewest new parts and reuses a credential path that already writes PROD every day.

Q3 · Announce a change of active season on Telegram?

Recommendation: yes, but only when the active season actually changes on an environment. That happens about once a year, and it is the moment CERT and PROD could disagree. The module reads the active code before and after the refresh and sends one line, for example "Active season CERT: SPWS-2026-2027 → SPWS-2027-2028". It sends nothing otherwise. Planning rule 8 says a new Telegram-fired event updates the GAS /help text. Whether a pure notification counts is unverified, so check at implementation. If you answer no, drop AS31.SCHED.03.

02 · What the system does today

The function, its callers, the failure, the grants

The function

fn_refresh_active_season() (supabase/migrations/20260411000003_auto_active_season.sql L19) is LANGUAGE plpgsql SECURITY DEFINER and returns VOID. It picks the season with dt_start <= CURRENT_DATE <= dt_end, or else the nearest future season, or else none. It then runs UPDATE tbl_season SET bool_active = FALSE WHERE bool_active = TRUE (L42) and UPDATE … SET bool_active = TRUE WHERE id_season = v_target_id (L44). The database runs in UTC (LOCAL SHOW timezone = UTC).

What the frontend does with the failure

  • refreshActiveSeason awaits getClient().rpc('fn_refresh_active_season') and ignores the result. postgrest-js 2.98.0 resolves with { error }; it throws only after throwOnError() (dist/index.mjs L48, L143). So the 401 resolves normally, and the .catch(() => {}) at L697 never runs.
  • Nothing uses the result. init() then calls fetchSeasons() and selects seasons.find((s) => s.bool_active). When the call succeeds, its only effect is that this read sees a fresh flag.
  • No test checks the call. Ten Vitest files only mock it to vi.fn().mockResolvedValue(undefined): CalendarEmbed, DrilldownRankedSeason, AppShell, SeasonRulesLink, DrilldownModeSwitch, SiteChrome, AdminScoringEngines, CalendarBoundary, identity-integration and env-toggle. No e2e spec checks console errors.

Draft ADR-031 amendment, for sign-off before it goes to disk (planning rule 6)

Amended 2026-10-xx. The browser no longer refreshes the active season. ADR-083 (23 Jul 2026) revoked anon's EXECUTE, so from then on the "frontend refresh on app load" returned 401 on every public page load and refreshed nothing. Date roll-over had no automatic path left. fn_refresh_active_season() now runs daily on CERT and then PROD as a step of Daily Event Close (event-close.yml, 04:00 UTC), after the close, even if the close fails.
