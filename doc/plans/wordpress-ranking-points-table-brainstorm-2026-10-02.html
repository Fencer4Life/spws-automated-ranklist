One thing checked in GitHub's documentation, which shapes §18

This repository belongs to a personal account. On such a repository a collaborator can read and push, but only the owner can change settings, secrets, environments and Pages, or invite collaborators. A second person added as a collaborator could therefore keep releasing and approving PROD, but could not rotate a secret or change a setting. Full continuity needs one of two things: the repository moved into an organisation with two owners, or a sealed break-glass record for the owner account. §18 covers both.

01 · Q8 · Decided 3 Oct: A

GitHub Pages goes live before PROD is approved: a rule, not a workflow change

A release builds once, then deploys GitHub Pages and CERT at the same time; only the PROD database waits for the approval. The WordPress pages load their code from Pages, so between the two, PROD's pages run new code against the old PROD database. In the last real release (run 36986509618, 2 Oct) the gap was 84 seconds.

The rule, now part of the release procedure (§12) and of ADR-108

  1. Code that needs a new database object ships in the release after the one that creates it: the database first, the code that uses it next.
  2. PROD is approved within minutes of CERT, and never left waiting.

This plan follows it: it changes no database object.

06 · Walk-throughs

Six scenarios, and the three environments side by side

  1. A fencer, on a phone. weteraniszermierki.pl → KLASYFIKACJA → Ranking. WordPress serves the page body, the browser loads main.ce.js from Pages, and the element reads PROD. The list shows. ☰ → Kalkulator punktów opens /kalkulator-punktow/ in the same tab. The bar draws, the frame loads embed/kalkulator-punktow.html from Pages and reports its height, and the page scrolls as one. Tapping the logo returns to weteraniszermierki.pl.
  2. An admin. /ranking/?admin=1 → modal → password → TOTP → the list. ☰ → Wydarzenia → an event → "use SPWS registration". The link is built from the asset base, so it points at the PROD register.html on Pages. A dispatch button calls the PROD Edge Function, which answers any origin today, so GitHub Actions runs against PROD.
  3. A release while someone is reading. Pages replaces main.ce.js at the same address. An open page keeps the old code until it is reloaded. Pages serves the file with max-age=600, so every visitor has the new code within 10 minutes.
  4. An old bookmark. fencer4life.github.io/…/kalkulator-punktow.html now shows the CERT copy with the TEST ribbon. The numbers come from CERT's season settings, normally the same as PROD's; the ribbon says it is a test.
  5. Wrong order. If a page were published with chrome="site" before the release, the old bundle would treat it as full, and its drawer links would lead to addresses that do not exist on WordPress. The order in steps 11 and 12 prevents this; step 12 starts only after step 11 has been checked.
  6. GitHub Pages is down. Every WordPress page shows an empty screen, because the theme is hidden and the content never arrives. There is no fallback today (§17).

How a change reaches PROD

  1. Work on a branch. AI agents each work in their own worktree (scripts/start-agent-worktree.sh, doc/claude/session-start.md). A person working alone can use any branch.
  2. Write the tests first, then the code. The change is ready when this exits 0: 
    scripts/preflight.sh   # all gates; pgTAP needs Docker
  3. Bring the docs index and the code graph up to date, then commit explicit paths only: 
    python3 tools/docs-search/ingest.py
scripts/refresh-graph.sh
git add <each path> && git commit
  4. Push main. This is the release trigger. With agents, run this from the registered integration checkout (git config spws.integrationWorktree): 
    scripts/integrate-agent-branch.sh claude/<task>
scripts/preflight.sh
git push origin integration/main:main
    Working alone: merge into main and git push origin main.
  5. Watch CI, then Release. 
    gh run list --workflow release.yml -L 3 \
    --repo Fencer4Life/spws-automated-ranklist
gh run watch <run id> \
    --repo Fencer4Life/spws-automated-ranklist
    If the change touched only documentation, the gate stops the release on purpose (ADR-094).
  6. Approve PROD. GitHub → Actions → the Release run → "Review deployments" → tick production → Approve. Only a required reviewer can do this, and today that is Fencer4Life alone (to add a second: §18, step 1). Approve within minutes of CERT, because Pages is already live (Q8).
  7. Check with §14.

Rules that have cost real failures

  • Never edit a migration that has been deployed. Add a corrective one (ADR-011).
  • Never copy a list of gates into a plan. scripts/preflight.sh is the list.
  • Never git reset --hard a working tree with changes in it.
  • The Q8 rule: code that needs a new database object ships one release after the migration, and PROD is approved within minutes of CERT.
  • A manual "Run workflow" on Release skips CI. The security posture check still runs inside both deploy jobs.

Read, change, create

# read a page (never needs confirmation)
scripts/wp_publish_page.py get --slug znajdz-zawody --content-out /tmp/znajdz-zawody.html

WP_PUBLISH_CONFIRM=yes scripts/wp_publish_page.py update --page-id 13472 \

WP_PUBLISH_CONFIRM=yes scripts/wp_publish_page.py create --slug ranking --title Ranking \

WP_PUBLISH_CONFIRM=yes scripts/wp_publish_page.py update --page-id <id> --status publish

# hide a broken page at once
WP_PUBLISH_CONFIRM=yes scripts/wp_publish_page.py update --page-id <id> --status draft
  • The bundle ships before the page. Release first, check, then publish the body (ADR-090).
  • Change bodies only with the script. Nobody has tested the block editor on these bodies. The rendered page also differs from the stored body: WordPress inserts <p> tags into the style block when it renders.
  • The script works around this host's quirks (see its header):
    • the host refuses Python's default User-Agent;
    • it silently redirects the standard library's single-quoted XML declaration;
    • WP_USER is the account name, not the password label.
  • The page template cannot be set over XML-RPC, and neither can menu items. Both are protected meta.
  • Caching. Pages serves main.ce.js with max-age=600, so a release reaches every visitor within 10 minutes. The bundle's address is fixed by name, and the build fails if that name would change.

18 · Manual · Deferred by decision (Q7 = C, 3 Oct)

Adding a second administrator: everything needed

Today you are the sole administrator. This is the complete procedure for the day a second person joins, or for whoever has to take over. Follow it top to bottom. Each step says what it grants, what it does not grant, and how to check it worked. Record people's names in §10, never their passwords.

Read first: every admin account has full power

The ranking application has no roles. Every account that can sign in at ?admin=1 can edit fencers, results and scoring settings, and can start workflows (ADR-016; the admin guide, Fact 2). The same holds for the Owner role in Supabase and the Administrator role in WordPress. Only add a person you trust with production data.

Before you start, the new person needs

  • a GitHub account with two-factor authentication on;
  • an e-mail address of their own (it becomes their Supabase and admin login);
  • an authenticator app on their phone (TOTP), and a password manager;
  • a Telegram account;
  • a computer, if they will change code (step 9).

The steps, in order

  1. GitHub: collaborator and PROD reviewer.
    • Repository → Settings → Collaborators → "Add people" → their GitHub user name. They accept the invitation from their e-mail or github.com/notifications.
    • Settings → Environments → production → Required reviewers → add them → "Save protection rules". One approval is enough, and up to six reviewers can be listed. Leave "Prevent self-review" off, so a person working alone can approve their own push.
    Grants: pushing to main, which starts a release, and approving PROD deploys.
    Does not grant (GitHub's rules for a personal-account repository): settings, secrets, environments, Pages, inviting collaborators or transferring the repository. These stay with the owner.
    Check: on the next release, "Review deployments" appears for them.
  2. Supabase: a second Owner, and MFA for both.
    • Organisation "SPWS" → Team → Invite → their e-mail, role Owner. The invitation link is valid for 24 hours. An Administrator can do everything except change organisation settings, transfer projects or add Owners.
    • Both of you: account → Security → turn on MFA. Today the owner account has none.
    Grants: both projects (CERT and PROD), the API keys, Edge Function secrets and Auth users.
    Check: they open spws-ranklist-cert and spws-ranklist-prod.
  3. Admin accounts inside the application, one on CERT and one on PROD. Follow doc/plans/admin-user-creation-guide-2026-07-23.html exactly. Authentication → Users → Add user, with Auto Confirm User ticked; the person then enrols TOTP on their first sign-in in the app, not in the dashboard. CERT and PROD have separate user databases, so one person needs two accounts.
    Check: they sign in at fencer4life.github.io/spws-automated-ranklist/?admin=1 (CERT) and, once this plan has shipped, at weteraniszermierki.pl/ranking/?admin=1 (PROD).
  4. WordPress: an Administrator account.
    • wp-admin → Użytkownicy → add a user with the Administrator role.
    • To publish with the script, they create their own application password (Profil → Hasła aplikacji). In their .env, WP_USER is their account name and WP_APP_PASSWORD is that password, in quotes.
    Check: scripts/wp_publish_page.py get --slug znajdz-zawody prints the page id 13472.
  5. Telegram: alerts and commands for two people.
    • Today one chat, TELEGRAM_CHAT_ID, receives every alert. It is also the only chat whose commands the Apps Script obeys (doc/gas/Code.gs L98 and L114).
    • Without changing code: create a private group with both of you and add the bot. In BotFather send /setprivacy → choose the bot → Disable, then remove the bot from the group and add it back. Telegram requires that re-add, and our commands are plain words such as status, which a bot in privacy mode never receives in a group.
    • Find the group's chat id, a negative number. One way: stop the Apps Script's 5-minute trigger, send a message in the group, call the bot's getUpdates once, then start the trigger again.
    • Put that id into the GitHub secret TELEGRAM_CHAT_ID (owner only) and into the Apps Script property TELEGRAM_CHAT_ID.
    • Bot ownership itself moves only by a full hand-over: BotFather → /mybots → the bot → Transfer Ownership. This needs two-step verification on the owner's Telegram account for at least 7 days.
    Check: both receive the next release alert, and status sent in the group gets an answer.
  6. Google: the Apps Script. The script project lives in spws.weterani@gmail.com. Share the project with them as an editor (script editor → Share), or arrange access to that account under the association's own rules.
    Check: they can open the script's project settings and see the property names in §11.
  7. Tokens that belong to a person. These keep working while your accounts exist. They only need replacing if your account goes away.
    • SUPABASE_ACCESS_TOKEN, the GitHub secret the release uses: a personal token of a Supabase account. A second Owner creates their own (Supabase → Account → Access Tokens), and the GitHub owner puts it into the secret.
    • GH_DISPATCH_PAT (Edge Function secret, CERT and PROD) and GITHUB_PAT (Apps Script property): today they are the owner's tokens. A fine-grained token cannot reach a repository where its user is only a collaborator, so a collaborator's replacement must be a classic token with the repo scope, which is what GitHub's workflow-dispatch endpoint requires. Set it with supabase secrets set GH_DISPATCH_PAT=… --project-ref <ref> for each project, and in the script's properties.
  8. Hosting and DNS. Find out who holds the DirectAdmin login and the domain registration for weteraniszermierki.pl, when it renews and who pays. Record the names in §10 and §16. Without this, a broken DNS record or a lapsed domain cannot be repaired by anyone on this project.
  9. Their computer, if they change code. Follow doc/handbook/operations/local-development.html: Python 3.11 or newer, Node for the frontend lockfile, Docker and the Supabase CLI, plus gh. Then create .env with the 14 names in §11, using their own WordPress and Supabase credentials where they have them. Run scripts/preflight.sh once to confirm the set-up works.
  10. Break-glass for the owner accounts. This is the only thing that fully covers "the owner is gone" while the repository stays personal. Write down where the recovery of each owner account lives: the password and the 2FA recovery codes of GitHub Fencer4Life, and of the Supabase owner if step 2 was skipped. Keep it outside this repository, for example in a sealed envelope held by the SPWS board, or a password manager's emergency access.

What the second person can do afterwards

CanCannot, while the repository stays personal
  • Push to main and release.
  • Approve PROD deploys.
  • Administer CERT and PROD in Supabase, including keys and Edge Function secrets.
  • Sign in as an admin on CERT and PROD.
  • Publish WordPress pages and edit the menu.
  • Receive alerts and send Telegram commands.
  • Change a GitHub secret, setting, environment or Pages.
  • Add another collaborator.

Only the owner account can do these. Lifting that limit means moving the repository into a GitHub organisation with both of you as owners (Q7, option B). GitHub keeps the secrets and redirects the repository's address on a transfer, but it does not redirect the Pages address. So every WordPress page body, the bundle address in them and every registration link already sent out would change at once. Plan that as its own change.

Removing a person later

Do the steps in reverse:

  • remove them as a GitHub collaborator and as a reviewer;
  • remove them from the Supabase organisation;
  • delete their two admin users in Authentication → Users;
  • delete their WordPress user, or change its role;
  • remove them from the Telegram group and the script's sharing.

Then rotate every secret they could read, following §11 and §16.
