PROD on WordPress · Ranking + Points table · Brainstorm and advice · 2 October 2026

One responsive version, one page per surface, full-screen

You asked whether we need two versions, one tied to the WordPress menu for computers and one with the hamburger for phones. My advice is no. Build one version that adapts by screen width. Give each surface its own full-screen page on weteraniszermierki.pl, and keep the hamburger and the admin sign-in in the GitHub Pages app, where they already work.

01 · Your question

Two versions? No. One version that adapts to the screen.

The split you describe already exists, and the WordPress theme does it for us. Its menu is a standard Bootstrap navigation bar (navbar-expand-lg). On a computer it shows as the horizontal red menu. Below 992 px it collapses into its own "Menu" hamburger. I read this from the live site's HTML today.

Our pages hide that theme menu so they can be full-screen. Inside the page we show one slim bar, and CSS changes how it is laid out by width. It is the same code at the same address, with a different arrangement on a phone than on a computer. That is how the calendar at /znajdz-zawody/ has worked since September.

! Why two versions would cost more than they give

  • Device guessing goes wrong. Tablets, rotated phones and narrow desktop windows land on the wrong version.
  • Shared links break. A fencer sends the ranking link from a phone and the board member opens the phone version on a computer, or the other way round.
  • Everything is tested twice, and every fix has to be made twice.

☰ The hamburger does not go away

It stays in the GitHub Pages app, which is the admin app. Admins sign in there today with ?admin=1, and the admin section appears in the hamburger drawer. ADR-090 §3 already decided that administration stays there and that the WordPress pages never offer the sign-in. The public never needed the hamburger. It only existed so one app could switch views, and on WordPress each view is its own page. So the hamburger does not need to come to WordPress at all.

Every public page gets the same treatment the calendar has:

  • One slim bar on top. It holds the SPWS mark, which links back to weteraniszermierki.pl as you suggested, the page name in the active language, and the PL/EN toggle. Decision D1 below is about adding a page switcher to this bar.

  • No hamburger and no admin sign-in. ?admin=1 is ignored on WordPress pages.

03 · "Full-screen always"

What full-screen can and cannot mean on a web page

✓ Achievable, and already proven: the page gets the whole browser window

No site header, menu, page picture, title or footer. Our content starts at the top edge. This is what the calendar and the FTL export page do today.

✗ Not achievable: the browser's own full-screen mode, which hides the address bar

On an iPhone, Safari lets only video go full-screen, not a web page. On a computer, full-screen needs a click on every visit and Esc ends it. ADR-090 §5 records that a full-screen button was built for the calendar and then removed, because it added nothing to a page that already fills the window.

The phone trick that does give the most room: the ranking and the points table should scroll as normal pages. Phone browsers then shrink their address bar while you scroll, which is the most screen a web page can get on a phone. The calendar is the exception. Its drum is built from fixed geometry, so it keeps a fixed full-height box, and it stays that way.

05 · Then these three

Three more decisions, each with a recommendation

You can take all four recommendations in one reply: accept all. Or reply with the ones you want to change.

D2 · How does the Points table get onto WordPress?

The Points table is not part of the app. It is a standalone 106 KB document, tabela-punktacji.html, with its own styles, its own PL/EN switch, a print layout, CSV export, and a script that reads the scoring parameters from the database. The ranking and calendar mechanism, a custom element in the shared bundle, does not cover it.

Recommendation: D2 P1.

D3 · Where does the Ranking live?

Today /klasyfikacja/ holds the age-category table and 30 links to SharePoint spreadsheets, one for each sub-ranking (3 weapons × 2 genders × 5 categories). The live ranking replaces exactly that, with one page and filters.

  • R1 · Replace the body of /klasyfikacja/ recommended. The address, old bookmarks, search results and the existing "Klasyfikacja → Klasyfikacja polska" menu item all keep working, and nobody has to touch wp-admin. The old body is kept as a reference copy in doc/wordpress/, so it can be restored with one XML-RPC call. Before the swap, the ranking is checked on an unlinked page.
  • R2 · New page plus a new menu item, old page left alone. This is ADR-090 §8's original position. You would create the menu item in wp-admin, because XML-RPC cannot (proven on 5 Sep). Old and new would run side by side.

The Points table needs one menu item either way, under Klasyfikacja. You create it in wp-admin, which takes about two minutes, and I write down the exact clicks. Recommendation: D3 R1.

D4 · What does the public see at the github.io address afterwards?

The GitHub Pages app opens on CERT, the test database, because it holds both environments. Once WordPress is the official address, someone with an old bookmark sees test data and has no way of knowing it.

  • G1 · A one-line notice for anyone not signed in recommended. It reads: "Test environment. The official ranking is at weteraniszermierki.pl/klasyfikacja", with a link. The app is otherwise unchanged, and admins never see the notice.
  • G2 · Leave it as it is.
  • G3 · Send everyone who is not an admin to WordPress automatically. This is the most drastic option. It also hides the CERT preview that you and testers use without signing in.

Recommendation: D4 G1.

06 · Measured in the code today

What has to change. All of it is small, but two items matter.

1 <spws-ranklist> still mounts the full app, admin sign-in included

frontend/src/ce/RanklistElement.svelte passes neither chrome nor view nor asset-base, so it gets the defaults: header, hamburger, drawer, and ?admin=1 honoured. Embedded as it is, it would put the admin sign-in on the association's site, against ADR-090 §3. The fix is the interface the calendar already has (chrome="none", view="ranklist", asset-base), with a test that fails first.

2 The Points table picks CERT whenever both environments are configured

Its loader reads supabaseCertUrl || supabaseProdUrl. This is the same "CERT wins silently" pattern as the 17 August registration defect and the calendar defect that ADR-090 §2 fixed in the app. The WordPress mode must read PROD and nothing else, and a test must pin that.

  • The bar's title is fixed to "Znajdź zawody" (embed_page_title in App.svelte). It has to follow the page: Ranking, Znajdź zawody, Tabela punktacji.
  • The ranking element needs its own height rule. It should be a block with natural height, so the page scrolls (§03). It must not use the calendar's fixed 100dvh box.
  • The "Reguły rankingu" pill is position: fixed. If any theme wrapper has a CSS transform, the pill pins to that wrapper instead of the screen. This gets checked on the real WordPress page at phone and computer width before the page goes public.
  • The annex has no SPWS mark and no route home. In WordPress mode it gets the same bar, and its links open in the top window, not inside the frame.
  • If D1 is B: one switcher component, two locale keys per language, and tests that pin the link list and the mark's target, the way CalendarEmbed.test.ts pins the calendar's.

07 · Honest gaps

Things I have not verified, and gates outside the code

  • SPWS Board approval of the ranking on the site. ADR-090 left this open, with a decision expected in the week of 8 September. I am assuming it has been given, because you are asking for the ranking. Please confirm in your reply.
  • The Points table refuses to render unless the 2026/27 engine is the joined engine. Its script checks the engine code returned by fn_public_scoring_params. I have not checked whether PROD's 2026/27 configuration carries that engine yet. I will check it read-only at build time. If it does not, the Points table page waits for ADR-104 steps 11–12, and the Ranking goes first on its own.
  • The annex is noindex "until adoption" (ADR-102). Publishing it on the association's site is the point of adoption. Is it adopted? If so, the noindex comes off on the WordPress copy only.
  • Draft pages cannot be viewed without a wp-admin login, as noted in the 5 September plan. That is why each page is checked on an unlinked published page first (§08).

08 · Order of work, once decided

How it would go live

One rule decides the order: no live page may link to a page that is not published yet, and no page goes live before the code it needs has been released. The switcher therefore shows only the pages that its WordPress page lists in an attribute. Releasing the new code changes nothing on the live calendar until its page body is updated, which is the last step.

  1. Implementation plan written as HTML with tests first (RED→GREEN), including the documentation coherence gate and the ADR-090 amendment draft for your sign-off.
  2. Build and release. The bundle keeps its stable address (assets/main.ce.js), and scripts/preflight.sh exits 0 before the push.
  3. Ranking on an unlinked page, checked at 375 px and at computer width. Then you approve it by name, and it is swapped into /klasyfikacja/ (R1).
  4. Points table page, checked the same way. You approve it, and you add the menu item in wp-admin.
  5. Calendar page body gains the switcher attribute last, once the other two pages are live.
  6. A final check of all three pages on a phone and a computer, followed by a report.

10 · Boundaries

Not in this plan

  • The top-level "Kalendarz" menu item still points at the hand-typed /kalendarz-2/, while the live calendar sits under LINKI. Pointing it at /znajdz-zawody/ is a separate decision for you, and it takes one minute in wp-admin.
  • The points calculator (ADR-085). The annex now contains a single-result calculator, so a separate WordPress page for the calculator looks redundant. I suggest leaving it out.
  • Moving admin off GitHub Pages. It is not needed for this, and ADR-090 §3 keeps it there.
  • Shareable filter links, for example a link that opens directly on women's épée V2. These could be added later. Nobody has asked for them.
  • Spotted in passing: the live "Członkostwo" menu item has the address http://czonkostwo. It opens a dropdown on a computer, so nobody notices, but the address is broken. It can be fixed in wp-admin.
