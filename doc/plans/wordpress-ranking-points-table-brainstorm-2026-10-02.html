02 · Point 1 · Navigation

The drawer, not tabs, not a logo menu, not a modal

The duplicate came from rev 1's option B. The bar showed the page title "Ranking", and the tab strip beside it showed "Ranking" again as the active tab. A title plus tabs only works when the title names the site, not the page. Our bar names the page, so the tabs repeated it.

▸ Measured: on phones the flags move into the drawer

On a 360 px phone the bar is already full. In the live github.io app, „Znajdź zawody" pushes the flags onto a second row today, and „Ile punktów za wynik?" does the same at 375 px. On the live WordPress calendar, adding a ☰ to the bar would clip "Find competitions" by 25 px and „Tabela punktacji" by 11 px.

With the flags moved into the drawer on phones, which frees 82 px in the WordPress bar, every page title fits on one line at 360 px, „Ile punktów za wynik?" included. On a computer the flags stay in the bar. Switching language on a phone costs one extra tap; most visitors read Polish.

03 · Point 2 · Admin

A bookmark for two or three people, in no menu

Once the environments are separated (§04), PROD needs its own admin page. Some admin work exists only on PROD, by design:

  • the registration switch bool_use_spws_registration, which PROD owns in both directions (handbook Event status lifecycle);
  • registrations and their identity proposals, because register.html writes to PROD only (ADR-079, amendment of 17 Aug);
  • corrections made on PROD to fees, links and the payment account, which the daily sync then leaves alone (ADR-086).

Today these are reached by switching the github.io app to PD. Rev 2 gives them a page of their own:

  • Where: an unlisted file on the Pages host, not a WordPress page. The bookmark is fencer4life.github.io/spws-automated-ranklist/<name nobody guesses>.html. It is a PROD build, linked from nowhere, with noindex in its own <head>. Rev 2's first draft put it on WordPress, and checking the live site overturned that, for two reasons:
    • WordPress would publish it. The site's built-in sitemap, wp-sitemap.xml, lists every published page. Today that includes the token-gated /pliki-zasilajace-xml-ftl/. The site has no SEO plugin, so one page cannot be marked noindex. An "unlisted" WordPress page would sit in the sitemap for anyone to find.
    • The registration links would break. When an admin ticks "use SPWS registration", EventManager.svelte L703–708 builds the fencers' link as new URL('register.html', this page). On a WordPress page that points to a register.html that does not exist there. On the Pages host it keeps pointing at the real PROD form, with no code change.
  • It also keeps ADR-090 §3 as it is: administration stays off the association's site.
  • What it shows. The same full-screen app as the public pages, plus a Zaloguj entry at the foot of the drawer. After sign-in (password and TOTP, ADR-016), the admin section appears in the drawer as it does today, and a red PROD tag sits in the bar so nobody forgets which database they are changing.
  • What protects it. Sign-in and the server-side grants (ADR-083), not the hidden address. The address only keeps the sign-in off the public pages. PROD's dispatch function already answers any origin (access-control-allow-origin: *, probed today), so the admin buttons work from this file.
  • "Keep it showing", as I read it. The admin UI stays fully available: hamburger, drawer, sign-in and the admin section, just not advertised. If you meant a visible link somewhere on the public pages as well, decision W2 has that variant.
  • CERT admin stays where it is: the github.io app with ?admin=1, now CERT only.

04 · Point 3 · Separate them permanently

PROD on WordPress, CERT on GitHub Pages, and a yellow ribbon

Agreed, and it is the plan you set at the start. The switch was only ever compensation for serving both environments from one host. Every page on github.io gets the ribbon. WordPress pages have no ribbon and no switch.

The ribbon's link points visitors to the official site. It stays on screen and does not scroll away: on github.io, being told it is a test copy matters more than 20 px.

! Three things the split must not break

  • "Promote to PROD" still needs to read PROD. The CERT app decides each season's button by reading PROD (refreshPromotionState, App.svelte L1455, through fetchProdSeasonCodes). Today that read and the switch share one flag, dualEnv. The split keeps the read-only PROD connection for this one purpose and removes the switch.
  • Dispatched jobs name their target from the page, not a switch. EventManager.svelte L567–587 sends target: activeEnv. On github.io it becomes always cert, and on the PROD bookmark always prod.
  • register.html stays PROD and gets no ribbon. It is the public PROD form that fencers reach through each event's registration link, and release.yml L146 gives it PROD only. It is a PROD form that happens to be served from the Pages host, not part of CERT.

GitHub Pages stays the file host. What a visitor sees as a site at github.io is CERT, under the ribbon. Four kinds of PROD files are served from the same host. None of them is a page a visitor browses to, and none carries the ribbon:

  • assets/main.ce.js, which the live WordPress calendar already loads;
  • the PROD builds of the calculator and the annex, which WordPress frames (W5);
  • register.html;
  • the unlinked PROD admin bookmark (§03).

ⓘ Zasady: Załącznik nr 1

The numbers in the mock are placeholders. The real ones come from the shared scoring module, as today.

  1. The ranklist's bar replaces the banner: ☰, the SPWS mark (home), the title, and the round flag pill instead of the text PL/EN switch. On a phone the flags sit in the drawer, as on every page (§02). On WordPress it opens the same drawer as the other pages.
  2. The title is the question: „Ile punktów za wynik?" The English is "How many points?", because the full "How many points for a result?" is clipped by 36 px at 360 px even with the flags moved into the drawer. The subtitle under the switches goes. It was the question without its "?", so the title now carries it.
  3. The calculator comes first, straight under the bar. Its inputs use the ranklist's filter style: small uppercase labels and rounded fields. "Stawka łączona" becomes the same blue segmented control as Ranking/PPW, and so does the rank coefficient.
  4. The result panel turns soft blue instead of pink with a red edge. In the ranklist, red appears only in the logo, and here a red result looked like an error.
  5. The premium table uses the ranklist's table style: a grey header row and plain rows.
  6. The rest folds away: the premium table on a phone, the step-by-step simulator, and "W skrócie" become collapsible sections below. The full rules leave this page; the floating pill at the bottom, the same pill the ranklist uses for its season rules, opens the annex.
  7. The annex takes the same bar and colours, so all four pages look like one product. Its content and order stay as reviewed. Only its bar, controls and colours change.

The maths does not move (ADR-102, scoring family)

Only markup and CSS change. Both pages keep computing through the one generated module, scoring.ts → build-scoring-pages.mjs. The shared bar and styles are generated into both pages the same way, between markers, so the look cannot drift either. Nothing is ported, pasted or rewritten.

08 · Measured in the code today

What has to change

  • RanklistElement.svelte has none of the calendar's options (chrome, view, asset-base), so as an embed it would mount the whole app with its defaults. It gets the calendar's interface, plus a drawer whose entries are WordPress links.
  • dualEnv does two jobs (App.svelte L503): it shows the switch (L114, and CalendarView.svelte L67) and it enables the PROD read for promotion state (L1456, L1480). It splits into "show switch", which is removed, and "can read PROD", which stays. env-toggle.test.ts retires with the switch.
  • release.yml gives index.html both connections (L121–123) and the static pages PROD only (L159–162). It changes to CERT for every github.io page, and PROD for the WordPress builds and the embed bundle's pages.
  • The bar's title is fixed to „Znajdź zawody" (embed_page_title). It follows the page instead.
  • The calculator source: .document-head (banner), .lead (subtitle), .lang-switch (text switch), .result (red accent, L120). These are replaced through the shared generated partial.

09 · Paper trail and order

ADRs, documentation, and the order of work

  • New ADR-108, "The environments split by host". PROD on WordPress, CERT on GitHub Pages, the switch removed, the ribbon, the read-only PROD connection kept for promotion state, and dispatch targets fixed per page. It also covers the PROD files the Pages host keeps serving: the embed bundle, the framed builds, register.html and the admin bookmark.
  • ADR-090 amendment. The drawer on WordPress pages, with the flags in the drawer on phones. Full-window frames for the static pages. /klasyfikacja/ modified (W6). §3 (admin stays off the association's site) is unchanged.
  • ADR-015 (the drawer), ADR-092 and ADR-102 (the static pages' look and WordPress destination; the maths untouched), and ADR-085 (the calculator stays).
  • Handbook: subsystems/frontend-and-automation.html, product/product-surfaces.html, operations/environments-and-release.html, reference/workflow-catalog.html. Reference copies of each WordPress page body go in doc/wordpress/, with the anon key redacted.
  1. On your decisions, an implementation plan as HTML: tests first, the documentation coherence gate, and the ADR-108 and ADR-090 drafts for sign-off.
  2. Build and release. The bundle keeps assets/main.ce.js, and scripts/preflight.sh exits 0 before the push.
  3. The PROD admin bookmark first, checked by you while the CT/PD switch still exists as a fallback.
  4. The Ranking, the calculator and the annex, each on an unlisted page, checked at 375 px and at computer width. You approve each by name, and then it goes live.
  5. The calendar page gains the drawer, and the github.io release removes the switch and adds the ribbon. This comes last, so nothing is lost while the rest is checked.
  6. A final check of every page on a phone and a computer, followed by a report.
