01Why I did not just run it

The repository has a script that runs SQL against CERT and PROD, and it would have executed this migration without complaint. Its own governing procedure forbids exactly that:

cloud-db-ops, “Scope — data, not schema” Schema changes belong in supabase/migrations/ and must flow through CI so CERT and PROD converge and the fingerprint gate stays meaningful. Applying DDL by hand desynchronises the environments and silently invalidates the release pipeline’s central check. If you find yourself reaching for ALTER TABLE here, stop and write a migration.

That is not bureaucratic. release.yml computes a schema fingerprint from a clean LOCAL stack and then refuses to deploy unless CERT and PROD hash to the same value. A hand-applied ALTER TABLE would make the environments correct and the gate blind — and the gate is the only thing standing between a schema drift and a silent production divergence. It is also the check that caught the 25 June 2026 PROD-deploy failure.

So the migration reaches CERT and PROD one way: scripts/apply-migrations.sh, called only from release.yml, which triggers on a successful CI run on main and checks out main.

That last row is the one that matters. Scheduled workflows only run from the default branch, so the daily PZSz scrape does not exist until the merge — and the morning after it, six PZSz events appear on the public PROD calendar without anyone pressing anything. That may be exactly what you want. It is not what “apply the migration” says.

04The one line that worries me

Unverified against your runner

queue: max is now on eight jobs, six of which already work today.

The approved plan called for it, measured against GitHub’s documentation on 3 September. I could not verify it — there is no actionlint on this machine and CI does not lint workflow files. If GitHub does not accept the key, every workflow carrying it becomes an invalid workflow file, and that now includes evf-sync.yml, promote.yml, promote-season.yml, evf-parity-sweep.yml, ftl-seed.yml and recompute-drain-prod.yml — the working EVF production pipeline.

The plan accepted this risk when it applied to one new job, where the worst case is that the new thing does not start. Extending it to the whole prod-write group was correct — the setting is per-job and a member without it can cancel a sibling’s pending promote — but it also widened the blast radius from the new feature fails to the existing EVF pipeline fails.

There is a free way to settle it Push the branch and manually dispatch pzsz-sync.yml from the branch. Nothing scheduled runs from a non-default branch, so the six existing workflows are untouched. If queue: max is invalid, the dispatch fails instantly with a syntax error and we learn it at zero cost. Expect the run to then go red at the CERT query anyway — id_pzsz_event does not exist there yet — which is harmless and, in fact, confirms the ordering the ADR insists on: schema first.

05A git detail you should know

Local main and origin/main have diverged, and it is not because of me:

origin/main   db2c2d0 → ba5cf43 → 6fcb337   (two CI reconcile-log commits, [skip ci])
local main    db2c2d0 → dbbecce            (the PZSz plan + handover — never pushed)
my branch     dbbecce → 65f91fb            (the implementation)

The commit carrying the approved plan and handover, dbbecce, has never left this machine. My branch sits on top of it, so pushing the feature also publishes those two documents — which is presumably fine, but you should know it rather than discover it. A rebase onto origin/main is needed either way, and it is clean: the two remote commits touch only doc/staging/reconcile/.

06The question, and my recommendation

Decision needed Getting 20260903000001 onto CERT and PROD means running a release from main. Do you want that release to carry the whole PZSz feature, or only the schema?
Option A — recommended

Ship the whole feature, in a verified order

Rebase onto origin/main, push the branch, dispatch pzsz-sync.yml from it to settle queue: max for free, then merge to main and let CI → Release apply the migration to CERT and then PROD.

  • Why: the feature is finished and fully gated — 890 pgTAP assertions, 1164 pytest, 721 vitest, every coherence script green, and six correct events verified on a real LOCAL run against the live source. Holding the schema back from the code that uses it buys nothing and leaves CERT in a state no code targets.
  • The queue: max risk is retired before the merge, not discovered by a red EVF run at 06:00 the next morning.
  • Cost: the morning after the merge, six PZSz events appear on the public PROD calendar. If you would rather look at them on CERT first, say so — I can merge with the cron commented out and dispatch the scrape by hand.
Option B

Schema only, in its own release

Put 20260903000001 alone on a branch, merge that, let Release apply it to CERT and PROD, and land the scraper, workflow, frontend and documentation afterwards.

  • Why you might: it is literally what you asked for, and PROD’s calendar does not change at all — an unused column and one unused organizer row are invisible to every fencer.
  • Cost: two releases instead of one, and the queue: max question stays open until the second. It also splits a commit whose message, ADR and tests describe one coherent change.
Option C

Hand-apply the DDL through cloud-sql.sh

Technically available, and I will do it if you tell me to after reading this — it is your database and your call.

  • What it costs: deployed_migrations.json would not record it, so the next release would try to apply it again (harmless — the migration is idempotent) while the fingerprint gate compares hashes it can no longer explain. The environments would be right and the mechanism that proves they are right would be wrong.
  • I do not recommend it when the sanctioned path is available, the queue is empty, and ours is the only pending file.
