Every CI run shows its test results

Your message (1 Nov): "I wanted a GH CI test summaries", with GitHub's page on job summaries. That page names this as the use: summaries of test results, so nobody has to open a log to find a failure. Today a CI run's page shows four job boxes and their times. To learn which pgTAP assertion failed on 18 Oct, someone had to open the log and search it. This plan makes each CI job write its results onto the run's Summary page. Signed 1 Nov 2026.

02 · What is there today

Read from ci.yml, the job logs and Vitest's own code

  • Four jobs, all with a read-only token (permissions: contents: read). pgTAP (database) starts LOCAL Supabase, runs postgrestools, then supabase test db. pytest (Python) runs Ruff lint and format, BasedPyright, three generated-page checks, check_docs.py and pytest. Vitest (frontend) runs svelte-check, then npm test. Coherence Checks runs the four gates of scripts/check-coherence.sh.
  • Nothing in the repository writes a CI summary. No step in ci.yml writes $GITHUB_STEP_SUMMARY.
  • Vitest probably already does. Vitest 4.1.12, which came in with the frontend toolchain upgrade (25 Oct), adds its github-actions reporter by itself when no reporter is configured and GITHUB_ACTIONS is set. That reporter's jobSummary is on by default and writes to GITHUB_STEP_SUMMARY (its own source, dist/chunks/coverage…js line 457, and its type definitions). frontend/vite.config.ts configures no reporter. Fetching a run page could not show it, because GitHub loads summaries after the page; V1 checks it on a real run.
  • What the logs already say, latest CI run 41300329245: pg_prove "All tests successful. Files=124, Tests=1619"; pytest "2554 passed, 20 skipped, 2 deselected in 52.65s"; Vitest "Test Files 73 passed, Tests 1256 passed, Duration 47.70s"; coherence four PASS lines. On a red run (CI 39112045045, 18 Oct) pg_prove printed # Failed test 2: "5.1b vw_score has all required columns" and 03_views_api.sql (Wstat: 0 Tests: 27 Failed: 1). That is exactly the line a summary would show.
  • GitHub's rules (the page you linked): each step's summary is its own file, up to 1 MiB. A job shows at most 20. Summaries are grouped per job when the job finishes, and jobs are ordered by when they finished. A summary that fails to upload does not change the step's status. Secrets are masked.

03 · How (C1 A, C2 A, C3 A)

One script, one summary step per job

  1. scripts/ci_summary.py, standard library only, with three inputs. junit <file> reads pytest's XML: the counts, the time, and each failed or errored test's id with its first message line. tap <file> reads pg_prove's output: files, assertions, the result, and each failed file with its failed test numbers and descriptions. checks reads NAME=outcome pairs from env:. It prints HTML that GitHub reads as plain text. The escaping moves out of scripts/release_notes.py into one shared helper, so the two scripts escape alike.
  2. pgTAP job: supabase test db runs under shell: bash with | tee pgtap.out, so a failure still fails the step. A last step with if: always() writes the postgrestools line and the pgTAP section.
  3. pytest job: pytest --junitxml=pytest.xml. A last step with if: always() writes Ruff, format, BasedPyright, the three page checks and check_docs.py as pass or fail lines, then the pytest section.
  4. Vitest job: Vitest's own summary, pinned (C3 A). A last step with if: always() adds the svelte-check line.
  5. Coherence job: check-coherence.sh output kept with tee; a last step writes each gate's PASS or FAIL line as the script printed it.
  6. A job that stopped before its tests ran, such as a failed Docker pull, shows which step stopped and "tests did not run". Every value reaches a step through env:, and the token stays contents: read.

Two changes from the wording above, both on the safe side

The frontend job's step lists Vitest's own outcome too ("svelte-check", "Vitest"). If svelte-check fails, Vitest never runs and writes no summary, and the line says so.

XML. A security hook flagged the standard library's XML parser. The file it reads is pytest's own output from an earlier step of the same job, never outside input, and ElementTree fetches no external entity. The script says so in its header, instead of adding a third-party parser to a job that installs nothing.
