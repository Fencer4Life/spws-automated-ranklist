ADR alignment before the calendar barrel

Every prior decision the barrel-and-card redesign touches, and which of them has to move before Phase 1 can be written. Four are blocking, five are concurrent, six are clean.

Date 9 August 2026 Corpus 81 ADRs (001–083) Verdict 4 blocking · 5 concurrent · 1 new Plan kalendarz-barrel-2026-08-08.html

What this document is. The plan's §08 documentation gate names one new ADR and, in passing, four existing ones. That list is incomplete. This is the full pass over all 81 ADRs, sorted by whether the decision has to be settled before calendarQuarters.ts is written or merely alongside the work.

The one finding that changes the plan. ADR-018 pins three live tests — R.23, R.24 and R.25 at CalendarView.test.ts:373–412 — to the rolling-progress strip the redesign deletes. The plan's test triage lists .slot assertions in its delete bucket without recording that deleting them retires a documented ADR consequence. That is exactly the case the triage rule was written to catch, and the triage as written walks past it.

01Blocking — settle before calendarQuarters.ts

ADR-015 §2 — Calendar Layout: Vertical Timeline Supersede

This is the decision the redesign reverses, and it is the only one that needs superseding rather than amending. ADR-015 §2 chose a vertical timeline with connected dots, month headers, colour-coded status dots and event cards carrying date, name, location, tournament count and status badge. The barrel removes every element of that, and the tournament count is a deliberate drop per the plan's §04.

It also rejected the shape we are now building. §2's rejected-alternatives line dismisses a horizontal timeline as poor on mobile. The barrel is a rotating horizontal drum, so the new ADR cannot quietly ignore that: it has to answer it with the 320px evidence — five panels flat, six fanning, full-size overlap instead of compression. An ADR that reverses a rejection without addressing the reason reads as an oversight to the next person.

Action. Supersede §2 only — §§1 and 3–9 cover the app shell, EVF import, tournament management, identity admin and scoring editor and stay valid. Mark the m8_calendar_view.html row in ADR-015's mockup table (line 95) as superseded rather than APPROVED; it is the only APPROVED artefact the redesign invalidates.

ADR-018 — Rolling Score for Active Season Amend

ADR-018's UI-changes section records the calendar consequence explicitly: a slot bar above the timeline for the active season, green ✓ completed, amber ↩ carried, grey — empty, with the mockup m10_calendar_rolling.html. Its test table pins three vitest assertions to it, and all three are live today:

TestLocationAsserts
R.23CalendarView.test.ts:374.rolling-progress and its .slot children render for the active season
R.24CalendarView.test.ts:390.rolling-progress is null for a non-active season
R.25CalendarView.test.ts:401.slot.completed / .slot.planned track event status

All three go in the redesign's delete bucket, and the plan's triage never names them or ADR-018. Deleting an ADR-pinned test without touching the ADR leaves a decision whose recorded verification no longer exists — the failure mode the triage rule exists to prevent.

The scoring rule itself is untouched. ADR-018's substance — completed_positions redefined as positions with a scored result, the per-(position, weapon, gender) either/or, migration 20260626120000 — is database-side and entirely unaffected. Only the visual surface is withdrawn. The amendment must say that plainly, or a future reader will misread a UI deletion as a scoring change.

Correction — an earlier draft of this section raised a decision that does not exist. It claimed the strip was rolling's only UI surface, that ADR-018's third state carried had nowhere to go in the barrel, and that this needed a decision. That was wrong, and checking the code settles it rather than the reader having to. The calendar strip has only two states: positionSlots at CalendarView.svelte:268 computes one boolean, completed: e.enum_status === 'COMPLETED', the template renders class:completed / class:planned, and the CSS at :638-656 covers exactly those two per bucket. The word carried and the ↩ glyph never appear in CalendarView.svelte, and nothing in it reads prior-season results.

So ADR-018's calendar line describes a strip that was never built. Its three-state description — green ✓ completed, amber ↩ carried, grey — empty — has two states implemented and the carried one absent. The strip is even named rolling-progress while carrying no rolling data; the name is a misnomer inherited from that ADR's framing. Carry-over's real surface is DrilldownModal.svelte:49-104 — the ↩ banner, .carried-row, striped swatches and legend — driven by bool_has_carryover on the ranking row types at types.ts:95. It is a ranking concept and always was.

This makes the item simpler, not harder. Nothing is lost by deleting the strip, no decision is required, and the barrel's fill-and-ring scheme is complete as designed. What the amendment must additionally do is correct a claim that was never true — a documentation defect that predates this redesign and would otherwise be inherited by whoever reads ADR-018 next.

Action. Amend ADR-018: withdraw the calendar UI consequence, correct the three-state description to the two states actually built, retire R.23–R.25 with the reason, and state that the scoring rule and its migration are unaffected. No product decision needed.

ADR-079 §7 — Event Self-Registration & Identity Amend

ADR-079 owns url_entry_list, the computed SPWS registration URLs, and the §7 amendment that made CalendarView render both links from the flags and open RegistrationModal on left-click with preventDefault(). The redesign changes the entry-list gate from regOpen to dt_start > today, and never on a cancelled event — a rule change that lands squarely in this ADR's territory.

It is blocking because registrationState(event, today) is a Phase 1 function and the plan requires it to return the registration and entry-list flags separately. That signature is the ADR change made executable; writing it before the decision is recorded means the module encodes a rule with no normative home.

The plan's cost analysis is sound and I re-verified the shape of it: no existing test pins the old coupling, so this costs new tests rather than rewrites. The uncomfortable half is the reason — the entry list's dependence on regOpen was never covered, so nothing would have caught it drifting either way.

Action. Amend §7: entry list gated on dt_start > today, decoupled from the registration cutoff, suppressed on CANCELLED; note that registration and entry list answer different questions and deliberately no longer share a date. Keep the modal and ADR-079 link behaviour as-is — those move unchanged.

ADR-017 — Season-Configurable EVF Toggle Amend

Two divergences, and the second is the one that matters.

Stale matrix. ADR-017 defines a single bool_show_evf_toggle with DEFAULT FALSE governing three components — FilterBar, CalendarView, DrilldownModal — from one flag. The calendar now has its own field, show_evf_toggle_calendar, defaulting to true, split from its ranklist sibling by ADR-044 so the surfaces are independent. ADR-017's three-column matrix no longer describes the calendar column, and its stated default is the opposite of the calendar's.

Unrecorded data constraint. ADR-017 records only visibility — buttons hidden, mode locked to PPW. It never says that with the flag off the calendar is domestic-only regardless of scope state. That behaviour is real and load-bearing: CalendarView.svelte:291 reads !showEvfToggle || scopeFilter === 'ppw', and in the mock it is the difference between 103 panels and 22. Hiding the control without forcing the scope would strand EVF events on screen with no way to filter them. Phase 1 ports that filter, so it needs a normative statement to port from.

Action. Amend ADR-017: record the ADR-044 split and the calendar's opposite default, and state the data constraint — the flag governs the event set, not merely the buttons. Confirm the ranklist sibling's FALSE default is untouched; the split was deliberate and must not be re-merged.

02Concurrent — move with the work

ADR-030 — Event Registration URL + Deadline Amend

ADR-030 is the normative home of the computation the plan warns against rewriting from memory: regCutoff = dt_registration_deadline ?? dt_start, the deadline text's stricter independent test, and the two-tier urgency where under seven days turns the block red. The redesign preserves all of it — this is a relocation, not a rule change.

What breaks is the DOM contract. ADR-030 names .timeline-registration as the container carrying .reg-urgent, plus .registration-deadline and .registration-link. The rewrite deletes .timeline-registration outright. An ADR describing a CSS class that no longer exists is a quiet trap for whoever next touches urgency styling.

Action. Amend: the logic moves to registrationState() in calendarQuarters.ts, presentation moves to EventCard.svelte, and the container class is renamed. Add a pointer to the ADR-079 entry-list divergence so ADR-030's display-logic table is not read as still governing both links.

ADR-005 — Svelte 5 $state for Internationalisation Amend

ADR-005 records a trade-off the redesign reverses outright: no pluralisation support, Polish has three grammatical forms, and the then-current 46 keys contained no plurals. The plan introduces a three-form Polish pluralisation helper keyed by count, including the trap that 12–14 take the genitive while 22–24 do not. That is the recorded trade-off being retired.

The live defect proves the trade-off expired on its own: tournaments_count is a flat string, concatenated with the count at CalendarView.svelte:72, so 2 turniejów and 1 tournaments are both in production today. The card drops that field, but the helper is needed regardless and the defect should be reported rather than silently absorbed.

Second, smaller divergence: ADR-005 records month localisation via toLocaleString('pl-PL', {month:'short'}). The card needs full months in the genitive — 18 kwietnia, not 18 kwiecień — which is why the plan gives the calendar its own keys rather than borrowing month_1…12.

Action. Amend ADR-005 with a pluralisation sub-decision and the genitive-month key rule. Cross-reference ADR-063, which already established that Polish grammatical case is a first-class concern in this codebase — that precedent makes this an extension rather than a new principle.

ADR-028 — EVF Calendar + Results Import Amend

This is the unstated prerequisite the plan flags against CountryFlag, and it lands here. ADR-028's refresh contract lists columns that are never refreshed, and txt_location and txt_country are both on that list. The redesign needs exactly those two columns written: ISO-3166 alpha-2 normalisation of free-text country (today Polska, Germany, GRUZJA, and both Great Britain and United Kingdom for one country), and the location backfill for the current and previous season.

A one-time, human-reviewed enrichment pass is a different act from a scraper refresh, and the distinction is worth writing down: ADR-028's rule exists to stop the scraper overwriting curated values, not to freeze the columns forever. Without the carve-out, the enrichment pass looks like a violation of the refresh contract.

Action. Amend ADR-028 to distinguish scraper refresh from one-time curated enrichment, and confirm the never-refreshed rule still binds the scraper afterwards. Also record the venue-in-city defect — the scraper writes venue strings into txt_location — since the card's location line assumes a city and the mock never infers one that is not literally in the string.

ADR-037 — Derived Display Status Amend

The helper itself is reused unchanged and the plan is right that this is zero new work — getEventDisplayStatus() is already exhaustive over the lifecycle plus derived awaiting-results. The amendment is pointer maintenance, not substance: ADR-037 names its consumers as CalendarView.svelte and EventManager.svelte, and its 2026-08-07 amendment states the cancelled-notice window is implemented in CalendarView.svelte and tested in CalendarView.test.ts. Both move — the window into calendarQuarters.ts, the consumer into EventCard.svelte.

Dependency worth checking before Phase 1. ADR-077 records a bug against this display map: it omits CREATED and SCORED, both rendering as Planned, marked fix and not obviously closed. The barrel hides CREATED so that half is moot, but SCORED is a real lifecycle state on the forward spine and the card must label it correctly. Verify against eventStatus.ts before assuming the helper is complete.

Action. Amend the consumer list and the amendment's implementation pointers. Confirm the SCORED label exists.

ADR-040 — Multi-Slot Event Result URLs Amend

ADR-040 states the five URL slots are equal-status with no role labels, no per-slot enum and no primary pointer, and it explicitly rejected a child table with role labels as overkill. The plan honours this: day labels are derived at render time from the URL's own content, never stored, and the plan cites the same clause when rejecting an earlier per-weapon design. So there is no conflict in substance.

The amendment is defensive. A reader who meets Dzień 1 / Dzień 2 in the new card and then reads ADR-040's no-role-labels rule will reasonably conclude the UI violates it. Recording that a render-time label derived from URL content is compatible — while a stored role remains rejected — closes that gap. Open item 1, the fallback for platforms that do not encode the date, is the same concern: Engarde puts the date in the path so those label themselves, FTL and 4Fence may not, and ADR-040 forbids inferring day from slot position because slots are compacted.

Action. Amend with a render-time-labelling clause and resolve open item 1 inside it. The plan's recommendation — bare numbering, Wyniki 1 / Wyniki 2 — degrades honestly and signals which platforms need a parser; I agree with it.

03The new ADR — and the one constraint on how it is written

Replacing the list and strip with a barrel and card is an architectural decision with a public-facing consequence, so it needs its own ADR. ADR-084 is the next free number: the corpus runs 001–083 with 051 and 054 absent.

ADR-084 must be authored as Markdown, not HTML. This is the one place where the standing "every deliverable is HTML" rule yields, and it yields to a recorded decision rather than to preference. ADR-082 makes the ADR corpus a source→artifact model: the .md is the hand-authored source of truth and the Appendix C link target, the .html is generated solely by scripts/render_adrs.py and never hand-edited. Each HTML embeds a source SHA-256 and CI's Validate generated ADR HTML step fails on a stale twin. A hand-written ADR HTML would fail that check.

Worth flagging: ADR-082 is still Draft, awaiting sign-off — it is the governing standard for the file I would be creating and has not itself been accepted. It is being followed in practice by the whole corpus, so following it is right; but if it is going to be signed off, doing that before adding an eighty-fourth file under it is tidier than after.

ADR-084 should carry, at minimum: the two-channel rationale that started this — hue for type, fill for completion, ring for next-upcoming, replacing a strip that encoded both in one channel; the barrel owning season state, which is what let the dropdown go; the overlap-not-shrink rule with its z-index formula and 320px evidence; the answer to ADR-015 §2's horizontal-timeline rejection; and the deliberate removals — weapon filter, tournament count, time filter, season dropdown.

Registry and traceability

  • Register ADR-084 in specification Appendix C — Architecture Decision Registry, line 1402 onward — as the plan's §08 requires.
  • Amended ADRs need their Appendix C entries updated too, not just their own files; the registry carries a status and summary per ADR.
  • RTM check for requirements touching calendar presentation. ADR-030 introduced FR-90 and FR-91, both worded as displayed in the Calendar; ADR-079 carries FR-120–FR-130. Those wordings survive the redesign but the test IDs they cite move.
  • Handbook pages per the plan's §08: product/product-surfaces.html, subsystems/events-and-registration.html, and reference/codebase-map.html with four new files — CalendarFilters.svelte is not built.

05Recommended order

  1. Nothing here changes the barrel's visual spec. The one candidate — ADR-018's carried state — was checked against the code and does not exist in the calendar (§01), so the fill-and-ring scheme stands as designed and no product decision gates the build.
  2. Draft the four blocking changes together — ADR-015 §2 supersession, ADR-018, ADR-079 §7, ADR-017 — and sign them off as one batch. They are interlocking: three of the four describe rules calendarQuarters.ts implements.
  3. Verify the SCORED label in eventStatus.ts against ADR-077's recorded fix. Cheap, and it decides whether ADR-037's amendment is pointer-only.
  4. Write Phase 1 — calendarQuarters.ts and its tests, RED → GREEN — with resolveAnchorQuarter() last, since the plan's open items 1 and 4 both land there.
  5. Author ADR-084 as Markdown, generate its twin, register in Appendix C.
  6. Amend the five concurrent ADRs as their behaviour lands, then run the documentation coherence gate: scripts/check_docs.py clean and scripts/refresh-graph.sh before the commit.

One thing this audit did not do. It reads the ADR corpus against the plan, not against the running system. Where an ADR and the current code disagree, I have quoted the code — CalendarView.svelte:291, :72, CalendarView.test.ts:373–412 — but I have not re-verified every ADR's claim of its own implementation status. The four blocking items are all evidenced against live source or live tests; the five concurrent ones are evidenced against ADR text and should be confirmed against implementation as each amendment is written.
