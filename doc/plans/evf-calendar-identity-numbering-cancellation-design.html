Number the complete EVF calendar chronologically and keep rolling identity separate

This document records the corrected approved repair: whole-word CAMP entries are ignored completely; an event already cancelled at first import receives base zero; every remaining competition receives a positive chronological PEW code with an authoritative weapon suffix; and prior-season geography remains independent through id_prior_event.

The short version

Returning event

Number by this season’s calendar

After camps and first-import cancellations are removed from the positive sequence, Madrid is second and becomes PEW2es even if it had another number last season. The rolling relationship is the foreign key.

Genuinely new

Use the same chronological rule

Returning and genuinely new competitions use the same calculation: exclude whole-word camps and first-import cancellations, sort by start date then EVF calendar ID, and use the one-based position.

Cancelled

Keep history; limit public display

Already cancelled at first import receives PEW0{weapons}. A later cancellation keeps its positive code. The public calendar shows the cancellation through seven days after the original end date, then hides it.

Numbering strategies considered

Chosen

Guarded filtered chronology

Filter camps and first-import cancellations, recompute the positive sequence, reflow unscored rows, and abort before renaming a scored row. Preserves the approved chronology without silently rewriting result identity.

Rejected

Always reflow

Perfect chronology, but an EVF insertion or reschedule could silently rename result-bearing events and their child codes.

Rejected

Assign once

Stable codes, but a late earlier entry makes the season permanently non-chronological and violates the approved business rule.

The invariant we want

Whole-word CAMP → no row; first-import cancellation → base zero; every other EVF competition → one database event and one positive chronological PEW{N}{weapons} code. A scrape may enrich, reschedule, rename, cancel, or safely reflow an unscored occurrence, but it may not allocate another row for the same calendar ID. Prior-season numbers never influence the current-season number.

Current failure

Why the current season jumped to PEW68–PEW80

The season initializer correctly pre-created low-number slots from the prior season. Those rows are marked CREATED and point to id_prior_event. However, they did not carry the EVF calendar’s stable identifier or slug.

The scraper then compared physical text. EVF often publishes a venue where SPWS stores a city, and it may use a three-letter country abbreviation where SPWS stores a country name. The same event therefore looked different even though it was not new.

The allocator did what it was told, but it was asked the wrong question

It was asked “does this venue text equal a current slot?” It should first be asked “does this EVF calendar identity already belong to a slot or its prior event?”

Why a new column is safer

Using id_evf_event for both APIs would make two unrelated ID namespaces appear equivalent. A numeric collision could silently join the wrong calendar event to the wrong results event. The calendar post ID therefore needs its own explicitly named field.

The calendar ID is already present in the HTML as a class such as post-877; the scraper can capture it without introducing a new external service or authentication requirement.

Architectural choice

Three approaches considered

Recommended

Separate calendar, results and rolling identities

Calendar ID identifies the public occurrence; original scoring URLs are authoritative for results; EVF results ID is secondary evidence; id_prior_event controls rolling. Strongest audit trail and lowest collision risk.

Rejected

Put both numeric IDs in one column

Smaller schema change, but the meaning of the field depends on the caller. Numeric collisions and later results linking become unsafe and difficult to diagnose.

Rejected

Continue with slug, city and country only

No new column, but repeats the existing failure when EVF changes venue text, abbreviations, spelling, or page naming. It cannot provide a durable numeric identity.

The first exact identity match wins even if the event date, public name, venue, or cancellation marker changed. This is essential for reschedules and renamed venues.

No silent guess on ambiguity

If the fallback finds two possible predecessors—for example two historical rows for the same city—the sync must stop for that event, report both candidates, and require an explicit mapping. It must not allocate a new number merely because the answer is ambiguous.

Season initialization

When next season’s skeleton is created, it may carry a verified reusable calendar identity as a matching hint together with id_prior_event, but it does not reserve or inherit the prior PEW number. The filtered current-season snapshot assigns the final ordinal. It will not copy the results DB ID, because that ID describes a particular results occurrence rather than the recurring calendar series.

Let N be the number of retained, not-already-cancelled competitions after whole-word CAMP exclusion. Their positive numeric bases must equal exactly {1,…,N}. First-import cancellations are retained separately at base zero. A prior-season code number is evidence of history only and is never an allocation input.

Current-season examples

Samorin becomes PEW0efs. Madrid is second and becomes PEW2es; Budapest is third and becomes PEW3ef. Athens is fourteenth and becomes PEW14es, while its independent id_prior_event points to Chania as the same geographic event series.

Every scrape records the source count before it writes

A dedicated calendar-scrape ledger records the run ID, environment, season boundaries, every distinct calendar ID counted, total N, cancelled count, proposed highest PEW number, create/update/unchanged/rejected counts, and the final verdict. Failed runs are retained too; mutation-only audit logs cannot explain a scrape that correctly refused to write.

Hard pre-write errors

After camps are excluded, the entire calendar write aborts when a retained entry has a missing or unparseable date; an entry crosses a season boundary; season definitions overlap or leave the entry unassigned; calendar IDs duplicate; a weapon set is missing or unsupported; one calendar ID maps to multiple database rows; positive bases are not exactly 1…N; two first-import cancellations collide on the same full zero code; or a required reflow would rename a results-bearing event.

Cancellation policy

Cancelled is a lifecycle state, not part of the event’s name

Today Samorin’s name changed to include “Cancelled,” but its database status remained PLANNED. That makes the UI look planned and keeps it visible indefinitely. The scraper should convert an authoritative cancellation marker into the existing CANCELLED status.

Numbering depends on when cancellation becomes known. Samorin is already cancelled before its first authoritative import, so it receives PEW0efs and consumes no positive ordinal. If an event is imported with a positive code and EVF cancels it later, it keeps that positive code; cancellation does not trigger a season-wide reflow.

Existing data

How CERT and PROD will be corrected safely

The repair will not be a hand-written collection of blind renames. It will first generate an exact manifest from current data and official EVF identities.

  1. Read-only source snapshot. Capture the source page, exclude whole-word CAMP names, separate first-import cancellations at base zero, validate retained competitions and calculate positive N.
  2. Read-only database inventory. List every current-season EVF row, its calendar ID, slug, prior link, tournaments, results, registrations and candidate predecessor in CERT and PROD.
  3. Classify identity separately. Mark each row RETURNING, GENUINELY_NEW, CANCELLED, or AMBIGUOUS for id_prior_event. This classification never changes the chronological number. Ambiguous prior links block the mutation.
  4. Produce a dry-run mapping. Show ignored camp IDs, zero-code cancellations, and calendar ID → positive ordinal/suffix → current code → target code → prior event, with proof that positive bases are exactly 1…N.
  5. Snapshot and migrate CERT. Apply one transaction. Preserve enrichment and children, restore prior links, cascade codes, and set cancellation state.
  6. Scrape CERT twice. The first run may enrich; the second must allocate zero events and leave all codes identical.
  7. Verify CERT invariants. No CAMP rows, no duplicate calendar ID/slug, Samorin at zero, exact positive bases 1…N, authoritative suffixes, no orphan tournaments, no results lost, exact prior links, and expected cancellation visibility.
  8. Apply the same business mapping to PROD. Resolve environment-local IDs by stable codes/identities, never by copying raw database IDs from CERT.
  9. Reconcile and verify PROD. CERT and PROD must agree on event codes and source identity; protected environment-owned differences remain reported.

Destructive guard

No row with results, registrations, or unresolved child data will be deleted. A merge that cannot prove where every child row goes aborts the transaction. CERT is verified before PROD is touched.

Idempotence is the live acceptance test

After repair, two consecutive calendar scrapes over unchanged EVF data must produce the same event set and exactly the same codes. “No new allocation on the second run” is mandatory evidence, not an assumption.

Decision gate

Approved decisions

The user approved these rules on 7 August 2026

  1. Store the EVF calendar post ID separately from the EVF results DB ID.
  2. Use original scoring-platform links as the results authority; use the EVF results database only as secondary evidence.
  3. Ignore any name containing case-insensitive whole-word CAMP before validation, counting or persistence.
  4. Assign first-import cancellations base zero; assign retained non-cancelled competitions positive chronological codes after sorting by start date then calendar ID. A later cancellation keeps its positive code.
  5. Use id_prior_event as the exact rolling/geographic relationship, including Athens→Chania.
  6. Persist every scrape attempt and abort before mutation on malformed retained data, duplicate identity/zero code, ambiguity, non-exact positive 1…N numbering, or a required scored-row rename.
  7. Cancelled event: retain permanently, show publicly through seven days after its original end, then hide publicly; never auto-reactivate.
  8. Repair CERT first from a reviewed dry-run manifest, prove repeated-scrape idempotence, then apply the same mapping to PROD and verify both.

The corrected CAMP-exclusion and zero-number design was approved on 7 August 2026. Before mutation, the executable dry run must still enumerate every exact old row → keeper/delete/create operation in each environment and re-check results, registrations and child ownership.
