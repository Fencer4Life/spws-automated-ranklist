SPWS · registration · design review · 2 September 2026

Per-event payment details

Yes to the shape — and your sync rule is not a new rule, it is tier two of the ownership model you shipped yesterday. Four things bother me, one of them a good deal.

Review — nothing built 1 decision needed 1 material objection

The part I like

The promotion rule already exists

I read f2634d6 and ADR-086's 2026-08-29 amendment. Every mirrored field now sits in one of three tiers:

Scraped from EVF dt_start, txt_name, txt_location … overwrite Admin enrichment url_*, num_entry_fee*, txt_organizer_email, url_entry_list, dt_registration_deadline fill-blank Per-environment bool_use_spws_registration, ts_ftl_sent not synced

What you described for the payment fields — "if PROD data is there the sync does not update them, but if PROD is missing and CERT exists, populate" — is the fill-blank tier, word for word. So this is not a new sync policy to design and defend; it is a classification: the two new columns join num_entry_fee* and txt_organizer_email, which are already their natural siblings. That is the strongest thing about the proposal, and it means the promotion work is small.

The fallback chain is sound too. Event → organizer → nothing is the right order, and overriding only payee and IBAN is coherent because the other two rows on that panel are derived, not stored: the title is generated from the event and the fencer, the amount from the weapon count and the event's fee tiers.

What bothers me

One material objection, then three loose ends

1 Nothing will validate an admin-typed IBAN — and this is the account fencers pay into

Today the account number is a vetted constant. We proved it yesterday: strip the spaces, run ISO 13616 mod-97, get exactly 1. The old value scored 73, which is how we knew it was the domestic NRB rather than an IBAN.

The system never touches the money, but it publishes the number. The moment that number becomes a per-event text field, a typo is a wrong or non-existent account, printed under a label saying IBAN and copied by every entrant with one tap. It is the fencer's own transfer that goes astray — a return, a fee, or a payment the association never sees — and we would find out from complaints rather than from a check.

I would not ship the override without validation. The rule is already written and tested in tests/orgPayment.test.ts; it needs to move to where the data enters: a database CHECK so no path can store an invalid IBAN, plus inline feedback in the event editor so an admin sees it before saving rather than after a fencer complains. That is the difference between a hardcoded-correct value and a typo-prone one, and it is cheap.

2 "No payment data → skip the form" cannot happen while the constant exists

lib/orgPayment.ts supplies SPWS_PAYEE and SPWS_IBAN unconditionally, so with it in place the chain never reaches empty and the skip branch is unreachable code. Remove it, and every event that has not been configured yet loses its payment details — including PPW1-2026-2027, which is live with 18 entries.

Resolution I would propose: migrate those two constants onto the SPWS organizer row, then delete the module. Current behaviour is preserved exactly (that organizer runs the domestic events), the chain becomes real rather than decorative, and the file's own comment finally comes true — it already says this belongs in the database rather than the bundle.

3 Organizer-level data has no route to PROD

tbl_organizer holds id_organizer, txt_code, txt_name, ts_created — no payment columns, which is expected. But the three-tier model governs events. Promotion only resolves organizers by code (_prod_code_to_id) and never syncs their attributes, so payment data added to an organizer on CERT would not reach PROD at all.

That is fine if we accept it deliberately — organizer payment details are entered once per environment, like the registration switch. It is a defect if we assume it syncs. It needs deciding rather than discovering.

4 Two smaller ones

Warning versus blocking. A toggle switched on with no payment data means fencers can enter but cannot pay, and a soft warning is easy to click past — the cost lands on fencers, not on the admin who dismissed it. I would still allow the save (an admin may reasonably enable first and fill in details later) but carry the state on the event list as a persistent badge, not only as a transient notice in the editor.

What "skip the payment form" costs. The registration is written at RODO-accept, before that step, so nothing is lost from the entry itself. But the payment step is also where the transfer title is generated — the string your treasurer reconciles a bank line against. If a fencer pays anyway using details from the invitation, they now have no reference. I would keep the confirmation and the title, and omit only the payee and IBAN rows, with a line saying the organizer will supply the account.

One thing to settle

Can an admin clear a payment field on PROD?

Fill-blank means an empty PROD field invites the CERT value. So if an admin deliberately clears a wrong IBAN on PROD, the next scheduled sync refills it from CERT — the value comes back on its own, which is exactly the failure shape as last week's switch-off: unattended, on the 06:00 schedule, correcting nothing.

Two coherent answers. Either empty string counts as a value that stops propagation, so clearing is a real act and only NULL invites a refill — which needs the editor to write '' rather than NULL. Or clearing is not supported on PROD and a correction must be made on both sides, which is simpler but must be stated so nobody expects otherwise.

I lean to the first: it keeps PROD authoritative once touched, which is the whole point of the tier. Which do you want?

Summary

Am I OK with it?

Yes. The shape is right, the fallback order is right, and the sync rule is one you have already designed, tested and shipped — this is a classification, not an invention. I would put it in the same tier as the fee fields without hesitation.

The condition I would attach is IBAN validation, in the database, in the same change. Everything else on this page is a loose end worth ten minutes of agreement; that one is the difference between a convenience feature and publishing an account number nobody has checked.
