Decided 2 October · S B

How the Criterium 2026 counts in the 2026/27 rolling score

Where it stands. LOCAL shows Zabłocki's win in the 2026/27 EVF+ rolling score (417.24). It does so through a hand-made 2026/27 row, PEW19efs-2026-2027 “EVF Criterium Mondial Vétérans 2027”, undated and CREATED, linked to the 2026 event. The same row and the 2026 event are now on CERT. Nothing is staged on CERT: the runner workflow refused the code PEW10efs (its input check allowed only upper-case letters; fixed test-first, WF.P5.02, not yet released).

What stopped it. pgTAP 74.9 fails on LOCAL: ADR-091 forbids an undated CREATED EVF placeholder anywhere, because such a row is a prediction the calendar sync cannot match and it caused duplicate events. My row is one. Its failure mode is real here too: when EVF publishes the 2027 edition, the sync reuses the row only if EVF's chronological code is exactly PEW19; with any other number it creates a second row, the unique index on (season, prior event) refuses it, and the whole calendar sync stops until someone joins the two by hand.

What the rule already does. A 2025/26 result carries into 2026/27 for 366 days after its event through the 2026/27 edition's link, until that edition is held; a cancelled or not yet held edition keeps carrying it. Only an event whose next edition has no row at all drops out at once. Measured read-only: on PROD every 2025/26 event with results has a 2026/27 row, so this gap holds only the Criterium.

S The mechanism

  • A keep the placeholder row on every environment: amend ADR-091 with this exception and pgTAP 74.9 to allow a linked successor, and accept that a misnumbered 2027 edition stops the calendar sync until it is joined by hand.
  • B amend the carry-over rule (ADR-042): a result of the previous season whose event has no row in the current season yet carries for the same 366 days. Built test-first in vw_eligible_event, released, then the placeholder rows are removed from LOCAL and CERT. When EVF publishes the 2027 edition, the sync links it by city and the carry continues until that edition is held. On PROD this changes only the Criterium; the 2026/27 ranking moves exactly as the preview on the review page (Zabłocki 305.55 → 417.24, eight more rows).

Recommendation: B. It is what the rolling score already means for a cancelled or not yet held edition, it needs no prediction of EVF's calendar, and it cannot stop the sync. A keeps a guessed row that ADR-091 was written to remove.

Resolved · CI was red on main

The first release push failed CI; fixed and released

Pushed 647f5a2d to main. CI's pgTAP job failed while loading the seed, before any test ran, and the Release workflow runs only after a green CI, so CERT and PROD are unchanged.

Cause. The new type guard (TT.CODE, migration 20261002000003) maps the code family DMEW to MPW, copied from derive_tourn_type_from_event_code, which routes the team championship to the MPW threshold. The seed (seed_prod_latest.sql, 12 September) still holds six bracket stubs of DMEW-2025-2026 typed MEW. CI applies migrations before the seed, so the guard refuses the first one. LOCAL passed because its database was not rebuilt and the guard checks writes only. CERT and PROD hold no DMEW tournament today (the event is PLANNED, with 0 tournaments), so the mismatch exists only in the seed.

T How DMEW is typed

  • A the guard leaves DMEW unmapped: it checks every other family and says nothing about DMEW until its type is decided. Seed loads, nothing else changes. One-line migration fix plus a test pinning it.
  • B DMEW is MEW in the guard and in derive_tourn_type_from_event_code; ADR-066 threshold routing for the team championship then moves from MPW to MEW.
  • C DMEW stays MPW everywhere, and the six stale stubs are removed from the seed.

Recommendation: A. It unblocks CI without deciding what a team championship scores as, which no stored result depends on today. B and C each change a rule or the seed beyond this fix.
