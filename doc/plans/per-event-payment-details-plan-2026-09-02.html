SPWS · registration · implementation plan · 2 September 2026

Per-event payment details

Payee and IBAN become overridable per event, falling back to the organizer's default account. The IBAN is vetted on save. Registration cannot be switched on with no account to pay into, and the admin always sees which account an event will show.

Plan — nothing built 2 migrations · 2 ADR amendments no new public RPC

1 · Today

How it works now

There is one account number in the whole system and it is compiled into the frontend bundle:

frontend/src/lib/orgPayment.ts SPWS_PAYEE = 'STOWARZYSZENIE POLSKICH WETERANÓW SZERMIERKI' SPWS_IBAN = 'PL 06 1090 1665 0000 0001 5004 1549' RegistrationForm.svelte effectivePayee = payee || SPWS_PAYEE ← prop, else the constant effectiveIban = iban || SPWS_IBAN

The payee / iban props exist but nothing meaningful sets them: register.html passes empty strings, and the in-app calendar modal passes nothing at all. So every event shows the same account, and the file's own comment already says this belongs in the database rather than the bundle.

Nothing validates it either — it is correct because a human typed it once. On 2 September we found it had been storing the domestic NRB under an IBAN label; it scored 73 on the ISO 13616 mod-97 check instead of 1.

2 · The change

What we add, and how it resolves

DBtwo columns, twice
  • tbl_organizer gains txt_payee and txt_iban — the organizer's default account. This is the SPWS / EVF / FIE "multi-event organizer" account you described.
  • tbl_event gains the same two columns, both nullable — the per-event override.
  • A one-off seed in the same migration writes today's two constants onto the SPWS organizer row, so current behaviour is preserved exactly and no live event changes what it shows. orgPayment.ts is then deleted, along with the now-pointless payee/iban attributes on register.html.
  • Why it is needed at all: the moment the constants are gone the fallback has to come from somewhere. Without the seed, every event — including the live one with 18 entries — would resolve to no account, and under the blocking rule below registration could not be enabled.
  • Written as a seed, not an assignment: guarded WHERE txt_iban IS NULL, so it fills an empty column and never overwrites a value an administrator has since changed. That matters because CI and reset-dev.sh replay the whole migration chain against a fresh database; on CERT and PROD it applies once and is thereafter inert.
Resolutionevent → organizer → nothing
  • Resolved server-side, in the view the registration page already reads, so the browser is handed one answer rather than a chain to walk. Both fields resolve together, from the same level — a per-event payee with an organizer IBAN would be a way to send money to the wrong account with the right name on it.
  • The view also exposes which level answered, so the admin UI and the handbook can state it rather than infer it.
Vettingthe mod-97 rule, reused
  • The rule is extracted from tests/orgPayment.test.ts into shared code and applied in three places: a database CHECK on both new IBAN columns so no path can store an invalid value, validation inside fn_update_event so the API refuses it, and inline feedback in the event editor so the admin sees it before saving.
  • The database constraint is the one that binds. The other two exist so the failure is understood at the point it happens rather than surfacing as a constraint violation.
  • Poland-specific and generic forms both accepted: an organizer abroad is plausible, so the constraint is ISO 13616, not PL-only. The value is stored normalised into the bank's printed grouping.

3 · CERT → PROD

Synchronisation behaviour

The rule you described is already the house model. ADR-086's 2026-08-29 amendment sorts every mirrored field into three tiers, and the payment fields land in the middle one beside the fee tiers and the organizer e-mail they belong with:

Scraped from EVF dt_start, txt_name, txt_location … overwrite Admin enrichment url_*, num_entry_fee*, txt_organizer_email, url_entry_list, dt_registration_deadline, txt_payee, txt_iban fill-blank Per-environment bool_use_spws_registration, ts_ftl_sent not synced

Fill-blank is expressed in the mirror exactly as its siblings are, and the ordering inside COALESCE is the whole policy:

txt_iban = COALESCE(txt_iban, NULLIF(btrim(v_evt ->> 'txt_iban'), '')) ↑ PROD wins when it holds a real value blank means blank, everywhere: NULL == '' == ' '
  • PROD holds a real value → CERT is ignored. A correction made on PROD stands, and a scheduled sync cannot undo it.
  • PROD is blank (NULL, empty or whitespace — all the same thing) and CERT holds a value → CERT seeds it. This is the "populate on first sync" case.
  • Both empty → nothing happens.
  • CREATE branch — a brand-new PROD event carries whatever CERT holds; there is nothing to preserve.

i Emptiness is never a sentinel — normalised at the write boundary

Raw COALESCE would treat '' as a value and only NULL as blank, so a field cleared in the editor would silently mean "locked, never sync again" while looking identical to one that was never filled. That is invisible state of exactly the kind that has bitten this system before, and a value of ' ' would slip through as real data.

So NULL, the empty string and whitespace-only all collapse to NULL on write. Enforced by a trim trigger on both tables — the idiom already used by trg_trim_fencer_names and trg_trim_registration_names — so every caller is covered, not just the editor: btrim the value, and store NULL when nothing is left. The database therefore only ever holds NULL or a real account, and the same definition of "absent" is used by the sync, the resolution and the toggle guard.

! The consequence, stated rather than discovered

Because blank is always blank, a field cannot be locked empty on PROD. Clearing a wrong IBAN there makes it NULL, and the next sync will seed it again from CERT if CERT holds one. To remove an account permanently it is cleared on both sides — or, more usually, corrected on PROD rather than emptied, since a PROD value wins outright.

This reverses what an earlier draft of this plan said. The trade is deliberate: no hidden lock, at the cost of one honest limitation.

4 · The toggle

Behaviour when there is no payment data

Registration exists to support collecting a registration fee. The system itself never handles the money — it displays transfer instructions and deliberately does not track whether a transfer arrives, which the organizer verifies in person at the venue (ADR-079 §4). What it does is publish the account a fencer is asked to pay into.

So switching registration on with no account to pay into is almost certainly not what the organizer intended: the fee cannot be quoted against anything, and the entrant reaches the end of the flow with nowhere to send it. It is a configuration mistake rather than a legitimate state, and a warning is easy to click past — the consequence surfaces later, for the fencer. So this blocks rather than warns.

  • Neither level resolves a non-blank payee and IBAN — whitespace does not count as data — → the toggle cannot be switched on. The checkbox is disabled, with the reason stated next to it and a link to the organizer, not a bare "invalid".
  • Enforced server-side too — fn_update_event refuses to set the flag true when neither level resolves a payee and an IBAN. The client check is a courtesy; the database is what binds. This mirrors how the registration deadline is enforced.
  • Already on, and the data disappears — an admin clearing the organizer account under a live event is refused for the same reason, rather than silently breaking the payment step. A live registration is not switched off by a side effect.

! One migration-time check

PROD currently has registration on for PPW1-2026-2027 with 18 entries. The data migration must seed the SPWS organizer before the constraint is armed, and assert that every event with the flag already on resolves an account. If any does not, the migration fails loudly rather than leaving a live event in a state the new rule forbids.

5 · Provenance

Telling the admin which account is in use

The resolved level travels with the resolved values, so the editor states it plainly instead of the admin inferring it from whether a field looks empty:

Konto: konto tego wydarzenia ← per-event override in force Konto: domyślne konto organizatora (SPWS) ← inherited Konto: brak — rejestracji nie można włączyć ← blocked

Shown in the Rejestracja SPWS panel beside the two fields, and carried as a badge on the event list so the state is visible without opening each event — the same reasoning as the FTL "not yet sent" stamp. Leaving the override fields empty is the normal case and must not read as an error.
