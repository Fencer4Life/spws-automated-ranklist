Decision needed · 13 September 2026 · FTL export tokens

Before minting: does the first token need to be scoped?

The handover flagged this and asked for a call before handing any link out. Reading the actual functions settles what the choice really is — it is narrower than "scoped vs. not."

What the code actually does today

The label doesn't gate anything yet

tbl_ftl_export_token has txt_label for naming a token so it can be revoked by who it was for. But all three RPCs — fn_ftl_export_events, fn_ftl_export_entries, fn_ftl_roster — only call fn_ftl_export_token_valid(p_token). None of them join the token back to an event. Any live token sees every live event's entry list, regardless of label.

The migration's own comment is explicit that this is deliberate for now: "Shaped so it can later carry an organizer id and scope each link to its own events without the URL changing. Not built: what was asked for is one aggregate page."

The confidentiality angle is weaker than it sounds

Every field this surface returns — surname, first name, gender, weapon, age category — is already public through vw_registration_entry_list. A token doesn't protect a secret; per the migration comment, it "keeps an organizer-only tool from sitting in front of four hundred fencers" and gives us something to revoke. Scoping would restrict which organizer can pull which event's seed files, not which names anyone can already see.

The real choice

Three options

A — Mint one token per organizer now, build no enforcement Recommended

Give PPW1's organizer a token labelled PPW1 Opole — organizer today. It will, honestly, also list Łomianki and every other live event — same as a single shared token would. The label buys nothing except a name to revoke by if a link leaks.

Ships today, no schema change, no new migration, no delay against the 20 Sep entry close. Revisit only if an organizer actually objects to seeing another event's list, or the association sets a policy that requires it.

B — One shared token for every organizer

Simplest possible thing: a single row, handed to whoever needs it. Same visibility as A. Loses the ability to revoke one organizer's access without cutting off everyone else — the only real cost, since the label in A is otherwise decorative until scoping exists.

C — Build per-organizer scoping before minting anything

Add an event↔token linking table (or an id_event array on the token row), filter all three RPCs on it, extend pgTAP 76/77, update the anon allowlist docs if the function signatures change. Real work — a migration, three function edits, new tests — not a five-minute job. Delays PPW1's organizer past today; entries close 20 Sep, so this needs to land fast if chosen.

Why A over C

Nothing secret is at stake yet

C is the correct long-term shape and the table was already built to grow into it. But building it speculatively — before any organizer has asked to be excluded from another event's list, and before the data it would hide is anything other than already-public roster facts — is exactly the kind of not-yet-needed abstraction worth avoiding. Option A ships the one thing that was actually asked for (an organizer can download their own seed files) and leaves C as a scoped, well-motivated follow-up if a concrete need shows up.

Once a choice is made

add &lang=en if the organizer doesn't read Polish.

Treat it like a shared bearer credential, not like public info

The data behind the link is already public, but the link itself is a capability — whoever holds it can pull every live event's seed files and pick-lists, and there's no login to fall back on if it circulates. So:

  • Send it the way you'd send any organizer-specific link today — direct e-mail or Telegram DM to that organizer, not a public channel, a shared doc, or a group chat with people outside that role.
  • Don't shorten it or repost it anywhere it could get indexed or archived.
  • If it leaks or the organizer no longer needs it, revoke by label: UPDATE tbl_ftl_export_token SET ts_revoked = now() WHERE txt_label = '…' — the link then reads as empty, not broken.
