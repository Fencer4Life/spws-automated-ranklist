Entry list · Administrator · TDD plan

An administrator removes an entry from „Lista zgłoszonych”

A signed-in administrator gets a „Usuń” button on each row of the entry list. Visitors see the list exactly as today. Design signed on 17 Nov 2026 (doc/plans/entry-list-admin-remove-design-2026-11-17.html, rev 2). This is the build plan: tests first, nothing else changed.

Signed off 17 Nov 2026 frontend only · no migration new requirement FR-166 Pixel sheet approved 18 Nov · released 18 Nov, main d6ca0435

01 · Verified before planning

What the system already gives us

  • The database already allows it, on LOCAL, CERT and PROD. Read on 17 Nov: a signed-in administrator holds the right to delete from the registration table, a visitor does not, and the table's one policy admits administrators only. So this change needs no migration.
  • A refused delete does not raise an error. When the database's row rules refuse a delete, the request still answers „success” with zero rows. The new code therefore counts a removal as done only when the database returns the removed row.
  • The administrator's calendar is the public calendar. App.svelte knows whether someone is signed in (isAdmin) but does not tell CalendarView; the list is opened through RegistrationModal → EntryList. The sign-in state has to be handed down that one path.
  • The public pages cannot show the button. The registration page and the WordPress calendar mount the list through custom elements that have no sign-in and will not pass the new setting.
  • The list already knows each entrant's gender, so the confirmation can say „Zawodniczka” or „Zawodnik”.

04 · Scope

Files that change, and what must not

  • frontend/src/lib/api.ts: a new deleteRegistration(id) that deletes one row by its identifier and fails unless the database returns that row.
  • frontend/src/components/EntryList.svelte: three optional settings (may remove, event name, registration open); the row button, the confirmation, the done and failed lines. Without the settings the component renders exactly as now.
  • frontend/src/components/RegistrationModal.svelte, CalendarView.svelte, App.svelte: hand the sign-in state, the event's name and whether registration is open down to the list. Whether registration is open comes from the rule that already hides the registration link on the calendar card; no second copy of that rule.
  • frontend/src/lib/locales/pl.json, en.json: the texts of §03.

Not touched: the database, the registration form, the two custom elements for the public pages, the tiles, search, filters and sorting, the organizer's download page. The 19 original entry-list tests and ELSEL.01–17 stay as they are and stay green.

10 · Issues met

Found during planning

  • W1 · The documentation search tool is missing from this session. The research for this plan read the owning pages and the source directly. It has to be back, or I read each page in full, before the documentation gate.
  • W4 · Found by CV.15: signing out removed the buttons but left an open confirmation on screen. Fixed: the confirmation renders only while removal is allowed.
  • W5 · P1, found in the pixel sheet: on a phone the „Usuń” button was clipped at the card's edge (its cell kept the desktop width rule, 3 px). Fixed in the phone layout; visitors never have that cell.
  • W6 · P2, found in the pixel sheet: after a removal far down the list the done line was out of view and focus fell to the page. Fixed: focus moves to the done line, which brings it into view (ELREM.05 extended, seen red first).
  • W7 · The WordPress calendar mounts the same application, so the setting reaches its code path. Checked: the application resets sign-in on load and opens one only on github.io or the page carrying admin-entry; WP.ADM.01 (frontend/tests/SiteChrome.test.ts) pins that the calendar page ignores ?admin=1. Nothing to fix.
  • W8 · The organizer's download could not be exercised end to end on LOCAL (no organizer key there). The deployed function reads tbl_registration live, with no snapshot, so a removed entry cannot reach the files.
  • W3 · The existing delete buttons in the event editor use the browser's bare confirmation box, which cannot name the fencer and the event the way the signed mock does. This plan builds the confirmation inside the list instead and leaves the event editor's buttons alone, because they are outside what you asked for.
