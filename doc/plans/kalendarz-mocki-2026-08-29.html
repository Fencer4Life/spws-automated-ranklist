Why this matters beyond tidiness The overlap-and-fan machinery in layoutRow() — PANEL_STEP_FLOOR, the z-index: 200 − |i−sel| × 2 stack, the two text tiers — exists only because quarters overflow. At monthly granularity nothing in today's pool overlaps at all. It stays in the code, because PZSz senior events could push a month to 6–8 tiles (303–399px), which still exceeds 320px. But it stops being the common case.

The colour budget is spent on the past

CalendarBarrel.svelte:40 sets the tinted-fill class on enum_status === 'COMPLETED'. On PROD that is 67 of 114 events. So roughly three-fifths of the drum is coloured-in and finished, while the events you can still enter render as plain white tiles. The flip you asked for is not cosmetic — it moves the colour onto the 39% that is actionable.

Nothing in the calendar is lit

The drum's cylinder illusion rests entirely on rotateX(±46deg) scale(0.88) plus a flat opacity: 0.42, inside overflow: hidden. There is no shading of any kind, and the rim is a hard clip. The card is flatter still: background, border-radius: 12px, padding: 12px — and not one box-shadow or gradient in all 533 lines.

Switzerland is drawn wrong, structurally

CH: cross('#DA291C', W) renders into a 19×13 box with arms at height:24% and width:24% — that is 3.1px vertically against 4.6px horizontally, so the cross has unequal arms. Switzerland's flag is also square, the only square European national flag besides the Vatican's. A 3:2 box draws a different flag. It is live right now on PEW10e-2026-2027 in Lausanne.

One claim in the code does not hold up CountryFlag.svelte:121 cites ADR-007 for a CSP that blocks fetched assets. ADR-007 is "Shadow DOM (Implemented M8)" and says nothing about CSP, images or assets, and no CSP exists anywhere in the repo. The second constraint in that comment is real — a document-relative <img src> inside a custom element resolves against the host page and 404s, because vite.config.ce.ts sets no base. That argues against <img>, not against images. Inlined SVG sidesteps it, which the component's own union and art branches already prove.

02The colour model

ADR-084 set out to give each variable its own visual channel, then tied fill to status — so completion and type ended up fighting over the same surface. The fix is not to add a dimension but to move organizer off hue and give hue to time.

I checked every candidate against the real pool before choosing:

CandidateCoverageVerdict
Time proximity91/91 datedprimary the only dimension with full coverage and decision value
Organizer / type100%answers "who runs it" — nobody chooses on it. Demote to a shape cue
Country19/20 upcomingkeep, but as a flag, not a hue
Registration open2 of 20 upcomingtoo sparse badge dot only
Weapons103/111 identicaldead channel
Status enum67 COMPLETEDredundant with time; CREATED-vs-PLANNED is admin noise

The resulting assignment, one meaning per channel:

  • Hue + saturation → time. Grey (past) → tint (upcoming) → saturated (≤7 days).
  • Organizer → non-chromatic. Already in the label (PPW1, EVF3); reinforced by an edge or dot.
  • Country → circle flag, now on the tile, not only the card.
  • Registration → badge dot. Cancelled → grey + strike. Next → ring. Selected → outline + caret.
The cost, stated plainly A past event loses its type hue. That is the deliberate trade: type stays legible in the tile label, and past events are the ones you scan least. If that turns out to be wrong, treatment B below keeps a type-coloured edge on past tiles at some cost to the recede effect.

03The whole UI, interacting

Barrel and card together, as they actually work: tap the row above or below to rotate, tap a tile on the focused row to select it, and the card beneath updates with the caret tracking your selection. Both are live against the real PROD pool, at phone width and desktop. "Today" is pinned to 29 August 2026.

Every link and button is here The card renders the copy-address button, the organizer announcement (invitation), the results links — labelled by day, never by weapon, per ADR-040 — the registration link and the entry-list link, each under the same conditions as registrationState(): registration while the cutoff is open, entry list until the event starts and never once cancelled, results only when the event is COMPLETED and URLs exist. 42 of 91 PROD events carry an invitation link, which an earlier version of this mock omitted entirely.
Rows are centred — reversing a deliberate choice The rows are now centred rather than left-aligned. CalendarBarrel.svelte chose left-alignment on purpose: "Every row starts on the same edge, so nothing drifts as the drum rotates between rows of different widths." Centring reintroduces that drift — a month with one event and a month with four now have different left edges, so tiles shift sideways as you rotate. Monthly granularity makes this more visible than quarters did, because row counts vary more (1 to 4 rather than 5 to 9).

It is implemented the safe way: margin: 0 auto, not justify-content: center. Auto margins absorb only positive free space, so a row that fits is centred while a row that overflows still left-aligns and stays scrollable — verified on a nine-tile quarterly row, whose leading tiles remain reachable rather than being pushed into negative scroll space. Worth looking at while rotating to decide whether the drift is acceptable.
Flags are off the tiles A flag at 11 px inside a 48 px tile added clutter without adding a decision, and it competed with the day number for the one thing a tile is for. The country stays where it reads properly — on the card's location line, at 15 px, next to the place name. The circle-flag work in §06 is unaffected; it is about the card.

04Rotation — the drum is a true cylinder

Two approaches were built. The first, gradient shading, was rejected outright: it painted a picture of depth onto a stack that was never curved, and read as exactly that.

Chosen — true cylinder geometry, seven rows, no motion effects Each row sits on the surface of a real cylinder — rotateX(i·θ) translateZ(R) with R = (rowHeight/2) / tan(θ/2) — and the drum rotates as one body. Foreshortening at the rim, the compression of spacing toward the horizon, occlusion, and rows turning away from the viewer all fall out of the perspective projection rather than being drawn. At θ = 26° the disc carries seven rows, and a receded row measures 50 px against the focused row's 77 px — real perspective compression, not a scale trick.

Momentum overshoot and motion blur are both off. They were the two motion effects layered on top, and they are what made the first pass feel wrong — the drum lurching past its stop and smearing while it moved. Without them the rotation is a clean, quiet 0.42 s step. The geometry was never the problem; the theatrics were.

Two implementation notes that cost time and are worth carrying into the build. A drum whose DOM is rebuilt on rotation cannot animate at all, because a CSS transition needs the same nodes on both sides of the change — CalendarBarrel.svelte already warns about this in its header. And the rotation is -active × θ, which reaches -1456deg by row 56, so a freshly built drum must arrive at its angle rather than travel to it; suppress it synchronously with a forced reflow, not requestAnimationFrame, which never fires in a hidden tab and would strand the transition permanently off.

The row-count control matters more than it looks. Today only three rows are ever visible, because .far is opacity: 0 — and three rows read as a stack of cards. Seven, with the outer ones properly foreshortened, is what makes the eye see a barrel. Because those extra rows are compressed hard at the rim they cost very little height: measured in the mock, a row at 26 deg is 50 px tall against the focused row's 77 px.

Implementation gotcha, found while building this The drum's rotation is -active × θ, so at row 56 it is rotateX(-1456deg) — four full turns. Stepping between adjacent rows animates only 26 deg, so that is harmless in use, but the first paint would spin through every one of those turns. Either suppress the transition on initial render or keep the angle modulo 360. Worth knowing before it is discovered as a bug.

05Card shading

The card is currently a flat rectangle. These add depth without removing or reordering a single piece of its content, and the caret keeps it welded to the selected tile.

Rejected — the top-lit surface gradient A vertical light-to-dark wash across the card face, so it would read as a panel lit from above and agree with the drum's light source. Rejected. The card carries a lot of small text — fee keys, chips, pills — and a gradient behind them shifts the contrast ratio from top to bottom, which costs legibility for an effect the elevation shadow already delivers more cleanly. Removed, not just switched off.

06Circle flags, and Switzerland

Circular chips remove the aspect-ratio problem entirely — there is no 3:2 box to force a square flag into, so Switzerland is simply correct. Below, the current CSS-geometry rendering against circular chips, for every country in the live pool.

The full set is ~260 countries at 564 KB, small enough to inline whole — so a championship in a country nobody has visited yet still renders.
Interaction model — settled The drum rotates only on a tap above or below the focused row, one row per tap, skipping empty months. Events are selectable only from the focused row; a tap on a receded row's tile rotates instead of selecting. There is no sliding, wheel, swipe or drag.

Two of these three rules already hold in CalendarBarrel.svelte: rotation is click and keyboard only, and pick() guards with if (qi !== active) { rotateTo(qi); return }. The only genuine change is skipping empty rows, which barely mattered across four quarters and matters a great deal across eighteen empty months.

Still open — these block implementation What counts as "past". The greying has to key off something, and it is not settled. Recommendation on file: dt_end < today with a seven-day grace window, which is also what ADR-084's own unresolved open item 1 proposes. The mock uses exactly that.

A 48-row drum. Monthly granularity spans 66 rows including empties, against 19 today. Auto-roll handles the gaps, but rolling from January 2023 to September 2026 is still a long spin — does it need a jump-to-today control?

The registration dot needs a column that does not exist. The rule is "today between the registration start and the event end", but tbl_event stores only dt_registration_deadline, dt_start and dt_end — there is no registration-start date anywhere in the schema. The mock approximates the opening bound with "a registration URL exists", which is not the same thing: the URL is typically set the moment the event is created, so the dot lights up far earlier than intended. Doing this properly means adding dt_registration_open (migration + ADR-030 amendment, since that ADR owns the registration window). Worth noting the closing bound is dt_end as you specified, which runs past the deadline — so the dot marks a live registration/participation window rather than the link's availability, and it will stay lit after the registration link itself has disappeared. Confirm that is intended.

08Decisions I need from you

Question 1 — tile treatment Which of A / B / C / D, or a hybrid? My recommendation is B with D's countdown text used for the imminent state. Everything else in the plan is independent of this choice.
Question 2 — what counts as "past" The greying has to key off something. Date (dt_end < today) is honest and predictable but greys an event the morning after it ends, while people are still hunting for results. Status (COMPLETED) is what the code does today, but an event can sit un-ingested for weeks still looking upcoming. My recommendation is date with a seven-day grace window, which is also what ADR-084's own open item 1 proposes and never resolved. The mocks above use exactly that.
Question 3 — the drum is now 48 rows deep Monthly granularity means the drum spans 65 rows including empties, against 19 today. You have asked for auto-roll past empty months, which the mocks implement. But rolling from January 2023 to September 2026 is still a long spin. Do you want a jump-to-today control, or is the drum opening on the right row enough?
