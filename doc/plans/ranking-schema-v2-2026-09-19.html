01 · Outcome and scope

What exists after this lands

Today, tbl_scoring_config.json_ranking_rules holds one implicit schema — {"domestic": [...], "international": [...]} — read by six independently-maintained functions (three ranking concerns × two carry-over engines). It has no room for a third, PZSz-flavored rule group, and no versioning to let a new shape coexist with the old one. Season default ranking mode (design §05's table) is not a column anywhere. This step:

  • Defines schema_version: 2 for json_ranking_rules: three independent Season Scoring Rules sections (spws, evf_fie, pzsz), each naming a display group, its types, and its buckets; a display_groups map from group to sections; a views map from mode (PPW, RANKING) to the groups it exposes — exactly the shape in design §06.
  • Adds tbl_scoring_config.enum_default_ranking_mode (PPW | RANKING), the column the governance-lock plan's own Flags section deferred ("its column doesn't exist yet... belongs to ranking schema v2, design step 4"), and folds it into the existing lock guard in the same migration.
  • Adds one new public RPC, fn_ranking_full, returning rank, id_fencer, fencer_name, spws_total, evf_plus_total, total_score, bool_has_carryover — the design's "generalized ranking RPC" — dispatched per season carry-over engine exactly like the three existing ranking functions (ADR-042/045 pattern).
  • Makes fn_ranking_full read either schema shape through one canonicalization step, so it is provably correct against the real, golden 2023/2024–2025/2026 seasons (still on schema v1) before any season is ever moved to schema v2.

Deliberately out of scope — found necessary during baseline verification, not assumed

No existing function is modified, and the real SPWS-2026-2027 season's json_ranking_rules is not touched. fn_ranking_ppw, fn_ranking_kadra, fn_fencer_scores_rolling and their four _event_code_matching/_event_fk_matching bodies are untouched, byte-for-byte. See §03 for why, and §11 for when the real cutover happens.

Also out of scope, per the design's own step boundary: the Admin UI for authoring season_scoring_rules (step 7); the SPWS/EVF+/Razem ranklist, drilldown and export UI (step 7); publication boundary / enum_ranking_publication (step 5); PZSz ingestion itself (step 6) — this step only makes the ranking side ready to score PZSz results once they exist.

03 · The gap this plan found

Cutting the active season over to schema v2 today would silently break the live ranklist

Design §11 step 4 says "Ranking schema v2... before changing frontend consumers." Read literally that sounds like a frontend-only deferral. It is not: the live, unmodified frontend today queries fn_ranking_kadra and fn_ranking_ppw for whichever season is active — currently SPWS-2026-2027 — and those functions read v_rules -> 'domestic' / v_rules -> 'international' directly. Schema v2 has no top-level domestic/international keys at all; it nests everything under season_scoring_rules. If this step wrote schema v2 into the real SPWS-2026-2027 row, fn_ranking_kadra would either error or silently return an empty international bucket for the currently active season — a production ranklist regression — for the entire interval between this step landing and step 7's frontend cutover.

This is exactly the class of gap planning.md rule 3 exists to catch (walk the concrete scenario, not the abstract design). The resolution below is locked into this plan rather than left as a live judgment call during implementation.

Locked decision: the real SPWS-2026-2027 row is not touched by this migration

fn_ranking_full is built and pgTAP-proven against (a) the real, golden 2023/2024–2025/2026 seasons on schema v1 — via the canonicalization adapter, §06 — and (b) LOCAL-only scratch seasons carrying real schema v2 JSON, the same fixture pattern this branch already used for SS26.LOCK/SS26.REVISION (isolated scratch seasons, not the shared active season). The live SPWS-2026-2027 config keeps its current schema-v1 shape, continues to be served by the untouched fn_ranking_kadra/fn_ranking_ppw, and is cut over to schema v2 only in design step 7, in the same change that moves the frontend onto fn_ranking_full. Doing both together means there is never a moment where the live season's stored JSON and the function reading it disagree about its shape.

04 · Proposed ADR-098 — sign-off requested before the file is written

Season Scoring Rules v2: three rule sections, two display groups, one new generalized RPC

Per doc/claude/planning.md rule 6, this ADR is drafted here and not written to doc/adr/098-… until you say so. Everything else in this plan — schema, canonicalization, fn_ranking_full, tests — can be implemented once you confirm the plan; only the ADR file's creation waits.

Context. The design (§06) requires three independently-configured Season Scoring Rules (SPWS, EVF/FIE, PZSz) that aggregate into exactly two publicly displayed groups (SPWS, EVF+), plus a governed "default ranking mode" per season. The existing bucket schema only has two implicit groups and no versioning, and no column exists for default mode.

Decision. Introduce schema_version: 2 for json_ranking_rules: season_scoring_rules (three named sections, each a group + types + buckets), display_groups (group → sections) and views (mode → groups), exactly as design §06 specifies. Add tbl_scoring_config.enum_default_ranking_mode, governed by the existing lock (ADR-097) from the moment it exists. Add fn_ranking_full(p_weapon, p_gender, p_category, p_season, p_rolling), dispatched per carry-over engine following the ADR-042/045 pattern already used three times in this codebase. Internally it canonicalizes either JSON shape (v1's domestic/international, or v2's season_scoring_rules) into one internal group/type/bucket representation, then runs a single generic best/always aggregation loop per declared group — one loop definition instead of duplicating it per (engine × group). fn_ranking_ppw, fn_ranking_kadra, fn_fencer_scores_rolling and their four per-engine bodies are left untouched. The real SPWS-2026-2027 row is not migrated to schema v2 in this step (§03) — that happens in step 7, together with the frontend cutover. PZSz (PPS/MPS) carry-over is explicitly excluded from the generic carried_eligible resolution and begins disabled, matching design §07's "future PPS/MPS carry-over... begins disabled."

Alternatives rejected. A legacy-shape translation shim inserted into all six existing duplicated ranking functions, rather than one new RPC — rejected: it multiplies the surface that must agree with the new validation rules, and this codebase already has one documented instance of exactly this drift class (ADR-096, two independently-drifting copies of the tournament-code formula). Cutting the real SPWS-2026-2027 row over to schema v2 immediately — rejected per §03: the live frontend still calls the untouched old functions against the active season, and they cannot read the new shape. Six new functions mirroring today's six (one per engine × group) — rejected as unneeded duplication now that a generic loop can cover all three groups from one canonical structure. Validating season_scoring_rules shape inside fn_import_scoring_config at save time — deferred, not rejected: no Admin UI exists yet to author schema v2 JSON (step 7), so validating where it can actually be exercised today — read time, inside fn_ranking_full — is what this step can test; save-time validation is added when the editor UI lands.

Consequences. fn_ranking_full becomes the only code that understands schema v2, and the only code that understands both schemas at once; the four frozen schema-v1-only functions and this one new function coexist for a bounded, documented interval ending at step 7. The default-ranking-mode column joins the governance lock's field list in the same migration, closing the flag the governance-lock plan left open. A later step must still build the Admin UI for authoring season_scoring_rules, migrate the frontend from fn_ranking_kadra/fn_ranking_ppw to fn_ranking_full, and cut SPWS-2026-2027's JSON over to schema v2 as part of that same change — not before.

Relationships. Extends ADR-042/ADR-045 (the dispatch pattern). Composes with ADR-097 (the field-level governance lock gains one more governed field). Prepares for, but does not implement, the still-open Proposed ADR B (PZSz) and Proposed ADR C (publication boundary) from the design's §12.

The schema v2 JSON shape (design §06, verbatim)

{
  "schema_version": 2,
  "season_scoring_rules": {
    "spws":    { "group": "spws",      "types": ["PPW", "MPW"],               "buckets": [{"best":4,"types":["PPW"]}, {"always":true,"types":["MPW"]}] },
    "evf_fie": { "group": "evf_plus",  "types": ["PEW", "MEW", "MSW", "PSW"], "buckets": [{"best":3,"types":["PEW","MEW","MSW","PSW"]}] },
    "pzsz":    { "group": "evf_plus",  "types": ["PPS", "MPS"],               "buckets": [{"always":true,"types":["PPS","MPS"]}] }
  },
  "display_groups": {
    "spws":     { "sections": ["spws"] },
    "evf_plus": { "sections": ["evf_fie", "pzsz"] }
  },
  "views": {
    "PPW":     ["spws"],
    "RANKING": ["spws", "evf_plus"]
  }
}

A section's own group field and its membership in display_groups.<group>.sections must agree — this is asserted, not merely documented (§06 RANK.07 double-count test covers the failure mode where they disagree).

06 · Canonicalization and validation

One function reads either shape; validation happens where it can be tested today

fn_ranking_rules_canonical(v_rules JSONB) RETURNS TABLE(section TEXT, grp TEXT, types TEXT[], best INT, always_include BOOLEAN, bucket_idx INT) — a new, small, set-returning function, called once at the top of fn_ranking_full's per-engine bodies, replacing what would otherwise be six copies of the same branch:

  • If v_rules is NULL or has no schema_version key (schema v1, or the pure-legacy NULL season): treat domestic as section spws/group spws, and international as section evf_fie/group evf_plus (no pzsz section — historically it cannot exist). This is the "frozen compatibility adapter" design §06 names.
  • If v_rules->>'schema_version' = '2': read season_scoring_rules directly, one row per bucket per declared section.
  • Any other schema_version value: RAISE EXCEPTION 'Unsupported ranking rules schema_version: %' — fail closed on a future, not-yet-understood version rather than silently misreading it.

Validation, raised inline while canonicalizing (each condition below maps directly to one SS26.RANK test in §09):

  1. A bucket's types array contains a value not in enum_tournament_type → RAISE 'Unknown tournament type in ranking rules: %'.
  2. A bucket has both best and always, or neither → RAISE 'Ranking bucket must declare exactly one of best or always'.
  3. best <= 0 → RAISE 'Ranking bucket best must be positive, got %'.
  4. A section's declared group does not match the group under which display_groups lists that section, or a section is listed under two different groups → RAISE 'Ranking section % is assigned to conflicting display groups'.
  5. The same tournament type appears in two sections that both feed the same views entry → RAISE 'Tournament type % is double-counted within view %' (computed by unioning, per view, every type reachable through that view's groups → sections → types, and checking for a non-empty intersection between any two sections in the same view).

07 · fn_ranking_full — the new generalized RPC

Same dispatch pattern as the three existing ranking functions, one new pair of bodies

fn_ranking_full(
  p_weapon   enum_weapon_type,
  p_gender   enum_gender_type,
  p_category enum_age_category,
  p_season   INT DEFAULT NULL,
  p_rolling  BOOLEAN DEFAULT FALSE
) RETURNS TABLE (
  rank               INT,
  id_fencer          INT,
  fencer_name        TEXT,
  spws_total         NUMERIC,
  evf_plus_total     NUMERIC,
  total_score        NUMERIC,
  bool_has_carryover BOOLEAN
)

A thin dispatcher (identical shape to fn_ranking_ppw/fn_ranking_kadra/fn_fencer_scores_rolling) resolves the season's enum_carryover_engine and calls fn_ranking_full_event_code_matching or fn_ranking_full_event_fk_matching, ELSE RAISE EXCEPTION 'Unknown carryover engine: % for season %' — the same fail-closed CASE ADR-042/045 established. Each body:

  1. Calls fn_ranking_rules_canonical once for the season's json_ranking_rules.
  2. Resolves current_eligible (this season's scored results, gender/category-effective per ADR-034) and carried_eligible (prior-season results for types in any section's types, at positions not yet completed this season — the existing FR-68/ADR-021 mechanism, reproduced not reinvented) exactly as the existing per-engine bodies do, except carried_eligible explicitly excludes PPS/MPS regardless of section membership — design §07's "begins disabled" (§09 RANK.12).
  3. For each canonical (section, grp, types, best, always_include) row, computes that section's contribution: always_include sums every eligible score of its types; a best bucket sums the top-best eligible scores of its types — the same rank-and-cap logic fn_ranking_kadra_event_code_matching's best_pew/next_pew CTEs already use, generalized to N groups instead of hardcoded to two.
  4. Sums every section whose grp = 'spws' into spws_total, every section whose grp = 'evf_plus' into evf_plus_total — no third bucket, no per-section subtotal returned, matching design §06's "EVF+ exposes one subtotal only."
  5. Returns rank ordered by total_score DESC, exactly like the three existing functions.

fn_ranking_full takes no view/mode parameter — the caller (eventually the frontend, in step 7) decides whether to show spws_total alone (PPW view) or both totals (RANKING view); the RPC always computes both, since a PPW_ONLY season's evf_plus_total will simply be zero or absent-in-practice until that season ever configures an evf_fie/pzsz section. Enforcing the views map's membership at the presentation boundary is step 5/7's job (enum_ranking_publication), not this RPC's.

Grants

GRANT EXECUTE ON FUNCTION fn_ranking_full(...) TO anon, authenticated; — identical grant to fn_ranking_ppw/fn_ranking_kadra today (public ranking read, no write). fn_ranking_rules_canonical is an internal helper: REVOKE ALL ... FROM PUBLIC, anon, called only from SECURITY DEFINER functions that already have season read access.

08 · Scenario walkthroughs

Concrete behavior at the boundaries

A. A schema-v1 season computed through the new RPC (parity check)

  1. A pgTAP test calls both fn_ranking_kadra(weapon, gender, category, id_season_2025_2026) (old, untouched) and fn_ranking_full(...) for the same arguments.
  2. fn_ranking_rules_canonical sees no schema_version key, applies the legacy adapter, and produces exactly the two sections spws/evf_fie that reproduce domestic/international.
  3. fn_ranking_full's spws_total equals fn_ranking_kadra's ppw_total; evf_plus_total equals its pew_total, for every fencer in the golden fixture — SS26.RANK.11.

B. A schema-v2 scratch season with all three sections populated

  1. A pgTAP fixture creates an isolated scratch season (not the shared active one — the pattern this branch's own 02_scoring_engine.sql fix already established) with a full schema-v2 json_ranking_rules and PPW, PEW and PPS results.
  2. fn_ranking_full returns non-zero spws_total (from the spws section) and a single evf_plus_total combining the evf_fie PEW score and the pzsz PPS score — no separate PZSz column exists in the row.
  3. Removing the PPS result changes only evf_plus_total; spws_total is unaffected — sections are independent, as designed.

C. A malformed configuration

  1. A test builds a season_scoring_rules value where evf_fie and pzsz both list PSW in their types, and both feed evf_plus.
  2. fn_ranking_rules_canonical detects the intersection under one views entry and raises before any aggregation runs — the caller gets a clear error, never a silently inflated total.

D. The real, active season today

  1. An operator calls fn_ranking_full against the real SPWS-2026-2027 id_season out of curiosity.
  2. Its json_ranking_rules is still schema v1 (§03 — untouched by this migration), so the legacy adapter path runs, and the result matches what fn_ranking_kadra/fn_ranking_ppw already return for it today.
  3. The live frontend is unaffected either way — it still calls the old functions, unchanged, until step 7.
