3 · What rebuilding LOCAL exposed

These were all found while trying to make LOCAL match PROD, and all three are pre-existing. None was introduced by the identity work.

a · The seed could no longer load at all

Migration 20260903000001 inserts the PZSz organizer, idempotently, and its comment says plainly that this is so "the seed dump that follows on a fresh bootstrap cannot duplicate it". But the guard was only on the migration's side: the seed's own INSERT INTO tbl_organizer was unguarded. Once PZSz reached PROD, the first dump taken afterwards failed the entire seed on idx_organizer_code. Two idempotent halves are not idempotent together unless both guard. Fixed in export_seed.py: the seed now upserts on txt_code, and wins, because the dump is the PROD truth.

b · LOCAL was never a copy of PROD — and wrong in the worst possible place

Three data migrations add fencers by hand and run before the seed, against an empty table — so their own WHERE NOT EXISTS guards pass, they insert, and the seed then inserted the same 18 people a second time.

LOCAL, beforePROD
Fencers385367
Same-name pairs172
Duplicate exact triples170

Same-name pairs are precisely the input that makes identity resolution ambiguous, so every local test of duplicate-name behaviour was running against a table PROD does not have — and against eight times as many collisions. Fixed: the seed now skips anyone already present on the identity triple, using IS NOT DISTINCT FROM so the nine fencers with no birth year do not duplicate on every reset. LOCAL now reads 367 / 9 null / 20 estimated / 2 pairs / 0 duplicate triples — PROD exactly.

c · A registration test that only passed on an empty table

57_registration_trim_trigger identified its fixture row by birth year alone (WHERE int_birth_year = 1979). That is unique only while tbl_registration holds nothing but the test's own data; PROD has several fencers born 1979, so the subquery returned more than one row and the file aborted. Fixed by scoping both affected assertions to the test's own event. This is the same class of fragility as (a) and (b): correct against an empty database, wrong against a real one.

4 · Repeatable, and CI-safe

scripts/mirror-prod-local.sh now does the whole thing in one command: export PROD read-only, reset LOCAL against that dump, and load the registrations. It deliberately does not disturb the committed seed_prod_latest.sql pointer — the symlink is repointed for the duration of the reset and restored on any exit, including a failed one, so a local experiment can never silently become a CI change.

Registrations are fetched separately rather than added to the dump, because ADR-079 makes tbl_registration ephemeral — purged once results are ingested. Baking real declarations into the shared seed would push 57 people's entries into every CI run and every developer's machine, permanently. They are resolved by natural key, since surrogate ids differ between environments.

5 · The open decision

Do we adopt the fresh 2026-09-12 seed, or keep the committed pointer at 2026-08-08?

On the 2026-08-08 snapshot the suite is 946/946 green. On current PROD data, six files fail — and not because the code changed, but because they assert things about the shape of the data that were true in August and are not true now:

FileWhy it fails on current PROD data
19_phase3_wizarddeletes an event that now has tournaments — FK violation
54_evf_calendar_prior_link_reassignmentsubquery now matches more than one event
56_evf_predecessor_event_fragment_repair56.25 expects a PEW count of 12
63_prod_mirror_rename63.3 expects a specific post-rename event code
67_event_first_published_date67.4 asserts no event shows the moved-date pill; one now does
74_no_evf_season_skeletonsdeletes an event that now has tournaments — FK violation

All six are calendar/event tests. Every registration and identity test passes on current PROD data, including all 25 of the new file, 52's security posture, and 57/58/59.

  • Keep the pointer at 2026-08-08. CI stays green. The fresh dump stays a local testing artifact, reachable any time via the mirror script. Nothing is hidden — the six tests are still coupled, we simply have not paid for it yet.
  • Adopt 2026-09-12 and fix the six. Honest, and stops the coupling growing quietly worse, but it is real work on event/calendar tests that has nothing to do with PPW1 — and PPW1 is in fourteen days.
Recommendation A for now, B after PPW1. The coupling is worth fixing, but not in the two weeks before the event it would delay, and not mixed into the identity change where a red suite would obscure what the identity work actually did. The exporter fixes in (a) and (b) stay regardless — without them no future refresh loads at all, and that is the part that would have bitten silently. Worth logging (67.4 especially: it asserts a property of PROD's data, not of our code, so it will keep drifting).
