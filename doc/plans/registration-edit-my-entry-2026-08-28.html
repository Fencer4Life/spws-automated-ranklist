Correcting a typo no longer makes a second entry

Adding a forgotten weapon always worked. Fixing a misspelled name did not — it left the wrong entry on the public roster and added a second one beside it. Both defects are now fixed and the edit path is built.

Decide this first

There is no edit path at all

You asked for more back buttons so a fencer who spots a mistake on the roster can go back and correct it. The back button is the easy half. The hard half is that there is no edit path at all — the only public write is fn_create_registration, and for an unmatched fencer it decides "same person" by the declared name. Change the name and it is, by definition, a different person, so it inserts.

× Proven on LOCAL, three calls in one transaction

Registered KOWALKSI Adam (typo) → row 18. Re-submitted as KOWALSKI Adam → row 19, a second row; row 18 survives, on the public roster and in the organizer's seed file. Re-submitted again adding a weapon → row 19 reused, arr_weapons updated to {EPEE,SABRE}.

typo_row=18 corrected_row=19 weapon_edit_row=19 18 | KOWALKSI | Adam | {EPEE} ← orphan, still public 19 | KOWALSKI | Adam | {EPEE,SABRE} ← weapon edit did update in place

Same for birth year — it is part of the arbiter by design, and the migration says so. Matched fencers are unaffected: their arbiter is UNIQUE(id_event, id_fencer), so a name correction updates in place. The exposure is exactly the unmatched population — newcomers typing their name into this system for the first time, which is the group the subsystem exists to collect data from.

So a back-to-identity button, shipped on its own, would not fix mistakes. It would make the duplicate easy to create instead of merely possible.

"Keep only one entry, the latest"

That already works — and it is already event-scoped

Both halves of what you asked for are implemented. Re-registering with an existing SURNAME · Name · BY updates the row in place rather than adding one, and registrations for different events cannot touch each other because id_event is the first column of both arbiters. Run against LOCAL:

A: first=21 second=21 same identity, same event, submitted twice B: other event=23 same identity, different event 21 | PPW1-2026-2027 | — | TESTOWY Jan | {FOIL,SABRE} ← one row, weapons updated to the latest 23 | MSW-2026-2027 | — | TESTOWY Jan | {EPEE} ← untouched by the other event

So nothing needs building for that. But the same run exposed a hole the rule does not close.

× One person, one event, two rows — matched and unmatched do not dedupe against each other

The two branches use different arbiters: UNIQUE(id_event, id_fencer) when matched, the partial index … WHERE id_fencer IS NULL when not. Nothing spans them. Register while unknown to the database, then get added to tbl_fencer, then register again — and the second submission takes the matched branch and inserts, leaving the first row standing.

C: matched re-reg=24 same person, same event, now known to tbl_fencer 21 | PPW1-2026-2027 | — | TESTOWY Jan | {FOIL,SABRE} ← the unmatched row survives 24 | PPW1-2026-2027 | 481 | TESTOWY Jan | {EPEE} ← and a matched one appears beside it

This is not hypothetical. Unmatched registration is now the normal path for newcomers, and a fencer's tbl_fencer row gets created during the very window in which registration is open — by result ingestion of an earlier event, or by an administrator adding them by hand. Both entries then reach the public roster and the organizer's seed file.

It is reachable from the other direction too, and by design rather than by accident: submitIdentity() deliberately treats a failed lookup as "no match" so a network blip never blocks an entry. A fencer who is in tbl_fencer but whose lookup times out is written unmatched, beside their own matched row.

The fix, if you want it: before either branch inserts, absorb the twin from the other. Matched insert finds an unmatched row with the same declared identity for that event and promotes it — sets id_fencer on the existing row rather than creating a new one, preserving ts_created and the consent stamp. Where a matched row already exists, the unmatched twin is removed instead. One migration to fn_create_registration, plus pgTAP for both directions. It is independent of the edit-path decision below and could ship first.

Your question — and it kills option A

"Will this still work a few days later?"

No. You are right, and it is worse than a session timeout.

× The token dies the instant you press ×

RegistrationModal is wrapped in {#if open}. Closing it does not hide the form, it unmounts it — every piece of component state goes with it, an edit token included. On the standalone page a reload does the same. So a token held in memory is gone in seconds, never mind days.

For a correction to work days later — plausibly on a different device from the one that registered — the capability has to outlive the browser session. That leaves three places to put it, and two of them do not survive contact with how this system is actually deployed:

✗localStorage
  • Survives reloads and days, but it is origin-bound. register.html is served from fencer4life.github.io; the calendar element is embedded in the WordPress CMS page. Different origins, separate stores — register through the modal, and the standalone page cannot see your token, or the reverse.
  • Device-bound too: register on your phone, correct on your laptop, nothing is there. Private browsing and cleared site data lose it outright.
✗E-mailed edit link
  • Would work across devices and time — but it needs an address on file, and the consent text a fencer accepts today says e-mail is „jednorazowa weryfikacja · nie przechowujemy". Keeping one to send an edit link inverts that, so it is a genuine CONSENT_VERSION bump, the same class of change as the club field.
  • The delivery infrastructure was never built either — ADR-079's Phases 4/5 are exactly the magic-link path that got skipped.
DRe-identify on return — the revised recommendation
  • Store nothing. The fencer comes back whenever they like, on any device, and enters the identity they originally declared — the name as they typed it plus their birth year. The system finds that registration, shows the current declaration and lets them change any field, including the name, updating the row by primary key.
  • Survives the ×, a closed tab, a new phone, and a week — because there is nothing to survive. The key is what the fencer knows.
  • Half of it already exists: checkForExistingEntry() already looks a fencer up on the roster and warns "someone with this name is already entered". It warns where it could offer to edit.

i Why the security objection is smaller than it looks

Gating on name + birth year is not a strong secret: the roster publishes the name, and enum_age_category narrows birth year to a ten-year band. But the write path has no identity proof at all today — fn_create_registration is anon-callable and nobody verifies that you are who you say you are, so anyone can already enter anyone under any name. An edit path gated this way does not widen that surface; a vandal has an easier route already, and the organizer checks identity in person at the venue.

This also retires option B: I proposed birth year as a shared secret without checking, and the published age category makes it roughly a one-in-ten guess. B is worse than I wrote it — it buys almost nothing over D while still needing a migration.

Correction to option A above: an id_registration-keyed RPC is not merely enumerable, it is directly published — id_registration is a column of vw_registration_entry_list. Any id-keyed update must carry a real secret, which is what makes A's token necessary and what makes A's storage problem unavoidable.

Answer needed: D — re-identify on return, storing nothing — or C, ship only the safe fields now and leave name corrections to the organizer? I recommend D: it is the only option that answers the question you actually asked.

! Live-data consequence either way

PROD has 14 real entries. Whatever we choose, a fencer who has already registered under a misspelling cannot fix it themselves — their browser never kept an id or a token. Those are an organizer cleanup, not a UI feature.

Shipped

What was built

1migration 20260828000002 — absorb the twin
  • Each write branch absorbs the other's row for the same declared identity before inserting. Promotion, not delete-and-insert: ts_created and the consent stamp are the RODO evidence, and consent was given at the first submission, so that row survives and merely gains its fencer link.
  • Where a matched row already exists for that fencer, the unmatched twin is the redundant one and is removed instead.
  • A repair step collapses any twins already present. Both live environments were checked first and hold none, so it is a no-op on CERT and PROD.
  • Ten pgTAP assertions cover both directions, consent survival, event independence, and that a namesake born in a different year still keeps their own row.
2migration 20260828000003 — the edit capability
  • uuid_edit_token on tbl_registration. The client mints it and keeps it; the server only stores and compares. That direction is what lets fn_create_registration keep RETURNS INT, so a cached older bundle goes on working — simply without an edit capability.
  • fn_update_registration updates by primary key, so no arbiter is consulted and the declared name and birth year can change. It refuses a wrong or missing token, honours the same D10 window, never touches id_fencer or the consent stamp, and raises rather than merging if the correction collides with another entry.
  • fn_get_registration reads the declaration back under the same token, including the birth year the public view withholds — so the device stores only the id and the token, never personal data.
  • The old 9-argument signature is dropped, not left beside the new one. Two overloads of a single function is exactly what made the release fingerprint non-deterministic in ba4ff3a; verified afterwards that exactly one remains.
3frontend
  • lib/registrationStore.ts keys the capability per event, so overlapping registrations cannot collide. Every access is wrapped: storage that throws, has no methods, or holds a corrupted entry costs the edit capability and never the registration.
  • A Popraw dane affordance on the payment step, and on return the form restores from the server and offers Zapisz zmiany instead of creating a second entry.

Registered KOWALKSI Adam through register.html against LOCAL, pressed Popraw dane, corrected the surname and saved. ! The limit is unchanged and worth repeating

The capability is per browser and per site. A token minted on register.html is not visible to the CMS-embedded element, and a fencer who registered on their phone cannot self-edit from a laptop. Those cases — and the 14 entries already on PROD, whose browsers never held a token — remain an organizer cleanup. Option D (re-identify on return) is still the answer if you want it to work everywhere; it is not built.

i The security gate caught it, correctly

Adding an anon-callable function failed pgTAP 52.7 — ADR-083's deny-by-default allowlist. Both new functions were added to that allowlist deliberately, with the reasoning recorded there, rather than the assertion being loosened.

Revised — session-handle model

Persistence removed, on your argument

The localStorage layer is gone. The handle is minted by a successful submission, held in component state, and lost when the form unmounts. A returning fencer re-enters the tuple they declared, which upserts onto their row and mints a fresh one — so re-submission rotates the handle, which is the mechanism rather than a side effect.

✓ The story that persistence was supposed to buy, working without it

On LOCAL through register.html: registered KOWALKSI Adam, then fully reloaded the page — no prefill, no restore, localStorage.length === 0 — then re-entered the same tuple and corrected the surname. The database held one row, id 31, corrected, consent intact. Nothing was written to the device at any point.

Deleted: registrationStore.ts and its ten tests, the restore-on-load path, and fn_get_registration — which had no caller once the fencer retypes their declaration, and an anon-callable SECURITY DEFINER function with no caller is the surface ADR-083 exists to prevent. What replaced it is editToken.ts: generation only, four tests, no storage.

! Two things found while doing it

A posture script was out of sync. ADR-083 records that scripts/check-security-posture.sh duplicates the pgTAP 52.7 allowlist and must be kept in step. It runs against the live database from inside the deploy jobs, so the new function would have failed the PROD posture check. Both lists now agree, verified by comparing them programmatically.

The graph could not see two files. graphify skipped …_registration_edit_token.sql and 59_registration_edit_token.sql as sensitive — purely because their names contain "token". They hold no secrets. Renamed to …_edit_handle.sql, which matches the language used throughout this work anyway, and both are now indexed.

i One gap left open, honestly

graphify's SQL extractor emits only a file node for the edit-handle migration, so fn_update_registration is not queryable by symbol name. Not the filename (renamed and retested), not CREATE OR REPLACE (tested), and it reproduces on the file in isolation — a limitation in the extractor, which I have not worked around by contorting the SQL. The file itself is indexed and the function is fully covered by pgTAP.
