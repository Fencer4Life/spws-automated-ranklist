Gates · Override files · I21 · Plan

Preflight checks the override files against CERT as well as LOCAL

On 21 Nov 2026 preflight passed, and CI then failed on the same commit, because the two check the override files against different rosters. This plan makes preflight check both, so a commit that passes preflight also passes CI's check. Three decisions are yours (§03); nothing is built before your sign-off.

Awaiting your sign-off amends ADR-119 G43 A (2026-11-01) tests OVR.DRIFT.07 (amended), OVR.DRIFT.08 (new)

01 · What happened

Green preflight, red CI, on the same commit

  1. On 21 Nov you approved correcting fencer 164's roster birth year from 1971 to 1972 on CERT and PROD. I made the change with scripts/cloud-sql.sh.
  2. doc/overrides/PEW4efs-2025-2026.yaml names that fencer by surname, given name and birth year 1971. After the correction, that key matched no fencer on CERT or PROD.
  3. Preflight passed all 23 gates. Its override gate checks the LOCAL roster, which still said 1971.
  4. CI's override check reads the CERT roster and failed on main 7615b2fd. The Release run was skipped, so nothing was deployed. Main 1918b0ed fixed the key, LOCAL and the seed record, and released.

No harm reached an environment: the Release refused to run. The cost was one failed push, a Telegram alarm, and a release that preflight had called ready.

02 · Why preflight could not see it

Two rosters, one gate name

  • By design (G43 A, ADR-119, 2026-11-01). The gate checks “the roster the run will meet: LOCAL's in preflight, CERT's in CI”. OVR.DRIFT.07 pins that split. The design assumed LOCAL and CERT hold the same roster.
  • They differ whenever a correction is made on CERT and PROD and the LOCAL seed has not been exported again. That is the normal way a roster is corrected (cloud-db-ops), so drift is expected, not rare.
  • The gate's own name claims more than it checks. Preflight prints „override files name the roster (CI: CERT)” (scripts/preflight.sh:79) but runs --roster local. A pass reads as “CI's CERT check will pass”, and on 21 Nov it did not.
  • Preflight can already read CERT. override_drift.transport_for("cert") reads the token through the shared reader (supabase_access_token, .env first), read only. No new credential path is needed.

03 · Decisions for you

Three questions, each with my recommendation

Q1 · Which rosters does preflight check?

A (recommended) · both, as two gates. „override files name the roster (LOCAL)” and „override files name the roster (CERT, as CI)”. LOCAL is what an ingest on LOCAL meets; CERT is what CI checks. Preflight then fails exactly when CI would.

B · CERT only. Matches CI, but drops the LOCAL check that a LOCAL rehearsal depends on.

C · keep LOCAL only and rely on the procedure in Q3. The gate stays blind to the next CERT correction.

Q2 · Without the token or the network, what does the CERT gate do?

A (recommended) · it fails, saying why. As postgrestools already does when the stack is down, a gate that could not run does not pass. transport_for already exits with “SUPABASE_ACCESS_TOKEN is required”; an unreachable API fails the run the same way.

B · it is skipped with a warning. Rejected in my view: it is the quiet pass that let today's drift through.

Either way, --fast keeps the gate: it takes seconds and makes one read-only request.

Q3 · Does the roster-correction procedure change too?

A (recommended) · yes, one step in cloud-db-ops. Before correcting a fencer's name or birth year on CERT or PROD, search doc/overrides/ and the LOCAL seed (supabase/seed_prod_latest.sql) for that fencer, and change them in the same piece of work. The gate catches a miss; the step stops it happening.

B · gate only.

05 · For your sign-off

ADR-119 amendment draft

ADR-119 · Amendment (2026-11-21, I21) — preflight checks the override files against CERT as well as LOCAL

Context. G43 A checks the override files against LOCAL's roster in preflight and CERT's in CI, on the premise that the two hold the same roster. On 21 Nov 2026 a birth year corrected on CERT and PROD left an override key naming nobody on CERT; preflight passed on LOCAL's older roster and CI failed on main 7615b2fd, skipping its Release.

Decision. Preflight runs the gate against both rosters, as two gates named for the roster each reads. The CERT gate reads through the shared token reader, read only; without the token or the API it fails and says why, and --fast keeps it. CI is unchanged: its own job alone holds the token. Before a fencer's name or birth year is corrected on CERT or PROD, the override files and the LOCAL seed are searched for that fencer and changed in the same work (cloud-db-ops).

Consequences. A commit that passes preflight passes CI's override check. Preflight needs the token in .env and the network. Tests: OVR.DRIFT.07 amended, OVR.DRIFT.08.

06 · Left out on purpose

Not in this plan

  • Exporting the LOCAL seed again from PROD. A larger change of its own; today's one corrected record already makes LOCAL agree.
  • Changing the override files to name fencers by id. Ids differ between LOCAL, CERT and PROD (P3.OV19), which is why the files name fencers.
