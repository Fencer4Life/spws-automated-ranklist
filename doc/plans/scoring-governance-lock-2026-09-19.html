01 · Outcome and scope

What "closes" after this lands

Today, an administrator can edit any season's scoring configuration at any time — the client hides the ScoringConfigEditor save button when isSeasonPast(season) (a date check), but nothing on the server stops a write. A season with 777 already-scored tournaments can still have its multipliers silently changed with no audit trail and no rescore. This step makes the boundary real: the moment a season's first result is scored — not its start or end date — its scoring configuration becomes server-enforced read-only, and the only way to change it afterward is an audited, out-of-band procedure that rescores the whole season atomically.

In scope: tbl_season.ts_scoring_locked_at; an append-only tbl_scoring_config_revision audit table; per-result revision provenance; field-level authorization inside fn_import_scoring_config (locked fields reject a change, unlocked fields — the EVF/Kadra toggles — keep working through the same call); trigger guards on direct tbl_scoring_config/tbl_scoring_type_config writes; a minimal Admin scoring-engine selector (does not exist today — see §02); the privileged fn_revise_and_rescore_season procedure, reachable only outside the web Admin session; all three editor mount points reading server-authoritative lock state instead of season dates; the Polish lock explanation; backfilling already-scored seasons as administratively locked.

Out of scope, deliberately: default ranking mode locking — the design's own lock table lists it, but its column doesn't exist yet (it belongs to ranking schema v2, design step 4, not yet built); adding it to this guard now would invent schema ahead of its owning step. It gets folded into the same guard when step 4 lands the column. Also out: creating new engine versions (a new formula needs code, not data — fn_revise_and_rescore_season only re-points a season at an existing released engine); ranking schema v2 itself; PZSz ingestion.

03 · Scenario walkthrough

SPWS-2026-2027, first PPW result of the season

  1. Admin opens Konfiguracja punktacji for SPWS-2026-2027 (unscored so far under the new field-scaled engine). Every field is editable; scoring_admin_locked reads false.
  2. Admin sets a real PPS multiplier (this repo's own recent commit, bb5596b7) and saves. Ordinary write, unlocked — succeeds exactly as verified live in that commit.
  3. Ingestion commits the season's first PPW result and calls fn_calc_tournament_scores. Inside the same transaction: no active revision exists for this season yet, so one is created — a snapshot of the current tbl_scoring_config + tbl_scoring_type_config + engine, reason "initial — first scored result" — and tbl_season.ts_scoring_locked_at is set. The result itself is stamped with that revision's id.
  4. Admin reopens the same editor. fn_export_scoring_config now returns scoring_admin_locked: true. Every input is disabled; the save button is still visible and still clickable.
  5. Admin edits the MPW multiplier anyway (an old page, a stale tab, a direct API call) and clicks save. fn_import_scoring_config sees mpw_multiplier present and different from the stored value while ts_scoring_locked_at is set — raises. The frontend shows the exact Polish explanation from §05. Nothing was written.
  6. Admin flips "Pokaż przełącznik +EVF w Kalendarzu" instead — same RPC, same full-config payload, but only show_evf_toggle_calendar differs from stored. Not a locked field. Succeeds.
  7. An operator notices the FTL URL for one PPW tournament was wrong. They fix tbl_event's URL (untouched by this lock), re-run ingestion, which calls fn_calc_tournament_scores again. Active revision is already set; the result is rescored and re-stamped with the same revision. No lock error, because scoring config was never touched.
  8. The board decides MPW's multiplier was wrong all along. An operator runs fn_revise_and_rescore_season directly via docker exec ... psql (LOCAL) or scripts/cloud-sql.sh (CERT/PROD) — this function is not reachable from the authenticated web session at all. They pass the new config, a reason, and a board reference. A new revision row is created inactive; every already-scored result in the season is rescored and re-stamped; only once that fully succeeds does the new revision activate and the old one deactivate. ts_scoring_locked_at is untouched (still set from step 3) — the season was never unlocked, its rules were audibly replaced.
  9. Admin reopens the editor. Still locked, still read-only — the privileged path does not reopen ordinary editing, matching §05's table exactly ("new revision + full rescore", not "editable").

Adjacent path — mid-rescore failure

If step 8's rescore raises partway through (a corrupt result row, a type newly missing its config), the whole transaction rolls back: the new revision row never commits, id_active_scoring_revision still points at the old revision, and every score keeps its prior value. No partial rescore is ever visible — this falls out of ordinary Postgres transaction semantics as long as no exception handler in the procedure swallows the error, which is why SS26.REVISION.07 exists as an explicit test rather than an assumption.

04 · Proposed ADR-097 — sign-off requested before the file is written

Versioned season scoring strategies and governed configuration revision

This is the design doc's own §12 "Proposed ADR A", carried forward for the specific piece this step implements. Per doc/claude/planning.md rule 6, the ADR is drafted here and not written to doc/adr/097-… until you say so. Everything else in this plan can proceed without that file existing — only its creation is gated.

Context. One mutable scoring function cannot preserve old seasons' history while introducing new formulas, while the board must retain authority to correct a season's rules and rescore it coherently.

Decision. A season is assigned an engine; a static CASE dispatcher resolves it (already landed, step 2) — extending the pattern ADR-042 and ADR-045 established for carry-over. Immutable released strategies behind that dispatcher (landed). tbl_scoring_engine as metadata only, no function reference (landed). Shared preview/persistence contract (landed). Normalized revisioned type policy (landed, step 3a). Base value and podium coefficients remain season configuration, not engine constants (landed). This step adds: database-enforced closure of the whole Admin scoring editor after first scoring; unrestricted source/result repair under the active revision; a privileged, audited, whole-season revision/rescore procedure reachable only outside the Admin web session.

Alternatives rejected. One growing IF tree holding the arithmetic inline. Dispatch through a function reference stored in a table — needs dynamic EXECUTE inside SECURITY DEFINER, defeats Postgres dependency tracking, hides the call edge from static analysis. A partial lock leaving ranking buckets editable while they silently reorder the published ranklist with no rescore and no audit trail. A whole-function guard on fn_import_scoring_config instead of field-level — verified above (§02) to break the legitimate EVF-toggle save path on any scored season. Deriving "actor" from Supabase Auth identity — this system has none; the field is an explicit, required parameter instead. Season-code inference of lock state instead of a server field. UI-only enforcement. Permanently forbidding authorized corrections. Overwriting released engine bodies or configuration history.

Consequences. Configuration audit history becomes mandatory going forward — every scored season carries at least one revision row. A formula change still requires a new engine version (code); this procedure only re-points a season at an already-released one or edits its data-only parameters. Exceptional revision remains an operator procedure outside Admin and can never publish a partially rescored season, by construction of the transaction.

Relationships. Extends ADR-042/ADR-045 (carry-over dispatcher pattern). Amends nothing new beyond what steps 1–3a already touched. Registry: next free number is 097 (098–099 remain free for the still-open Proposed ADR B/C).

05 · Schema

One migration: lock evidence, revision history, provenance

ObjectShape
tbl_season.ts_scoring_locked_atTIMESTAMPTZ NULL. Set once, transactionally, by fn_calc_tournament_scores on the season's first successful score. Never cleared by anything, including the privileged revision.
tbl_season.id_active_scoring_revisionINT NULL REFERENCES tbl_scoring_config_revision. The season's single source of "which revision is authoritative right now" — a direct FK rather than an inferred WHERE bool_active scan.
tbl_scoring_config_revisionid_revision SERIAL PK, id_season INT NOT NULL REFERENCES tbl_season, id_engine INT NOT NULL REFERENCES tbl_scoring_engine, json_snapshot JSONB NOT NULL, ts_effective TIMESTAMPTZ NOT NULL DEFAULT NOW(), txt_actor TEXT NOT NULL, txt_reason TEXT NOT NULL, txt_board_ref TEXT, bool_active BOOLEAN NOT NULL DEFAULT FALSE. json_snapshot is fn_export_scoring_config's own shape plus the type-config rows and engine code — one self-contained audit record, not a diff. Partial unique index (id_season) WHERE bool_active enforces "exactly one active revision".
tbl_result.id_scoring_revisionINT NULL REFERENCES tbl_scoring_config_revision. Written only by fn_calc_tournament_scores, stamped from the season's currently active revision at scoring time.

Backfill

Existing scored seasons (2023/2024 through 2025/2026, and 2026/2027 once it carries the PPW1 fixture) get an initial revision synthesized from their current stored configuration, activated, with ts_scoring_locked_at set from the earliest surviving ts_points_calc in that season per §05 — not NOW(), so the audit trail's timestamp reflects when scoring actually happened, not when this migration ran. Idempotent and split from the migration transaction the same way fn_backfill_scoring_engines/fn_backfill_scoring_type_config are, because supabase db reset applies migrations before the seed loads (the trap this branch has hit twice already).

Grants

ENABLE ROW LEVEL SECURITY on tbl_scoring_config_revision (52.1). New functions default-REVOKE from PUBLIC, anon (52.7) — except the privileged revision function, which is additionally revoked from authenticated (§07).

06 · Field-level authorization

Inside fn_import_scoring_config, not around it

At the top: read ts_scoring_locked_at for the season. For each field the §05 table marks locked — mp_value, the three podium coefficients, all eight type multipliers, both threshold columns, json_ranking_rules, and the new engine_code key (§below) — apply the existing COALESCE(new, stored) logic first, then compare: if the season is locked and the resolved new value differs from the currently stored value, raise the exact exception text §05 quotes. show_evf_toggle, show_evf_toggle_calendar and json_extra apply unconditionally regardless of lock state — this is what keeps handleUpdateSeason's toggle-only save (§02) working forever.

Comparing "differs from stored" rather than "key present" is deliberate and verified necessary: the toggle-save path always resends the entire config object, including every locked field at its unchanged value. A presence check would reject that legitimate call outright.

engine_code — new key

fn_export_scoring_config gains an engine_code field (tbl_scoring_engine.txt_code for the season's current id_scoring_engine — currently absent from its JSONB entirely). fn_import_scoring_config accepts the same key: if present and locked and the resolved engine differs from the season's current one, raise; if present and unlocked, resolve txt_code → id_engine (raise "Unknown scoring engine: %" for a bad code — no silent no-op) and UPDATE tbl_season. If absent, no change — existing callers (the EVF-toggle path, any caller not sending it) are unaffected.

Trigger guards (defense in depth)

BEFORE UPDATE on tbl_scoring_config: same locked-field comparison, for a direct table write that bypasses the RPC entirely. BEFORE INSERT OR UPDATE OR DELETE on tbl_scoring_type_config: unconditionally rejects any writer other than fn_sync_scoring_type_config itself and the privileged revision path — ordinary users should never reach this table directly, locked or not, since it is already trigger-owned. Both guards are bypassed only when current_setting('app.privileged_revision', true) = 'true', a session-local flag fn_revise_and_rescore_season sets for the duration of its own transaction (§07) — this is how the privileged path writes through triggers designed to stop everyone else.

07 · Privileged revision procedure

fn_revise_and_rescore_season — reachable only outside the Admin session

fn_revise_and_rescore_season(
  p_id_season   INT,
  p_new_config  JSONB,   -- fn_import_scoring_config's shape (governed fields only)
  p_new_engine  TEXT,    -- NULL keeps the current engine
  p_reason      TEXT,    -- NOT NULL, non-empty
  p_actor       TEXT,    -- NOT NULL, non-empty — no session identity exists to infer this from
  p_board_ref   TEXT     -- nullable, but a real decision reference is expected in practice
) RETURNS TABLE(id_revision INT, rescored_count INT)
  1. Validate the season exists, p_reason and p_actor are non-empty. Resolve p_new_engine to an existing id_engine if given (never creates one — a new formula is a code change, not data).
  2. Set app.privileged_revision = true for this transaction (lets the two trigger guards in §06 step aside for this call only).
  3. Apply p_new_config to tbl_scoring_config and the engine change to tbl_season — same COALESCE-over-current-values semantics as ordinary import, but with no lock check (the lock exists to stop ordinary editing; this function is the authorized exception).
  4. Insert a new tbl_scoring_config_revision row: bool_active = FALSE initially, snapshotting the state just written.
  5. Loop every tournament in the season with enum_import_status = 'SCORED', calling fn_calc_tournament_scores for each — which stamps every result it touches with whichever revision is currently active. Because step 4's row is not yet active, results are still stamped with the old revision at this point.
  6. Activate: UPDATE tbl_scoring_config_revision SET bool_active = FALSE WHERE id_season = p_id_season AND bool_active, then the new row to TRUE, then UPDATE tbl_season SET id_active_scoring_revision = new. Re-run step 5's loop after activation so every result actually carries the new revision id — or, simpler and chosen here: activate first (steps 4–6 reordered so the INSERT already sets bool_active = TRUE and immediately deactivates the sibling in the same statement via a CTE), then rescore once. One rescore pass, not two.
  7. Assert SS26.REVISION.06's invariant inline before returning: no result in this season references any revision for this season other than the new one. A mismatch raises — the transaction (including the activation) rolls back.
  8. Reset app.privileged_revision.

Grants

REVOKE EXECUTE ON FUNCTION fn_revise_and_rescore_season(...) FROM PUBLIC, anon, authenticated; — deliberately including authenticated, unlike every other function in this codebase. Reachable only as postgres/service_role: docker exec -i supabase_db_SPWSranklist psql on LOCAL, scripts/cloud-sql.sh <cert|prod> on CERT/PROD (the existing, established privileged-write path per the cloud-db-ops skill — no new access mechanism invented). This is the concrete meaning of design §05's "an operator procedure outside Admin": not a UI affordance behind an extra permission check, but a function the web session's role cannot call at all.

08 · Frontend contract

Server-authoritative lock state at all three mount points

ScoringConfig gains scoring_admin_locked?: boolean, scoring_locked_at?: string | null, engine_code?: string — optional, same reason as the PPS/MPS fields: MOCK_CONFIG fixtures in ScoringConfigEditor.test.ts/SeasonManagerWizard.test.ts must keep compiling.

  • SeasonManager.svelte:148 — readonly={isSeasonPast(season)} becomes readonly={scoringConfig?.scoring_admin_locked ?? false}. isSeasonPast's own comment ("used to hide the 🎯 Konfiguracja punktacji button") describes a different, still-valid use — showing the button at all is unrelated to whether its contents are locked; only the readonly prop changes.
  • SeasonManagerWizard.svelte:104 — same field, read explicitly rather than left unset. Always false for a brand-new season in practice, but now provably so rather than assumed.
  • ScoringConfigEditor.svelte:283 — the {#if !readonly} around the save button is removed. The button (label unchanged — sc_save, "Zapisz i przelicz", already matches the design's intent even though §05's prose paraphrases it as "Zapisz konfigurację") is always rendered; onclick checks readonly first and, when locked, shows the guarded explanation instead of calling onsave. A native disabled attribute is not used for this reason alone — §05: "cannot communicate on click".
  • New locale keys, both files: sc_locked_title, sc_locked_explanation (the exact Polish text from §05, with an English equivalent) and a label for the new engine selector, sc_scoring_engine_label.
  • Minimal engine selector: one more <select> in ScoringConfigEditor.svelte's base-parameters section, bound to draft.engine_code, options from the two released engine codes (fetched once, not hardcoded — a third engine version must not require a frontend redeploy). Disabled when readonly, same as every other field.

SS26.LOCK.01–12 and SS26.REVISION.01–08, written before implementation

All land in supabase/tests/80_season_scoring_contract.sql (extends the existing SS26 file) except the Vitest/integration rows, which land in frontend/tests/ScoringConfigEditor.test.ts, SeasonManager.test.ts and SeasonManagerWizard.test.ts.

IDAsserts
SS26.LOCK.01Every governed field (engine, base, podium, all 8 multipliers, both thresholds, ranking buckets) is writable before first score.

SS26.LOCK.05Direct INSERT/UPDATE/DELETE on tbl_scoring_type_config is rejected unconditionally (not just post-lock — this table was never a direct write surface).
SS26.LOCK.06ts_scoring_locked_at persists across a same-revision rescore (repair path) — set once, read many times, never cleared.

SS26.LOCK.08updateSeasonCarryoverEngine's underlying column stays writable regardless of lock state.
SS26.LOCK.09Result deletion, tournament URL correction and same-revision fn_calc_tournament_scores all remain unaffected by the lock (they never touch tbl_scoring_config).
SS26.LOCK.10Concurrent write: two ordinary saves racing on the season's first score do not both create a revision row — the partial unique index makes the loser's INSERT fail closed, not silently double-create.
SS26.LOCK.11Vitest — ScoringConfigEditor renders every field disabled and the save button visible when scoring_admin_locked: true; clicking save shows the exact Polish text, not a native alert, and calls no RPC.
SS26.LOCK.12Vitest — SeasonManager and SeasonManagerWizard both derive readonly from scoringConfig.scoring_admin_locked, never from a season date, for a season row engineered to disagree with isSeasonPast in both directions.
SS26.REVISION.01authenticated cannot execute fn_revise_and_rescore_season — has_function_privilege('authenticated', ...) is false. The one function in this codebase revoked from that role.
SS26.REVISION.02Empty p_reason or p_actor raises before anything is written.
SS26.REVISION.03The prior active revision row survives, bool_active = FALSE, snapshot intact — append-only, never deleted or overwritten.
SS26.REVISION.04Passing an engine code identical to the current one is a data-only revision — no new engine row, existing engine reused.
SS26.REVISION.05Multiplier/threshold-only revision (no engine change) is permitted and rescoring reflects it.
SS26.REVISION.06After a successful call, every result in the season references the new revision id — zero rows reference the old one.
SS26.REVISION.07An injected mid-rescore failure (a tournament with a deliberately unconfigured type) leaves the prior revision active and every score at its pre-revision value — the whole transaction rolled back, asserted by re-querying after the call raises.
SS26.REVISION.08A successful call is atomic end-to-end: id_active_scoring_revision, every rescored result's stamp, and the new row's bool_active all flip together or none do — checked by asserting no intermediate state is observable from a concurrent read (advisory lock or single-transaction assertion, matching the pattern evf_historical_event_fragment_repair.sql already uses for a comparable all-or-nothing migration).
