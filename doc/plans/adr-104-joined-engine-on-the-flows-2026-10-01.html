Browse ranklist and calendar

  2. The frontend API queries curated Supabase views/RPCs.
  3. changed PostgreSQL ranking functions apply season configuration, category, eligibility and carry-over policy.
    vw_score and the three rolling-score functions return three more columns per result: category steps (d), the joined premium and the cap reduction; −1 means “not applicable”.
  4. changed The frontend renders rankings, calendar cards or score drilldown.
    The drilldown export gains the same three columns — „Różnica kategorii (d)”, „Premia w stawce łączonej”, „Obniżenie do ograniczenia” — and −1 reads „nie dotyczy”. scoring.ts computes each joined row as the database stores it, with the cap.

Flow 3

Ingest domestic results

  1. An operator/workflow chooses a source URL, file or storage artifact.
  2. A source parser emits ParsedTournament and source rows.
  3. The rule engine plans and runs parse, validation, event resolution, identity resolution, pool handling, count checks, category assignment and commit.
  4. The bridge delegates selected plugin work to existing stage functions while maintaining the new context/fault contract.
  5. changed Commit files the result set through the joined-bracket module paired with the tournament type’s engine and persists it transactionally; the database scores each tournament with that engine.
    For a 2026/27 PPW or MPW listing the joined module first builds the category order: one digit per place, 0 = V0 … 4 = V4, from every listed fencer with a category, matched or not. Before anything is written it refuses two kinds of listing: a joined one that repeats a place (the operator asks the organiser for the fenced order) and one with a fencer who has no category (a pending match, or no birth year). A tie inside one category is accepted.

    Every category’s tournament gets the same order (txt_joined_order). The database scores the whole bracket from it:
    • N ≤ 3 is a meeting and scores 3, 2, 1.
    • One category of 4 or more, or any bracket of 16 or more, scores EVF.
    • In a joined bracket of 4–15, the youngest category scores EVF and an older one max(EVF × (1 + 0,05 · d), EVF + d).
    • Nobody scores more than the fencer directly ahead, minus 1 point.
    The cap is applied in one place, fn_score_joined_bracket, and the rank coefficient multiplies the capped value. Each tournament writes only its own rows.
  6. Post-commit validation, notification and staging-report formatting run as a separate flow.
  7. new At the end of the event run, the joining check compares how each PPW and MPW listing was fenced with the scoring table’s § 2, stores the verdict and reports a change on Telegram; it never blocks.
    The verdict lives in tbl_joining_check, one row per event, weapon and gender. Telegram hears only when a verdict changes; the results are already scored as fenced.
Review path: when the operator uses draft review, run-scoped draft tables and three-way comparison provide an explicit inspection step before fn_commit_event_draft. changed The draft tables carry the order and the three columns, and the commit copies them across.
Evidence. All seventeen Part C orders store the spec’s finals to the cent through the real writer. The cap’s guarantees hold over 1,700 generated orders, and the browser module returns the same seventeen sets of numbers. pgTAP 1,183 assertions, pytest 1,356 and Vitest 1,050 pass.

Flow 4

Correct identity and recompute

  1. An admin confirms an alias, birth year, duplicate merge or identity correction.
  2. The database records master-data change and enqueues affected events.
  3. changed The recompute worker loads committed FK-linked results for an event.
    It also loads each tournament’s stored order.
  4. changed The rule engine reassigns effective category/counts and recommits derived state without scraping or fuzzy matching again.
    Under the new engine, N and the order are read back as stored. Every stored place gets its fencer’s current category digit; places never stored keep theirs.
  5. new Post-commit checks and notifications run for the updated event, and the joining check runs again.
    A fencer who moves category changes the category sizes that § 2 is computed from.

Where I departed from the plan or changed tests

  • A season already scored. If 2026/27 holds a scored result when the migration runs, the engine is still registered but the season is left as it stands, with a NOTICE; moving it takes a privileged revision. The plan and ADR-104 specify this. My first version aborted the deploy instead.
  • The annex link. The calculator links the annex by its full GitHub Pages address, because the WordPress copy is uploaded alone; inside the ranklist the link is relative. If the annex goes to WordPress too, the address changes.
  • The annex simulator. The youngest category’s rows are now labelled like the other joined rows. Its two premium columns still show „—”, as in the version you approved.
  • Tests. One new pgTAP assertion could never see its own write; I fixed the test, not the migration. File 81 now names EVF classic for PPS instead of “the newest engine”. File 10 passes a category order when it ingests a 2026/27 PPW result.
  • Commit 1 for context. The place-and-medal engine of ADR-103 is gone (9056d50e): K, m and b, its three components and PLACE_MEDAL. A guard refuses to drop any column that holds a value.
