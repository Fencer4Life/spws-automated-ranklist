Report 2 · confirmed, and larger than reported

The club box is decorative

In RegistrationForm.svelte the club input appears exactly three times, and one of those is a privacy label:

  • line 307 — let club = $state('') declares it;
  • line 95 — <input bind:value={club} …> binds it;
  • nothing reads it. It is never passed to createRegistration, because fn_create_registration has no club parameter, because tbl_registration has no club column.

So the value is typed, held in memory, and thrown away when the page closes. Downstream, every layer then hardcodes the gap: fn_ftl_export_entries returns no club, and ftlSeedExport.ts emits a literal Club="" on every <Tireur> (line 323), as does its Python twin.

The clubs for PPW1 are gone, and a fix will not bring them back

Nothing was written, so there is nothing to backfill. tbl_fencer.txt_club exists, but of the 43 PPW1 registrants 0 have a club recorded there (36 are matched to a fencer row; none of those rows carry a club). Repairing the pipeline today produces correct future files and a still-empty PPW1 file.

Why this is a decision and not just a bug fix

The form promises the fencer we do not store it

This is the part that stops me from simply adding a column. The field's own label and the RODO notice beneath the form both say so, in both languages:

KeyPolishEnglish
reg_club_optionalKlub (opcjonalnie — nie zapisujemy)Club (optional — not stored)
reg_rodo_basis_clubKlub — tylko do plików startowychClub — only for the start files
reg_rodo_basis_club_lawnie zapisujemy—

The intent was clearly right: the club is for the start files and for nothing else. But the design is self-contradictory as built. The start files are generated days later, by the organizer, on a different page, from the database. A value that is never stored cannot be there when they press download. "Not stored" and "appears in the start files" cannot both hold.

So storing the club is not a neutral bug fix — it reverses a promise currently displayed to every fencer who registers, and ADR-078's minimisation rule is what put that promise there.

The choice

Three ways to make the club reach Fencing Time

A — Store the club on the registration, and change the notice to match Recommended

Add txt_club to tbl_registration, thread it through fn_create_registration, return it from fn_ftl_export_entries, and emit it in both exporters. Change the two locale strings from "nie zapisujemy" to something truthful — the club is kept for the event's start files and is not published on the public entry list.

Why this one: it is the only option that actually delivers what the form already promises the club is for. The public entry-list view stays unchanged, so the club is still not published to four hundred fencers — only the token-gated organizer export sees it. That keeps ADR-078's substance (don't publish it) while dropping a clause the system was never honouring anyway.

Cost: one migration, RPC + view changes, both exporters and their byte-for-byte tests, locale copy in two languages, an ADR-078 amendment. Does nothing for PPW1's existing 43.

B — Keep the promise: remove the club field entirely

Delete the input and its RODO row. Fencing Time gets Club="" forever, which is what it gets today, and the form stops asking for something it discards.

Honest and cheap. But the organizer keeps typing clubs in by hand, and the reason the field was added does not go away.

C — Organizer supplies the clubs at download time

Truly stores nothing: the export page lets the organizer paste or edit a club per fencer before building the XML, held in the browser only.

Keeps the privacy promise exactly and fixes PPW1 immediately — but it is the most build, it puts the typing back on the organizer that the form was meant to remove, and the work is lost on every re-download.

For PPW1, right now

Whichever you pick, this event's clubs need collecting again

A, B and C all leave the 43 existing registrations without a club, because the data never existed. If the clubs matter for PPW1 specifically, they have to be gathered outside the system — and option C is the only one of the three that gives the organizer somewhere to put them without a database write.
