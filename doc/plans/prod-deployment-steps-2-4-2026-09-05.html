02What rendering does to it

The plan named the save-time filter. There is a second filter at render time, and it behaves differently — worth knowing now rather than discovering on the live page.

WordPress filters content at two separate moments. Saving runs wp_kses_post, which is what step 2 tested and passed. Displaying runs wpautop, which inserts paragraph and line breaks. A draft cannot be rendered without a login session, so instead I compared three published pages' stored content against their live HTML. That measures the real pipeline without publishing anything.

StoredRenderedReading
bare text line<p>-wrappedwpautop is active on this theme
newline inside a <div><br /> insertedit rewrites inside elements too
top-level <img><p>-wrappednon-block elements get wrapped
top-level <div>untoucheddiv is a known block — passes through
Consequence for the embed spws-calendar is not a tag wpautop recognises, so on its own line it would be wrapped in a <p> — which constrains a full-viewport-height element. The fix costs nothing: wrap the embed in a plain <div>, which the measurements above show passes through untouched. That is how the page will be built. It is confirmed on the live page before the menu item points anywhere.

The one thing that looked like a defect, and is not

23 rows in the current season carry no date, no real name (the name simply repeats the code) and status CREATED — for example PEW63e-2026-2027. On a public page that would read as 23 lines of noise.

Already handled, by design These are dated-later planning skeletons under ADR-077, and the frontend hides them in two independent places: calendarMonths.ts:258 drops any event without a dt_start, and calendarMonths.ts:549 filters enum_status !== 'CREATED' outright. 2 · Two project refs were missing from .env

Steps 3 and 4 need SUPABASE_PROD_REF, which cloud-sql.sh documents as living in .env. Neither ref was there, so both checks failed at the first hurdle. I resolved them from supabase projects list and appended SUPABASE_CERT_REF and SUPABASE_PROD_REF. These are not secrets — they ship inside the public frontend bundle. .env remains gitignored and the worktree is clean.

3 · A bug in the cloud-sql.sh safety gate

A plain SELECT was sent to the write-confirmation gate. The cause is at scripts/cloud-sql.sh:96:

sed -E 's@--[^\n]*@ @g'

sed has no \n escape inside a bracket expression, so [^\n] means “not a backslash and not the letter n”. Any leading SQL comment containing an n — most comments — truncates the strip, and the first-word detection then misreads the statement. It fails safe, so nothing dangerous happens; it just blocks read-only queries that open with a comment. This is the same defect class the script's own comment records having fixed once before. Worth a one-line fix, but it is outside this plan's scope, so I have not touched it.
