3 · The design

A PZSz plugin, copied from EVF and changed

The pipeline is built from plugins. engine/flows.py names the flows. engine/rulebook.py gives each flow an ordered list of plugins, with optional params. The plugins live in python/pipeline/plugins/, and run_flow runs them in order. The EVF admission is not a plugin: it is a module that stages.py and evf_sync.py call.

The plugin: AdmitPzszRoster

New file python/pipeline/plugins/pzsz_admission.py. Its first commit is a copy of python/pipeline/international_admission.py, the EVF admission: _words, identity_matches and admit. Later commits change the copy into a plugin for PZSz, which is a different, non-veteran organizer. Nothing is shared with the EVF module, so a later change on either side cannot alter the other. What the copy changes:

  • The birth year: EVF checks our year against the bracket's category band. The copy compares it with the exact year on the PZSz start list.
  • The starter gate: EVF requires a PPW or MPW start (fn_spws_starter_ids). The copy drops that gate; being in the fencer table is enough.
  • The outcomes: EVF has PENDING for a row printed POL. The copy has none, so a row is either stored or skipped with its reason.
  • The shape: EVF is a module called from stages.py. The copy becomes a plugin step in the PZSz flow.

What it does for PZSz:

  • Birth year: from the PZSz start list (pzszerm.pl/zawody/kalendarium-zawodow/turniej/?id=N, column Data urodzenia). The year of the date is the birth year. The tournaments are listed on the event page, which is found from the event's stored id_pzsz_event.
  • Keys: surname, first name and birth year. Names are compared with Polish letters folded and case ignored. The diacritic folding is the existing fold_diacritics, and the name split is the existing parse_scraped_name.
  • Store only when exactly one fencer of ours matches all three keys.
  • Skip everything else, with the reason recorded: not on the start list, the name appearing twice on the start list, no fencer of ours, a fencer of ours with the same name and another birth year, or two fencers of ours matching.
  • Never create a fencer, write an alias, change a birth year or queue a review.

The flow

Flow.INGEST_PZSZ_SENIOR (engine/rulebook.py) becomes ParseSource → ValidateIR → ResolveEvent → AdmitPzszRoster → ValidateCounts → CommitPzszSenior. The new plugin replaces ResolveFencers in this flow only. The PPW and EVF flows are untouched. CommitPzszSenior keeps writing one SENIOR tournament per weapon and gender, with the full N and the original places.

Getting there from ingest <code>

  • ingest_cli reads the event's organizer. A PZSz event takes the PZSz path. Every other event keeps the PPW path, unchanged.
  • The PZSz path reads the FTL schedule from the event's own URL and takes each finished listing's weapon and gender. It never decodes an age category from the name. It pairs each listing with the PZSz tournament of the same weapon and gender, and joins the start list to the results by the folded name.
  • A new pure reader, python/scrapers/pzsz_start_list.py, parses a PZSz tournament page into (name, club, birth date) rows. It is tested on saved copies of Poznań's two pages.
  • The run report, which already comes back to Telegram, lists every skipped starter with the reason. Same-name fencers with a different birth year are shown first.

pzszerm.pl answers some requests with a JavaScript check

A plain request gets a "Wczytywanie danych…" page on some days. That happens from this machine, and from GitHub Actions on 30 September and 3–6 October. (This note first said Actions read the site without trouble; the sync logs show otherwise, see D1.) If a start list cannot be read, the run fails and writes nothing. The plan does not try to get past the check.

One addition the plan did not name: the release step

With Q5 A, CERT's id can overwrite PROD's. id_pzsz_event has a per-season unique index (idx_tbl_event_pzsz_season), so a re-key on CERT that swaps two ids would fail mid-loop. That is the collision the id_prior_event swap hit before it got the same step.

The migration therefore clears an id before the loops when another element of the same payload claims it:

  • an update naming a different event;
  • or a create whose code PROD does not hold yet.

A payload that says nothing clears nothing. Each part is mutation-checked:

  • without the step, the swap test dies on the unique index;
  • without the create half, the create test dies on the unique index;
  • without the skipped-create guard, a skipped create takes another row's id.

Postgrestools: the migration is clean. The test file shows only the pgTAP functions (plan, is, lives_ok, finish), which the checker's database does not have, the same baseline as the other mirror tests.
