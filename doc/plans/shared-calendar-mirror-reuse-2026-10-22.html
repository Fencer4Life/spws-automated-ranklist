One mirror, fired by every sync

The CERT→PROD calendar mirror is copy-pasted into every sync, and a value changed on CERT only reaches PROD on evf-sync's once-a-day cron. Extract one reusable workflow that evf-sync, pzsz-sync and any future FIE sync all call — right after each writes CERT.

The symptom you hit

Why the PROD fee is blank — and it is not a bug

The entry fee is set on CERT and absent on PROD for one reason: the mirror that carries it has not run since you set it.

⏱ A seven-hour miss

The last successful calendar mirror (evf-sync) ran 2026-10-21 11:23 UTC. You set the fee at 18:45–18:48 UTC — ~7 hours later. No mirror has run since. The mechanism is sound: fn_mirror_events_to_prod fills a blank PROD fee from CERT (COALESCE(num_entry_fee, cert_value)), and promote_calendar sends every active event each run. It simply has not fired after your edit.

! The real gap: the mirror is cron-only, and only on one workflow's clock

evf-sync mirrors CERT→PROD on its daily 06:00 UTC cron (and around its scrape). pzsz-sync has its own copy that runs on its cron. A hand edit to CERT between runs — or a value a sync writes to CERT — waits for the next cron. That is exactly the stranded fee.

The duplication

The same job, pasted three times

The mirror's logic is already one module — python/pipeline/promote.py --mode calendar calling the one RPC fn_mirror_events_to_prod. What is duplicated is the CI wrapper: a ~70-line GitHub job, copied verbatim into three places, differing only by a label string and an if: gate.

△ A future FIE sync is a fourth copy — and copies drift

Each copy carries the same delicate concurrency: prod-write · queue: max block, whose own in-file comment warns that a single member missing queue: max silently cancels a sibling's pending promote. Three hand-maintained copies of a trap is the defect to remove, not add a fourth to.

The fix

One reusable workflow, called with uses:

Add .github/workflows/promote-calendar.yml with on: workflow_call. It holds the single mirror job — the prod-write concurrency, the promote --mode calendar step, the reconcile-log commit, the Telegram-on-failure — with the only varying piece, the label, as an input. Every sync calls it and passes its label and secrets.

# .github/workflows/promote-calendar.yml  (the one definition)
on:
  workflow_call:
    inputs:
      label: { type: string, required: true }   # "EVF" · "EVF pre-scrape" · "PZSz" · "FIE"
    secrets:
      SUPABASE_ACCESS_TOKEN: { required: true }
      SUPABASE_CERT_REF: { required: true }
      SUPABASE_PROD_REF: { required: true }
      SUPABASE_CERT_SERVICE_ROLE_KEY: { required: true }
      TELEGRAM_BOT_TOKEN: { required: true }
      TELEGRAM_CHAT_ID: { required: true }
jobs:
  mirror:
    runs-on: ubuntu-latest
    permissions: { contents: write }            # reconcile-log commit/push
    concurrency: { group: prod-write, cancel-in-progress: false, queue: max }
    steps: [ checkout · setup-python · pip install httpx supabase ·
             run: python -m python.pipeline.promote --mode calendar ·
             commit reconcile log · notify "${{ inputs.label }} promote FAILED" ]

# every caller, after it writes CERT:
  promote-calendar:
    needs: sync
    if: ${{ !cancelled() && ... }}            # caller keeps its own gate
    permissions: { contents: write }
    uses: ./.github/workflows/promote-calendar.yml
    with:    { label: "PZSz" }
    secrets: inherit

The details that make this safe

GitHub Actions constraints — got right on purpose

1 Concurrency lives in the shared file now

A job that calls a reusable workflow (uses:) cannot declare steps or job-level concurrency. So the prod-write · queue: max block moves inside the shared job — which is the point: the trap is defined once. Concurrency groups are repo-global by name, so prod-write still serialises against promote.yml, promote-season.yml, event-close.yml and the parity sweep, exactly as today.

2 Permissions are intersected — pzsz-sync needs a bump

A called workflow's contents: write is capped by the caller's token. evf-sync.yml is already contents: write at the top. pzsz-sync.yml is contents: read — so its calling job gets permissions: { contents: write }, or the reconcile-log push fails.

3 mode / dry_run gating stays on the caller

A called workflow cannot read the caller's github.event.inputs. That is fine — the if: gates already belong on the calling job (the table above), so each sync decides for itself whether to fire the mirror. secrets: inherit passes all six secrets with no re-listing.

Out of scope — deliberately

Start lists are not part of this mirror

The pzsz-start-lists.yml workflow writes tbl_pzsz_start_list on CERT, which reaches PROD by hash replay in promote_event (ADR-108/112), not by the calendar mirror. It does not call promote-calendar.yml. The two PZSz workflows stay separate, as you decided. This plan touches only the calendar path (tbl_event via fn_mirror_events_to_prod).
