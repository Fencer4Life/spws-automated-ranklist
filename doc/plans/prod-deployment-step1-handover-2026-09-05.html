02Two defects the tests found

Both were latent in the existing code and invisible while the application only ever ran on GitHub Pages. Each was caught by a failing test written before the fix.

1 · A PROD-only embed rendered blank, with no error

activeEnv started at the literal 'CERT', and the URL derived as activeEnv === 'PROD' && prodUrl ? prodUrl : certUrl. Give it only the PROD pair — exactly what the embed gets — and that yields an empty string, the init guard supabaseUrl && supabaseKey never passes, and nothing loads. No banner, no console error, just an empty box.

Why this one matters beyond today It is the mirror image of the 2026-08-17 RegistrationElement defect, where (certUrl || prodUrl) silently resolved to CERT and a real registration landed in the wrong environment. Same root cause — credential resolution that assumes both pairs exist — failing in the opposite direction. A surface now opens on the environment it actually holds credentials for, and a test pins the Pages behaviour so the fix cannot drift the other way.

2 · Opening on the calendar loaded the ranking

App.init() ended in an unconditional loadRanking(). That was correct while the app always started on the ranklist and the calendar was only ever reached through navigateTo(), which loads it. An embed that opens straight on the calendar fetched ranking rows nobody sees and left the barrel empty. I verified the guard is real by reverting the fix and confirming the test fails.

04Where I stopped, and why

The menu item is not created WordPress stores a menu item's structure in protected _menu_item_* meta. I proved over XML-RPC that such meta is accepted on write but hidden on read — item 7128, a working live menu item, returns no custom fields at all. So the channel that would create a menu item cannot verify it is correctly formed. A menu item is the most public artifact on the site, and one I could not delete if it came out wrong. Creating an unverifiable one on a live association website was not mine to do unasked.
No test registration was written to PROD The plan's step 9 asks for a registration end to end. Doing that on PROD creates a real entry on a live event's public start list — precisely the 2026-08-17 incident, where a test row could not be removed and sat on a public list while you were sharing the link. The cloud-db-ops rule is to prove the delete path before writing. Say the word and I will do it with a verified exit, or we test the form on CERT instead.
The knowledge graph could not be refreshed ./scripts/refresh-graph.sh refused: it found 76 source files deleted since the graph was last built and a net −45 nodes, and would not overwrite. This is pre-existing drift — the graph dates from 26 June and I only added files — but it means the code layer is stale and assetBase.ts is not in it. The repo rule is a refresh before every commit, so this is unfinished. The tool's own instruction is a full /graphify . rebuild, which is not free, so it is your call rather than mine.

Also found, not fixed

scripts/cloud-sql.sh:96 strips SQL comments with sed -E 's@--[^\n]*@ @g'. sed has no \n escape inside a bracket expression, so [^\n] means "not a backslash and not the letter n" — any leading comment containing an n sends a plain SELECT to the write-confirmation gate. It fails safe. Outside this plan's scope, so left alone; one line to fix when you want it.
