Ingestion · identity · fix plan · 3 Oct 2026

Namesakes are told apart by birth year, on every path

The name matcher already chooses the namesake whose birth year fits the bracket. The exact-name step that runs before it doesn't: it takes the first namesake it reads, links the result to that fencer and overwrites his birth year. This plan applies the matcher's birth-year rule to that step, and refuses a listing when the birth year can't decide.

Decided: go, D1 ABuilt and checked on LOCAL Blocks PPW1 2026/27 test first

The defect, with evidence

Where the birth year is skipped

× _find_exact_fencer returns the first namesake it reads

python/pipeline/stages.py:191 walks the roster and returns at the first exact name or alias match. It never looks at the birth year and never notices a second namesake. Two paths call it:

  • ResolveFencers, phase A (plugins/resolve_fencers.py:114). This is ingest-event.yml, the path PPW1 takes. A hit is linked as AUTO_MATCHED with confidence 100 and its birth year is reconciled, so the row never reaches the matcher.
  • Stage 0 (stages.py:558, 570, the Phase 5 runner path). A hit has its birth year reconciled before the matcher runs.

✓ The matcher already has the rule

find_best_match (python/matcher/fuzzy_match.py:306) takes the namesakes tied at the best score and keeps those whose birth year fits the bracket's category. If exactly one fits, it links him; if none or several fit, the row is PENDING. Its docstring uses KRAWCZYK Paweł, 1954 and 1989, as the example.

What happened on 1 Oct (trial on LOCAL, doc/staging/PPW1-2026-2027.20261001-044227Z.md): the V4 épée result went to KRAWCZYK Paweł born 1989, whose year was changed to 1957. The V4 sabre win went to MŁYNEK Janusz born 1984, whose year was also changed to 1957. Both changed rows were confirmed birth years. PROD and CERT hold both pairs: KRAWCZYK 1954 (registered for PPW1) and 1989, MŁYNEK 1951 (19 results) and 1984.

Decide this

D1 · One roster fencer, a birth year far from the bracket

The same step also handles a name with only one fencer on the roster. Today, if his confirmed year doesn't fit, it is moved into the bracket's category (ADR-056). One category up is the intended correction: PĘCZEK Sandra, 1991, fenced V1 and is 1987 on PROD, as she declared. A move of two or more categories means it is not the same person. Example: a V4 KRAWCZYK Paweł when only the 1989 one exists would make the 1989 man 1957.

✓ Decided 3 Oct: A

"A move of two or more categories is FORBIDDEN, it means a data error." This applies in both directions and to an estimated year as well as a confirmed one.

A (recommended): a move of two or more categories is not made. The row is PENDING and the listing is refused, as for undecidable namesakes. A one-category move stays as it is. B: change namesakes only.
Under A, PPW1 gives the same results as under B: in the trial every single-fencer move was one category (PĘCZEK, WALCZEWSKI, CHUDY, STANISŁAWSKI, KIEROŃSKI).

The change

Four pieces

  1. One lookup for every path (stages.py). _find_exact_fencer collects every exact name or alias match, with the nationality rule unchanged. It takes the row's category and the season's end year. With none, the result is a new person. With one, it is that fencer. With two or more, it keeps those whose birth year fits the category, using birth_year_matches_category, the check the matcher already uses. If exactly one fits, it is that fencer. Otherwise the result is undecided, carrying the list of namesakes. It never picks the first one read.
  2. ResolveFencers phase A (resolve_fencers.py). It passes the row's category. An undecided row becomes PENDING, with the namesakes and their birth years as alternatives. No birth year is written, no fencer is created, and a conflict namesakes_undecided goes into the report.
  3. Stage 0 (stages.py, s0_reconcile_roster). It uses the same lookup. An undecided row is neither created nor reconciled, and the conflict is recorded. The matcher then marks it PENDING, as it already does for namesake ties.
  4. Commit refuses a domestic listing that holds a PENDING row (plugins/ingest.py, next to the existing international refusal). The error names the fencer and the namesakes, and nothing of that listing is written. Today such a row is quietly left out. To resolve it, correct the roster birth year, or add an identity entry with a birth year to doc/overrides/<event>.yaml (overrides.py already tells namesakes apart by year). Then run the ingest again; --replace makes that safe.

The staging report lists each namesake decision, for example "KRAWCZYK Paweł → born 1954 (fits V4); 1989 does not".
