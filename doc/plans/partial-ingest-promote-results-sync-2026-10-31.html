00 · The one-sentence design

Partial in what it reads, whole in what it writes, and one route end to end

Every cycle reads the event's sources and takes only the listings the engine says are final. What it writes is the whole event as of now, in one transaction, on CERT exactly as promote already does on PROD (fn_promote_event_apply, ADR-108 §6). So CERT always equals exactly one recorded run, PROD always equals one earlier or the same run, a failure leaves either environment untouched, and "partial promote" is simply promote replaying the newest run while the event is still IN_PROGRESS. The sync workflow runs that cycle every hour for every event in its window and reports by exception.

Why not tournament-by-tournament writes

Today's invariant — one result fingerprint per event, the same SQL function on CERT and PROD, promote refusing anything it cannot reproduce — is what makes PROD trustworthy (ADR-108 §1, §6). Per-tournament bookkeeping would need per-tournament fingerprints, per-tournament promote records and a second comparison path. The event-level write already gives the outcome you asked for: run 1 stores the two finished listings, run 2 stores four, run 3 stores six, and each promote carries exactly that. That is D1.

03 · What is missing

Seven gaps, each with its evidence

G1 PROD never loses a tournament the new run no longer has

CERT's replace wipes the whole event first. PROD's apply knows six operations — insert a fencer, move a birth year, find or create a tournament, ingest a tournament's results (which deletes that tournament's old rows, 20261003000001_…:453), set a URL, set the sources — and no delete (20261003000017_promote_apply.sql:186–248). A listing renamed by the organiser, or a category whose keep-rule owner changed between runs, leaves a tournament on PROD that CERT does not have; the fingerprint check then refuses the promote (:250–254), correctly, and nothing but hand surgery can move it on. D4.

G2 A CERT ingest wipes before it reads, and commits listing by listing

The wipe at ingest_cli.py:843 runs before the per-listing fetches at :861 and the per-listing commits at :907; the international and PZSz drivers do the same (:1016, :1260). FTL dropping on listing 5 of 14, or a ListingRefused there, leaves CERT holding four listings of a FAILED run. Promote is blocked (the latest run has no fingerprint), the daily close says "ingest CERT again" — but CERT itself is neither the old state nor the new one until someone acts. D3.

G3 An Engarde final still running does not keep the event IN_PROGRESS

Engarde publishes a state per competition and the reader skips anything not completed (engarde.py:176, 182–183) — a finality signal as good as FTL's. But the lifecycle counts a listing as not final only when its skip reason equals FTL's text (lifecycle.py:24, 65), so the day after the end date the event is COMPLETED with a final still running. Proven this morning as error 7 of doc/plans/ingestion-source-errors-findings-2026-10-31.html. D2.

G4 Nothing records a promote's outcome

The gate writes its outcome on the run row only through a writable transport (gate.py:577); promote reads CERT read-only (replay.py:663), so even that is skipped there. The daily close infers the state from fingerprints. An automation that must not repeat a refusal every hour needs to know a promote was tried and why it refused. D10.

G5 Four engines have no finality signal

4fence (f=clafinale), Ophardt (a results page with a "Last transmission" stamp, ophardt.py:230–239), d'Artagnan (<id>-rankings.html) and EVF's API are read as "final once published" (international_sources.py:107–108, 127). Ophardt transmits live. Nothing in the code can tell a provisional ranking from a final one. D2.

G6 Every ingest and promote run has the same title

Neither workflow sets run-name: the Actions list reads "Ingest event (NEW pipeline, from URL)" twenty times (run list, 31 Oct). With a cycle an hour, the list must say the event and what the cycle did — the rule you set this morning for CI and Release (NAMING.01–07).

G7 The results link is the switch (decided by you, 31 Oct)

A person sets the link (ADR-117). On PROD today none of the next fourteen events has one, Madrid included. Under your decision an event without a link is not in the sync at all: not selected, not refreshed, not read, not mentioned. The moment its link is on CERT — set in CERT's Admin, or in PROD's Admin and copied by the cycle's refresh (ADR-117 D2 A) — the next cycle takes it. The select step reads the link on both environments, so a link set on PROD enables the event before any refresh has copied it.

G9 The route learns the organizer from the event code, in five places

stages._organizer_for_event maps PPW/MPW, PEW/MEW, MSW and PPS/MPS to SPWS, EVF, FIE and PZSz and answers UNKNOWN otherwise (stages.py:48–76); _is_international_intake asks derive_tourn_type_from_event_code, a twelve-prefix table that returns None for anything else, which the fail-closed minimum-participants gate turns into a refusal (db_connector.py:904–926, stages.py:78–90); the international driver picks FIE or EVF from FIE_TYPES (ingest_cli.py:1020, international_admission.py:55, 148); the daily close selects by ROUTE_CODES, a regex of the same prefixes (close.py:39, 215); and tbl_organizer has four rows (EVF, FIE, PZSz, SPWS) and no column saying how an organizer's events are ingested. A USA Fencing event today would be refused before its first read, whatever its link. D13.

G8 A refusal's traceback is public

The repository is public, so every Actions log is. The ingest's own log lines name listings, categories, tournament ids, N and fault kinds, never a fencer (ingest_cli.py:377–381; the PPS1e log of 26 Oct shows "EPEE/F: 76 starters, stored 2026-10-23…" and nothing more about them). But a ListingRefused ends the job with a traceback, and its message names the fencer and the birth years that decided it (core/contract.py:65–76; the runbook's first check is "the last line of the traceback"). D12.

  1. Read. The route's reader reads the schedule, every final listing with its parsed rows and hashes, the keep-rule's verdicts, and the PZSz start lists or the international sources. It records sightings and stores captured start lists, and writes nothing else. If it fails, there is no run and nothing is written.
  2. Save the given link (B2), then read the prior (B3).
  3. Open the run. It records the input fingerprint and the roster as the plan will find them, and takes every listing read.
  4. Plan against CERT with reserved ids (B6). A refused listing closes the run FAILED, with its kind, and nothing is written. A plan that commits nothing follows R2.1.
  5. Apply in one fn_promote_event_apply call: expected fingerprint NULL, the prior, the run's input parts and the plan's status. The function deletes the tournaments the plan does not name (D4), writes everything else, sets the status and returns the fingerprint. Any refusal rolls the whole call back. If the call ends without an answer, B5 applies.
  6. Close the run FINISHED with the apply's fingerprint and the master-data changes.
  7. Drain CERT's recompute queue to empty, then run the gate, which records its outcome on the row (B7).
  8. Report: the staging report goes to Storage, the full report and the gate's verdict go to Telegram, and the joining check runs, as after a promote.

04.1 · The cycle

  1. Select (read-only, CERT): active-season events on the route (close.ROUTE_CODES), not COMPLETED or CANCELLED, first day ≤ today ≤ end date + 1 in Warsaw, decided by the moment the cron was due (the PZSz capture's rule, pzsz_start_list_store.select_window_events). Only an event with a results link on CERT or on PROD (or, for an EVF or FIE event, an EVF results id) is selected: the link is the switch (G7). A paused event (D8) is skipped. The repository variable RESULTS_SYNC=off ends every scheduled cycle here; a manual run ignores it.
  2. Read: the schedule and every listing, through the same readers the ingest uses; split_final by the engine's signal (D2); the 60-minute sightings rule for engines without one (D2 B); the schedule hash and every listing hash exactly as the run record computes them.
  3. Compare with the latest FINISHED CERT run's jsonb_listings. Same hashes and PROD holds that run's fingerprint → nothing to do, no write, no message. Same hashes, PROD behind → go to step 8. Different → continue. A PZSz round's start-list hash is part of the comparison, so a new stored version of a start list alone starts a cycle (§04.9).
  4. Refresh CERT from PROD with --auto, as ingest-event.yml does (ADR-113 §7). A renumbering stops here, reported once (D8).
  5. Open the run (fn_ingest_run_open): inputs and roster snapshot, after the refresh.
  6. Plan: the same driver (_ingest_event_rounds) with the RecordingConnector against CERT, fed the listings read in step 2. New fencers take ids reserved from CERT's sequence (§04.3).
  7. Apply on CERT: fn_promote_event_apply with no expected fingerprint (it returns the one it produced), the prior = the previous FINISHED run's fingerprint, and the replace semantics of D4. One call, one transaction. Then CERT's recompute queue is drained in the same job (drain_recompute_queue, debounce 0, as promote drains PROD), the run closes FINISHED with the fingerprint, the gate runs and records its outcome. A raise anywhere: the run closes FAILED, CERT is exactly what it was, and the sync pauses the event (D8).
  8. Promote: promote.yml as a reusable workflow, unchanged in substance — gate, plan on PROD, source check, dry apply, apply, drain, compare — plus the ledger write (D10).
  9. Report: one line per event (D7, §04.6). Then the seed export, as today.

Steps 2–7 are the CERT ingest; the manual ingest <code> runs exactly them, without step 3's silence and with the full report. Steps 8–9 are promote. The sync is the cycle in a loop.

04.8 · How you are told, and how a broken event stops

  • Telegram, the admin chat — every line of §04.6: a promote, a failure with its reason and the resume command, and the day's first cycle naming what is in window and what is paused. The daily close keeps its own messages after an end date, unchanged.
  • The Actions list — each run titled by its event and mode (Ingest · PPS2e-2026-2027 · sync, Promote · PPS2e-2026-2027, Results sync · 2 events in window), red when a cycle failed, green when it changed nothing. No more twenty identical titles (G6).
  • The ledger on CERT — the run row: txt_status, txt_error, jsonb_gate, jsonb_promote (D10); and tbl_results_sync_event (one row per event, service role, CERT only): paused_at, paused_reason (kind, listing, one sentence), paused_by_run (the Actions run URL), last_cycle_at, last_verdict. Admin can show it later; the daily close quotes it.
  • The pause (D8) — any failed step of a cycle pauses the event. The select step skips a paused event, so nothing runs and nothing repeats. It is lifted by sync <code> (the manual dispatch of results-sync.yml with a code clears the pause before its cycle), or by a manual ingest <code> whose run finishes (the ingest job clears it on FINISHED). A pause is never lifted by time or by the organiser publishing more.
  • The switch — the repository variable RESULTS_SYNC: set to off, every scheduled cycle exits at the select step with one log line and no message. For a day you want the machine quiet, without editing a workflow. A manual run ignores it.
  • What never notifies — a cycle that changes nothing; an event without a results link (your decision); a paused event, after its first message, except in the morning line.

04.9 · PZSz start lists and birth years

Managed, by the machinery you already signed, reused unchanged; the sync adds three explicit rules and stores nothing new about a person.

  • Unchanged.   • In a cycle, the reader phase is today's _pzsz_start_lists_for_cert (ingest_cli.py:1098–1128): one capture attempt over plain HTTP (on a gated day "not read from pzszerm.pl now", as on 26 Oct), then the newest stored version per weapon and gender.   • Nothing new about a person.
