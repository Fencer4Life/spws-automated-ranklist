01 · Outcome and scope

What exists after this lands

  • A PZSz PPS/MPS event (already on the calendar, childless, via the merged PR #7 scraper) can have an FTL results URL ingested into it, producing one SENIOR-labeled tournament per weapon/gender with the full source field size as int_participant_count and original placements (no bracket-relative renumbering).
  • Each imported veteran's result row carries the fencer's own season-derived V0–V4 category (via the already-existing enum_source_age_category escape hatch), so ranking reads (which key off the fencer's computed category, not the tournament's stored one) work with zero changes to fn_ranking_ppw/fn_ranking_kadra/fn_ranking_full.
  • Matching is exact-or-approved-alias only for PZSz senior brackets: no fuzzy auto-link, no auto-created fencer. A fuzzy near-miss goes to a new lightweight review queue instead of being linked or dropped; a genuine non-match is skipped and never appears in tbl_result.
  • An unconfigured tournament type raises before writing a score — already true as of today's fn_get_min_participants/fn_assert_type_configured rewrite (§07's own fail-closed requirement), and PPS/MPS are already configured (multiplier 1.0, threshold 1, hardcoded — no result-counting bucket).
  • derive_tourn_type_from_event_code gains PPS/MPS prefix branches so a real PZSz event code (PPS4e-2025-2026, MPS-2025-2026) resolves to its type instead of raising on an unresolvable None.

Deliberately out of scope

No new Admin UI. The review queue (§06) is backend-only this step — two RPCs (approve/reject), no screen — matching the same backend-first sequencing steps 4/5 already used for fn_ranking_full. A resolver UI, if wanted, is a UI-surface decision for whoever scopes step 7 (which is about ranking display, not match review, so it is not assumed to absorb this automatically — see §12 Flags). No historical PPS/MPS backfill: 2025/2026 and earlier carry no scoring configuration for these types by design (§07) and none is added. No PZSz carry-over: begins disabled, per §07 and the existing exclusion already built into fn_ranking_full's per-engine bodies (ADR-098).

03 · Proposed ADR-100 — sign-off requested before the file is written

A senior-field bracket is a tournament label, not a veteran category; matching for it is a third, stricter policy

Per doc/claude/planning.md rule 6, this ADR is drafted here and not written to doc/adr/100-… until you say so. Schema and pipeline changes can proceed once you confirm this plan; only the ADR file's creation waits.

Context. PZSz national senior competitions (PPS, MPS) already exist on the calendar (PR #7) as childless events. Veterans enter them alongside much younger fencers in one undivided senior field — unlike every existing source this pipeline ingests, which already carries either a single V-category or a small number of them per physical pool. Design §07 requires the stored tournament to preserve the field's full size and each veteran's original place (the "34-of-107 invariant"), reuse the existing FTL parser rather than build a second one, and match conservatively: only an existing canonical fencer or an approved exact alias auto-links; anything else needs a human decision, and nothing is ever auto-created.

Decision. Three additions, each reusing an existing mechanism rather than inventing a parallel one:

  1. enum_age_category gains SENIOR — a tournament-level source-bracket label, never a result-level category. A CHECK constraint on tbl_result.enum_source_age_category forbids the value SENIOR there, so the one column that already carries a per-row category override (ADR-056) cannot be used to publish a non-veteran category by mistake.
  2. A new Flow.INGEST_PZSZ_SENIOR and Rule, built from the same plugins Flow.INGEST_DOMESTIC already uses (ParseSource → ValidateIR → ResolveEvent → ResolveFencers(intake="PZSZ_SENIOR") → ValidateCounts → Commit) minus the three pool-splitting steps that do not apply (DetectCombinedPool, SplitByAge, DetectJointPool — PZSz never splits one physical field into several tournaments; it writes exactly one SENIOR tournament per weapon/gender and lets each row carry its own V-cat instead). ResolveFencers reads the now-activated intake param for the first time: "PZSZ_SENIOR" selects a third Phase-B outcome — no fuzzy auto-link, no auto-create, an UNMATCHED row is dropped, an in-between (fuzzy found something, below the auto-match threshold) is queued for review instead of linked or dropped. A new Commit-variant (CommitPzszSenior, same plugin kind/effects, same _row/find_or_create_tournament/ingest_results helpers) groups matched rows by (weapon, gender) instead of by V-cat, writes one SENIOR tournament per group with participant_count from the parsed IR's full field size (not the written-row count) and each row's own enum_source_age_category set, and never calls _rerank_places.
  3. A new, dedicated review-queue table for the one genuinely new state this policy introduces — "a candidate exists, but auto-linking it would be a guess" — modeled directly on tbl_registration_identity_override's already-proven shape (dedicated table, nullable candidate FK, CHECK-constrained status, decision timestamp, admin-only RLS) rather than forcing it into tbl_match_candidate, which structurally requires an already-written result. See §06.

Alternatives rejected. A second FTL parser specifically for PZSz. Rejected: §07 item 1 requires reuse, and nothing about PZSz's FTL export differs from any other organizer's — the difference is entirely in what the pipeline does with the parsed IR afterward. Treating a PZSz event as "domestic" (auto-create unmatched) or "international" (silently exclude unmatched). Rejected: both are real, tested behaviors for real reasons elsewhere, and neither matches §07's explicit "never auto-create... skip unmatched... uncertain enters review" — forcing PZSz through either existing branch would either fabricate fencers who never had an account or silently lose a competitor with no trail. Splitting a PZSz field into per-V-cat tournaments, matching every other ingestion path. Rejected: this is precisely the case that would break the 34-of-107 invariant — a per-V-cat tournament can only report its own slice's N and would need _rerank_places, both explicitly against §07. Writing an uncertain match into tbl_result under a placeholder/best-guess id_fencer, tagged for later review. Rejected: tbl_result.id_fencer is a real FK to a real person; a still-uncertain candidate is not yet known to be that person, and publishing it (even provisionally) into a ranking is a bigger, harder-to-undo mistake than the read simply not showing that competitor's row for a few days.

Consequences. fn_ranking_ppw, fn_ranking_kadra, fn_ranking_full, Flow.INGEST_DOMESTIC's own Rule, and every other existing ingestion path are untouched. A review-queue row with no UI to act on it (this step ships RPCs, not a screen) is inert but visible via direct query/RPC — the same "backend real, frontend later" shape steps 4/5 already used for fn_ranking_full. A future carry-over engine for PPS/MPS (explicitly deferred, begins disabled) will need its own ADR when it lands, since a SENIOR-to-SENIOR prior-event link crosses a different kind of tournament than every existing carry-over matcher assumes.

Relationships. Implements the design's own §07 and §12. Extends the ADR-056 revision (enum_source_age_category trust-the-splitter rule) to a second, unrelated reason for divergence. Composes with ADR-098 (PZSz results feed the evf_fie/pzsz-aggregating evf_plus_total once a season's Season Scoring Rules name a PZSz bucket — not yet true for the real active season). Relates to ADR-036 (PZSz organizer/event-id insertion already handles the migrations-before-seed-dump ordering; this step's schema changes are pure ALTER TYPE/new-table, no seeded-row backfill, so that hazard does not recur here).

04 · Schema

Two migrations (enum value first, everything that uses it second) plus one new table

The enum-value-then-use split applies again

Exactly the hazard the design doc already flags for PPS/MPS (§11): a new enum value cannot be used in the transaction that adds it. SENIOR needs the same split — one migration adds it to enum_age_category, a later migration adds the CHECK constraint referencing it and any code path that writes/reads it.

ObjectShape
enum_age_categoryALTER TYPE ... ADD VALUE IF NOT EXISTS 'SENIOR' — own migration.
tbl_result.enum_source_age_category CHECKCHECK (enum_source_age_category IS NULL OR enum_source_age_category <> 'SENIOR') — a result row's own category may be any real veteran category or NULL, never the source-bracket label. Later migration, after SENIOR exists.
derive_tourn_type_from_event_code (Python)New prefix branches: PPS{round}{weapons} (and the gender-split W/M-infixed form, per the glossary's own PPS code shape) → 'PPS'; MPS → 'MPS'.
tbl_pzsz_match_review (new table)Modeled on tbl_registration_identity_override: id_review PK, id_event FK, txt_scraped_name, int_place, enum_weapon, enum_gender, id_candidate_fencer (nullable FK — the fuzzy matcher's top guess, if any), num_confidence, enum_status CHECK-constrained to PENDING/APPROVED/REJECTED, ts_created, ts_decided. Admin-only RLS, same shape as the override table's own policy.

Approve writes the held row into tbl_result via the same fn_ingest_tournament_results-shaped insert path (one row, not a re-run of the whole bracket) and marks the review APPROVED; reject marks it REJECTED and writes nothing.

05 · Pipeline: a new flow, not a new parser

Flow.INGEST_PZSZ_SENIOR

ParseSource -> ValidateIR -> ResolveEvent -> ResolveFencers(intake="PZSZ_SENIOR")
  -> ValidateCounts -> CommitPzszSenior

Compared to Flow.INGEST_DOMESTIC's existing Rule: DetectCombinedPool/SplitByAge/DetectJointPool/AssignFinalVcat are dropped (nothing to split — one tournament per weapon/gender, full stop), ValidateCounts is reused unchanged (it already does the URL→data + count validation §07 item 2 asks for, plus the now-fail-closed min-participants gate against the season's PPS/MPS configuration), and Commit is replaced by CommitPzszSenior (§03 item 2).

Dispatch. The one existing call site that hardcodes Flow.INGEST_DOMESTIC and organizer_hint="SPWS" (ingest_cli.py's _run_parsed_through_flow/ingest_event_from_url) reads the resolved event's own organizer (already joined and available on pctx.event/the event dict — confirmed queryable per the existing test 70.10) and selects Flow.INGEST_PZSZ_SENIOR + organizer_hint="PZSz" when it is PZSz, else the existing behavior, unchanged. No new CLI flag, no operator action beyond pointing the ingester at the event by its already-existing code — identical to how SPWS/EVF ingestion is triggered today.

ResolveFencers, intake="PZSZ_SENIOR". Phase A (exact/alias, _find_exact_fencer) is unchanged — it is already exactly "an existing canonical fencer or an approved exact alias," §07 item 4's own wording. Phase B changes: find_best_match still runs (to produce a candidate for the review queue), but _should_link's auto-link branch is skipped entirely for this intake; a candidate found below the auto-match threshold is written to tbl_pzsz_match_review (§04) instead of linked, and a genuine UNMATCHED result is dropped (id_fencer=None, no row written, no review entry — a true non-match is not "uncertain," it is simply absent from this competition's veteran data).

06 · Uncertain matches: a review queue, not a live link

Why this needs new schema, and why it stays backend-only this step

§07 item 4 draws three outcomes, and the third one is new: exact/alias (auto-link, already built), no candidate at all (skip, already the shape of "unmatched" elsewhere), and an uncertain candidate ("uncertain matches enter Admin review" — not yet a real code path anywhere). A genuinely uncertain match cannot be written into tbl_result at all, uncertain or not: that column is a real, NOT-NULL foreign key to a real fencer, and design §07 is explicit that nothing should be guessed into the ranking. tbl_match_candidate — the codebase's one existing "match needs review" table — requires an already-written id_result, so it cannot hold a pre-write hold; it exists to let an admin re-point or correct a result someone already committed, a different problem. tbl_registration_identity_override is the closest existing shape for "a decision is pending and nothing downstream has happened yet," so this plan copies its shape into a new, PZSz-specific table (§04) rather than overloading either existing table for a case it wasn't built for.

This step ships the table and the two decision RPCs, not a review screen — matching the backend-first sequencing already used for fn_ranking_full in steps 4/5. An admin resolves a pending row via direct RPC call today; a UI for it is a scoping decision for whoever picks it up next (flagged, not assumed, in §12).

07 · Scenario walkthrough

PPS round 4, épée, 2026/2027 — 107 senior fencers, 6 of them SPWS veterans

  1. The event PPS4e-2026-2027 already exists on the calendar (PZSz sync, PR #7), childless, organizer PZSz.
  2. An operator ingests the FTL results URL by event code, exactly as for any SPWS/EVF event. ResolveEvent resolves the event and its organizer is PZSz → dispatch selects Flow.INGEST_PZSZ_SENIOR.
  3. ResolveFencers(intake="PZSZ_SENIOR") processes 107 rows: 4 exact/alias matches to existing SPWS veterans (AUTO_MATCHED); 1 fuzzy near-miss against an existing veteran whose name FTL mangled slightly — below the auto-match threshold, written to tbl_pzsz_match_review as PENDING, not linked; 1 exact match to a veteran whose birth year on file conflicts (reconciled the same way domestic exact matches already reconcile it); the remaining 101 rows are young non-veteran competitors or unmatched-anyone — every one of them UNMATCHED, dropped, no row, no review entry.
  4. ValidateCounts confirms the URL's own reported field size is 107 and passes the (hardcoded-1) min-participants gate — trivially, since 1 is the floor and 5 matched rows clear it regardless.
  5. CommitPzszSenior writes one tbl_tournament row: enum_type='PPS', enum_age_category='SENIOR', int_participant_count=107 (the full field, from the parsed IR — not 5). Five tbl_result rows are written, each keeping its ORIGINAL placement from the 107-field (e.g. 34th stays 34, not renumbered to 1st-of-5), each carrying its own enum_source_age_category (say, three V2s and two V3s) so fn_assert_result_vcat trusts the splitter and the ranking functions place each veteran in their own bracket exactly as if enum_age_category on the tournament had been their own V-cat.
  6. fn_calc_tournament_scores runs as part of the same RPC, applying the season's num_pps_multiplier to each of the 5 rows — no different from any other tournament type's scoring path.
  7. A day later, an admin resolves the pending review row: it really was the same veteran, slightly misspelled. fn_approve_pzsz_match_review writes the 6th tbl_result row (place preserved from the review record, same enum_source_age_category treatment) and marks the review APPROVED. int_participant_count does not change — it was always 107, matched or not.
  8. The veteran's PPS result now appears in fn_ranking_kadra/fn_ranking_full's EVF+ total for their own V-cat once a season's Season Scoring Rules name a PZSz bucket (not yet true for the real active season — that wiring is a later step, per ADR-098's own deferral) — but the underlying scored, correctly-placed tbl_result row already exists and is correct today.
