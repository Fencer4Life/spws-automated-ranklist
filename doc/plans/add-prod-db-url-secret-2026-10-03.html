ADR-108 · promote · one-time setup

Add the secret SUPABASE_PROD_DB_URL

Promote’s apply writes PROD in one transaction over a direct database connection. That connection string lives in one GitHub repository secret. You do this yourself: the value contains PROD’s database password, so it never goes into chat, a file or a commit.

about 5 minutes PROD project ywgymtgcyturldazcpmw repository secret, not the production environment

✓ Decided 3 Oct: option B. No new secret.

Promote’s apply goes through PROD’s service-role API with SUPABASE_PROD_URL and SUPABASE_PROD_SERVICE_ROLE_KEY. Checked: the PROD drain uses that pair successfully, service_role may execute the apply, and the API allows a call 8 seconds, which PPW1’s full apply fitted on LOCAL. Decide this first · 3 Oct, after your screenshot

The existing PROD secrets cannot open a database connection

Your list has no SUPABASE_PROD_DB_URL; it would sit between SUPABASE_PROD_ANON_KEY and SUPABASE_PROD_REF. None of the PROD secrets already there can stand in for it:

SecretWhat it isOpens a database connection?
SUPABASE_PROD_URLThe API address, https://ywgymtgcyturldazcpmw.supabase.co (the ingestion and the drain use it with the key below)no
SUPABASE_PROD_SERVICE_ROLE_KEYThe key for that API (PostgREST): each call is one HTTP requestno
SUPABASE_PROD_ANON_KEYThe public read key of the frontendno
SUPABASE_PROD_REFThe project’s idno
SUPABASE_ACCESS_TOKENYour personal Management API token (the gate’s and promote’s reads use it)no

A direct connection needs the database password, and no secret holds it. The signed-off plan put the apply on a direct connection with its own statement_timeout, “not through the Management API or PostgREST” (pre-mortem row on the transaction timing out).

OptionWhat it means
A (recommended)You add SUPABASE_PROD_DB_URL as below (Parts 1 and 2). Nothing in the code or the plan changes. Promote sets its own timeout (900 s) and runs the apply in one transaction it controls.
BNo new secret: the apply goes through the API with SUPABASE_PROD_URL and SUPABASE_PROD_SERVICE_ROLE_KEY, the way the LOCAL acceptance of step 9 ran it. Still one transaction (one function call), but the time limit is the API’s, not one promote sets, and a call cut off by the API cannot be told apart from a slow one until PROD is read again. The plan and ADR-108 §6 are amended; a small code change.
CNo new secret: the apply goes through the Management API with SUPABASE_ACCESS_TOKEN. Same limits as B, and it puts PROD writes on your personal token, which has rights over every project in your account.

Recommendation: A. It is the design you signed off, it costs five minutes once, and it keeps the one write to PROD under a timeout and a transaction promote controls. B is what applied PPW1’s 58 writes on LOCAL in step 9’s acceptance, so it is the fallback if you would rather not hand GitHub the database password.

Part 1 · Supabase

Copy the connection string

  1. Open the PROD project (ref ywgymtgcyturldazcpmw; CERT is the other one).
  2. Click Connect in the bar at the top of the project.
  3. Under Connection string, type URI, take the Session pooler string. Not Direct connection: it is IPv6 only, and GitHub’s runners cannot reach it. Not Transaction pooler (port 6543).
  4. It looks like postgresql://postgres.ywgymtgcyturldazcpmw:[YOUR-PASSWORD]@aws-0-<region>.pooler.supabase.com:5432/postgres. Replace [YOUR-PASSWORD], brackets included, with the database password.
  5. If the password contains @ : / ? # % or a space, write those characters URL-encoded (@ is %40, # is %23, % is %25), or reset the password to letters and digits only.

? Don’t know the database password?

Project Settings, Database, Reset database password. No workflow in this repository uses it today (they use the service-role key and the Management API token), so a reset breaks none of them. It does break anything of your own that logs in with the old password, such as a saved psql or database-client connection.

Part 2 · GitHub

Store it as a repository secret

  1. Open Settings, Secrets and variables, Actions of the repository.
  2. On the Secrets tab, click New repository secret. Not under Environments: the promote job runs without an environment, so a secret of the production environment is invisible to it.
  3. Name: SUPABASE_PROD_DB_URL. Secret: the whole string from Part 1. Click Add secret.

Or, in your own terminal: gh secret set SUPABASE_PROD_DB_URL --repo Fencer4Life/spws-automated-ranklist. It asks for the value with the input hidden, so it stays out of your shell history.

Part 3 · check

How we know it works

  • The secrets list shows the name; the value is never shown again. Tell me when it is there and I check the name with gh secret list, which prints names only.
  • The real test is promote’s dry run after the rehearsal (promote.yml with dry_run). It connects and runs the apply’s dry run, which writes nothing. A wrong value fails at the connection, with nothing written. A string that points anywhere but PROD is refused before connecting: promote checks that the connection names PROD’s ref.
