Workflow 1 · phase5-event-runner.yml

"Phase 5 Event Runner": loads one event's results, or replaces them

"Phase 5" is history, not function: it was the fifth phase of the 2026 rebuild of the ingestion pipeline (ADR-050, phases 0–6). The name tells you nothing about what a run does.

You start it by hand (Actions → Run workflow, or gh workflow run) with an event code, a target (cert or prod) and an optional staged run id. The run id decides which of two different jobs it does:

STAGEstaged run id empty
  • Reads the event's result URL from tbl_event.url_results and scrapes it (logging in to FencingTimeLive when the source is there).
  • Matches each fencer to the master list and writes the results into the draft tables on the target. The stored, published results are not touched.
  • Writes the review report staging-reports/<event>/full.md to Storage and sends it to Telegram.
REPLACEstaged run id given
  • Runs the sign-off checks on that staged run: it refuses a run that still holds an unresolved PENDING fencer or a ❌ match.
  • Then, in one transaction, removes the event's stored results (by its exact code) and commits the staged run in their place (fn_replace_event_from_draft). On prod, this rewrites published results.

Today it is kept for LOCAL work and for repairing a past-season event. A new event of any organizer goes through ingest-event.yml on CERT and promote.yml to PROD (ADR-113), because promote.yml only reaches the active season.

Workflow 2 · ftl-seed.yml

"FTL Seed Organizer Delivery": built to e-mail the entry files, never commissioned

It was built in July 2026 (ADR-080 §5) to do one thing: take an event's declared registrations, generate the FencingTimeLive import files (the "seed"), zip them, e-mail the zip to the organizer's address on the event from the SPWS Gmail, and stamp the event with ts_ftl_sent. It has two jobs:

JobTriggerWhat it would doWhat happens
Deliver current FTL seed bundlemanual: event code + cert/prode-mail one event's seed zip to its organizernever dispatched
Deliver due PROD rostersdaily, 04:00 UTCe-mail every PROD event whose registration deadline has passedskipped every day — runs only if the repository variable ENABLE_FTL_DEADLINE_SEND is true, and it was never set

0 It has never sent an e-mail, and it cannot

Every finished scheduled run (101) was skipped; there has never been a manual run; when ADR-080 measured it on 25 September, 0 of 103 events carried a delivery stamp on CERT or PROD. The repository has no SPWS_GMAIL_USER or SPWS_GMAIL_APP_PASSWORD secret, so a run would fail at the sending step. ADR-080 withdrew the e-mail delivery on 25 September 2026: the association holds no registered sending identity.

What replaced it: the organizer downloads their own event's files from the page reached by their capability link (tbl_ftl_export_token). The workflow, its Python sender and generator stay in the tree, unused.

So the only trace it leaves is one skipped run a day near the top of the Actions list, under a name that reads like a working delivery.

! The admin UI still offers the withdrawn action (D5)

The event form in frontend/src/components/EventManager.svelte:147-154 still has the send-to-organizer button and the read-only "sent at" field, and the button dispatches ftl-seed.yml. Since no Gmail secret exists, a click would start a run that fails at sending and posts a Telegram failure; nothing reaches an organizer. Removing the button is UI work, so I recommend its own task with before/after screenshots rather than mixing it into a rename.

How the names would look

Two knobs: the workflow's name and each run's title

GitHub shows two different labels. name: is the workflow's label in the Actions sidebar. run-name: is the title of each run in the list; without it, every run is titled with the workflow's name, which is why all 144 runs read "Phase 5 Event Runner". No workflow in this repository sets run-name: today.

Worth knowing about these two labels

  • A run's title is fixed when the run is created. The 144 old runs keep "Phase 5 Event Runner"; only new runs get the new titles.
  • run-name: can read only the github and inputs contexts, not vars or secrets. It is a display string, never executed by a shell, so putting an unvalidated input in it is safe; the job still validates every input before its first use.
  • The file names do not change. Everything that starts these workflows uses the file name: the dispatch-workflow edge function, the admin UI, gh workflow run, the tests. The only workflow that follows another by its display name is release.yml, which follows CI, and CI is not renamed.

Why these recommendations

Reasoning

  • D1 A. It names both modes and the dangerous verb, "replace", and says when the workflow is used today, so nobody reaches for it to load a new event. B is accurate but hides that a commit overwrites stored results.
  • D2 A. The run title is where the confusion is: 144 identical lines, some of which rewrote PROD. A title with the event, the environment and the mode makes a REPLACE on prod stand out in the list.
  • D3 A. "NOT IN SERVICE" first, because that is the one fact a reader of the Actions list needs; B puts it last, in parentheses.
  • D4 A. The daily run is the only reason this workflow keeps appearing in the list, and it changes nothing: every run is skipped, and the sweep job can only be reached from the schedule. The cost is small and named below: one contract test, one handbook row, one line in the ADR-080 amendment.
  • D5 A. The button is a UI change and follows the UI rule (before/after sheet signed off first). It also touches the edge function's allowlist and a contract test that asserts "ftl-seed.yml" is allowlisted, so it is its own small decision.
