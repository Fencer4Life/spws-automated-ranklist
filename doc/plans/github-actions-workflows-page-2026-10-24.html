§ 1 · what is on the page

One block per workflow, grouped by the process it serves

  • The six things you named, for every file in .github/workflows/: the name (as GitHub shows it, and the file), an elaborate description of what it does, how often it runs and who starts it, what it depends on, the process it supports, and what a red run usually means with the first thing to check.
  • Layout. Six long columns do not fit the ADR text column (818 px beside the contents column), so each workflow is a two-row block in one common table design: the short facts (workflow, process, how often, depends on) on the first row, the two long texts side by side on the second. On a phone each field stacks under its own label.
  • Five process groups: quality gate and release; results intake; calendar and start-list synchronization; promotion to PROD and event close; self-healing recompute. Plus a daily schedule (UTC and Warsaw, summer and winter), how the workflows connect (the chains, and the four shared lanes), and keeping this page current.
  • How often is measured, not just configured. GitHub starts scheduled runs late: measured 10–24 Oct 2026, the daily ones started 4–9 hours after their cron, and the 15-minute drains ran 5–6 times a day, not 96. The page states both, with the dates.
  • Linked from the GitHub card in System context → External systems: “Actions workflows” is now the link (§ 2, last pair).
  • Kept current. python/tests/test_github_workflows_page.py (GHWF.01–06, seen red before the page existed) fails in preflight and CI unless the page has one block per workflow file, the workflow’s own name, every field filled, every cron, every called or triggering workflow and every lane. Both copies of the release skill (.claude/skills/release/SKILL.md, .agents/skills/release/SKILL.md) now carry the step: a workflow added, removed, renamed or changed updates its block in the same commit.
