So, per day

  • No FTL event in progress (most days): 0 requests, 0 sign-ins. 1 request the day before an FTL event; 1 a day for an open event waiting to close.
  • One FTL event in progress (an EVF weekend, L ≈ 25): 4 schedule checks + 1 close + two or three ingests of 1 + L: about 40 to 80, and a sign-in on at most one of those days.
  • Hard ceiling, whatever runs: 120 requests and 2 sign-ins a day (F1); the 121st is refused before it is sent, and Telegram says so. A sixth of the day that got us blocked, and no run, mine included, can exceed it.

The strategy · one push, test-first

Eight changes

  1. S1 · Count and cap (B1, B6). ftl_auth.get_authed_ftl_client takes a ledger: before any request it draws from the day’s allowance (Warsaw day), ten requests at a draw, and gives back what the run did not use when the client closes; a sign-in is drawn the same way. Spent: the client raises FtlBudgetSpent (an FtlAuthError) before sending; the run reports it like a refused sign-in and goes on with its other sources; the results sync records the cycle as “budget” and pauses nothing (the next day reads the event). No ledger, no read: a process without one gets “FTL is read only with a ledger”. CI’s ledger is one CERT row per day (tbl_ftl_read_ledger, fn_ftl_ledger_take, fn_ftl_ledger_give_back, service role only, as tbl_results_sync_cycle), reached through ManagementTransport with the access token every FTL step already holds, and a LOCAL run draws from the same row (F2). The run’s last line prints the day’s count (“FTL today: 31/120 requests, 1/2 sign-ins”); the sync’s outcome line adds it from 80% up.
  2. S2 · Capture the session token at every sign-in and reuse it for its whole life (B2). FTL’s session is the connect.sid cookie, valid a fixed 10 days from the sign-in and not extended by use (ADR-068), so 10 days is the most one sign-in can give. The client takes a session store: it loads the stored cookie and its expiry, and signs in only when there is none, it ends within 12 hours, or a fetch bounces to the login page; after a sign-in it stores the new cookie at once, before any other request, so no session is ever lost. One store for everyone (F2): one CERT row (tbl_ftl_session, fn_ftl_session_get / _put / _drop, service role only), read and written by CI and by a LOCAL run alike, so a sign-in made anywhere serves every run for ten days. Expected sign-ins: at most three a month, and none in a month with no FTL read. Never GitHub’s Actions cache (a pull request’s workflow could restore it in this public repository). A refused sign-in is still remembered per process (G71), counted by the ledger, and stores nothing. Today’s check threw its session away; capturing one now would cost a sign-in that nothing could use until this ships. ADR-068’s deferred follow-up, done.
  3. S3 · The compare reads the schedule only (B3). For an event whose every source is an FTL schedule (the domestic route by ingest_cli.is_ftl_schedule; the international route when its only slot is FTL), the sync’s compare step reads the schedule with close.read_ftl_schedule (1 request) and compares run_record.schedule_sha256 with the latest finished CERT run’s listings.schedule.sha256, as close.check already does. Equal: nothing changed; the promote-only check runs as today. Different, or no run: changed, and the ingest reads every final listing as today. Events with another engine compare as today.
  4. S4 · FTL events four times a day (B3). results_sync.select learns the cycle’s UTC hour: an FTL-only event is taken in the cycles of the hours 08, 12, 16 and 20 (F3) and otherwise deferred, named in the select’s log. A manual --code run always takes its event. Other organisers stay hourly; the Telegram bot’s dispatch does not change.
  5. S5 · No automatic re-read of a completed FTL event (B4, B5; F4 B). source_regression.past_events leaves out every FTL-only event that is COMPLETED, printing “n completed FTL event(s) not re-read: by hand only”; the daily line and the stored report say the same. An FTL event still open is re-read weekly as today (1 + L a week), to catch a listing corrected after its ingest before the close. A by-hand re-read of one FTL event stays: source-regression.yml with its code, inside the cap. upcoming marks an FTL-only event for the dry read only the day before it starts, which with S3 costs 1 request.
  6. S6 · A pause between requests (B7). At least one second between two FTL requests (FTL_PACE_SECONDS, default 1.0; tests pass 0). A 25-listing ingest takes half a minute.
  7. S7 · My own runs (B6). I do not read FTL on LOCAL. The one exception is a check of one event when you ask for it in so many words, on the LOCAL ledger (F2), reported with its count. No re-read of mine, ever, for an investigation: an investigation reads CERT’s stored runs and reports, which hold what FTL gave. Into memory and the operator runbook.
  8. S8 · The client says who it is (B8). ftl_auth sends User-Agent: SPWS-ranklist/1.0 (Polish Veterans Fencing Association ranking; reads final results) on every request, the name today’s check used (F7). The same name goes into your letter to FTL, so they can allow or refuse it by name.

Not changed: the daily close, the ingest’s read (the event written whole), G71, every other organiser’s rhythm, the eight workflows’ secrets (no new secret; the CERT rows hold a session cookie and a count, never the password).
