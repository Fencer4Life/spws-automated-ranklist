Naming and shaping the registration document

One page that follows a single registration from the fencer opening the link to the row being purged after ingestion — including what happens when it goes wrong, which is where today's three defects lived.

Plan — 1 decision below new handbook page no code change

Decide this first

The name

House style across the handbook is plain, hyphenated noun phrases — events-and-registration, end-to-end-flows, workflow-catalog, codebase-map, test-and-traceability. Nothing evocative, nothing branded.

✓ Recommended — doc/handbook/reference/registration-lifecycle.html

Title “Registration lifecycle”, doc-id: HB-REF-REG-LIFECYCLE. “Lifecycle” is not decoration here — it is literally the arc the page describes. A registration row is born at declaration, matched or not, corrected, published to the roster, exported to the organizer, resolved against a fencer at ingestion, and finally purged. ADR-079 calls the table ephemeral and purged after reconciliation; nothing currently documents that ending.

! The one thing against it

“Lifecycle” is already spoken for. ADR-077 is Event Lifecycle & Season Skeletons, and tbl_event.enum_status is the event lifecycle. A reader could reasonably expect this page to be about CREATED → PLANNED → COMPLETED. The alternative avoids that entirely and echoes your own words: registration-end-to-end.html, “Registration end to end”, HB-REF-REG-E2E.

Answer needed: registration-lifecycle (richer, one collision) or registration-end-to-end (unambiguous, plainer)? I lean to the first — the collision is with a different noun (event lifecycle vs registration lifecycle) and the page earns the word by actually covering the purge.

Placement

A reference page, deliberately not a second subsystem page

Checked in scripts/check_docs.py rather than assumed: doc-type: subsystem forces ten section ids — purpose, boundaries, mental-model, current-flow, invariants, implementation-map, operations, tests, decisions, change-triggers. Other types are structurally free (workflow-catalog.html is reference and uses its own five).

That matters twice over. Forcing the skeleton would bend a journey into a subsystem template, and it would create a second owner for registration beside subsystems/events-and-registration.html — which CLAUDE.md forbids, since current-system facts belong in exactly one canonical place.

So the new page is a walkthrough that derives from the subsystem page and links to it. The subsystem page stays the owner of the invariants; this page owns the sequence.

Content

The eleven stages, and the failures at each

The organising idea: every stage states what happens on the happy path, then what happens when it does not. Three defects shipped this month because the code did something no document described — a form that validated with .trim() and submitted the raw string, two dedupe arbiters that could not see each other, and a page that silently wrote to CERT.

1Arriving
  • Three entry points: the shared register.html?event=CODE link, the calendar card, the roster link. The card's “Rejestracja →” only opens the in-app modal while bool_use_spws_registration is true — otherwise it navigates to the deployed page.
  • Which environment each surface talks to, and why register.html carries the PROD pair only.
2Gating before the form
  • Registration disabled → external link. Past dt_end → expired. Past COALESCE(dt_registration_deadline, dt_start) → closed, with the roster still viewable (the ADR-084 decoupling).
  • Client-side gate mirrors a server guard; the server is the one that binds.
3Declaring an identity
  • What is collected, and — as important — what is not validated: no birth-year bounds, the V-category is display-only, so an implausible year passes straight through.
  • Normalisation at the boundary, and the duplicate warning that compares on name alone.
4Matching
  • Exact triple only; no fuzzy matching in the browser, by decision. A miss is not a dead end — it registers with no fencer link.
  • The deliberate “treat a failed lookup as no match” choice, and its consequence.
  • That the match RPC answers per birth year before any write, so the year is effectively public. Stated plainly, because several arguments elsewhere lean on it being private.
5Consent
  • What is stamped, what the presented text actually promises, and why the club field is a consent-version change rather than a string edit.
6The write
  • One constrained public path, why it runs with definer rights, and the registration-window guard.
  • Two arbiters and why a single insert cannot carry both — the matched link, and the declared identity for the unmatched. Then twin absorption, and why promotion beats delete-and-insert (the consent stamp is evidence).
7Correcting
  • Why the create path cannot fix a misspelled name or a mistyped year: both are the arbiter, so a change reads as a different entrant and inserts.
  • The short-lived handle, why it is not persisted, and how a returning fencer obtains a new one.
  • What a mistyped birth year does instead — a second entry the fencer cannot merge.
8What the public sees
  • The roster projection and its GDPR minimisation — no birth year, no club. And what is published: the row identifier and the age band, which is why the identifier cannot authorise anything.
9What the organizer receives
  • Seed generation from every declared registration, canonical naming, the category marker, the empty club field, delivery and its stamp.
10After the competition
  • Identity resolution at ingestion; the read-only invariant; the reconciliation rule where an estimated stored year yields to the declaration and a known one does not.
  • The purge — the part of the arc nothing currently documents.
11Failure boundaries, as one table
  • Closed window · wrong birth year · double submit · lookup blip · blocked storage · edit collision · impersonation. Each with the observed behaviour and where it is pinned by a test.

Closing section: known gaps, named rather than implied — no rate limiting, no birth-year challenge, no audit trail on edits, club not carried, post-deadline entries. Each pointing at its ADR-079 open item so the page cannot quietly drift into claiming more than the system does.

Constraints the page must satisfy

What the validator enforces

  • Five required meta tags — doc-id, doc-status, doc-type, doc-owner, last-verified — with a unique doc-id.
  • A current page must appear in documentation-map.html's ownership JSON with source_globs, or check_docs.py fails.
  • Every internal link target and anchor fragment is resolved; a link to a heading that does not exist is an error. No links to Markdown, none to legacy narrative.
  • Present tense, current behaviour only. No implementation history — that is what doc/plans/ holds.

And one edit outside the new file: reduce Flow 2 in architecture/end-to-end-flows.html to a pointer. It is five bullets last verified 12 July, predating the unmatched path, the routing fix, trimming, twin absorption and the edit path. Left alone it will keep contradicting the new page.

Verification

How this is checked

  • python scripts/check_docs.py — meta, map registration, and every link and anchor.
  • bash scripts/check-coherence.sh and check-spec-sync.sh; render_docs.py --check and render_adrs.py --check for the twins.
  • Source-verified while writing, not after: every behavioural claim traced to the migration, RPC, component or test that implements it — the same discipline that found the three defects. Anything I cannot evidence goes in “known gaps” instead of the prose.
  • ./scripts/refresh-graph.sh before commit.

No code change, no migration, no test change. Documentation only.
