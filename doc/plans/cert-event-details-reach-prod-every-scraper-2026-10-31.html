02 · The rule, half 1: the mirror

Every organizer, every event in the active season

  1. When CERT's details were last written: the latest change on CERT to any of the nine fields, by a scraper or a person, read from the audit log. If there is none, the row's creation time. PROD's time is worked out the same way.
  2. CERT's time is later: PROD takes every one of the nine fields CERT holds. Under S1 A, a blank on CERT leaves PROD's value alone.
  3. PROD's time is later (a person edited PROD after CERT's last write): PROD keeps every value it holds until CERT is written again. Only a field that is empty on PROD takes CERT's value, as it does today. The differences stay listed under "Divergences NOT synced".
  4. Registration link: copied only when neither side holds our own register.html?event=… link (ADR-079 §7). PROD's own link is never replaced.
  5. Values are compared as their type, so a fee of 50 equals 50.0. An event with nothing to change is not written at all (F2).

The nine fields: name, start and end dates, city, country, weapons, venue address, invitation letter, the organizer's registration link, and the entry fee with its currency. Keys, results links, status, the ingest record and our own registration stay exactly as they are today (field list, groups 2 and 3).

Safe in any release order

CERT's time is read with a plain subquery in promote.py, not a new SQL function, because the scheduled mirror can run before the migration reaches CERT. PROD's new function falls back to today's rules when an older payload has no time in it, and PROD's old function ignores the new key.

03 · The rule, half 2: the contract every scraper follows on CERT

Five lines, for EVF, PZSz and whatever comes next

  1. The field is empty: the source's value is written.
  2. The source reports a value different from what the scraper last wrote: it replaces the scraper's own value (the source changed).
  3. A person's value (S2 A): kept. The source's disagreeing value is reported once.
  4. The source sends a blank: nothing is cleared.
  5. Our own registration link: never written by a scraper.

A conformance test suite enforces the contract. Every scraper's writer is run through the same cases, and a new scraper (USA Fencing) has to pass them before it ships.

Two clarifications found during the build (31 Oct). Each keeps a rule you already signed.

C1. An event page in the letter counts as empty, for every scraper (ADR-117 D7 A). On CERT, 8 future EVF events still hold the EVF event page that a person moved into URL komunikatu on 9 Aug: Guildford, Faches, Lausanne, Napoli, Stockholm, Athens, Salzburg, Liège and Dublin. Read as "a person's value", line 3 would hold those pages forever. Read as empty, EVF's real PDF replaces them, as it did for Budapest, Munich and Łomianki.

C2. EVF's weapons stay written together with its event code. The code's letters (PEW5efs) and arr_weapons "state the same fact" (ADR-089), so the code plan keeps writing both. No future EVF event has weapons a person set. The mirror still carries weapons to PROD, as you signed (row 5).

06 · Found along the way, fixed in this change

Six issues

F1 EVF clears a city and country a person set on CERT

Two EVF writers disagree. The identity sync keeps a value when EVF sends none: COALESCE(NULLIF(…), txt_location). The calendar ingest, which runs before it, writes txt_location = NULLIF(v_location,'') and the same for country (fn_ingest_evf_calendar, its existing-slot UPDATE in migration 20261025000001). On 10 Aug at 07:47 it blanked the values a person had set on 9 Aug: Finlandia (PEW8), Ateny/Grecja (PEW13), Toronto/Kanada (PEW17). Fix: contract line 4. Restore: once the release is live, I write those three back on CERT from the audit's 9 Aug values, on your go.

F2 The mirror rewrites every event on every run

The UPDATE sets ts_updated = NOW() on every row, whether or not anything changed. Since 29 Jun, PROD's audit has gathered 10,570 event rows; Skopje alone has 133 since 15 Sep, with no change. Fix: an event is written only when a value changes.

F3 ADR-028 states something the code no longer does

It says the refresh "is the only auto-write path that touches existing events, and it never overwrites a populated column". The code plan has overwritten populated columns since ADR-086. Fix: an amendment that records the contract.

F4 A test file counts 5 of its 25 checks

supabase/tests/19_phase3_wizard.sql plans 25 checks, but pg_prove reported "planned 25 tests but ran 5". Twenty checks sat inside savepoints, and each ROLLBACK TO SAVEPOINT also rolled back pgTAP's own counter, so their results were never counted. Fix: each block now stores the value under test in a psql variable inside the savepoint and checks it after the rollback, the pattern 103_promote_apply.sql already uses. All 25 run and pass.

F5 Four records still say "release pending" for work that is live

ADR-109 and ADR-090's amendment (released 4 Oct, Release run 37180095894), ADR-113 (released 17 Oct, run 39038074124) and ADR-117's D2/D7 amendment (released 25 Oct, main 09179f2c, run 40204836946) said "release pending" in their status lines and in Appendix C. Nineteen RTM rows of that 25 Oct release (CALURL.20–23, NAMECASE.01–04, SEED.09, LOCALSL.01–04, six PZSZ.SL rows) said "Built, LOCAL", beside rows marked "Released". Fixed: each now names its release run, checked on GitHub. The RTM's other rows record where their tests landed ("Landed (date, LOCAL)") and keep the release in the FR row; that convention is unchanged.

F6 The specification is at its line cap, so no ADR can be registered

Main's specification is 1620 lines, the cap. ADR-118's registry row made it 1621, and Gate D failed. Fixed (C): Appendix D's per-change history moved to an archive page; the specification keeps the gated pgTAP total, the suite table and a link. doc/claude/planning.md now sends each change's note to that page.

F7 Appendix D's suite table still showed May's counts

It read pgTAP 566 in 43 files, pytest 754, vitest 371, Playwright 7, while the gated total line said 1519. Nothing checks the table, and planning.md asked every change to update it. Fixed: measured on 31 Oct in this worktree: pgTAP 1555 in 119 files, pytest 2304 in 156 files (2290 pass, 14 skip; 2 deselected by configuration), vitest 1256 in 73 files, Playwright 62 in 4 files. The table now says it is a dated measurement and that only the pgTAP total is checked by CI. The May table is kept on the archive page.

10 · Release, then the data

How it reaches PROD

  1. Branch claude/cert-event-details-reach-prod-every-scraper. The merge message and the Release run say what changes and why (your 31 Oct naming rule, done by hand for now).
  2. scripts/preflight.sh exits 0, then integration, then a push to main. CI and the Release are watched in the foreground. The PROD deploy is yours to approve.
  3. The next EVF or PZSz sync applies the contract on CERT, and its mirror run carries the result to PROD. On your go, I run promote-calendar.yml by hand instead.
  4. Verification goes through PROD's vw_calendar (what the calendar reads) and the reconcile log. F1's three rows are restored on CERT on your go.
