01Duplication — what is happening

Eight events in the current season exist twice: once as a dateless CREATED skeleton, once as the real PLANNED event.

The weapon suffix is a symptom, not the cause It is tempting to read this as "the code changed, so the match failed" — the skeleton predicted one weapon set, EVF published another, and PEW1efs ≠ PEW1f. That reading is wrong, and it matters: the matcher never compares codes at all. Fixing the suffix prediction would change nothing.

02Why a skeleton can never match

_find_existing_match — python/scrapers/evf_calendar.py:1225, the ADR-039 dedup ladder.

RungMatches onSkeleton has it?
Step 0EVF calendar post id (id_evf_calendar_event)no — 0 of 23
Step 1EVF results id (id_evf_event)no — 0 of 23
Step 2EVF slug (txt_evf_slug)no — 0 of 23
Steps 3–5date gate, then country / locationno — 0 of 23 have a date

Steps 3–5 never even reach the country and location comparison. The loop opens with

ex_date = str(ex.get("dt_start", ""))
try:
    ed = datetime.strptime(ex_date, "%Y-%m-%d").date()
except (ValueError, TypeError):
    continue        # <-- every skeleton exits here, every run
The finding A CREATED skeleton carries none of the four identities the ladder can use, and is eliminated by the date gate before the physical-property rungs are tried. It is structurally unmatchable. Every sync run therefore falls through to "no match" and inserts a fresh row beside it. This is not intermittent and not a tolerance problem — it cannot succeed.

03The scale, and what is still coming

8 today, up to 23 Only 8 skeletons have had their real event published by EVF so far. The remaining 15 will duplicate the same way as EVF publishes them through the season. The count grows on its own; it does not settle.

What is not affected, and why you have not seen this on the public page: the calendar hides CREATED events twice over — calendarMonths.ts:258 drops anything with no dt_start, and visibleEvents at :545 filters enum_status !== 'CREATED' (ADR-077). So fencers see one event, correctly. The duplication is visible to administrators, and it quietly inflates the season's event count.

04Three ways to fix it

This changes the skeleton lifecycle, which is ADR-077 territory — your call, not mine.

#ApproachTrade-off
A
recommended		 Adopt the skeleton instead of inserting. When a scraped event matches no existing row, look for an unclaimed dateless CREATED skeleton in the same season and same PEW number, and fill it in — date, name, weapons, EVF ids — instead of creating a row. The skeleton becomes the event, which is what a skeleton is for. A new rung below the ladder, deliberately last so it can never outrank a real identity. Needs a rule for what counts as "the same slot": the PEW number is the natural key, and it is what the season bootstrap assigns.
B Give skeletons an identity at creation. Carry the prior season's EVF calendar id or slug onto the skeleton so Step 0 or Step 2 matches. Cleanest conceptually — it makes skeletons first-class to the existing ladder with no new rung. But EVF issues a new post id per season, so last season's id will not match this season's event. Likely ineffective.
C Reconcile after the fact. Leave the sync alone; add a job that pairs orphan skeletons with real events and retires the skeleton. Does not prevent the duplicate, only cleans up behind it. More moving parts, and a window where both rows exist. Reasonable as a one-off to clear the 8 that exist now.
My recommendation A for the mechanism, C once as a cleanup for the 8 pairs already on PROD. A stops the bleeding at source and keeps the skeleton's purpose intact; C clears the existing pairs without waiting for a season roll. B is worth ten minutes of checking — if EVF calendar ids are stable across seasons it becomes the cheapest fix — but I expect them not to be. I have changed nothing here.

05Currency — root cause and fix

Fixed — data and code 73 EVF and FIE rows now read EUR; the Budapest event on the live page shows 40 EUR where it showed 40 PLN.

Nobody ever wrote PLN. The scraper recognised only the symbols € £ $ and left fee_currency = "" otherwise (evf_calendar.py:469-480), so a listing written "50 EUR" — how EVF usually writes it — fell through to the column default:

ALTER TABLE tbl_event ADD COLUMN txt_entry_fee_currency TEXT DEFAULT 'PLN';
-- 20260327000004_entry_fee_currency.sql:8

This is the same shape as the ADR-089 defect already in the corpus: a column with a non-null default is never NULL, so nothing downstream can tell "not set" from "deliberately PLN", and 40 EVF events across 12 countries — none of them Poland — were labelled Polish złoty.

What changed

  • Code. parse_fee_and_currency() replaces the inline block: symbol first, then the ISO code as a word (EUR, GBP, USD, PLN, …, case-insensitive), then a bare number falls to EUR rather than to the database default. An explicit PLN is still honoured — that is a real claim. "free", "TBC" and an empty cell give no fee and no currency at all. 15 new test cases.
  • Data. 63 rows in scope, 57 updated to EUR (the difference is the rows you had already corrected by hand). A rollback snapshot was taken first and is kept. Verified through vw_calendar — what the public page actually reads — not the write's own output.
Two things I did not do 1. The column default 'PLN' is still there. Dropping it would make "unset" legible again and stop this class of bug recurring on any new code path — but it is a migration touching a shared table, so it wants its own change. 2. I scoped the fix to the families the codebase itself classifies as EVF and FIE (^PEW and ^(IMEW|IMSW|MEW|MSW|PSW), per panelType). DMEW, EVFLEGACY104, VFC and the GP codes match neither pattern and were left alone — tell me if any of those are EVF or FIE and should be EUR too.
