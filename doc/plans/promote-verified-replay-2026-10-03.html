CERT → PROD · domestic events · plan and ADR draft · 3 Oct 2026

Promote copies nothing: it replays a verified CERT ingestion on PROD

Today's promote.py copies CERT's rows to PROD and gets the fencers wrong. The new promote checks that CERT and PROD started from the same inputs and that CERT holds no open issues. It then runs the same ingestion on PROD, writes the result in one transaction that rolls itself back if it differs from CERT, and moves the event through its lifecycle.

Decide this first

Five decisions

✓ P1 Every ingestion starts with a CERT master-data refresh from PROD (your proposal, 3 Oct)

You said it: a birth-year difference like today's is the normal state, because birth years are corrected on PROD during registration (ADR-093). I agree, and I'd make the refresh cover the whole roster, not only the rows one event mentions. The whole roster is easier to reason about, it also carries admin edits and merges made on PROD, and it is about 370 rows.

  • PROD → CERT, in this order: the roster (names, birth year and its estimated flag, gender, nationality, aliases), then PROD’s registrations for the event (name, gender, declared birth year, weapons, FTL name, club and the fencer link; no e-mail hash, edit token or consent stamp), replacing CERT’s test entries.
  • Then CERT's recompute queue drains. A moved birth year re-files the fencer's earlier CERT results (trg_fencer_change_enqueue). The CERT ingestion starts only on an empty queue.
  • Then the fingerprint is recorded on both. Nothing on PROD is ever written by this step.

✓ P1b Fencer ids identical on CERT and PROD; matched by name and birth year at every refresh (B, decided 3 Oct)

Your rule: the fencer id is the same on PROD and CERT, and nothing is ever guessed. Every refresh matches CERT to PROD by name and birth year, with the namesake rule below, and leaves CERT with PROD's ids. The confirmed flag on the birth year is what makes a match certain. After PPW1 every participant's year is confirmed (gate check in step 2), so matching gets easier with each event.

The matching rule, per folded surname and first name:

  • one fencer of that name on each side: the same person; PROD's birth year wins;
  • namesakes on either side: paired only by an equal confirmed birth year; anything left over is not paired;
  • only on PROD: created on CERT with PROD's id;
  • only on CERT: deleted when nothing refers to it; otherwise not paired.

Anything not paired stops the whole refresh before it writes, and is listed for your decision. A typical case is a name corrected on PROD.

The first refresh is the big one. Today the ids differ for most fencers (CHUDY Tomasz is 37 on CERT and 38 on PROD), so CERT's rows are renumbered to PROD's ids and every reference follows. Step 0 below spells out how. After that, a refresh mostly confirms the ids are equal and copies PROD's values. Promote then writes each new fencer on PROD with the very id the CERT ingestion gave him.

✓ P1c LOCAL too: master data identical on LOCAL, CERT and PROD (decided 3 Oct)

Today the seed export drops id_fencer (python/pipeline/export_seed.py lines 29 and 82). It inserts fencers by name and points each result at its fencer with a name-and-birth-year lookup (fencer_lookup, line 161). LOCAL therefore numbers fencers its own way: KRAWCZYK Paweł is 5 and 6 on LOCAL, 354 and 355 on PROD.

  • Export: keeps PROD’s id_fencer and writes every reference with the id itself, not a lookup.
  • Load: inserts fencers at those ids. A fresh bootstrap runs migrations before the seed, and three data migrations add fencers by hand, so those rows already exist under other ids. The load renumbers them with the same fn_align_fencers_to the CERT refresh uses, so one renumbering routine serves both. It then sets the id sequence.
  • Check: scripts/mirror-prod-local.sh and the CI bootstrap compare LOCAL’s roster with PROD’s, id for id (names, birth year, confirmed flag, gender), and fail on any difference.
  • ADR-036 amendment: the seed carries PROD’s fencer ids.

✓ P2 Three kinds of issue block promote (decided 3 Oct)

A fencer identity issue, a scoring error, or a joined-bracket issue. Each one blocks: you fix it, CERT is re-ingested, and promote looks again. There is no acknowledge step. Everything else is either a precondition, which is always required, or information in the report. Step 2 says which check falls where.

P2a, decided as recommended: when the organiser grouped the categories differently from § 2 of the scoring table, ADR-104 §7 says "scored as fenced, never blocks". It stays information, because the results are correct as fenced.

✓ P3 How the PROD write is made safe to undo: A, as recommended

A (recommended): plan, compare, apply in one transaction.

  1. The ingestion runs on PROD in plan mode: it reads PROD and writes nothing, recording every write it would make.
  2. That plan is compared with CERT's committed result, by identity.
  3. One RPC applies the whole plan in a single transaction and checks the result against CERT's fingerprint before it commits. Any difference raises, and PostgreSQL undoes everything: new fencers, birth years, aliases, results, scores, the season's first scoring revision and its lock, and the recompute queue entries.

Nothing half-written is ever visible on PROD.

B: run the live ingestion on PROD, keep a journal of its writes and undo them on failure. Simpler to build, but PROD shows a partial event while it runs. Undoing the season lock also needs a new privileged unlock, which ADR-097 forbids. C: stage into the draft tables and commit in one transaction. That covers results only: new fencers and birth years are still written live, before the comparison.

✓ P4 COMPLETED only once the end date has passed (decided 3 Oct)

Your amendment: organisers sometimes add tournaments the next day. All listings being in is therefore not proof that the fencing is over.

  • COMPLETED: every individual listing on the organiser’s schedule (pools-only and team rounds excluded) is committed with its final results, and the end date has passed: today, Warsaw time, is later than the end date.
  • IN_PROGRESS: anything else, including the evening of the last day with everything in.

The same rule runs on CERT and PROD. SCORED is not set by automation. The Telegram complete command stays for a manual close.

✓ P4b What closes the event once the end date has passed: A, as recommended

Under P4 the last promote usually runs on the final day, before the end date has passed, so something must come back afterwards.

A (recommended): a daily check. A scheduled workflow in the prod-write group takes every domestic event still IN_PROGRESS whose end date has passed and re-reads the organiser’s schedule.

  • Every listing committed on both environments and nothing new published: it sets COMPLETED on CERT and on PROD.
  • New listings published, or one dated after the end date: it changes nothing and sends a Telegram message to ingest CERT and promote again, or to correct the event’s dates.

B: you run promote again after the end date. C: only the Telegram complete command.

✓ P5 PPW1 in the meantime: A, as recommended

A (recommended): build the refresh first (identical ids, P1b), run the refresh for PPW1, and ingest PPW1 on CERT straight away. You can then look at CERT's results while the rest is built. PROD gets PPW1 only through the new promote, after a rehearsal (step 6). B: ingest CERT now, before the refresh exists. CERT would read its own 8 registrations and stale birth years, so that run would be thrown away.

Why

What today's promote does wrong

× Five defects in python/pipeline/promote.py

  1. It sends CERT's fencer ids. read_cert_event reads r.id_fencer (line 123), and write_prod_results hands it to PROD's fn_ingest_tournament_results. Ids differ between the environments: CHUDY Tomasz is 37 on CERT and 38 on PROD.
  2. It creates no fencers. A fencer created on CERT by the ingestion does not exist on PROD.
  3. It drops the joined-bracket order. It never passes p_joined_order, which the 2026/27 engine needs (ADR-104 §3).
  4. It keeps going after a failure. A failing tournament is appended to errors and the loop continues (line 286). Nothing is rolled back.
  5. It always sets COMPLETED. PLANNED → IN_PROGRESS → COMPLETED (line 291), whether or not the event is finished. It also finds the event by a code prefix (LIKE 'PPW1%') in the active season only.

One more gap, outside the promote: ingest-event.yml belongs to no concurrency group. A run with target prod can therefore overlap the PROD recompute drain and a promote, both of which are in prod-write.

The design

Five steps, two of them new gates

0 REFRESH   PROD ──roster──▶ CERT     pair by name + birth year; CERT gets PROD ids;
                                       drain CERT queue; fingerprint both
1 INGEST    CERT                       ingest-event.yml target cert → run record
2 GATE      CERT                       identity · scoring · joined bracket; preconditions
3 PROMOTE   PROD                       re-check · source unchanged · plan on PROD ·
                                       compare with CERT · apply in ONE transaction
                                       (raises and rolls back on any difference)
4 LIFECYCLE CERT + PROD                IN_PROGRESS or COMPLETED by the rule in P4

0 · CERT master-data refresh from PROD (new, P1 and P1b)

The refresh reads PROD and writes CERT only. Every run goes through three gates:

  1. a dry run that computes the pairing and lists every change, writing nothing;
  2. your sign-off on the first run, and on any run that renumbers a fencer;
  3. one transaction on CERT that checks itself before it commits.

Inside that transaction, in this order, with plain statements and no trigger switched off:

  1. Find every reference to tbl_fencer from the database's own constraint list, so no table is missed: results, registrations, match candidates, season nationality, review queues, audit tables.
  2. Renumber in two phases. First, every CERT fencer whose id changes is copied to a temporary negative id, its references move there, and the old row is deleted. Then a final row is inserted at the PROD id, the references move again, and the temporary row is deleted. Each row keeps CERT's own values during this step, so the category check on results is satisfied exactly as before.
  3. Copy PROD's values onto each pair: names, birth year and its confirmed flag, gender, nationality, aliases. This is an ordinary UPDATE, so a changed birth year queues the fencer's CERT events for recompute, the same path ADR-093 corrections take on PROD.
  4. Create the PROD-only fencers at PROD's ids. Delete the CERT-only fencers nothing refers to. Set CERT's fencer id sequence to PROD's.
  5. Check before commit. CERT's roster (id, names, birth year, confirmed flag, gender) must equal PROD's exactly, and every fencer must hold the same number of results as before, counted by person. Any difference raises and nothing changes.
  • Then PROD’s registrations for the event, every time. CERT’s entries for that event, today 8 test rows, are replaced by PROD’s, today 90. Copied: surname, first name, gender, declared birth year, weapons, FTL name, club, and the fencer link (id_fencer), which is valid on CERT once ids are identical. Not copied: e-mail hash, edit token and consent stamp. The ingestion does not read them, and personal data stays on PROD (RODO minimisation). These are the declared years D5 reads, and they are part of the input fingerprint: a registration made on PROD after the CERT run blocks promote until CERT is refreshed and re-ingested.
  • Then CERT’s recompute queue drains to empty before any ingestion starts.
  • Checks without copying:
    • schema fingerprints equal (scripts/schema-fingerprint.sh);
    • the season's scoring settings, engines and lock state equal;
    • the event row as the ingestion reads it equal: code, dates, season, previous edition, source skip/process choices;
    • the override file is the same commit.
    Any difference refuses, listing every field.
  • Fingerprint: a hash of those inputs, normalised by identity (never by id), is recorded for both environments.

1 · CERT ingestion and its run record (new record)

ingest-event.yml with target cert runs unchanged, plus a row in a new tbl_ingest_run:

  • event code, environment and the git commit of the code that ran;
  • the input fingerprint;
  • a hash of each source listing as parsed;
  • the result fingerprint by identity: per tournament code, N and the category order, and per fencer surname, first name, birth year, place, score and match method;
  • the master-data changes: fencers created, birth years moved, aliases added;
  • the gate outcome.

3 · Promote (rewritten, P3 A)

  1. Trigger: promote <exact code> (Telegram), which dispatches promote.yml in the prod-write group, so the PROD drain cannot run alongside. The event is found by its exact code, never a prefix.
  2. Re-check: every gate check and precondition again. PROD's event must be PLANNED, or IN_PROGRESS holding exactly the previous promoted run (day 2 of a multi-day event).
  3. Source unchanged: each listing is fetched and hashed. A hash different from CERT's run means the organiser edited the results in between. Promote refuses: re-ingest CERT first.
  4. URL: CERT's event results URL goes into PROD's event-level field (url_event) inside the same apply transaction.
  5. Plan on PROD: the same INGEST_DOMESTIC flow runs against PROD with a recording connector. It reads PROD and records every write: fencers to create, birth years to move, aliases, tournaments, rows, joined orders. A new fencer takes the id the CERT run gave him, so ids stay identical; the apply refuses if that id is taken on PROD.
  6. Compare: with identical ids, the plan must equal CERT's result fingerprint and CERT's master-data changes, id for id. Any difference refuses with a diff table, and nothing has been written.
  7. Apply: one RPC, fn_promote_event_apply(plan, expected_fingerprint), makes every write, scores and computes PROD's fingerprint, all in one transaction. A difference raises and everything rolls back. Then the joining check runs, and the post-commit report goes to Storage and Telegram.
  8. After: the PROD drain processes the queued recomputes. Promote waits for the drain and compares the affected events with CERT's. A difference here cannot be rolled back automatically, so it is reported loudly. With identical inputs it should not occur.
  9. Seed: the PROD seed export and its commit stay as today (ADR-036).
