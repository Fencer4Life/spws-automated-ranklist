First, the uv question

uv is load-bearing here. The 7.6 GB mostly is not.

Each restart of that server built a whole new 1.8 GB environment, and I restarted it three times. Those environments are ephemeral and now unreferenced — nothing points at them any more. uv cache prune is the command designed for exactly this: it deletes cache entries nothing references and leaves the two tool installations alone. It cannot break basedpyright or graphify, because both live outside the cache in ~/.local/share/uv/tools/.

I have not run it. Say the word and it reclaims about 6 GB; leave it and the space is merely wasted, not harmful.

The requirement, stated bluntly

What today taught us to demand

Anything that gets installed now must satisfy all four, or it does not go on the shortlist:

  1. No API key, no account, no metered call — ever. Not "optional", not "you can configure a local model instead." Nothing in the stack may be capable of billing.
  2. Docker, one command up, one command gone.
  3. Runs on this Mac Mini without a fight — it has 20 GB of RAM and 83 GB free, and the rest of your work needs most of that.
  4. First-party MCP server, not a hobby wrapper that stops being maintained.

Researched on GitHub

Four candidates

RAGFlow — infiniflow/ragflow, 90.8k ★, Apache-2.0 Disqualified

The most popular self-hosted RAG on GitHub by a wide margin, with real document parsing (MinerU, Docling) and an MCP server since August 2025. Two facts end it for us. Its own README states the requirement as “CPU >= 4 cores, RAM >= 16 GB, Disk >= 50 GB” — that is your whole machine, for five megabytes of documents. And setup requires selecting an LLM factory and filling in an API_KEY field: an LLM key is mandatory, not optional. The compose stack also brings up Elasticsearch, MySQL, Redis and MinIO.

Popularity is not fitness. This is the same shape of trap as this morning, with more moving parts.

Onyx — onyx-dot-app/onyx, 32.1k ★, MIT core

A polished product: 50+ connectors, hybrid search over OpenSearch, a web UI, and it genuinely does support fully local inference through Ollama for both the LLM and the embeddings. Two reservations. It is open-core — the Community Edition is MIT, with an Enterprise Edition held back — and it describes itself as “the application layer for LLMs”: an LLM is central to how you use it, so a no-LLM deployment means fighting the product's grain. A "Lite" mode under 1 GB exists.

The right answer if you later want a searchable company knowledge base with a UI and Slack/Drive connectors. Considerable overkill for indexing one doc/ folder.

Qdrant + qdrant/mcp-server-qdrant — 1.5k ★, Apache-2.0, official

The semantic option that cannot bill you: the MCP server's default embedding provider is FastEmbed with sentence-transformers/all-MiniLM-L6-v2, running in-process, and credentials are needed only if you point it at Qdrant's cloud instead of a local one.

The catch is what it actually is: a memory store, exposing two tools — qdrant-store and qdrant-find. No file ingestion, no chunking, no HTML handling. Indexing doc/ means writing that part myself. Also worth knowing before adopting: 28 open issues and 52 open pull requests.

Meilisearch + meilisearch/meilisearch-mcp Recommended

Meilisearch is MIT, a single Go-fast search engine in one container, and the MCP server is first-party — published by Meilisearch themselves as getmeili/meilisearch-mcp on Docker Hub, with 25+ tools for index, document, search and settings management. Typo-tolerant full-text search with intelligent ranking, and no model of any kind: nothing to download, nothing to warm up, nothing that can be metered. The “master key” in its config is a password you invent, not a key you buy.

Why this beats the semantic option for our corpus specifically. Our documentation is made of exact tokens: ADR-084, fn_commit_event_draft, arr_weapons, vw_calendar, Polish names with diacritics, dates that decide which of two facts is current. Exact-token lookup is where lexical search beats embeddings outright — an embedding model is most useful for paraphrase, and least useful for identifiers. Add typo tolerance and 5.2 MB of text, and this is not a compromise; it is the better tool.

Footprint: one container, one volume, on the order of 100 MB of RAM. And if semantic recall does turn out to be missing, Meilisearch supports vector search with a local embedder later — additive, not a rewrite.

What I have to build either way

The ingest script — about a hundred lines, standard library only

No off-the-shelf option handles our HTML correctly, because our HTML is unusual: every hand-written page carries its full stylesheet inline. I measured it earlier — the 81 files in doc/plans hold roughly 330 KB of pure CSS. Indexing the raw markup would put --surface-2 and prefers-color-scheme into the search index and poison every result.

So: walk the corpus, strip <style> and tags, split on headings, post each chunk with its file path, page title and heading as fields. Concretely —

  • In scope: doc/handbook (27 files), doc/governance (2), doc/adr (Markdown sources only — the HTML twins are generated duplicates, so indexing both would double every hit), doc/plans (81), doc/evidence.
  • Excluded: doc/archive/ — never current-behaviour evidence, and already excluded from graphify via .graphifyignore. Same rule, same reason.
  • Re-run on demand; an incremental pass keyed on file modification time is a later refinement, not needed at this size.

What this is not

It does not touch graphify, which stays the answer for code structure, call edges and blast radius — lexical search over prose cannot answer affected fn_commit_event_draft. It does not change what is canonical: the handbook, governance and ADRs remain the record, and this is an index over them, not a replacement for them. And nothing about the ranking system changes.

Verification

How we know it works, and that it cannot phone home

  1. Exact-identifier queries — ADR-084, fn_commit_event_draft, arr_weapons, vw_calendar: the owning document must come back in the top three. This is the class of query the whole choice rests on, so it is graded first.
  2. Prose queries with known answers — the ten questions already written for the earlier pilot (carryover rules, the two denominators, the CERT calendar defects, which Tbilisi handover is current). Same scoring: 2 correct and sourced, 1 partial, 0 wrong or missing.
  3. Polish and diacritics — a query for a fencer surname with and without diacritics must find the same document.
  4. No egress. Run the container with networking restricted to loopback and confirm the full index-and-search cycle still works. A stack that cannot reach the internet cannot bill you, and after today that gets verified rather than assumed.
  5. Clean removal, rehearsed before we rely on it: docker compose down -v, remove the MCP entry, delete the compose file. Proven on day one, not discovered later.

Decide this first

How wide should the index be?

The plan above indexes doc/ only. Two other scopes are possible, and it is cheap to decide now and expensive to re-chunk later:

A — doc/ only, minus archive/ Recommended

Handbook, governance, ADR sources, plans, evidence. This is what you asked for — "all our documentation" — and it is the part with no index today beyond filenames and the registry.

B — doc/ plus the 132 memory notes

Adds the narrative layer that the abandoned pilot was aimed at. Cheap to add, and it would finally make those notes searchable by content rather than by filename. The cost is that finished and superseded notes would rank alongside current ones — the same staleness problem, now in a search box.

C — everything, including python/, SQL migrations and the frontend

Tempting, and wrong: graphify already indexes code structure deterministically, and full-text over source would compete with it while answering worse. If a code question needs answering, the graph is the tool.

Recommendation: A, with B as a second index later if the first one proves useful. One container, one volume, no models, nothing that can charge you — and if it disappoints, it comes off the machine in one command with nothing to reclaim but disk.
