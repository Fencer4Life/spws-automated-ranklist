Event revenue forecast

A report an organiser opens from a link: what the entries declared so far add up to in fees, in total and by weapon and gender, with an elegant printable spreadsheet. Nothing is built. Ten decisions below, each with my recommendation; answer „all as recommended” or name the ones to change.

awaits your answers R1–R10 no code written

01 · What I found

Four facts that shape the design

  • The fee rule already exists, in one place in the browser. The registration form quotes by weapon count: one weapon → num_entry_fee, two → num_entry_fee_2w, three → num_entry_fee_3w, in the event's currency (RegistrationForm.svelte). The report must use the same rule, so I move it into the database as the one source.
  • We record declarations, not payments. Nothing in the system knows who paid. The report can only say „declared”; it is a forecast, and it must say so on its face.
  • Our spreadsheet module cannot style anything. frontend/src/lib/export.ts uses the free SheetJS library, which writes values only: no fonts, colours, borders, column widths or page setup in an .ods. An elegant, printable sheet needs a different writer (R8).
  • A link that guards something needs a key. The entry list is public; revenue is not. The organiser's download page already works this way: a long random key in the link, checked inside the database, revocable (tbl_ftl_export_token, ADR-095). That key covers all events and is created by hand; this report needs one per event, created from the admin screen.

03 · Where the link lives

My proposal for the UI

Two places do two different jobs, so I recommend both, each small:

A · The home: the event form, „Rejestracja SPWS” section

This is where the entry-list link already sits, read-only, for copying. The report link goes right under it. It is the natural place to create and manage a link: the administrator is already deciding how registration works for this event.

Before a link exists the row shows one button, „Utwórz link”. „Nowy link” asks first, because the old one stops working for whoever holds it.

B · The shortcut: the event card in „Znajdź zawody”, signed-in only

On PROD the administrator works from the calendar. A signed-in administrator's card gets one more pill beside „Lista zgłoszonych”: „Prognoza przychodu”, which opens the report in a new tab (creating the link if none exists). A visitor never sees the pill. This is for looking; copying and replacing the link stay in the form.

Why not only the card

The card is a public surface with one line of pills; link management (copy, replace, the warning) does not fit there and would crowd it. Why not only the form: on PROD the form is two screens away from where the administrator watches entries arrive.

04 · Decisions

R1–R10

#QuestionOptions
R1What counts.A · recommended Every entry on the list at that minute, at the fee of its weapon count. Labelled „na podstawie zgłoszeń, nie wpłat”. One figure, no no-show scenarios.
B Add a „pessimistic” figure with an assumed no-show rate. Rejected for now: an invented percentage, not data.
R2A fee tier that is not set (an entry with two weapons at an event with no two-weapon price).A · recommended Count it as one-weapon fee × number of weapons, and say so in a note on the report naming how many entries it touched. With no base fee either, the report shows the counts and „brak opłaty w ustawieniach wydarzenia” instead of money.
B Count such entries as zero and flag them.
R3Splitting one entry's fee across its weapons, for the weapon × gender table. A two-weapon entry pays one amount.A · recommended Equal shares (110 for épée + sabre → 55 each), so the table adds up exactly to the total. Stated under the table.
B Full one-weapon price to the first weapon, the rest to the others. Adds up too, but the order of weapons is arbitrary.
R4The list of entries with each fee as a third block and second sheet (name, gender, category, weapons, fee).A · recommended Include it. The names, weapons and categories are already public on the entry list; the organiser needs it to tick off incoming transfers. Never a birth year, e-mail or club.
B Totals only.
R5Who may open it.A · recommended A key per event, in the link, checked in the database; a wrong, replaced or missing key shows an empty „link nieaktywny” page, never an error. Kept in its own table that only a signed-in administrator can read (not on the event row, which visitors can read).
B Reuse the organiser download page's key. Rejected: that key opens every event, and is made by hand.
R6Where in the UI.A + B · recommended The form row as the home, the signed-in pill on the card as the shortcut (section 03).
A only / B only
R7Where the page is served.A · recommended The same public page as the form and the entry list: register.html?event=…&view=revenue&k=…. One more view of an existing page, shareable exactly like the other two links, no WordPress work.
B A new page of its own on weteraniszermierki.pl.
R8The spreadsheet. The current module cannot style.A · recommended Write the .ods ourselves for this report: a small module that builds the sheet with the report's look (title block, coloured header rows, borders, money format with the currency, column widths) and a page setup for print (A4 portrait, margins, fitted to the page width, a footer with the event, the date and page numbers). Totals are live SUM formulas, so an organiser who changes a fee sees the totals follow. One small, well-known packing library (fflate, about 8 kB) is added to make the file. The existing ranking exports are untouched.
B Keep SheetJS: values in a plain grid. Does not meet „elegant, printable”.
C Buy SheetJS Pro for styles. A licence cost, and still no page setup control we can test.
R9Which events get it.A · recommended Events with our registration on. The row in the form is disabled without it, like the ranking-place box.
B Every event.
R10Later (out of scope now, as you said): cost per weapon, judges, pistes, medals, medics.A · recommended Build nothing for it now, but shape the data so it can grow: the database gives one row per start (entry × weapon) with gender and category, which is exactly what those forecasts will count.

05 · How it would be built

Outline, for the detailed plan after your answers

  • Database: a table of report keys (event, key, created, replaced-at; administrators only); a function for the administrator to create or replace an event's key; one visitor-callable function that takes the event and the key and returns each entry with its weapons, gender, category and fee by the one fee rule, or nothing for a bad key. Added to the visitor allowlist with its justification. The registration form keeps quoting as today; a test pins both to the same rule.
  • Page: a new RevenueReport component shown by register.html for view=revenue; the grouping (tiers, weapon × gender) is one pure module with its own tests, used by both the page and the spreadsheet so they cannot disagree.
  • Spreadsheet: a new module beside export.ts; tests read the produced file back (structure, formulas, styles, page setup), and I open it in LibreOffice and print to PDF for the picture sheet.
  • Admin: the row in EventManager.svelte; the pill in EventCard.svelte behind the signed-in flag.
  • As always: requirement FR-176 with its tests registered first, each test seen failing; a picture sheet for the form, the card and the report (existing states identical); an ADR amendment draft (ADR-079 for the report and its key; ADR-095 names the second kind of key); handbook pages; preflight; release on your word.

One thing to know

A link with a key can be forwarded. Whoever receives it sees the forecast until an administrator presses „Nowy link”. That is the same trade the organiser download page makes, and why replacing the link is one click.
