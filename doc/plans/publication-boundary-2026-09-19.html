01 · Outcome and scope

What exists after this lands

  • tbl_season.enum_ranking_publication (PPW_ONLY | FULL), immutable once set — a trigger rejects any later change to this one column, on any UPDATE, from any role. Design §06: "Migration/season-creation policy only; never an Admin display toggle."
  • The three spreadsheet-derived seasons (SPWS-2023-2024, SPWS-2024-2025, SPWS-2025-2026) are backfilled to PPW_ONLY. SPWS-2026-2027 is backfilled to FULL.
  • The column defaults to FULL, so every season created after this migration — through fn_create_season or fn_create_season_with_skeletons, neither of which needs to change — is FULL by construction, matching design §06's "later seasons: FULL by season-creation policy."
  • fn_ranking_full (design step 4) rejects the call outright for a PPW_ONLY season. fn_ranking_ppw, fn_ranking_kadra and every other existing read path are untouched — a PPW_ONLY season's own PPW ranking keeps working exactly as today; only the combined SPWS+EVF+ view is refused.

Deliberately out of scope

Frontend enforcement — season selection normalizing to PPW, the Ranking/PPW switch disappearing, drilldown/export/deep-link constraints, stale-response discarding — is design step 7's job, the same step that wires the live frontend onto fn_ranking_full in the first place. Enforcing a capability boundary in a UI that does not yet call the RPC the boundary protects would be enforcement with nothing to enforce against. This mirrors exactly the boundary step 4 drew for the same reason.

03 · Proposed ADR-099 — sign-off requested before the file is written

An immutable per-season publication capability, checked once, in one function

Per doc/claude/planning.md rule 6, this ADR is drafted here and not written to doc/adr/099-… until you say so. Schema and fn_ranking_full changes can proceed once you confirm this plan; only the ADR file's creation waits.

Context. The three spreadsheet-derived seasons (2023/2024–2025/2026) reproduce what the association's Excel workbooks already published — PPW-only material that never represented an official combined ranking. 2026/2027 is the first season with a real, database-computed EVF+ total. Design §06 requires this distinction to be a stored, permanent fact rather than something inferred from a date comparison against "the active season" (which would silently flip once 2026/2027 itself becomes historical).

Decision. Add tbl_season.enum_ranking_publication (PPW_ONLY | FULL), NOT NULL DEFAULT 'FULL'. Backfill the three historical seasons to PPW_ONLY; SPWS-2026-2027 stays at its default, FULL. A BEFORE UPDATE trigger rejects any change to this one column specifically — checked column-by-column like fn_guard_scoring_config_write already does for the scoring lock, not a blanket freeze on the row — so the column is genuinely immutable once a season exists, for every writer, not just the ordinary Admin session. fn_ranking_full reads the season's publication capability first and RAISE EXCEPTIONs before doing any aggregation work if it is PPW_ONLY; every other ranking function is untouched, so a PPW_ONLY season's plain PPW ranking keeps working exactly as it does today.

Alternatives rejected. "Older than the active season" logic — rejected per design §06: this would silently reclassify 2026/2027 as PPW-only the moment a later season becomes active, when design explicitly requires 2026/2027 to "retain Ranking/PPW forever." A hardcoded date cutoff duplicated at each call site — rejected: one stored, queried fact is what makes the boundary a database invariant instead of a convention every new caller has to remember. Inferring publication from the assigned scoring engine — rejected: engine and publication are orthogonal facts (a season could in principle reuse an old engine while still being a first-class published season), and conflating them would make a future engine reuse silently change publication too. Enforcing only in the UI — rejected on the same grounds as every other governance decision in this codebase (ADR-097): a disabled button is presentation, not a guarantee, and this codebase has already paid for that lesson once. Governing this column through the existing scoring-config lock (the same mechanism as default_ranking_mode) — rejected: publication capability is not something an administrator ever legitimately changes after the fact, even before a season scores its first result, whereas every field the scoring lock governs is ordinarily editable until that point. A different, stricter mechanism (permanent immutability, not "editable until first score") matches what the value actually means.

Consequences. A historical season's underlying EVF/FIE result data is never deleted or hidden from other read paths (fn_ranking_kadra, raw queries, audit, future carry-over) — only the new combined-view RPC is restricted. A future season wanting to launch as PPW_ONLY (unlikely, but not impossible) would need an explicit migration statement, matching the "migration/season-creation policy only" phrase in design §06 literally. The frontend cannot yet observe or react to this column — that wiring, and the actual UI-level restriction design §06 also describes, is design step 7.

Relationships. Implements the design's own §12 "Proposed ADR C". Composes with ADR-098 (adds a check to the same fn_ranking_full that ADR-098 introduced). Directly supersedes ADR-017's historical PPW/+EVF presentation rule, per design §12's own note.

04 · Schema

One migration: the column, its immutability guard, the backfill

ObjectShape
enum_ranking_publicationNew enum: PPW_ONLY, FULL.
tbl_season.enum_ranking_publicationNOT NULL DEFAULT 'FULL'. Existing rows: the three historical seasons explicitly set to PPW_ONLY by txt_code; SPWS-2026-2027 left at its default.
fn_guard_season_publication_immutable() trigger functionBEFORE UPDATE ON tbl_season: IF NEW.enum_ranking_publication IS DISTINCT FROM OLD.enum_ranking_publication THEN RAISE EXCEPTION 'Ranking publication capability for season % is immutable and cannot be changed after creation', OLD.txt_code; END IF; — one column checked, every other tbl_season column (dates, active flag, carry-over engine, scoring engine, lock timestamp) passes through untouched. No role check: unlike the scoring lock's trigger guards, which exist specifically to let privileged/internal callers past an ordinarily-blocked write, nothing should ever change this value, including a migration correcting a mistake — that case is an explicit, reviewed DROP TRIGGER/ALTER/CREATE TRIGGER sequence in its own migration, not a bypass built in ahead of time.

05 · Enforcement in fn_ranking_full

One check, at the top, before any aggregation runs

fn_ranking_full's dispatcher (not each per-engine body — the check belongs where the season is first resolved, before the engine is even read) gains one lookup and one guard:

SELECT enum_carryover_engine, enum_ranking_publication INTO v_engine, v_publication
  FROM tbl_season WHERE id_season = v_resolved_season;

IF v_publication = 'PPW_ONLY' THEN
  RAISE EXCEPTION 'Season % is PPW_ONLY and does not publish the full (SPWS+EVF+) ranking -- historical ranking publication boundary', v_resolved_season;
END IF;

The exact phrase "historical ranking publication boundary" is embedded in the error text deliberately — design §13 requires it to be the one searchable phrase used consistently across implementation, docs and now the error message itself, so a future `grep`/docs-search hit on the phrase leads straight to the enforcing code, not just the prose describing it.

Nothing else changes in fn_ranking_full_event_code_matching/fn_ranking_full_event_fk_matching — a FULL season's call proceeds exactly as design step 4 left it.

06 · Scenario walkthrough

Concrete behavior at the boundary

  1. An operator calls fn_ranking_full('EPEE','M','V2', id_season_2025_2026) directly, out of curiosity or by an old script. It raises immediately, naming the season and the reason, before touching fn_ranking_rules_canonical or any result row.
  2. The same operator calls fn_ranking_ppw('EPEE','M','V2', id_season_2025_2026) instead. It succeeds exactly as it does today — 2025/2026's domestic PPW ranking is real, published, and untouched by this step.
  3. A migration attempts UPDATE tbl_season SET enum_ranking_publication = 'FULL' WHERE txt_code = 'SPWS-2025-2026'. The trigger raises; the season stays PPW_ONLY unless a human deliberately drops and recreates the guard in a reviewed migration.
  4. A new season is created for 2027/2028 via the ordinary wizard path (fn_create_season_with_skeletons). Its enum_ranking_publication is FULL from the column default — no code in the wizard path needed to know this column exists.
  5. 2027/2028 eventually becomes historical. Its enum_ranking_publication is untouched by that transition — still FULL, matching design §06's "2026/2027 keeps full Ranking after becoming historical," now proven true of every later season by the same mechanism rather than a special case for 2026/2027 alone.
