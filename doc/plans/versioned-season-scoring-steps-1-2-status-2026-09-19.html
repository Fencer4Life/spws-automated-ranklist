Step 1

What the preflight found before a line of production code

scripts/check-scoring-migration-preflight.sh <local|cert|prod> asserts the data preconditions the migration depends on but does not write. It is read-only and was run against all three environments, which returned identical results. LOCAL passing proves nothing about CERT or PROD — that is the same failure shape check-anon-allowlist-sync.sh exists to prevent.

✓ The place > N CHECK is safe to add

Zero violating rows in LOCAL, CERT and PROD. That is what let me apply rejection to the classic engine too, not just the new one — a decision I would not have made on assumption.

✓ Assigning the classic engine to history is truthful

All three historical seasons store mp=50, podium 3/2/1, read per season rather than assumed. Because these are season configuration and not engine constants, a deviation would have meant a season needing its own frozen engine; the migration RAISEs rather than coercing.

! 18 tournaments carry a participant count of 0

Identical in all three environments, all with zero result rows, nine of them marked SCORED. A blanket CHECK (int_participant_count >= 1) would abort against live rows; the place <= N constraint is unaffected because these hold no results. Worth knowing before anyone proposes the former.

! Per-season multipliers genuinely differ

SPWS-2023-2024 has MEW 2.0; SPWS-2024-2025 has MEW 1.2. MSW moves 2.0 → 1.2 as well. A step-3 migration that wrote column defaults instead of stored values would silently rescore history. SS26.HIST.07 — the one RED assertion — pins exactly that, which is why it is worth keeping RED rather than deleting.

Step 2

Three things the existing gates caught that I would have shipped

1 The anon allowlist, three times

Postgres grants EXECUTE to PUBLIC by default, so all nine new functions silently widened the anon surface, and tbl_scoring_engine needed RLS under ADR-083. 52_security_posture.sql asserts the anon set as a set equality and failed locally each time — including once more after I added fn_backfill_scoring_engines below the revoke block. This is precisely the §08 trap, caught on my machine instead of in the deploy job.

2 Fresh bootstrap scored nothing at all

supabase db reset applies migrations before loading the seed dump, so the backfill ran against an empty tbl_season, assigned nothing, and all 777 subsequent scoring calls failed closed. This is the ADR-036 amendment hazard exactly. The backfill is now an idempotent fn_backfill_scoring_engines() called again from seed_post_backfill.sql — the same pattern the Phase 2 slug sweep already uses. It now bootstraps with 0 errors.

3 A fixture with places 5 and 7 in a field of 1

36_alias_rpcs_return_tournaments.sql carried incoherent placeholder data that the old engine scored silently as zero. Rejection surfaced it. The numbers are arbitrary to what that file asserts, so I made them coherent rather than weakening the rule.
