25 · your decision

What to do with fn_backfill_joint_pool_split()

ADR-049 calls it a one-shot remediation, and it ran on LOCAL, CERT and PROD on 30 April. Its own later fix had to be applied event by event, because running it across the database would collapse the full-field N of international events (migration 20260613000001, ADR-038). A 2026/27 joined bracket is now a second kind of row it would rewrite wrongly — this time the constraint catches it. Nothing in the application, the scrapers or the release workflows calls it.

B · Retire the function RECOMMENDED

A new migration drops it. Test 25 keeps its column and index checks (25.1–25.2); 25.3 becomes „the function no longer exists”; 25.4–25.7, which test what the function does, go with it. ADR-049 gets an amendment: the backfill is retired, with the reasons above. pgTAP total 1183 → 1179.

Why: a repair that already ran and is now wrong for two kinds of rows is a hazard to keep callable. Dropping it removes the hazard instead of fencing one case.

A · Keep it, skip 2026/27 joined brackets

A new migration redefines it so step 2 leaves rows with a joined order alone; test 25 gains 25.8 with a joined-bracket fixture (1183 → 1184). Smaller — but the function stays wrong for international events, the hazard the June fix already documented.

Either way the migration reaches CERT and PROD with the next release, on your go; it touches no data.
