Active season · brainstorm · 6 Oct 2026 · supersedes the recommendation in active-season-401-2026-10-06.html

Stop storing the active season. Compute it when it is read.

„Active“ is a pure function of the season dates and today. Today changes without anything being written, so any stored flag needs a writer at midnight. The 401, the daily job, the two audit rows per call and the stale-flag risk all come from that one fact. If the database computes the flag on every read instead, there is nothing to refresh, nobody needs write rights, and anonymous visitors only ever read.

Recommendation: V. It removes the class of bug, not just this instance: the flag can never be stale, on any environment, at any minute, with no job to forget. Its cost is mostly mechanical test fixtures (§04), and the two things ADR-031 feared (19 rewritten references, high migration effort) mostly disappear because of how PostgreSQL resolves s.bool_active (§02).

Q2 How do tests pick „the active season“?

Today ~59 pgTAP lines set bool_active to make a season active. A computed value cannot be set. Recommendation: tests set „today“ instead, inside their own transaction: SELECT set_config('spws.today', '2025-03-01', true). The date rule reads that setting when present and CURRENT_DATE otherwise. The alternative, rewriting every fixture to real dates around the actual today, would break every year.

02 · How V works

One rule, exposed as a column that is not stored

-- The date rule, read-only. Tests may set spws.today; everything else uses CURRENT_DATE.
CREATE FUNCTION fn_today() RETURNS date STABLE LANGUAGE sql AS $$
  SELECT COALESCE(NULLIF(current_setting('spws.today', true), '')::date, CURRENT_DATE)
$$;

CREATE FUNCTION fn_active_season_id() RETURNS integer STABLE LANGUAGE sql AS $$
  SELECT COALESCE(
    (SELECT id_season FROM tbl_season WHERE dt_start <= fn_today() AND dt_end >= fn_today() LIMIT 1),
    (SELECT id_season FROM tbl_season WHERE dt_start > fn_today() ORDER BY dt_start LIMIT 1))
$$;

-- "bool_active" becomes a computed field of tbl_season.
ALTER TABLE tbl_season DROP COLUMN bool_active;
CREATE FUNCTION bool_active(tbl_season) RETURNS boolean STABLE LANGUAGE sql AS $$
  SELECT $1.id_season = fn_active_season_id()
$$;

DROP TRIGGER trg_season_refresh_active ON tbl_season;
DROP FUNCTION fn_trg_refresh_active_season(), fn_refresh_active_season();
GRANT EXECUTE ON FUNCTION fn_today(), fn_active_season_id(), bool_active(tbl_season) TO anon, authenticated;

Why most code does not change. Once the table has no bool_active column, PostgreSQL reads s.bool_active as the call bool_active(s) („attribute notation“ for functions taking the row type). PostgREST treats the same function as a computed field, so the frontend’s select=…,bool_active and a filter bool_active=eq.true keep working. The rule is the same as today’s function: current season by date, else the nearest future one, else none.

Proven on LOCAL, 6 Oct (in a transaction, rolled back)

A throwaway table with seasons 1 (2025/26) and 2 (2026/27) and a bool_active(row) function, no column: WHERE s.bool_active returned 2; with spws.today = 2026-01-15 it returned 1; unqualified WHERE bool_active failed with column "bool_active" does not exist, which is why the six unqualified functions and five Python queries are rewritten.

Deploy order is safe both ways. Release deploys Pages before the database. The new page against the old database still finds a real bool_active column; the old page against the new database gets the computed value, and its leftover refresh call fails as it does today.

04 · Risks, and the tests that answer them

Where V could go wrong

  • Rankings called without a season fall back to the active one. Red first: pgTAP sets spws.today to a date in a chosen season and expects that season, then a date between seasons and expects the next one, then a date after the last season and expects none.
  • No season active at all (after the last season ends) gives the same result as today’s function, which also leaves none active. A pgTAP test pins it.
  • A fresh rebuild (reset-dev.sh): run end to end after the seed is regenerated.
  • Promote’s active-season check compares the computed values on CERT and PROD; a pytest pins it.
  • The browser: a Vitest proves the app never calls the refresh RPC (red first while the call exists).
  • Time zone: unchanged. „Today“ is the database’s date (UTC), as in the current function.
