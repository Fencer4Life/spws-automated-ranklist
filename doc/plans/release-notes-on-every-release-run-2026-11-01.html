Release workflow · GitHub UI · Plan — signed and built 1 Nov

Every Release run shows what it carries

Your request (31 Oct): "display release notes somewhere in the GH UI for the given release". The title half is released (main 05caf9f0): each Release run is now named after its merge, and the merge commit holds the explanation. But GitHub shows only that first line. Open a Release run today and you see five job boxes, nothing else; a docs-only run's reason is buried in the gate's log. This plan writes the notes onto each Release run's own Summary page. Signed 1 Nov 2026 and built test-first on LOCAL (§11); not pushed.

02 · What is there today

Read from the workflow, the scripts and the runs

  • Nothing writes a job summary. No file under .github/, scripts/, python/ or tools/ writes $GITHUB_STEP_SUMMARY. Step outputs go to $GITHUB_OUTPUT only: the gate's deploy, build's sha and fingerprint, and the migration scripts' lists.
  • How the commit travels. The gate checks out main with full history and gets the CI run's commit as RELEASE_GATE_HEAD_SHA from github.event.workflow_run.head_sha, through env:. It measures from .prod.last_sha in deployed_migrations.json (ADR-094, amendment of 24 Oct). build checks out main again and outputs that commit as sha. deploy-cert and deploy-prod check out exactly that sha (ADR-011, amendment of 25 Oct). So the deployed commit can be newer than the CI run's commit if main moved in between.
  • A docs-only run (Release #542, 82b6ba78): gate green, the other four jobs grey "skipped". The reason, "every changed path is documentation-only", and the 16 paths are lines in the gate's log.
  • No GitHub Releases and no tags on GitHub. The only tag anywhere is a local pre-reset-backup in the primary checkout, never pushed. Nothing in the repository reads tags (git describe, refs/tags), and no workflow is triggered by a tag or a release.
  • Retention. Run logs are kept 90 days, the most a public repository allows (repository setting read through the API). GitHub does not document whether a job summary outlives its run's logs, so this plan treats the Summary page as a 90-day view. What lasts is the merges in git.
  • GitHub's limits. One step's summary may be up to 1 MiB, and a job shows at most 20 step summaries. Secrets are masked in summaries as in logs (GitHub's workflow-commands reference).
  • Alerts. WFALERT.01 (python/tests/test_workflow_alerts.py) requires the Telegram alert to be the last step of deploy-cert and deploy-prod. Any new step in those jobs goes before it.

03 · How (R1 A, R2 A, R3 A, R4 A)

One new job, one new script, short sections in three jobs

  1. Gate. scripts/release-gate.sh also outputs base and head: on a CI-triggered run, .prod.last_sha and the CI run's commit; on a manual start, .prod.last_sha and main as the gate sees it. When $GITHUB_STEP_SUMMARY is set, it appends its verdict, its reason and the changed paths (collapsed). Run locally, it writes nothing there. Every decision stays as it is.
  2. Notes job notes ("Release notes"), new. It needs gate and build and runs when the gate ran: if: always() && needs.gate.result == 'success'. Its permission is contents: read only. It checks out main with full history and runs python3 scripts/release_notes.py (standard library only, like scripts/branch_description.py). It covers the range from base to build's sha when build ran, or to the gate's head when it did not. Every value reaches it through env:. The section is "What this release carries", plus a compare link …/compare/<base>...<head>. No deploy job needs this job (R4 A).
  3. How a merge is written. Oldest first, as they reached main. The title is a heading with the short commit linked, then the explanation, then Branch:; other trailers (Co-Authored-By:) are left out. A merge from before 31 Oct, with no Branch: line, shows the branch named in "Merge branch '…'" and that branch's own commit subjects. Text is written so that GitHub reads it as plain text: <, >, & escaped; @ as &#64; (no mention); # before a digit as &#35; (no issue link). Beyond 900 KB the list shows titles only, then "and N more" with the compare link.
  4. Pages, CERT, PROD. deploy-pages gets a last step, if: always(): "GitHub Pages published <URL>; WordPress pages load the new bundle within 10 minutes, before the PROD approval", or the failure. deploy-cert and deploy-prod each get one step, if: always(), just before their Telegram alert, which stays last. It is plain printf of values passed in env:: the deployed commit, the migrations applied (from check-new-migrations.sh) or "no new migration", the fingerprint check, the Edge Function, the security posture and the record on main. If a step failed, the section names it. CERT's section ends: "PROD waits for approval in the production environment; its section appears when deploy-prod has run."
  5. Telegram. The notes job ends with its own alert (R4 A). The deploy jobs' alerts and their wording do not change.
  6. Any past range, locally. python3 scripts/release_notes.py --base <sha> --head <sha> prints the same Markdown. Every past PROD base is in the history of deployed_migrations.json. This is the lasting record once a run's 90 days are over.

Why the escaping matters, from main's own history

Release 3b's explanation (e7f8a3a3) contains Telegram's sync [<code>] runs it. Written into Markdown as it stands, GitHub would read <code> as an HTML tag and print the rest of the paragraph in code type. Merges also mention W2 #4, which would link to issue 4, and a bare @word would link someone's GitHub account. In a GitHub Release (R1 B) it would also list that account as a contributor; one public project hit exactly this and fixed it with &#64;.

What landed on the branch, test-first

Branch claude/release-notes-on-every-release-run, described; the naming check prints "Release · Every Release run's Summary page lists what it carries and deployed". Not pushed.

  • RED first. All 13 RELNOTES tests were written before any code and run: 21 test functions failed, each for its own reason (no script, no notes job, no base output, no summary, no section step). The one that passed, "without a summary file the gate writes none", is the guard it is meant to be, true before and after. All 21 existing gate tests stayed green throughout.
  • scripts/release-gate.sh outputs base and head and writes its verdict, why, and the paths onto the Summary page; every decision is unchanged (RELNOTES.12–13, 27 gate tests pass).
  • scripts/release_notes.py (standard library only): RELNOTES.01–08. Run over the two real ranges of §04 it prints exactly the merges, counts and escaping shown there, e.g. sync [&lt;code&gt;].
  • release.yml: the notes job, the Pages section step, and step ids (verify, functions, record) so each CERT and PROD section can name the step where it stopped (RELNOTES.09–11). The 117 release and workflow tests pass, among them WFALERT.01–03, WFINJ.01, WFPERM.01, WFEXPR.01 and GHWF.01–06.
  • Records: ADR-011 and ADR-094 amendments (1 Nov) and their Appendix C rows, twins regenerated; the workflow catalog's Release block and the environments-and-release page; RTM NFR-16 and RELNOTES.01–13, Landed on LOCAL; both release skills, still identical (NAMING.06).

Two changes from the wording above, both on the safe side

The CERT and PROD sections are a small script, scripts/release-section.sh, not printf written into the workflow twice. It is still only printf of values passed in env:, it always exits 0 so the alert after it never names the wrong cause, and a script can be tested; RELNOTES.11 now runs it for a clean CERT deploy, a PROD deploy with two migrations and a failed migration. The Pages section stays inline, because deploy-pages checks out no code.

The escape carries the word joiner from the start. §03 planned &#64; alone, with a word joiner only if V2 failed. GitHub finds mentions in the rendered text, where &#64; is already a plain @ again, so the code writes &#64; followed by a word joiner (&#8288;), and the same after a # before a digit. It looks the same and nothing can link it. V2 still checks it on the first run.

Found and fixed on the way

The gate tests ran scripts/release-gate.sh with the whole process environment. In CI, pytest runs inside GitHub Actions, where GITHUB_STEP_SUMMARY is set, so once the gate writes summaries, every gate test would have written into the CI run's own page. The test helper now points it at a file of each test's own, or unsets it.
