PZSz calendar workflow · complete rewrite · implementation plan · 21 October 2026

Rebuild the PZSz calendar workflow: work from our list, read every page with a real browser, read each letter in independent passes, and never fail silently

A self-contained plan for a fresh session. It replaces the PZSz calendar sync and its start-list capture end to end. Every decision below is settled — there are no open questions. Build it test-first, ship it LOCAL → CERT → PROD, and verify on both.

Plan — for a new implementation session Branch claude/pzsz-calendar-update-fix, based on main New: ADR-116 · amends ADR-087, ADR-112 Start-list window for Gdańsk & Szczecin is open now (20–23 Oct): §16

1 · Context — why this rewrite

The daily run has failed every day since 6 October, and a missed start list stops the result ingest

The PZSz calendar sync (.github/workflows/pzsz-sync.yml, python/scrapers/pzsz_sync.py, pzsz_calendar.py) keeps CERT’s calendar of senior Polish Cup and Championship events in step with pzszerm.pl, and a daily capture stores each event’s start lists on CERT. Two things are broken:

  • pzszerm.pl now answers its calendar, event and tournament pages with a JavaScript “Wczytywanie danych…” page (the element <p id="pzs-m">) that a plain HTTP request never gets past. Since 6 October every scheduled run has failed on it, and no start list has been captured since 10 October.
  • The old code was brittle in a dozen other ways even when the site answered: one bad row aborted the whole run, the venue address was read as the first “ul.” line (so Poznań stored the payee’s address), the listing’s dates overrode an organizer letter and reverted admin corrections, the entry fee was never read, past events were scraped daily, and a failed day sent two Telegram messages. The companion findings page lists all of them: doc/plans/pzsz-calendar-events-findings-2026-10-21.html.

Why a missed start list matters. A PZSz result row is admitted to our ranking only when its surname, first name and birth year match one of our fencers (ADR-111), and the birth year is available only from the event’s start list. If the start list is never captured, the result ingest for that event stops. So the capture is not best-effort; missing it is a fatal condition that must be loud.

What this rewrite delivers

A workflow that reads from our list of events, reads only events still ahead, reads every gated pzszerm.pl page with a real browser engine that runs the page’s own JavaScript, fills each field in an independent pass that no other pass or event can stop, writes nothing it is unsure of, captures each start list inside a fixed window, states every warning on Telegram, and turns the run red only at the end, only for a fatal state on a named event.

2 · The binding rules

The shape of the workflow, fixed

  1. Work from our list. The run reads CERT’s PZSz events and processes each one independently. pzszerm.pl’s calendar listing is used only to discover new events and new letter links, never as the list of what to process.
  2. Future only; stop at the first day. For an event whose first day is D (Warsaw date), the workflow reads pzszerm.pl for it only while today < D. From D onward it reads nothing for that event — no listing row, no event page, no letter, no start list — and waits for the operator to add the FencingTimeLive results link.
  3. Independent passes. Each field is filled by its own pass, in order. A pass that finds nothing, finds two candidates, or raises is recorded; the next pass still runs. One event’s outcome never stops another event.
  4. Read-once vs watch. The letter link (pass 0) and the fee (pass 3) are read only while the field is empty. The city (pass 1), address (pass 2) and dates (pass 4) are read on every run while the event is ahead, and compared with what is held.
  5. Letters have no agreed structure. They are written freely, year to year and club to club. No pass may depend on a label, a line order, or a format being present.
  6. A real browser reads the gated pages. Headless Chromium loads each pzszerm.pl page and runs the page’s own JavaScript, exactly as a person’s browser does. No forged cookie or pixel, no CAPTCHA, no login, no manual saving.
  7. Start lists only inside their window. Captured only on the Warsaw dates D−4, D−3, D−2 and D−1 — never earlier, never on D or later.
  8. Never stop; judge at the end. The run processes everything, states every warning on Telegram, and sets its exit status last: red only for a fatal state on a named event, green otherwise.
  9. Store on CERT; PROD replays. Start lists live on CERT only. PROD never contacts pzszerm.pl; the PROD promote replays the CERT-stored lists by hash (ADR-108, ADR-112 §4).

3 · Decisions, settled

Eight decisions the user made on 21 October — a record, not open questions

#DecisionWhat it means in the build
D1The letter wins on dates.When a readable letter gives the event’s dates, they are authoritative. The listing and the home page fill the dates only while no letter is readable. A later listing move against a letter already applied is held and reported, never written silently (§9 rule 6). Evidence: 7 of the 29 past listing rows that have a letter disagree with it, and the letter is right each time.
D2The city stays the city; the letter’s postcode must match it.The city is set from the listing / home page. A postcode-city in the letter is a check, not a source: a match confirms, a mismatch is flagged and nothing changes. The letter never renames the city on its own.
D3The address is the full venue line.Hall name + street + number, with the postcode and city when the letter gives them (e.g. “Hala Sportowa MOSRiR Szczecin, ul. Narutowicza 17”; “Hala lekkoatletyczna AZS Poznań, ul. Pułaskiego 30, 60-995 Poznań”). This extends ADR-088: the hall name is kept, not dropped. The city column (txt_location) still holds the city on its own; the address lives in txt_venue_address, and may repeat the city.
D4Store the individual PLN fee.The fee a licensed Polish fencer pays, in PLN. Team fees, the foreign-fencer fee in euro, prize money and late fees are never stored.
D5A corrected address reaches PROD.For PZSz events the CERT→PROD mirror overwrites txt_venue_address, as it already does for dates and city. Admin corrections are made on CERT, where the sync keeps them (§9).
D6“Past” means from the first day.From D the workflow reads nothing from pzszerm.pl for the event (rule 2). Supersedes ADR-087’s 7 Oct amendment (“the sync keeps the dates of an event that has started”).
D7A letter with no text layer is reported, not OCR’d.The passes report “no text in the letter” and the operator enters the fields in Admin. One letter in three seasons (Katowice 2025/26) is a scan; OCR would need its own sample and tests.
D8Build and test on the 31 letters already available.No extra sample-gathering. The golden set still grows whenever a future letter cannot be read.

The earlier “D9” (how saved pages reach CERT) and “D10” (ask PZSz for access) are dropped: the real-browser fetch makes the capture fully automatic, so there is no manual-save path to configure and no request to send.

6 · The fetcher

A real browser engine runs the page’s own JavaScript — nothing more

Every gated pzszerm.pl page (the calendar listing, each event page, each tournament start list) is loaded by headless Chromium via Playwright, which this repo already carries as a dev dependency and which GitHub Actions installs in CI. The page’s own script runs, sets its cookie, requests its pixel and reloads the page, and the real content appears — exactly what a person’s browser does, and what the browser pane did on 21 October.

What it is, and is not

A real browser rendering a public page the ranking is authorized to read. There is no cookie or pixel forged by us, no CAPTCHA solved, no login, no access control touched. The “pzs-m” page is a “does this client run JavaScript” check, and a browser that runs JavaScript is its intended reader.

  • One browser context, reused across every page in a run, so the cookie set on the first page spares the reload on the rest. A normal desktop user-agent, viewport and Polish locale.
  • Per page: load; wait for the real content marker (the start-list table’s “Data urodzenia” header, or the listing’s rows) up to a short timeout; if still the check page, reload and wait again, a few times; still not rendered → return “not served”.
  • Courtesy: pages one at a time, a second or two apart. Each workflow visits only the pages it needs (events still ahead / events inside the start-list window) — fewer requests than a person clicking through.
  • The parsers are unchanged. The fetcher hands rendered HTML to the existing parse_calendar_html, parse_event_detail_html and parse_start_list. A check page is refused by those parsers too, as a second guard.
  • Fallback: if Chromium is unavailable in a run, the fetcher makes a plain request; a gated answer is then “not served”.

Note for local development

The real run is in GitHub Actions. A local sandbox may refuse to execute a headless fetch of a site that shows a bot-check; that is a local policy, not a failure of the design. Develop the fetcher against saved fixture HTML and the fake driver in the tests (§15); let CI exercise the live fetch.

8 · Reading a letter (shared by passes 1–4)

Two text views, normalised, cut at labels, then a relevance guard

FETCHthe held link, once per run
  • One GET (not gated). First bytes decide the kind: %PDF → PDF; PK with word/document.xml → DOCX; an HTML/check page → “not a letter”. 20 MB limit.
  • The file’s SHA-256 is kept; the same file always yields the same answers, so a change shows as a new hash. An encrypted PDF is opened with the empty password; a broken one is “unreadable” and the last good values stand.
VIEWStwo extractions, because each fails differently
  • Plain (extract_text()) and layout (extraction_mode="layout"), page by page; DOCX gives one view. T11 is why both exist. No text in either → “no text in the letter (scan?)” (T22, D7); every pass then reports “no letter text”.
NORMALISEeach view, in this order; nothing is guessed here
  1. Unicode NFKC; soft hyphens and zero-width chars removed; no-break spaces → spaces; every dash → “-”; curly quotes → plain; bullets (“➢”, “•”) → spaces.
  2. Collapse tripled glyphs: a word whose characters are each repeated 2–3× becomes the single word (T12).
  3. Rejoin letter-spaced words: ≥4 single letters separated by spaces join when the result is a word from the label lexicon (T11).
  4. Rejoin end-of-line hyphenation when the next line starts lower-case.
  5. Strip a footnote digit glued to a label word (“Startowe3” → “Startowe”, T13).
  6. Keep a folded copy for matching only (lower-case, Polish diacritics removed, spaces removed). All matching is on the folded copy; every stored value is cut from the original text.
SEGMENTScut at labels and numbered headings, not at line breaks

A label lexicon (matched on the folded copy, one typo tolerated for words of ≥6 letters) marks the start of each region: venue (miejsce zawodow, miejsce, obiekt, hala, lokalizacja, adres), date (data, termin zawodow, w dniach, w dniu), programme (program, terminarz), fee (startowe, oplata startowa, wpisowe), entries (zgloszenia, potwierdzenie), lodging (zakwaterowanie, noclegi, hotel), organizer/contact (organizator, wspolorganizator, kontakt, sedzia, komisja techniczna), other (nagrody, regulamin, punkt gastronomiczny). Text before the first heading or the “KOMUNIKAT” line is the letterhead; lines with “tel”, “e-mail”, “@”, “www”, “fax” and the two lines above them are contact. Segments only add or subtract evidence; no pass requires a label to exist, so a letter with no colons, no numbering and no labels is still read.

GUARDis this letter about this event?
  • Weapon: the event’s weapon in any form (floret/florecie/floretu; szpada/szpadzie/szpady; szabla/szabli). A letter naming only other weapons contradicts the event.
  • Dates: at least one letter date within 10 days of the held start. Every date >30 days off → contradicts; a whole year off → a copied letter (T23).
  • A contradiction makes the letter suspect: passes 1–4 still run and are reported so you see what it says, but nothing is written, and the digest flags it once.

9 · The five passes, and how a finding becomes a write

Each pass abstains rather than guess; one rule set decides every write

PASS 0the letter link — only while none is held
  • Held → skipped. The held link is what passes 1–4 read.
  • Empty → looked for: first in the listing rows from R2 (each carries its letter icon, titled e.g. “Komunikat organizatora z dnia 30_04_2026”); if the listing did not render, the event page’s “Komunikaty organizatora” section. Several links → the newest by the date in its title. Before storing, the link is fetched and must be a document that passes the guard.
  • Outcomes: stored · none published yet · source not served · not a letter. A letter published later under a new link is picked up only after the old link is cleared in Admin (read-once rule).
PASS 1the city — validate, never rename (D2)
  • The city is the value from the listing row, else the home-page row’s name suffix (“… – Gdańsk 2026/2027” → Gdańsk). The letter does not set it.
  • If the letter’s venue section has a postcode-city (“dd-ddd City”), it is checked against the held city (folded, case-insensitive): match → confirmed; mismatch → flagged, city unchanged, nothing written. Locatives/adjectives/hall-names (“w Obornikach Śląskich”, “MOSRiR Szczecin”) only confirm. Postcode-cities in the letterhead, contact, fee or lodging sections are ignored (T2, T3).
PASS 2the address — the full venue line, located by score (D3)

Score every street-bearing line to find the venue block, then emit the whole venue line(s), joined and cleaned — hall name + street + number, with postcode + city when present. A street marker is ul/ul./ulica/al./aleja/pl./plac/os./osiedle/rondo/skwer (any case, dot and space optional), or a “name number, dd-ddd City” with no marker.

The best street must score ≥ 5 and lead the best different street by ≥ 3. The address returned is the venue line containing that street — the hall name before it (same or previous line, T6/T7) and the postcode-city after it, joined; the house number may sit on the next line (T7); an entrance clause in parentheses (T5) is dropped. Otherwise two candidates (both reported) or not found. Validation: 4–80 chars, has a letter, no 7+ digit run, no “@”, no “tel”. The weights are fixed in code and set on the sample; changing one reruns every letter. Worked cases: Poznań 2026/27 → “Hala lekkoatletyczna AZS Poznań, ul. Pułaskiego 30, 60-995 Poznań” (payee −3, entrance −5 lose); Oborniki → “Hala Sportowa OSiR, ul. Józefa Poniatowskiego 22” (Wrocław club −6 loses); Konin → “ul. Dworcowa 2A, 62-510 Konin” (no hall name in the letter).

PASS 3the fee — individual PLN, only while empty (D4)
  • In the fee section plus any line with startowe/opłata/wpisowe. An amount is digits (with “,00”, “.00”, “.-”, “,-”) and a currency within two words or glued: zł/zł./zl/złotych/PLN → PLN; euro/EUR/€ → EUR.
  • Each amount is classed by its own clause (to the next “/”, “;”, “(” or line end): team (drużyn), foreign (zagraniczn / “nie posiadający licencji” / any EUR amount), prize (miejsce, nagrod), late (po terminie), other (hotel, nocleg, kaucja) — else individual (od zawodnika/zawodniczki/uczestnika, indywidualnie) or unmarked.
  • Store the individual-or-unmarked PLN amount. One value → found; two different → two candidates; a section naming no amount → not stated (T19). Sanity 1–500 PLN. Written to num_entry_fee with txt_entry_fee_currency = PLN.
PASS 4start and end dates — the letter wins (D1)
  • Date grammar on both views: dd.mm.yyyy, d/m/yyyy, yyyy-mm-dd, “dd.mm.” (year from the range or the held start), Roman months, month names in any case/without diacritics, and ranges (“7-8.12.2024”, “19.10. – 20.10.2024”, “24 - 25 października 2026”, “od 28 do 31 maja”, “24 i 25 października”, “08–09.03.2025”).
  • Not dates: a number after “godz.”, one with a colon, “hh.mm” whose second part > 12 or is a time range, “900” (T15).
  • Role from surroundings — event: in the date/programme section; after “w dniach/w dniu”; on a line with a weapon, gender, “godz.”, eliminacje, finał; on a title line with the name or city (“POZNAŃ 14.03.2026”); next to a weekday. Not event: “do dnia”, zgłoszenia, przelew, konto, płatne, rezerwac, “z dnia”, “regulamin z dnia”, or anything in the fee/entries/lodging sections (T14).
  • Window: event dates within 10 days of the held start and inside the season. Start = earliest, end = latest; one date → a one-day event. Checks: ≤ 4 days long; a weekday beside a date must match it; dates a year off → copied letter, reported; dates outside the window → “letter differs from the calendar”, a possible move, reported. Worked: Gdańsk 2026/27 “Data: 24.10.2026 r.” → 24–24 (listing had 24–25); Poznań “4 października 2026 r. (niedziela)” → 4–4 (listing 3–3); the amateur league’s five dates → only 5 Dec is in-window (T16).

From findings to writes — one rule set for every field

Per field the run keeps three things: the value now in tbl_event, the value it last wrote (with that value’s source), and each source’s last report.

#SituationAction
1nothing foundno write; outcome recorded
2the field is emptywrite
3the value now differs from what the run last wrotea person changed it: never overwritten; a disagreeing source reported once
4the value now is what the run wrote, and a source of equal/higher rank differsreplaced, and reported
5a lower-rank source disagreeskept; reported once (letter beats listing: Gdańsk 24 vs 25)
6a lower-rank source changes its own report against a higher-rank one (the listing moves the event after the letter was applied)held and sent to you with both values — the one case a person decides
7the event has started (D6)nothing read or written for it; awaits the FencingTimeLive link
8link or feewritten only while empty

Source ranks (higher wins, D1/D2): letter > listing > home page for dates; for the city the letter only validates. The write for one event is a single transaction, fn_pzsz_apply_event; every UPDATE names the value it expects to replace, so an admin edit made between read and write wins and is reported “changed by hand meanwhile”. One event’s write failing rolls back only that event (and is fatal for it, §12). Admin corrections are made on CERT; D5 carries the address to PROD.

10 · Start lists

Captured only inside the D−4…D−1 window, by the real browser, or the run goes red

The window. A PZSz start list exists from 4 days before the event’s first day to 1 day before, and is closed afterwards. The newest version captured inside the window is what the CERT ingest reads for birth years (ADR-111, ADR-112 §3). Miss the window and the result ingest stops.

THE WORKFLOWits own file, CERT only, five runs a day
  • pzsz-start-lists.yml, separate from the calendar sync, CERT-only (no PROD write, no prod-write queue). CI installs Playwright’s Chromium. Five runs a day — 06:00, 10:00, 14:00, 18:00, 21:00 Warsaw — so a list that appears at any hour of any window day is caught.
  • Per event: render the event page, read its tournament ids, render each tournament page, parse the start list. Each list is stored when its hash is new. One tournament page that will not render does not drop the others; the missing ones are named. A whole attempt that meets the check records “not served” and stays green.
THE WINDOW RULE — never before, never aftertwo independent checks
  • Only on D−4, D−3, D−2, D−1. “Today” is the Warsaw date at run time (zoneinfo Europe/Warsaw), so the 25 October clock change cannot shift it. The five crons are set in UTC so every attempt lands between 06:00 and 21:00 Warsaw in both summer and winter time, never after midnight into day D.
  • Check 1 — selection: the run picks only PZSz events, not COMPLETED/CANCELLED, with D−4 ≤ today ≤ D−1; none → it ends before opening the browser.
  • Check 2 — the reader: pzsz_start_list.py refuses any event or tournament page of an event outside its window, whoever asked, and records the refusal. A bug in one check cannot cause a request outside the window. The saved-page store fallback obeys the same rule.
  • D is re-read from CERT each run; if the event moves, the window moves with it.

Unchanged from ADR-112 §6: open the event and tournament pages in your own browser, save them, and run python -m python.scrapers.pzsz_start_list_store store <CODE> --event-page FILE --tournament ID=FILE …. With the real-browser fetch this should not be needed; it stays as the safety net, and it obeys the same window rule.

The “send ingest” notice (R5, ADR-112 §5), corrected. Today it fires when a start list is stored for an event that has ended and has any non-empty url_event — but a PZSz url_event is filled at creation with the pzszerm.pl page, and with the window rule no list is ever stored after the event. So the trigger is replaced: the calendar run (CERT-only, no pzszerm.pl request) finds past PZSz events whose url_event is now your FencingTimeLive link (no longer the pzszerm.pl address), that have a stored start list, and that have no FINISHED CERT run, and tells the operator once: “📋 Send ingest PPS1f-2026-2027”. If no list is stored, it says the ingest will stop instead. The ingest itself stays manual (ADR-108 §2).

11 · Failures, warnings, and the red-at-end rule

The run always finishes; it warns as it goes and goes red only for a fatal state on a named event

Nothing stops a run part-way: one event never stops another, a source that will not read is recorded, a bad row is skipped, a pass or an event that raises is caught. The run processes everything, sends one digest with every warning, and sets its exit status last.

13 · Resilience to letter mistakes nobody has seen

Why an unforeseen mistake yields “not sure”, never a wrong value

  1. No pass depends on structure. Labels, order and formats only add or subtract evidence. A mistake removes evidence or adds a contradiction, so the result drops below the threshold/margin → “not found” or “two candidates” → reported, nothing written.
  2. The golden set. Each of the 31 letters is a test case with the expected value (or “not stated”) for city, address, fee, start and end, in both views. Expected values come from reading the letter, not the listing. Masked text copies are committed; the PDFs are not.
  3. The mutation suite. ~25 seeded operators (label spelling/case/missing-colon; section reorder; hall+street joined or split; house number on the next line; look-alike letterhead/hotel/payee/entrance/other-city addresses added; date and fee shapes swapped; year off by one; weekday wrong; tripled glyphs; letter-spacing; page-as-one-line; city removed) applied one at a time and in pairs, ~6,000 cases per CI run. Property: each field’s result is the expected value or an abstention; where an operator changes the truth (the fee, the year), the test expects the new value.
  4. CI gate. Wrong values on the golden set and the mutation suite: zero (hard fail). Fields filled on the golden set: ≥ 95% of those a human can read.
  5. The sample grows. A future letter the passes cannot read produces a report with its lines; it joins the golden set, masked.
