Event status, and the moved-date pill

A live event with 14 registered fencers is invisible on the PROD calendar, because the reconciler carries an event's dates but not the status that makes them visible — and I argued, wrongly, for keeping it that way.

live outage · PPW1 hidden 4 migrations 1 new column 1 new handbook page blocked on PROD approval

What is wrong

The row is on PROD. The calendar refuses to show it.

PPW1-2026-2027 exists on PROD with the correct dates, the correct season, and registration open — deadline 20 September, 14 entries already taken. It reaches vw_calendar intact. It is then dropped by visibleEvents(), which hides enum_status = 'CREATED' rows as “date-less planning skeletons”.

That premise is false for this row: it has dates. It is CREATED only because enum_status is absent from fn_mirror_events_to_prod's UPDATE branch — present when the row is created, never sent again. The reconciler carried the dates and withheld the one field that publishes them.

✗ My error, on the record

Earlier today I audited all 41 event columns, found enum_status already frozen, and chose to keep it that way — reasoning that promote_event advances PROD independently, so CERT could regress a scored event. I then wrote that justification into ADR-086 as if settled.

It does not survive measurement. Across all 97 events present on both environments, PROD is ahead of CERT zero times. Results land on CERT first, so CERT always leads or equals. I blocked a real fix with a hazard that has never once occurred, and this plan corrects the ADR as well as the code.

Decision 1

The automation boundary

The calendar is scraped on CERT and its result must be visible on PROD. Scoring and results ingestion keep today's behaviour. Once an event is PLANNED on PROD, the only status change automation may make is a cancellation.

FromToAutomatedWhy
CREATEDPLANNEDyesthe scrape made it real
CREATEDCANCELLEDyescancelled before it was ever dated
PLANNEDCANCELLEDyesthe only automated change once PLANNED
PLANNEDCREATEDnobackwards — would hide a live event
→ IN_PROGRESS / SCORED / COMPLETEDnopromote_event, unchanged

All three automated pairs already exist in fn_validate_event_transition, and trg_event_transition fires only when the status actually changes. So the validator always accepts them, and a status can never abort the promote — which matters after a day spent learning that one row must not be able to red the daily run.

The principle underneath

Status follows the thing it describes. Planning status records an admin decision held in CERT, so it propagates. Results status records data, and must never reach PROD ahead of the results it claims — or PROD advertises an event as finished while holding none of it. promote_event owns that axis precisely because it is what moves the results.

Decision 2

SCHEDULED and CHANGED are retired

ADR-077 documents both as “Set by: EVF sync (ADR-039)”. Neither ever was. Zero rows carry either status in either environment, and no code path sets them — they exist only in the enum, the admin dropdown, and a label map. The intended gradient (we have a date → EVF confirmed it → EVF moved it) was designed and never built.

Deprecated behaviourally: removed from the validator's transitions and from the admin UI, so nothing can reach them; the labels stay in the enum type. Dropping an enum label means recreating the type and cascading through vw_eligible_event and several migrations that name SCHEDULED in NOT IN lists. With zero rows the outcome is identical for a fraction of the blast radius.

Decision 3

A moved date is a pill, not a status

CHANGED was meant to flag exactly this. Rather than revive it, the signal becomes a visual qualifier that composes with PLANNED instead of replacing it.

AspectDecision
Anchorthe first date EVF ever published — a new dt_start_first_published, set on first import, never updated
Predicateenum_status = 'PLANNED' and dt_start > today and dt_start <> dt_start_first_published
Renders asamber chip, “Moved from 12 Dec 2026”, in the card's existing two-chip line
Clears whennever — it stands until the event passes or leaves PLANNED. No acknowledgement step

Because it is a stored field comparison rather than an audit-history scan, a twice-moved event still reads against the date originally announced, and there is no predicate to re-tune later.

✓ Why the two guards matter

Every date change in recorded history belongs to a COMPLETED event and is a data repair, not a reschedule — one-day corrections, DD/MM parse fixes, and a five-event batch from the 2025–2026 fragment repair. Restricting the pill to future PLANNED events takes false positives across all recorded history to zero, with no threshold and no “was it the scraper or an admin” test.

Amber rather than red keeps it distinct from a cancellation. The barrel is deliberately left alone: ADR-084 already spends hue on event type, fill on completed and ring on next-upcoming, and a fourth channel would crowd the overview you scan first.
