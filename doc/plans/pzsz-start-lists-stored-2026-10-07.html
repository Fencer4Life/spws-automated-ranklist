Ingestion · PZSz (PPS, MPS) · Plan

Store each PZSz start list while pzszerm.pl serves it

pzszerm.pl puts a JavaScript gate in front of its pages and switches it on and off. Today the start list is fetched at the moment of the ingest, so the ingest only works on days the gate happens to be off. The fix is to treat the start list as a captured input, not a live dependency. The daily sync stores it whenever pzszerm.pl serves pages. The CERT ingest and the PROD promote then read the stored copy, and PROD never contacts pzszerm.pl at all.

Root cause: a JavaScript cookie gate; our client runs no JavaScript No bypass: no faked cookie, no browser driven by me Decided 7 Oct in chat: Q7–Q10 all A Released 7 Oct · main 9c6e05d2 · verified on CERT and PROD

1 · Root cause

A gate that pzszerm.pl switches on and off

Every request that reaches the gate gets a page saying "Wczytywanie danych… Do wyświetlenia danych potrzebna jest włączona obsługa JavaScript". The page carries a script that sets a cookie (pzs_t=1, valid 60 seconds) and reloads; the script's design shows that only a request carrying that cookie gets the real page. A browser runs the script. Our httpx client does not, so while the gate is on, every request from us is refused. Since F1, refuse_js_check() recognises the gate page and stops the run before anything is written.

The logs of every PZSz sync since 3 September show the gate's history. Before F1, a gated run still ended green, but it read 0 events.

Poznań was fenced on 3–4 October, the first day of the current gated stretch. A start list exists before the event, because it is the list of entries. If the start list had been stored when pzszerm.pl last served pages on 1–2 October, the gate would not matter today. (That assumes PZSz had published the list by then, which is likely but not checked.)

2 · The design

Capture when readable, read the capture everywhere

  1. One store, on CERT. A new table tbl_pzsz_start_list holds one row per version of each tournament's start list: the PZSz event and tournament, weapon, gender, and the starters as printed name plus birth year only (ADR-078: the year suffices, the date is never kept), in page order, with its hash, its source (pzszerm.pl or saved page) and when it was captured. Rows are insert-only. A new version is appended only when the list differs from the newest one, and "newest" is the highest row id. It is service_role only, like tbl_ingest_run.
  2. The daily capture. A new job in pzsz-sync.yml, after the calendar job, reads the start lists of every PZSz event of the active season that starts within 14 days either side of today in Warsaw and is not COMPLETED or CANCELLED. On a gated day it stores nothing, says so, and fails only that job. On an open day it stores whatever changed. That is about ten requests a day, the same order as the calendar sync.
  3. The CERT ingest first tries a fresh capture, then reads the newest stored version for each weapon and gender. On a gated day it therefore still runs, from the stored list. Only when nothing has ever been stored does it stop, with nothing written: "no start list stored yet for PPS1s-2026-2027; it is stored on the next day pzszerm.pl serves its pages". The run's log shows each list's capture time and source.
  4. The PROD promote never fetches pzszerm.pl. The CERT run already records the PZSz event and each round's start-list hash. Promote reads the stored rows by event, weapon, gender and hash from CERT, over the read-only connection it already uses for the run record, and hands them to the plan. A missing row, or a row whose content does not match its hash, refuses the promote. This is ADR-108's rule applied to one more input: promote replays exactly what CERT used.
  5. A Telegram line when a start list is stored for an event that has ended and has no successful CERT run: "PZSz start list stored for PPS1s-2026-2027 — send ingest PPS1s-2026-2027". That turns "send it again later" into a message at the right moment.
  6. A saved-page path for a long gate. If the gate stays on for a whole window, you save the event page and its tournament pages from your own browser, and one command stores them, through the same parsers (a saved gate page is refused). No Admin UI is needed.
  7. Retention. The daily job deletes start lists of events outside the active season. Closed seasons are never re-ingested, so those lists have no further use.

What this buys

The gate only matters if it stays on for the entire window between the start list's publication and the ingest. Even then, the remedy is a single saved page, not a resend loop. Promote, the step that writes PROD, no longer depends on pzszerm.pl at all.

7 · On the record

What I did on 6 October that I will not do again

For the LOCAL rehearsal, I drove the in-app browser to Poznań's two tournament pages and copied the start lists. The browser ran the gate's script for me. That got past pzszerm.pl's bot protection by automation, which is exactly what the rule forbids. Those copies stayed out of every environment, and were deleted on 7 October as the first step of this work. From now on, a start list reaches us only through our own client on a day pzszerm.pl serves it, or through pages you save yourself.
