4 · New requirement — the entry list as a birth-year source

A registration is a first-hand declaration by the fencer about their own birth year. It outranks anything we derived. So it writes back, on a three-rung ladder:

State of tbl_fencerActionFlag afterPROD today
int_birth_year IS NULLPopulate from the declaration, silently.bool_birth_year_estimated = false9 rows
present and bool_birth_year_estimated = trueOverwrite with the declaration, silently.false20 rows (18 with results)
present and confirmed, and it differsAsk — the §5 D prompt. Never silent.per the answer4 cases across 2 events
The good news — the dangerous half is already built

My first worry was that changing a birth year would silently rot the ranking. It does not, and the reason is machinery you already have. trg_assert_result_vcat fires BEFORE INSERT OR UPDATE OF id_fencer, id_tournament ON tbl_result — so it does not fire on a tbl_fencer update, and on its own a birth-year change would indeed leave old results in their old V-cat with no error.

But trg_fencer_change_enqueue fires AFTER UPDATE ON tbl_fencer and is column-aware — the migration says it plainly: "BY / nationality change → enqueue; name / alias change → nothing." A birth-year change enqueues a recompute of every event that fencer participated in (fn_enqueue_affected_events → tbl_recompute_queue, ADR-071 / 20260615000001_cdc_recompute_dedup.sql). The ranking heals itself. The plan's only obligation is to not bypass it — the write must be a plain UPDATE, never a trigger-disabling path.

6 · Problems I see

Problem 1 · same name, different person — this is live on PROD

Not hypothetical. Two pairs exist right now, both with confirmed birth years:

#197 MŁYNEK Janusz   1951   19 results
#356 MŁYNEK Janusz   1984    0 results     ← 33 years apart

#354 KRAWCZYK Paweł  1989    0 results
#355 KRAWCZYK Paweł  1954    0 results     ← 35 years apart

So a name-only lookup can return more than one row. Every rule in §4 and §5 must therefore carry the same guard: act only when exactly one row matches on (surname, given name); otherwise do nothing and surface it. Without that guard, a MŁYNEK Janusz registering could write his birth year onto the wrong Janusz — and one of them has 19 results behind him.

Problem 2 · the null-birth-year match cannot happen through the existing matcher

fn_match_registration_fencer requires int_birth_year equality, and NULL is never equal to anything. So a fencer whose birth year is NULL can never be matched by it — the populate rule in §4 would never fire through the existing path. It needs its own lookup: surname + given name, restricted to int_birth_year IS NULL, with the exactly-one guard from Problem 1. Small, but it has to be built deliberately rather than assumed.

Problem 3 · this lets an anonymous form write master data — and it reverses ADR-079

ADR-079 made the declared birth year a read-only invariant that never writes back to tbl_fencer; ADR-080 §2 repeats it. This requirement deliberately reverses that, which is your call — but it should be on the record as a decision, not arrive as a side effect.

The concrete exposure: fn_create_registration is SECURITY DEFINER and granted to anon. Adding a master-data write widens what an anonymous visitor can do from "insert a registration row" to "mutate the fencer table". Anyone who knows a fencer's name can change that fencer's birth year.

Three guards make it acceptable, and two are already yours: a confirmed birth year is never overwritten silently (only NULL or estimated), the exactly-one-match guard from Problem 1, and trg_audit_fencer — which already logs every UPDATE on tbl_fencer, so every write of this kind is traceable after the fact. With those three, the residual risk is someone vandalising one estimated birth year, which the recompute queue would then propagate. For a veterans' ranking I think that is acceptable; it is worth one sentence in the ADR saying we accepted it knowingly.

Problem 4 · B does not cover the Łomianki case

B fires only when the swapped name hits an existing fencer. ŁĘCKI Krzysztof is #168, so PPW1's case is caught. NAGY Orsolya is not in the table at all — she is a foreign EVF entrant — so B stays silent and ORSOLYA Nagy Dr. enters exactly as typed. B covers people we already know; it cannot cover a first-time international entrant, which is the population most likely to write their name in a different order. Not a reason to change the decision — just the honest boundary of it. The organizer's roster file and the reconciliation report remain the backstop, and the canonical-name echo is there to be added later if this keeps happening.

Two smaller ones

  • Roster suppression must key on the fencer, not the name. The rule was "exclude any fencer whose name matches a registration, ignoring birth year". Given MŁYNEK Janusz, that would hide the 19-result Janusz from the roster because a different Janusz registered — exactly the person the organizer might need to tick in. Refined rule: suppress the matched id_fencer always, and suppress by name only when exactly one fencer bears that name.
  • The recompute queue drains, but verify the worker still runs. PROD shows 42 DONE rows and nothing PENDING, last activity 14 July — which is consistent with "working, nothing to do since". Before relying on it for a live birth-year correction, confirm the consumer is still scheduled. If it is not, a correction would sit un-propagated and we would not notice.
Overall The design is sound and the riskiest part — keeping the ranking consistent after a birth-year change — is already solved by the CDC recompute queue. What it needs is the exactly-one-match guard applied uniformly in four places, a dedicated NULL-birth-year lookup, and an ADR that says out loud we are reversing ADR-079's read-only invariant and why.

TDD scope for this block

  • pgTAP — populate on NULL; overwrite when estimated; refuse when confirmed; refuse when two fencers share the name (the MŁYNEK case, as a fixture); confirm bool_birth_year_estimated ends false; confirm a row lands in tbl_recompute_queue for each affected event; confirm trg_audit_fencer recorded the change.
  • Python — the swapped-name retry returns the twin for KRZYSZTOF Łęcki and nothing for a name absent from the table; the near-miss lookup returns exactly one candidate or none.
  • vitest — each of D's three answers produces the right call; the B alert renders the canonical form; neither prompt appears on a clean exact match.
  • Regression — an ordinary matching registration still takes the fast path and shows no prompt at all. This is the one that protects the other 36 of 43.

7 · How each one is solved

All four collapse into one lookup function plus one write function, because the guard that fixes Problem 1 is the same mechanism that fixes Problem 2, and the capability that fixes Problem 3 is already on the table.

The lookup — one function, four classifications

fn_registration_identity_candidates(p_surname TEXT, p_first TEXT, p_birth_year SMALLINT)
  RETURNS TABLE (id_fencer INT, txt_surname TEXT, txt_first_name TEXT,
                 int_birth_year SMALLINT, bool_birth_year_estimated BOOL,
                 enum_kind TEXT)   -- EXACT | SWAPPED | BY_NULL | BY_DIFFERS

It scans by name, not by tuple, so it sees the nine NULL-birth-year rows the current matcher structurally cannot — that is Problem 2, gone, with no second lookup to build and no change to fn_match_registration_fencer, which stays exactly as it is and keeps serving the fast path for the 36 of 43 who match cleanly.

The caller resolves in a fixed order, and the "exactly one" guard is the order itself rather than a condition bolted onto each rule:

#ConditionActionPrompt?
1exactly one EXACTlink and stop — today's behaviour, untouchednone
2more than one EXACTrefuse and flag: two fencer rows share a name and a birth year, which is a duplicate-fencer defectadmin
3exactly one SWAPPEDB promptfencer
4exactly one BY_NULLlink, populate the birth year silently, mark confirmednone
5any BY_DIFFERSD prompt, listing every candidatefencer
6nothing matchednew person — canonical-form confirmation (see Problem 4)fencer
Problem 1 · solved, and it mostly dissolves on inspection

MŁYNEK Janusz 1984 registering hits rung 1, not rung 5. There is an exact match — #356 — so the ambiguity with #197 never arises. Ambiguity only bites when no exact match exists, and then rung 5 shows both Januszes with their birth years and lets the person pick. That is better than the "refuse and surface" I proposed: the one human who knows the answer is already looking at the screen.

Rung 2 covers the case I cannot rule out: tbl_fencer has no uniqueness constraint on name + birth year — only idx_fencer_name (non-unique) and the primary key. PROD has zero duplicate triples today, so this is a guard against a future defect, not a present one. It must exist anyway, because a silent write to the wrong one of two identical rows is unrecoverable.

The write — gated on a capability that already exists

fn_confirm_registration_identity(
    p_id_registration INT,
    p_edit_token      UUID,      -- tbl_registration.uuid_edit_token
    p_id_fencer       INT,       -- must be in this registration's candidate set
    p_action          TEXT       -- ADOPT_DECLARED | FIX_REGISTRATION | DIFFERENT_PERSON
)  SECURITY DEFINER
Problem 3 · solved — this is not "any anonymous visitor"

tbl_registration.uuid_edit_token already exists (migration 20260828000003_registration_edit_handle.sql) and fn_update_registration already takes it as a parameter. So the master-data write is gated on a capability only the person who made that registration holds. We reuse an established pattern instead of widening fn_create_registration, which stays a registration-only function.

Four rules inside, each closing a specific hole:

  • The token must match the registration — otherwise no write.
  • p_id_fencer must be in the candidate set, recomputed server-side from the registration's own name. Without this, a caller could name any fencer and rewrite their birth year; with it, the reachable set is the handful of people who share the registrant's name.
  • Confirmed birth years are never touched by a rule — only rungs 4 and 5 write, and rung 5 requires an explicit human answer. That is the difference between your two requirements: NULL and estimated are overwritten by policy, confirmed only by a person saying so.
  • Plain UPDATE, never a trigger-disabling path — so trg_fencer_change_enqueue fires and trg_audit_fencer records it.

The three actions map to D's three buttons: ADOPT_DECLARED links and corrects the master birth year; FIX_REGISTRATION corrects the registration and leaves the fencer untouched; DIFFERENT_PERSON links nothing, and the fencer is created at scraping time as today.

Problem 4 · solved by narrowing option A instead of adding it whole

You declined the canonical-form echo because it would sit in front of everyone. So put it on rung 6 only — the path where we are about to mint a brand-new identity.

That is precisely the population B cannot reach. B needs a fencer already in the table: ŁĘCKI Krzysztof is #168, so PPW1's case is caught; NAGY Orsolya is absent, so B stays silent for her. Rung 6 catches her, because she is new by definition.

Cost: zero for everyone who matches. It fires for 7 of 43 at PPW1 and 6 of 14 at Łomianki. And it is honest about why it is asking — "nie mamy Cię jeszcze w bazie, sprawdź proszę, czy tak ma wyglądać Twoje nazwisko na liście startowej: NAGY Orsolya" — with a swap button. Nobody is accused of a mistake; they are asked to check a name we have never seen.

The two smaller ones

Roster suppression · keyed on the fencer, with a narrow name fallback

Two clauses in fn_ftl_roster, not one. Always suppress any id_fencer that a registration for this event and weapon already points at — exact, unambiguous, no names involved. Additionally suppress by name only when an unmatched registration bears that name and exactly one fencer does too. So registration-BUJKO hides fencer #30 BUJKO (one name-holder), while a registering MŁYNEK Janusz 1984 hides only himself and leaves the 19-result Janusz in the roster where the organizer can still tick him in.

Recompute worker · verified, not assumed

.github/workflows/recompute-drain-prod.yml runs on cron: '*/15 * * * *' and its last five scheduled runs all succeeded — most recently 2026-09-12 05:50Z, in 19 seconds. So the queue is drained every quarter hour and the self-heal path a birth-year change depends on is live. The 42 DONE / 0 PENDING reading was "working, nothing to do", as hoped.

Net effect on the build Two new database functions and one extra prompt branch, instead of four separate fixes. Nothing existing changes behaviour: fn_match_registration_fencer and fn_create_registration keep their current signatures and their current fast path, so the 36 of 43 registrations that already work keep working byte-for-byte — which is also the regression test that matters most.

9 · The instruction manual — PL and EN

Two files, linked side by side from the download page, written against the Fencing Time 4.7 User's Guide with menu paths quoted.

  1. What you are downloading — the file manifest: exact name, fencer count, purpose, and whether it is imported as a competition or used as a pick-list. Generated from the same query that builds the files, so it cannot drift.
  2. Before the event — Import Events → choose file → check Age/Gender/Weapon → Import (pp. 22, 144). Per weapon, then the DE files.
  3. These are the maximal split — combine freely (Combine Events, p.22); we re-split by birth year regardless. Please do not rename an event to a category it does not contain.
  4. The digit in the name — KAMIŃSKA (1) Gabriela means V1. Leave it; it is how we read results back.
  5. On the morning — re-download, then Re-Import Competitors from XML File on the Summary tab (p.144). Rounds and entered scores are kept.
  6. Someone turns up unannounced — Event Competitors → Import from XML → the roster → tick that one person → OK (p.145). Do not type the name.
  7. Sending results back.   8. Contact.
