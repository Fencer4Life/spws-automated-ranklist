The admin import buttons, and who can run Phase 5

Neither import button in the admin UI runs the Phase 5 runner. The event ⬇ only looks up result links. The tournament ⬇ writes one tournament's results straight into CERT, and those results never reach PROD. You can run Phase 5 yourself from GitHub or your terminal. Nothing else starts it.

Short answers

Your three questions

1 What happens when I press an import button?

It depends which ⬇ you press. Each one starts a different GitHub workflow, and neither of them is Phase 5. Details are in § 1.

2 Can I run the Phase 5 Event Runner?

Yes: from the GitHub Actions page, with gh workflow run, or with Python on LOCAL. You cannot run it from the admin UI or from Telegram. It suits past-season repairs only, never a current-season event (§ 2).

3 Does any other script or workflow run it?

No. No other workflow, no schedule, the bot and the admin UI never start it. Three programs do borrow helper functions from its Python file without running it (§ 3).

§ 1 · the admin UI, Events screen

The two ⬇ buttons do different things

ButtonIts tooltip saysStartsWhat it really does
⬇ on an event row
shown when the event has an event-page URL		 "Import results from event page"
„Importuj wyniki ze strony wydarzenia”		 populate-urls.yml Imports no results. It reads the event's URL slots (FTL, Engarde, 4Fence, d'Artagnan) and finds each competition's results link. It writes that link into every tournament that doesn't have one yet, then sends a Telegram summary.
⬇ on a tournament row "Import results from URL"
„Importuj wyniki z URL”		 scrape-tournament.yml Scrapes that tournament's results link and writes the placings straight into CERT's live results. The steps are below.

Each button targets the environment of the admin page you're on: the CERT page sends cert, the PROD page sends prod.

The tournament ⬇, step by step

  1. The browser calls the dispatch-workflow edge function. It requires you to be signed in with your authenticator code. It then starts the workflow on GitHub with its own token. The UI shows "✓ Triggered" as soon as GitHub accepts the request. That means the run started, not that it worked. The list refreshes 40 seconds later.
  2. The workflow refuses any target but cert. From the PROD admin page the button sends prod, so the run fails at its first step. The UI has already said "✓ Triggered", and only Telegram reports the failure.
  3. It reads the tournament and its siblings. Siblings are the other categories that share the same results link, which happens when categories fenced in one pool.
  4. If any sibling already has results, it stops. The script can delete and re-import with --replace, but the workflow never passes that flag, so the button cannot re-import a tournament that already has results.
  5. Domestic: it splits the pool into categories by each fencer's birth year and ranks each category on its own. International: it keeps one bracket, with the whole bracket as N (ADR-105), and stores only SPWS starters (ADR-106).
  6. It deletes any sibling tournament that has 0 fencers in the source, treating it as a registration mistake.
  7. It matches names to fencers and writes the placings directly into the results table with fn_ingest_tournament_results. For an international tournament, a name that isn't matched automatically is left out; only the log mentions it.
  8. It sends a Telegram summary.

× What the tournament ⬇ skips

No drafts, no review report, no sign-off step. It also leaves no recorded run in tbl_ingest_run.

That last point matters: promote.yml only replays a recorded CERT run of ingest-event.yml. Results written by this button stay on CERT and never reach PROD. Its whole history is one run, on 30 May 2026.

The route that ingests an event today has no button

  1. Telegram ingest <EVENT-CODE> starts ingest-event.yml on CERT. It refreshes CERT's fencer list from PROD, reads every result link of the event, commits the results, records the run, and sends the report to Telegram.
  2. Telegram promote <EVENT-CODE> starts promote.yml, which replays that verified CERT run on PROD (ADR-108, ADR-113).

The front end has a function for this, reingestEvent (frontend/src/lib/api.ts:260), and the edge function's comments mention a "Re-ingest event" button. No screen calls it: that button doesn't exist.

§ 2 · running it yourself

Yes, you can run Phase 5: three ways

WhereHow
GitHub websiteActions → Phase 5 Event Runner → Run workflow → branch main, then fill in the event code, the target (cert or prod) and the staged run id. Leave the run id empty to stage. Enter a run id to replace the event's results.
Your terminalgh workflow run phase5-event-runner.yml -f event_code=<CODE> -f target=cert, plus -f commit_run_id=<id> to commit.
LOCALpython -m python.tools.phase5_runner --event-code <CODE> against your local database. The stage report prints the matching --commit-run-id command.
Admin UINot possible: no button sends it. The edge function would accept it from a signed-in admin, but no screen calls it.
TelegramNot possible: the bot has no command for it (the old /stage is gone).

! Never on a current-season event

A current-season event goes to CERT with ingest and to PROD with promote. If Phase 5 commits results on PROD for such an event, PROD holds results that no CERT run produced.

From then on, promote refuses that event: "PROD holds results … that no FINISHED CERT run produced … Promote never overwrites them" (python/pipeline/promotion/replay.py:162-166). Phase 5 suits LOCAL work and past-season repairs, like the 2–3 October batch.

Staging on prod writes only draft rows, and published results stay untouched. It is still a write to PROD.
