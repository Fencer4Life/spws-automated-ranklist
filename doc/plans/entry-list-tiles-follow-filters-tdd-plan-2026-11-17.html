One component changes: frontend/src/components/EntryList.svelte. It is the same component in the calendar modal, in the registration flow's list step and on the standalone register.html?view=list page, so one change covers all three.

02 · Verified in the source

What the code does today

  • Tiles, EntryList.svelte lines 17–22: the first reads rows.length; the three weapon tiles call countByWeapon(w) (lines 164–166), which counts over rows, the whole event.
  • Selection, lines 153–162: filteredRows filters rows by the trimmed, lower-cased search text, then weapon, category and gender. The table (lines 58–85) renders filteredRows; with none, it shows reg_no_entries.
  • Issue 1, line 156: the name test is `${surname} ${first}`.toLowerCase().includes(q). No diacritic folding. There is no folding helper anywhere under frontend/src.
  • The Python side already folds: fold_diacritics in python/matcher/fuzzy_match.py (line 58) replaces ł/Ł by hand, then strips combining marks after NFD. The frontend helper follows the same rule.
  • Translations: t(key, vars) in frontend/src/lib/locale.svelte.ts replaces {name} placeholders. frontend/tests/locale-parity.test.ts requires identical key sets in pl.json and en.json; translation-completeness.test.ts (TR.01, TR.03) requires every used key to exist and flags a value pasted identically into both files.
  • Who renders the component (code graph): RegistrationModal.svelte, RegistrationForm.svelte, ce/EntryListElement.svelte. None of them reaches into the tiles or filters. No test outside frontend/tests/EntryList.test.ts asserts on the tiles, the search box or the filters, and no Playwright spec covers the entry list.
  • Existing tests: frontend/tests/EntryList.test.ts holds 19 tests in three groups (list and filters 10, back and close 5, surname order 4).

Not verified, and said so: how the modal is best captured in a real browser with fixed data. Step 2 of the build settles it before any code changes (§10).

05 · No deterioration

What must not change

  • The unfiltered form, pixel for pixel: back row, title, language switch, close button, four tiles, search box, three dropdowns, table, legend; desktop and phone; Polish and English.
  • The list itself in every state: rows, order (Polish collation), badges, column headers, the phone row layout, the empty message.
  • Which rows a filter selects. The only change is that a search now also matches when the visitor leaves out Polish marks. A search that matched before still matches.
  • The data: the fetch, the view, the columns, the absence of birth year and club.
  • Component props (eventId, onclose, onback, backLabel) and the three hosts.
  • Everything else in the app. No other component, style sheet or page is edited.

While narrowed, the agreed differences are the only ones: tile text, the frame, the highlights, the ×, the clear link (which moves the list down by its own height), and dimmed tiles.

06 · Walk-throughs

Scenarios

  1. Phone, from a calendar card. A fencer opens the list, picks V2, then Mężczyźni. After the first pick the tiles read "… z 76" inside the frame, the Kategoria dropdown is highlighted, and "Wyczyść filtry" appears under the dropdowns. After the second, both dropdowns are highlighted and the numbers shrink. One tap on the link returns the plain form.
  2. A guest without Polish keys types "zak". ŻAK appears; the first tile reads "1 z 76"; the search box is highlighted and shows ×. Tapping × empties the box; with no other filter set, the form is plain again.
  3. Search plus filters. Category V2 is set, then "kow" is typed. × removes only the text and V2 stays; the link removes both.
  4. Weapon chosen. Szpada: the Szpada tile reads "47 z 47", Floret shows the épée fencers who also fence foil and is dimmed with Szabla.
  5. No match. Tiles read "0 z 76"; the list shows the existing empty message; the clear link is there to get out.
  6. Language switched mid-filter. Labels, "z"/"of" and the link's text change; the search text and the dropdown choices stay.
  7. From the payment step. The Back button is present above the title and works as before; filters do not affect it.
  8. An event with nobody registered. Tiles read 0; the empty message shows; a filter gives "0 z 0".
  9. Screen reader. The tile group is a polite live region, so a change of selection is announced after the user stops; both new controls are buttons with names in the page's language.

The two questions, answered

Q1 ADR-079: amend if needed. Checked: not needed.

You said to amend ADR-079 if needed. I read doc/adr/079-event-self-registration-identity.md: its entry-list passages cover the roster's spelling of a name, how long the list stays visible, the modal presentation and the onclose/onviewlist props. It says nothing about the tiles, the search box or the filters, so nothing in it is contradicted or left stale by this change. No ADR is written; FR-165, the design page and this plan carry the record. If you want the amendment anyway, say so and I draft it here for sign-off first.

Q2 The fold follows the Python rule.

ł by hand, then every accent mark stripped, as fold_diacritics in python/matcher/fuzzy_match.py does. Letters that are not accents (ø, đ, ß, æ) are not mapped.

08 · Red before green

The build, step by step

Every "red" below is run and read before the code that turns it green is written. A test that passes before its code is rewritten. No existing test is edited, skipped or deleted.

  1. Branch. Rename to claude/entry-list-tiles-follow-filters and write its description (title of at most 72 characters, then what was wrong and what it does now).
  2. Before captures, on the untouched code. Settle the capture method (§10), then photograph every state in the sheet's list. Nothing has changed yet, so these are the reference.
  3. Register the requirement. FR-165 and the FOLD / ELSEL acceptance table go into doc/requirements-traceability-matrix.md, marked planned; render with python scripts/render_docs.py.
  4. Folding helper. Write FOLD.01–05 → run → red (the module does not exist). Add frontend/src/lib/foldName.ts with one pure function → green.
  5. Issue 1. Write ELSEL.16 → red ("zak" finds nobody). Use the helper on the typed text and on the names in filteredRows → green. Run the 19 existing tests: green.
  6. Tiles. Write ELSEL.02–06, 08, 09, 17 and the guards ELSEL.01, 07 → the eight are red, the guards hold. Add the derived isNarrowed; tile values read filteredRows when narrowed and rows otherwise; countByWeapon takes the list to count; add reg_sel_of_total to both locale files; aria-live on the tile group → green. Record the mutation runs for the two guards.
  7. Frame and highlight. Write ELSEL.10, 11 → red. Add el-narrowed and el-active with their style rules → green.
  8. × in the search box. Write ELSEL.12 and the × half of ELSEL.14 → red. Add the button and reg_search_clear → green.
  9. Clear link. Write ELSEL.13 and the link half of ELSEL.14 → red. Add clearAll(), the link and reg_clear_filters → green.
  10. Dimming. Write ELSEL.15 → red. Add el-dim → green.
  11. Refactor and check. Tidy with tests green. npm run check -- --fail-on-warnings at zero findings; npm test; npm run test:e2e.
  12. After captures and the pixel sheet (§10). Send you the sheet and stop until you approve it.
  13. Documentation (§12): handbook page, approved mockup, matrix status, renderers, check_docs.py.
  14. Graph and search index. scripts/refresh-graph.sh, then python3 tools/docs-search/ingest.py, before the commit. Commits name explicit paths and are authored as Fencer4Life.
  15. scripts/preflight.sh exits 0. Any finding is fixed at its cause, never by loosening a gate.
  16. Release, only on your go. Through the integration checkout (scripts/integrate-agent-branch.sh, then integration/main:main), watched in the foreground. A push to main puts the frontend bundle on PROD's pages with no approval gate, so step 12 is the gate. Done means workflows green and the live list checked on CERT and PROD in both languages.

Nothing is pushed before step 16. Commits before then stay on the branch in this worktree.
