No way back from the entry list

A fencer who opens the roster before copying the IBAN loses the transfer data. It is not a missing button — viewing the roster unmounts the form, and the payment details are derived from live form state.

Decided · built

Back button only — no history manipulation

Once the roster renders in place, the address bar keeps showing ?event=PPW1-2026-2027 while the fencer browses it, instead of …&view=list. I can additionally push ?view=list into history, which would make browser Back a second route home and keep the URL copyable while the roster is open.

✓ My recommendation — back button only, no history manipulation

RegistrationElement is a custom element destined for the WordPress CMS page. Pushing history from inside a component on a page it does not own is how a host's own navigation gets broken. The shareable roster link is unaffected either way, because register.html?event=X&view=list stays exactly as it is for cold visitors.

? The alternative, if you want it

Add history.pushState on entering the roster and a popstate listener to return. Browser Back works, URL stays shareable mid-flow. Cost is a history listener living inside an embedded custom element.

Why

The roster destroys the form, in both paths

The payment step is the only place the transfer data exists — payee, IBAN, the transfer title (PPW1-2026-2027 JAN KOWALSKI SZPADA V2) and the amount, each with a copy button. All of it is $derived from form state.

1 × Standalone register.html — a full page load

The affordance is <a href="?event=X&view=list">. That URL makes register.html mount spws-entry-list instead of spws-registration — a different custom element entirely. Browser Back re-mounts the form at the identity step, so the fencer must re-submit to see the IBAN again.

2 × Calendar modal — the component is swapped out

onviewlist sets regModalView = 'list', and RegistrationModal renders EntryList in an {:else} branch that unmounts RegistrationForm. Only onclose exists, and it closes the whole modal back to the calendar.

The change

Stop unmounting the form

RegistrationForm gains a list step and owns the roster itself. Because it is never unmounted, surname, firstName, weapons, fee and title survive untouched and the payment step re-renders exactly as it was.

UIEntryList.svelte
  • Optional onback prop, rendered in the existing .el-top header — the same conditional-affordance pattern already used for onclose.
  • Cold entry points pass no onback and are unchanged: a shared ?view=list link and CalendarView.openEntryListModal have nothing to go back to.
UIRegistrationForm.svelte
  • list added to the step union; the roster replaces the .reg-card rather than nesting inside it — EntryList renders its own full card with its own header and LangToggle, so nesting would stack two headers and two language toggles.
  • listReturnStep holds where the fencer came from. The closed step carries the same affordance and must not land someone on a payment screen they never reached.
  • onclose is passed through, so the modal's × still closes from the roster.
DROPonviewlist
  • Once the form owns the list step, both call sites exist only to route around the form. Removing it collapses two divergent behaviours — navigate away vs. swap the component out — into one that works identically in the standalone page and the modal.
  • Touches RegistrationModal.svelte and CalendarView.svelte. The modal's view prop stays: it still serves the cold entry-list entry point.

register.html is not changed — ?view=list must keep working as the shared roster link. No database, migration or API change; vw_registration_entry_list and fetchEntryList are reused as they are.

How it gets built

Tests first, RED verified by reversion

  1. EntryList.test.ts — renders a back button and calls onback when provided; renders no back button when it is absent. Mirrors the existing onclose test.
  2. RegistrationForm.test.ts — from the payment step the affordance shows the roster without unmounting the form; back returns to payment with the transfer title and amount still populated. That last assertion is the one that encodes the actual bug — a back button returning to a blank payment panel would pass a weaker test.
  3. The same round trip from the closed step returns to closed, not payment.
  4. Two existing tests are replaced, not deleted quietly: the onviewlist test and the standalone <a href> assertion both pin behaviour being deliberately removed.
  5. Only then edit the components. RED was observed before any component code existed — 1 failure in EntryList.test.ts, 3 in RegistrationForm.test.ts, each failing because the button genuinely was not there — which is the stronger form of the proof, so no reversion pass was needed.
  6. One RED was my test's fault, not the code's: the closed step styles its affordance .reg-btn, not .reg-entry-list-link. Selector corrected rather than the component bent to fit it.
