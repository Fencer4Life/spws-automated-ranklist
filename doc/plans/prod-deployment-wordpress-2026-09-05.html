01What we are building

What step 1 actually is The calendar is not the goal. The goal is a validated way to publish an SPWS PROD surface as a WordPress menu item — full-screen-capable, PROD-backed, updated by release rather than by hand. The calendar is simply the first surface through it, and the one that proves the mechanism works.

Three surfaces are queued for that mechanism. Only the first is being built now:

Calendar

Ranking
step 2		 Not yet decided. Possibly not KLASYFIKACJA. An SPWS Board decision, expected in the week of 8 September 2026 — which may also settle where in the menu it belongs.
Points calculator

Technically unlike the other two — a static page, not the Svelte bundle — but it shares the same full-screen menu-item pattern.

The calendar and the ranking run the same JavaScript bundle, served from the address GitHub Pages already publishes, differing by one attribute. All three are full-screen capable, because a phone's screen is the binding constraint for every one of them. CERT and the administrative interface stay on GitHub Pages, unchanged.

Neither gate is a build step. Step 2 waits for both: the calendar working on the live site, and an SPWS Board decision expected in the week of 8 September 2026.

Step 2 is governed, not just verified Moving the ranking onto the site needs an SPWS Board decision, expected sometime in the week of 8 September 2026. That is a governance gate, not a technical one, and it sits outside this plan's control.

It reinforces the ordering rather than disrupting it. Step 1 depends on nobody: the calendar page is additive — a new page in the LINKI menu, replacing nothing — so it can be built, verified and published while the Board question is still open. Step 2 is different in kind: the classification is the association's official record, and where it is published is the Board's call, not a deployment detail.

Practical consequence: step 1 proceeds now and stops cleanly at its own sign-off. If the Board decides against the move, or defers it, nothing built in step 1 is wasted and nothing needs unwinding — the ranking simply stays on GitHub Pages and /klasyfikacja/ stays as it is.

03Locked decisions

These are settled. The ADR will be written from this table.

How it is embedded and delivered

Mechanism A custom element inside a normal WordPress page. The theme's header, menu and footer surround it; shadow DOM keeps the two style worlds apart. This is what ADR-007 anticipated in M8.
Delivery The bundle is served from the existing GitHub Pages address at a stable file name. WordPress is touched once; every later release updates the live page with no upload and no cache-busting. The PROD URL and anon key sit in the page as attributes, so the environment is named where a human can read it.
Element interface The application gains view (calendar | ranklist) and chrome (full | none). <spws-calendar> becomes a thin wrapper mounting the application with view="calendar" chrome="none", inheriting the loader that already works.
Assets An asset-base attribute, defaulting to empty so nothing on Pages changes. It points at the Pages origin, where the four organizer logos already deploy.

What the embed shows

No app chrome chrome="none" removes the header, the hamburger and the drawer. A single embed has no second view to navigate to, so nothing is lost.
Top row Four things on the row that already exists, costing no extra height: the SPWS mark linked to weteraniszermierki.pl, the page name in the active language only („Znajdź zawody” / “Competition finder”), the 🇵🇱/🇬🇧 toggle, and a ⛶ fullscreen button.
No page heading No H1 and no intro paragraph on the WordPress page. Vertical space is the scarcest resource and the drum needs it; the menu label and the top row already name the page.
Height Full viewport height by default. The ⛶ button goes edge-to-edge via the Fullscreen API — which a browser only grants after a tap, so it cannot be forced on load.
Kept as-is The PPW / +EVF scope toggle, live registration and the entry list (both writing to PROD), and — on the ranking page — the filter bar, the category subtitle, the fencer drill-down and the spreadsheet export.
Admin The embed ignores ?admin=1. No sign-in modal, no admin views, whatever the address bar says. Administration stays on GitHub Pages.
CT/PD switch Left in the code untouched. It is derived from having all four credentials, and the embed gets only the PROD pair, so it never renders there. The Pages app keeps it.

On the WordPress side

A new page Slug znajdz-zawody, title „Znajdź zawody / Competition finder” — bilingual in one string, because the site has no multilingual plugin and its menu is static text. Nothing existing is overwritten: /kalendarz-2/ and /klasyfikacja/ stay exactly as they are, so the two can run side by side until you choose to retire the old ones.
Menu placement A nav_menu_item appended to the bottom of the LINKI submenu (parent item 7128).
Naming inside the embed The embed calls itself „Znajdź zawody” / “Competition finder”, matching the menu, one language at a time — it has its own toggle, so it never needs the slash form. Embed-only locale keys: the Pages app keeps “Kalendarz”, which is right there, where it is a drawer section beside “Ranking”.
Pages app, one change The drawer's SPWS mark (Sidebar.svelte) gains the same link home. That copy has no other route back to the association's site.
Points calculator Gets its own menu item — but it is a .html upload, so it waits for FTP. Independent of both phases.
Naming of this work This is PROD deployment. The plan file and the ADR carry that name.

05The code gap

The calendar element has no data path. src/ce/CalendarElement.svelte takes one prop, demo, and renders either two hard-coded mock events or an empty calendar. It has never talked to a database. Everything that loads calendar data lives in App.svelte: initClient(), fetchAllCalendarEvents() (all seasons — the barrel crosses season boundaries, so the season-scoped fetch is the wrong one), the scoring-config lookup behind the +EVF scope, and the locale store. Mounting the application with view="calendar" inherits all of it.

The ranklist element is already finished. RanklistElement.svelte takes four credential attributes and passes them through. Given only the PROD pair it renders the PROD ranking with no environment switch. Step 2 is a page, not a rewrite.

Relative paths break outside the site root. EventCard.svelte loads the organizer marks as bare names — SPWS-logo.png, EVF-logo.png, FIE-logo.svg, PZSz-logo.png — and the header and drawer do the same. They resolve on Pages because the app sits at the root; from /znajdz-zawody/ they 404.

The bundle is 1.08 MB uncompressed (~300 KB over the wire), carrying the admin wizard, the import modals and the whole xlsx library. Measured properly in step 1.

09The anon key — is this safe?

Short answer: the key is safe and this deployment adds no new exposure. But one documented gap becomes more relevant when the page moves into the main menu, and you should decide about it rather than inherit it.

Why the key itself is not a risk

It is already public, by design The same PROD anon key is already embedded in the GitHub Pages bundle, on a public website anyone can read today. Putting it in a WordPress page does not widen anything: a key's blast radius is defined by what the database grants it, never by where it is printed. The handbook says so in as many words — “Its API key ships in the public frontend bundle and is not a secret.”

What anon may actually do, per ADR-083 and doc/handbook/reference/security-posture.html:

  • SELECT on the tables and views the public ranking and calendar render.
  • A fixed allowlist of read-only functions, plus the two self-registration RPCs.
  • No write privilege on any table — INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES and TRIGGER are all revoked. Registrations are written only through SECURITY DEFINER RPCs, never by touching a table.
  • Pipeline and staging tables have RLS on and no policy at all, with every grant revoked — no policy being the correct amount of policy, since RLS with zero policies denies everyone but service_role.
  • vw_fencer_aliases is specifically denied to anon.

And this is verified against the real deployed database, not just asserted: pgTAP 52.1–52.12 cover LOCAL, and scripts/check-security-posture.sh runs inside the deploy job against actual CERT/PROD, failing the release on any RLS-disabled table, any anon write grant, any anon-executable function outside the allowlist, or any stray default ACL.

The one thing that genuinely changes

The sign-up form is open to anyone, and that is deliberate

Three functions are callable by anonymous visitors, confirmed in the migrations and asserted as an exact set by pgTAP 52.7:

  • fn_create_registration — submit an entry. SECURITY DEFINER precisely so that anon can call it without holding table privileges.
  • fn_update_registration — correct a submitted entry. Explicitly GRANT EXECUTE … TO anon.
  • fn_match_registration_fencer — match the declared name to a fencer record.

That is the feature, not a mistake: a fencer signs up without an account. But it means the form has no throttle and no proof of who is filling it in. A person is identified by declared name and birth year, and birth years are effectively public — the ranking categories publish them by decade.

So two things are possible today, by using the form exactly as designed:

  • Bulk junk entries. A script submits hundreds of entries for an event; the public start list fills with rubbish and an administrator deletes them.
  • Entering somebody else. Signing a real fencer up for a competition they are not attending. They find out when they see a start list they never joined.

ADR-079 §4 specified the two defences — a salted-hash abuse log and a rate limit — and records that neither was built: “No rate limit anywhere, so §4's defence (d) does not exist.” A migration comment repeats it.

Decision · 5 September The exposure is accepted for now and closed later. Registration ships live with the calendar.

Nothing about the privilege changes with this deployment — only the number of people who walk past it. Today the form sits on a GitHub Pages address almost nobody knows; step 1 puts it in the main menu of the association's own site.

It is bounded: anon cannot read private data, cannot change rankings, results or scores, and cannot write to any table. The damage is confined to entry lists and is undone by deleting rows.

Follow-up — scheduled for 6 September 2026, alongside the planned XML export work, and tracked there rather than here: build ADR-079 §4 defence (d) — the rate limit plus the salted-hash abuse log — and close the corresponding ADR-079 open item. Separate piece of work with its own tests; it does not gate step 1, and step 1 does not gate it.
One check to run before publishing scripts/check-security-posture.sh against PROD, so the posture is proven green now rather than as of the last deploy. It is read-only and needs SUPABASE_ACCESS_TOKEN, which is already in .env. Added to step 1.
