ADR-104: remove the place-and-medal engine, then add the joined-bracket engine

This plan first deletes everything the place-and-medal engine added that nothing will ever use, and only then adds the rule locked on 30 September. That rule reaches the database, ingestion, the Admin editor, the drilldown and both public pages. The work runs RED before GREEN, is done when scripts/preflight.sh exits 0, and ships only on your explicit go.

The plan in nine lines
  1. Step 0, immediately after approval: your two wording changes in the annex's W skrócie.
  2. Cleanup first (D0). One migration deletes the place-and-medal strategy and every column and parameter it added. No row in any environment holds a value in them. The migration refuses to run if one ever does.
  3. Then the new engine. A second migration adds SPWS_EVF_JOINED_V1_2026_2027 for PPW, MPW and the 2026/27 default.
  4. The cap reads the whole bracket. Every category tournament of a listing stores the listing's category order (D1), and the scoring reads the cap from it.
  5. Ingestion refuses a joined listing it cannot score: one with a repeated place, or with a fencer who has no category.
  6. The joining check is automatic, with no sign-off (D2). After every event run it compares the fenced brackets with § 2, stores the verdict, and sends a Telegram message on a mismatch.
  7. The points calculator is rebuilt in line with the annex.
  8. No 2026/27 ingestion before the release (D3). CERT's coefficients are aligned to PROD's (D4).
  9. Two commits, each green on its own: the cleanup, then the engine. They ship together.

4 · The new engine, exactly

per bracket: N, the joined order (one category digit per place), the season's EVF settings, the type coefficient
per row:     d = the digit at the row's place − the youngest digit in the order

N ≤ 3                                   → N − p + 1                           method TABLE
one category in the order, or N ≥ 16    → EVF(N, p)                           method EVF_CLASSIC
joined, 4 ≤ N ≤ 15 (every row)          → method EVF_JOINED
    premium  = max(EVF · (1 + 0.05 · d), EVF + d) − EVF      (0 when d = 0)
    raw      = EVF + premium
    capped_p = min(raw_p, capped_(p−1) − 1)                    walked from place 1 down
    cap reduction = raw − capped
final = ROUND(capped × type coefficient, 2)                     rounded once, after the cap
  • The strategy fn_score_spws_evf_joined_v1_2026_2027(n, place, d, joined, mp, de_round, gold, silver, bronze) is one row at a time and IMMUTABLE, with no cap. Its EVF part calls fn_score_evf_classic_v1_2025_2026.
  • The chain fn_score_joined_bracket(engine, order, mp, de_round, gold, silver, bronze) returns every place:
    • category, d, the EVF parts, the premium;
    • raw, the cap reduction and the capped value.
    The writer, the preview and pgTAP all call it, so the cap lives in one SQL function. scoreBracket mirrors it.
  • New result columns, NOT NULL DEFAULT −1, each with a CHECK allowing only ≥ 0 or −1:
    • num_joined_premium;
    • num_cap_reduction, stored as a positive amount;
    • int_category_steps (d).
  • The joined order, txt_joined_order, goes on tbl_tournament and tbl_tournament_draft. Its CHECK allows only digits 0–4, with length N. It is required for tournaments of a type on the new engine.

5 · The automatic joining check (D2)

Why a mismatch can happen at all:

  • The organiser forms the brackets on the day.
  • A joined bracket needs one fenced order, so the system can score only what was fenced.
  • § 2 is the organiser's rule. The check measures whether the organiser followed it.

What runs, in both options, with no human step

  1. When it runs. At the end of each event run (python/pipeline/ingest_cli.py, the path ingest-event.yml takes) and after each recompute of a PPW or MPW event. Running at the end of the run, not after each listing, avoids false alarms from a half-ingested event.
  2. What it reads. For each weapon and gender, the stored orders of the event's listings. They give every category's exact size, including fencers who were never stored, and which categories fenced together.
  3. What it compares. plan_brackets(sizes), a port of the spec's A14 brackets() into python/pipeline/joined_brackets/, gives § 2's grouping, which is compared with the fenced one.
  4. What it stores. The verdict per event, weapon and gender goes in a new table, tbl_joining_check: the fenced grouping, § 2's grouping, match or not, and when.
  5. When it alerts. Only when the verdict changes, to a mismatch or back, the pipeline sends one message to the existing alert chat through TelegramNotifier (python/pipeline/notifications.py). The scores are already final.

What a mismatch looks like (made-up line-ups)

Fenced§ 2 would giveMessage
V2 (5) + V3 (5) togetherV2 alone, V3 alone (V3 has 4+ and is not the youngest, ust. 5)„PPW2-2026-2027 szabla M: fenced V2+V3 (10); § 2: V2 (5) | V3 (5). Scored as fenced.”
V3 (5) alone, V4 (2) aloneV3 + V4 (7) (ust. 1)„… fenced V3 (5) | V4 (2); § 2: V3+V4 (7). V4 scored as a meeting.”
V0 (3) + V1 (7) + V2 (6) togetherV0 + V1 (10), V2 alone (the exception reaches only V1)„… fenced V0+V1+V2 (16); § 2: V0+V1 (10) | V2 (6). Scored as fenced.”

The options

  1. Score every listing as fenced, and check and alert as above. recommended
    • Scores stay true to the bouts fenced.
    • Every deviation is recorded and reported automatically, so the board can take it up with the organiser.
    • Nothing waits.
  2. Also re-bracket automatically where the listing allows it.
    • A listing that joined more than § 2 allows is split into § 2's brackets. Each gets its own N and the relative order of its fencers in the listing. For example, V2 5 + V3 5 fenced together would be scored as two brackets of 5.
    • It works in one direction only: categories fenced apart that § 2 would have joined have no common order, so they stay as fenced.
    • The split order is an estimate. A V3 fencer who lost a bout to a V2 fencer in that listing is ranked as if that bout never happened.
    • It adds an event-level re-filing step and its tests.
  3. No check. Deviations go unnoticed.

7 · ADR-104 draft Proposed — awaiting your sign-off

ADR-104: SPWS 2026/2027 — the place-and-medal engine and its columns are removed; EVF with a joined-bracket premium and a whole-bracket cap replaces it

Supersedes: ADR-103 §1 (the strategy) and §5 (K, m, b and the three components); the ADR-103 amendment's retention of K, m and b for PZSz.

Amends:

  • ADR-103 §2 (the assignment), §4 (the module), §7 (the pages);
  • ADR-102 (the module);
  • ADR-092 (the annex);
  • ADR-085 (the calculator).

Relates to: ADR-097, ADR-042 and ADR-045, ADR-049, the ADR-036 amendment, ADR-083, ADR-100 (PZSz stays on EVF classic).

Context

  • The released engine never scored a result. It moved single-category scoring away from EVF: 53.5 points for the winner of 8, where EVF gives 98.00.
  • Its columns are empty. Every column it added holds only −1 in every environment (verified 30 Sep).
  • The locked rule (doc/plans/joined-scoring-final-spec-2026-09-30.html):
    • it keeps EVF for single-category brackets and for brackets of 16+;
    • it treats 1–3 fencers as a meeting;
    • it pays older categories of a joined bracket of 4–15 max(EVF × (1 + 0.05 · d), EVF + d);
    • it caps everyone 1 point below the fencer directly ahead.
  • The cap crosses categories. Categories are stored as separate tournaments, and some fencers of a listing are never stored.

Decision

  1. Cleanup first, in its own migration.
    • It deletes the strategy, its branch, its registry row (or marks it inactive while something names it), the six result columns, the review column and parameter, the PLACE_MEDAL value and three breakdown fields.
    • It recreates the readers without them.
    • It starts with a guard that aborts if any of those columns holds a value.
  2. The new engine, in a second migration: the strategy, the chain function, the registry row (SPWS_EVF_JOINED_V1_2026_2027, „SPWS — punkty EVF i premia w stawce łączonej (od sezonu 2026/2027)”, paired with JOINED_BRACKET_CATEGORY_PLACE), the three new columns, the joined order, and the replaced fn_backfill_scoring_engines with the §11 gate.
  3. The joined order is stored, not derived (D1 A), and recompute patches it.
  4. Ingestion refuses a joined listing with a repeated place, or with a fencer who has no category.
  5. The joining check is automatic (D2): stored, and reported by Telegram, never blocking.
  6. Public pages: both compute only with the new engine. fn_public_scoring_params is unchanged.

Alternatives considered

  1. Keep K, m, b and the components "for later". Rejected (D0): unused columns, readers and tests with no consumer.
  2. Edit the old strategy in place. Rejected: released strategies are immutable.
  3. Cap within the category. Rejected: the rule caps at the fencer directly ahead, of any category.
  4. Read sibling rows, or a separate bracket table. Rejected in D1.
  5. A human sign-off on § 2 mismatches. Rejected (D2): the check is automatic.
  6. Put the cap in the strategy. Impossible: it needs the places above.

Consequences

  • Single-category brackets of 4+ and all brackets of 16+ score exactly EVF.
  • Readers move to the new columns in the same release: vw_score, the rolling functions, the drilldown export and the seed export.
  • The PZSz review queue goes back to its five-argument RPC.
  • The operator must resolve pending matches in a joined PPW or MPW listing before commit.
  • New: two migrations, supabase/tests/85_spws_evf_joined_engine.sql, tbl_joining_check, and python/tests/test_joining_rules.py.
  • Deleted: supabase/tests/83_spws_place_medal_engine.sql.

9 · Scenario walk-throughs

  1. PPW1, a joined V3 3 + V4 3 foil listing.
    • The module writes N = 6 and order 343344 to both tournaments.
    • Each writer scores the whole bracket: 96.35, 65.04, 35.41, 22.09, 6.99 and 2.00.
    • The end-of-run check finds the grouping matches § 2, so no message is sent.
  2. A single-category V2 listing of 8. Order 22222222, EVF_CLASSIC, 98.00 … 1.00.
  3. MPW, V0 3 + V1 3 + V2 2 + V3 1. 7th place has a raw 19.60, capped at 19.04, so 22.85 at × 1.2.
  4. A joined listing of 17. EVF_CLASSIC on the joined place, with no premium and no cap.
  5. A joined listing with two 3rd places. Commit is refused, and the refusal asks for the fenced order.
  6. A joined listing with a pending match. Commit is refused until the match is resolved.
  7. A birth-year correction moves a V3 fencer to V4. Recompute patches the digit in every sibling's order, rescores both tournaments, and re-runs the check.
  8. The organiser fenced V2 5 + V3 5 together. The listing is scored as fenced (D2 A). The verdict is stored and one Telegram message goes out. Nobody has to act for the scores to stand.
  9. PEW via evf-sync, or PPS1s. Both run on EVF classic and are unaffected. A scored result would still lock the season, which is why D3 holds ingestion.
  10. The lock race: something is scored before the deploy.
    • The cleanup leaves the assignment unchanged and marks the old engine inactive instead of deleting it. Anything still assigned to it fails closed ("Unknown scoring engine").
    • The engine migration's backfill leaves the assignment and raises a NOTICE.
    • On your go, one privileged revision per affected environment moves PPW and MPW to the new engine.
    • The columns are still dropped, because the guard sees no values in them.
  11. An alias transfer or discard in a joined bracket. The writer rescores from the stored order; the siblings stay correct.
  12. The Admin editor. PPW and MPW show the new engine's panel; the other six show EVF classic. It is read-only after the first score.
  13. A fencer opens the calculator. It follows the active season and shows the same tools and numbers as the annex.
