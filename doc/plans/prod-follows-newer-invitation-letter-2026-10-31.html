04 · The rule

Exactly what the mirror does with the letter

  1. CERT sends no letter: PROD's stays. A blank never clears PROD.
  2. PROD has none: it takes CERT's, as today.
  3. PROD holds an event page and CERT a letter: it takes CERT's, as today (D7 A).
  4. New. PROD's event has not ended (end date today or later), CERT's letter differs, and CERT set its letter later than PROD set its own: it takes CERT's.
  5. Otherwise PROD's stays, and the difference stays listed under "Divergences NOT synced".

"Set its letter" means, on each environment, the time of the last audited change to url_invitation. When there is none, it is the row's ts_created, because the letter came with the insert. Only a changed value counts, so writing the same letter again moves no time. Both projects stamp their server clock in UTC.

After step 4, PROD's own write is audited later than CERT's change. The next run therefore finds equal letters and does nothing. If a person then sets a different letter on PROD, it is newer, and it stands until CERT's letter changes again (N2 A).

Reported: the reconcile log already has a table of every PROD field the run changed, old → new (reconcile_report.py:138). A replaced letter shows up there with no new report code.

Why CERT's time is read in the query, not by a new SQL function

The calendar promotion runs on a schedule from main, so it can run between the push and the migration reaching CERT. A call to a function that doesn't exist on CERT yet would fail that run. A plain subquery works on either schema. PROD's old function ignores the new payload key, and PROD's new function skips step 4 when an older payload doesn't send the key. The release is safe in any order.
