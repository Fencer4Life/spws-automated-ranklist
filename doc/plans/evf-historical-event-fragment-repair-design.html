Consolidate results that belong to the same physical weekend, remove the emptied fragments, repair three independently contaminated event identities, and prove ranklist conservation. No complete-season renumbering and no Guildford prior-link assignment.

Decision boundary

What this repair is—and is not

Approved invariant: preserve the historical numbering

The canonical Guildford event remains PEW62efs-2025-2026. This correction does not chronologically reflow the 2025–2026 season and does not use a prior-season number to choose a new code.

  • In scope: consolidate proven same-weekend result fragments; correct the Munich, Faches/Stockholm and Chania identities uncovered by the full audit; delete only emptied donor events; apply the same reviewed migration to LOCAL, CERT and PROD.
  • Out of scope: renumbering the rest of the calendar, changing ranking rules, fabricating EVF-results-database identities, or assigning a 2026–2027 Guildford carry-over link.
  • Prior-link cardinality: id_prior_event is nullable. The partial unique index permits zero or one link on a current event and prevents two events in the same season from sharing one non-null prior event. “No reliable link” is represented by NULL.
  • Deletion effect: when a donor event is deleted, its incoming references become NULL through the existing ON DELETE SET NULL FK. The repair will not redirect those references.

Deferred decision

After every data repair and validation has passed, run a read-only audit of all 2026–2027 rows that could represent Guildford. Show their codes, dates, locations, EVF calendar identities, and current id_prior_event targets. Stop there. The user will separately decide which event, if any, should link to the repaired Guildford survivor.

Evidence model

One physical weekend owns one event

Event identity comes from the original calendar occurrence—date, location, weapons and durable public EVF calendar identity. The EVF results database is secondary; tournament result URLs continue to point to the original scoring provider such as Fencing Time Live, Engarde or 4Fence. Matching result URLs help expose fragments but are not sufficient by themselves to merge events.

Every mutation is guarded by preconditions over season, event code, dates, location, weapon/category slots, result-source URLs and result counts. Any unexpected CERT/PROD divergence aborts that environment before mutation.

Safety

Fail closed before touching scored history

  1. Acquire an advisory transaction lock so two repair executions cannot interleave.
  2. Resolve events by full txt_code plus season; never by numeric database id copied between environments.
  3. Assert the expected survivor/donor set, organizer, dates, weapons, result URLs and audited row counts.
  4. Build a temporary canonical result map keyed by physical event, weapon, gender, age category and fencer.
  5. For duplicate fencer-slots, prefer original-provider facts, then the EVF results DB, then the explicitly approved stored full-field fallback. An equal-field place conflict or any unreviewed state raises an exception and rolls back.
  6. Move results before tournaments, remove duplicate result rows only after equivalence is proven, and delete an event only after it has zero children, results and registrations.
  7. Recompute affected events through the normal scoring path; compare ranklists and event/result conservation assertions inside the same transaction.
  8. Make the migration idempotent: an already-correct environment is a verified no-op; a partially matching unknown state is an error, never a best-effort continuation.

No broad delete

No event is removed because its name merely resembles a skeleton. Only the explicitly named donor codes above may be deleted, and only after the migration proves they are empty following the reviewed transfers.

TDD

Acceptance assertions first, then RED → GREEN

  1. Write pgTAP acceptance tests. Seed representative fragmented rows; assert the exact canonical codes, tournament/result ownership, duplicate-collapse rules, conservation totals, donor deletion, FK nulling and idempotent rerun.
  2. Prove RED. Run only the new repair test file against the current schema and record the expected failures before adding the migration.
  3. Implement one atomic SQL migration. Use data-driven helper blocks scoped to the named event clusters; no production dependency and no public API change.
  4. Prove GREEN locally. Run the new pgTAP file, affected carry-over/calendar/scoring tests, then the complete database suite.
  5. Update authoritative documentation. Amend the Markdown sources and regenerate HTML for ADR-039, ADR-028, ADR-043 and ADR-046. Correct “exactly one” to “zero or one” in R008. Synchronize the Project Specification, requirements traceability matrix, events handbook and scoring handbook.
  6. Pass the documentation coherence gate. Follow the documentation standard, refresh Graphify, run generated-document checks, python scripts/check_docs.py --changed-from origin/main, coherence and spec-sync checks.

Ranklist impact

Expected points outcome: conservation, not recalculation drift

The repair changes event ownership, not sporting facts. For every affected fencer/category, the pre-repair and post-repair effective result set must be compared. Equivalent duplicates currently capable of presenting one physical result more than once are consolidated; genuine unique results are preserved. The migration must fail if the final place, field size or calculated points of any unique sporting result changes unexpectedly.

  • Capture affected ranklist rows and result facts before the migration.
  • After recompute, produce a diff classifying each change as duplicate removal, event-code presentation change, or unexpected scoring change.
  • Require zero unexpected scoring changes and zero lost unique sporting results before promotion beyond LOCAL.

Release runbook

Apply consistently to all environments

  1. Commit the reviewed tests, migration and coherent documentation on the isolated task branch after Graphify refresh.
  2. Integrate through the clean integration checkout, run the required repository gates, push main, and monitor CI.
  3. Deploy to LOCAL; capture before/after event, tournament, result, prior-link and affected-ranklist evidence.
  4. Deploy the identical migration to CERT; rerun the same assertions and compare with LOCAL.
  5. Deploy the identical migration to PROD only after CERT evidence matches; rerun read-only proof queries and compare all three environments.
  6. Final mandatory read-only Guildford-link check: list every 2026–2027 Guildford candidate and every row referencing any repaired/deleted 2025–2026 fragment. Report current links and unlinked candidates to the user. Do not assign, move or clear any additional link. Wait for the user to specify where the real event link should be hooked.
