1 · Why this is being done

doc/tools/Tabela-punktacji-SPWS_2026-2027.html is a finished, self-contained Polish document — Załącznik nr 1 to the Regulation on selecting the Polish veterans national team. It carries a single-result calculator, the full scoring table for fields of 4–300 entries across places 1–300, and a CSV export. Version 0.1, status projekt, dated 11.09.2026.

It has to be reachable at an address, for the same reason the points calculator did: messenger and iOS Files previews open HTML with JavaScript disabled, and this document computes its entire table in the browser. Sent as an attachment it arrives blank.

GitHub Pages is the review-and-circulation address. The document's final home is weteraniszermierki.pl as a PROD deployment once the annex is official — which is why nothing in its design may depend on the ranklist application around it.

2 · Planning-gate result

Publication path — already proven

Vite copies frontend/public/ into dist/ unaided; no build-configuration entry and no workflow step are required. .github/workflows/release.yml uploads frontend/dist with actions/upload-pages-artifact@v3 (job build) and publishes it with actions/deploy-pages@v4 (job deploy-pages). The points calculator has shipped this way since 15 August 2026.

Algorithm parity — verified, exact

The document states it uses the algorithm marked “SPWS” in the official calculator. That claim was checked against the implementation rather than taken on trust, and it holds line for line:

One deliberate difference, stated in the document's own heading: the table's domain starts at N ≥ 4 where the calculator accepts N ≥ 2. Not a defect — a scope choice — but worth knowing that the two tools answer over different ranges.

Release guards

The release job greps the whole of frontend/dist/ for service_role, 127.0.0.1 and supabase-demo and fails on a hit. The document contains none of the three. Its only external reference is an absolute link to the calculator on Pages, which is the right choice for the WordPress destination — a relative link would 404 under a WordPress path.

Governance

ADR-085 §2 closed the static-page route as a one-off and requires any further standalone page to carry its own decision. This plan supplies that as ADR-092. Two corrections to earlier assumptions, both verified against the corpus:

Corrections
  • ADR-091 is already taken — 091-no-season-skeletons-for-scraped-events. The next free number is ADR-092.
  • The calculator was never given its own FR. It was folded into FR-59 (app shell / drawer navigation). Following that precedent, this change amends FR-59 rather than minting FR-136.

ADR-085 itself needs no amendment: it anticipated this case. Leaving it untouched keeps it free to be superseded on its own expiry condition, when the proposed scoring becomes the scoring in force and the calculator page is deleted.

4 · Locale implementation

The calculator holds every string in a JavaScript dictionary T = {pl:{…}, en:{…}} and rewrites [data-i18n] text nodes. That suits a UI of about twenty-five short labels. It does not transfer here: this document is prose as well as UI, and a dictionary would render an empty page when JavaScript does not run — the exact failure that made hosting necessary in the first place.

Instead: one file, both languages in the markup, switched by CSS alone.

<nav class="seg lang">          <!-- radios PRECEDE the content, sharing a parent with <main> -->
  <input type="radio" name="lang" id="langPl" checked><label for="langPl">PL</label>
  <input type="radio" name="lang" id="langEn"><label for="langEn">EN</label>
</nav>
<main>
  <div class="copy-pl" lang="pl">…</div>
  <div class="copy-en" lang="en">…</div>
</main>

#langPl:checked ~ main .copy-en { display: none }
#langEn:checked ~ main .copy-pl { display: none }

What this buys:

  • The switch works with JavaScript disabled. Polish renders from the markup alone, and the toggle still functions — so even the messenger and Files previews that broke the calculator show a usable document, in either language.
  • JavaScript adds enhancements only, never preconditions: honour ?lang=pl|en when present, remember the choice, and correct document.documentElement.lang and document.title. Reuse the calculator's param() regex helper and its try/catch around localStorage — that guard exists because storage access throws when the file is opened over file:.
  • One URL, one file, one upload. The same ?lang= contract the drawer already speaks, and a file that is fully functional opened cold at any address.
  • Only the static copy is duplicated. The table, the calculator logic and the script stay single.
Implementation constraint worth recording

The general sibling combinator ~ requires the radio inputs to precede the content blocks and share a parent with <main>. Reorder the markup later and the switch stops working silently — no error, just a page stuck in one language. :has() would lift the constraint and is deliberately not used: these files are opened straight from phone filesystems, and the house style for them avoids newer browser APIs, which is why the calculator hand-rolls param() instead of using URLSearchParams and numberPl instead of Intl.

5 · The English version

Roughly thirty static strings: the eyebrow and h1, the lead, three meta chips, both card headings and their prose, the formula legend, the source note, the table heading and its explanatory paragraph, two button captions, the status-line templates, six breakdown labels, the legend, the footer, <title> and the description meta.

Terminology is reused, not invented

The calculator's T.en already defines every term this document needs — Number of entries, Finishing place, Competition rank coefficient, pts, Place, Points, Base for 1st place, Place points, Round bonus, Podium bonus, Subtotal, Result. Two documents describing one formula must not ship two competing English vocabularies for it, so these are carried over verbatim. New terms needed beyond that set: Annex 1, Polish Veterans Fencing Cup, Draft, place not possible, Download table as CSV, Show selected result in the table.

Three script-level additions, since the script is shared: numberPl gains an English branch (decimal point rather than comma, mirroring the calculator's num()), the CSV header row is localised, and the CSV download filename gets an English form.

The translation goes to the user for review before release. It reaches fencers, so approving it is the user's call, not the implementer's.

6 · ADR-092 — for sign-off

Draft decision, to be signed off before any code

Title: A second standalone static page — the scoring-table annex, published bilingually.

Status: Proposed, 2026-09-11. Relates to: ADR-085 §2 (which requires this decision to exist), ADR-011 (the page rides the existing Pages artifact), ADR-090 (the WordPress destination), ADR-015 §1 as amended by ADR-085 (the drawer gains a fourth entry).

Decision, in four parts:

  1. The annex ships as frontend/public/tabela-punktacji.html, copied into dist/ by Vite and published to Pages by the existing release pipeline. The drawer links it with a relative <a href> carrying the active locale, opened in a new tab.
  2. Bilingual in one file, switched by CSS, so the document works with JavaScript disabled and depends on nothing around it — a precondition for the WordPress destination.
  3. This remains an exception. Two pages now use this route, both informational documents about the scoring formula. It still establishes no general pattern; a third requires its own decision. The default routes remain a view inside the application, or the register.html mechanism.
  4. Expiry and succession. While the annex carries Status: projekt the page is noindex, nofollow. When the annex is adopted it moves to weteraniszermierki.pl as a PROD deployment; the drawer entry then becomes a WordPress menu item and this ADR is revisited rather than silently outlived.

Why neither default route applies: the annex is content, not application state; it needs no ranklist data and no scoring engine; and it must remain a single file that transfers byte-identically to WordPress, which a bundled view cannot.

Consequence to accept, stated plainly: the scoring function now exists in three implementations — the ranklist engine (fn_calc_tournament_scores, the scoring in force), the calculator page and this annex (both the proposal). The two pages are verified identical by reading, not by a test, because they are independent documents rather than copies of one file. ADR-085's own expiry condition already commits to collapsing this duplication when the proposal becomes the scoring in force.

9 · Scenario walk-through

A fencer on a phone, Polish interface. Opens the ranklist, taps the hamburger, sees four entries, taps “Tabela punktacji”. A new tab opens at …/tabela-punktacji.html?lang=pl; the drawer closes behind them. The document renders in Polish, the calculator is usable immediately, and the table fills in progressively with a status line reporting progress.

The same fencer sends the link to a colleague abroad. The colleague opens it with the ranklist set to English — or simply taps EN on the page itself. Either route reaches the English copy; the URL alone is enough, because language is a property of the page rather than of the app that linked it.

A board member opens the file from a WhatsApp attachment. JavaScript does not run in the preview. Polish still renders, the PL/EN toggle still works, and the page says plainly what it is — the calculator and table are inert, which is the signal to open the link instead. The calculator page, by contrast, shows nothing at all in this situation.

After adoption. The annex moves to weteraniszermierki.pl. The file transfers unchanged because it never depended on the drawer, the ?lang= parameter or any relative path. The noindex meta is removed as a deliberate act, and the drawer entry is replaced by a WordPress menu item built by hand in wp-admin.
