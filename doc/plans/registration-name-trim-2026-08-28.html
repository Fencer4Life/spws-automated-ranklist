The trailing space on the entry list

Two of the fourteen live PROD entries were stored as "Gary " and "KUCIĘBA ". The form validated with .trim() and then submitted the raw string. Fixed at the form boundary and in the table, with the backfill riding along in the migration.

What was actually wrong

Validate one value, submit another

RegistrationForm.svelte gated its Continue button on surname.trim() !== '', then passed the untrimmed surname straight into the match lookup, the transfer note and the RPC payload. The trim was only ever used to decide the button was enabled — it never reached the data.

tbl_fencer has carried trg_trim_fencer_names since May (migration 20260503000004), added after the same class of defect stored ' Bartosz'. tbl_registration never got the equivalent, so when the public form went live the identical bug reappeared on a table that anyone on the internet can write to.

× The public roster carries the padding

vw_registration_entry_list projects the names straight through and EntryList.svelte renders them raw. HTML collapses the whitespace visually, so the page looks correct — the stored and published value is not.

Correction to the handover

The FTL seed file was never affected

The 28 August handover lists the seed file as a casualty. It is not. ftl_seed_export.to_canonical_name() already calls .strip() on both names, and it is the only path a registration name takes into the XML — confirmed by reference search, not by reading around it. Dedupe was never affected either: uq_registration_unmatched_identity arbitrates on upper(btrim(...)).

So the blast radius is narrower than recorded: what we store and publish, not what we export or match on. The fix is still worth making — it is what puts all three in agreement instead of leaving two of them quietly compensating for the first.

The change

Both boundaries, same as the fencer precedent

DBmigration 20260828000001
  • trg_trim_registration_names — BEFORE INSERT OR UPDATE, btrims both name columns for every caller. The table carries an admin FOR ALL RLS policy, so a PostgREST write never passes through the form at all; the trigger is the only thing that covers it.
  • Backfill scoped to rows that actually differ — a no-op on a clean environment, and re-running the migration cannot touch a clean row.
  • Safe against the unique index: its key is already upper(btrim(...)), so trimming leaves every key byte-identical and no collision can be introduced.
UIRegistrationForm.svelte
  • Normalise once in submitIdentity() rather than at each consumer — one funnel covers the match lookup, the duplicate check, the transfer note and the RPC payload.
  • Deliberately not in the input handler: that would stop a fencer typing the space inside a compound name.

→ Why the trigger cannot change dedupe behaviour

In INSERT … ON CONFLICT, Postgres fires BEFORE INSERT row triggers first, then arbitrates on the modified tuple. A trigger that rewrites the arbiter's input is normally a hazard. Here it is inert, because btrim is idempotent against a btrim-normalised index key. Test 57.7 pins that rather than assuming it.
