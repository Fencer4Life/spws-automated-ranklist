01What this adds, and what it defers

The calendar carries SPWS (PPW/MPW), EVF (PEW) and FIE (MEW/MSW/PSW) events. It carries nothing from PZSz — Polski Związek Szermierczy, the Polish national federation, so a veteran planning to test themselves at a senior national competition has to look somewhere else entirely.

The goal is to encourage veterans to enter harder fields. That splits into two deliverables, and this plan is the first only.

#DeliverableStatus
1PZSz as a fourth organizer; scrape the Polish national senior calendar; show the events in light redthis plan
2Ingest veteran results from FTL and score them into the rankingdeferred — §10

Deliverable 1 stands alone. Veterans can see and plan for these events the day it ships, and nothing in it depends on the scoring rules being settled.

Scope, as confirmed

  • Age category Seniorzy (S) only.
  • Series PPS (Puchar Polski Seniorów) and MPS (Mistrzostwa Polski Seniorów) only — not the World Cups, Grand Prix and World/European championships that carry the same age category on the same page.
  • Current season only. No backfill. Membership is decided by our season window, not by PZSz's season label — §4.
  • The PZSz Weteran (W) category is ignored outright. Those are SPWS's own MPW and PPW events, already ours.

03The source, and its 70-row cap

pzszerm.pl/zawody/kalendarium-zawodow/ is WordPress, server-rendered, no JavaScript. Rows are td.tab-row cells: name (linked to …/zawody/?id=NNNN), age category, weapons, season, start date, end date, location, attachments. Detail pages additionally carry a full weapon × gender tournament breakdown — better metadata than EVF publishes, and nothing like evf_calendar.py's invitation-PDF weapon archaeology is needed.

The finding that shapes the whole scraper

The listing caps at 70 rows, with no pagination — and different filters return entirely different windows.

Reading the obvious default view would have silently lost all three round I events. The cap truncates from the bottom, the view renders descending, and its earliest row is 14.11.2026 — so October 2026 is simply not there.

QueryRowsVerdict
no filter70capped; descending, earliest 14.11.2026 — Sept/Oct 2026 invisible
Kategorie_wiekowe = Seniorzy (S)70capped
Nazwa = Puchar Polski senior70capped
SezonAutocomplete = 2026/202770capped
Nazwa + SezonAutocomplete6complete

Therefore: any response of exactly 70 rows is presumed truncated and must raise. It is the one assertion that stops this scraper failing quietly.

Why a last-seen-id cursor does not replace the cap assertion

The natural instinct is to persist the highest PZSz event id and start the next run at id + 1. It does not work as a query cursor, for three separate reasons — though the id is worth storing for other reasons entirely (§6).

ObstacleEvidence
The listing has no offset parameterThe form exposes only Nazwa, Kategorie_wiekowe_z_turniejow, Bronie[0], SezonAutocomplete and Miejsce. There is no cursor to pass, so an id cannot narrow the capped query.
Detail pages lack the fields we needId-walking /zawody/?id=N is possible, but the detail page of a future event carries only name, start date, city and organizing club — verified on id 4588. No end date, no weapons, no season, no age category. Those exist only on the listing row.
Ids are creation order, not date orderId 4637 is July 2027; id 4661 is December 2026. So last + 1 finds only newly created rows and would never revisit an edited one — a moved date, a changed venue, a cancellation. For a calendar that is precisely the wrong failure mode.

The cap is also not currently biting: the narrowed query returns 6 rows this season and 13 last season, far under 70. The assertion exists for the day that changes, and there is a third narrowing axis held in reserve — Bronie[0], giving Nazwa × season × weapon at roughly five rows apiece. That is the escape hatch, not an id cursor.

Source data quality

Live rows carry an end date of 11.05.0251 (id 4307), the typo mężćzyzn (id 4412), and inconsistent Seniorów/seniorów casing inside one series. Date parsing rejects an out-of-range year loudly rather than writing it to tbl_event.dt_end; name matching is case- and diacritic-tolerant.

04Our season decides, not theirs

PZSz does not define seasons the way we do, so their season label decides nothing. An event belongs to SPWS-2026-2027 if and only if its dates fall inside our own season window — tbl_season.dt_start … dt_end.

SezonAutocomplete is demoted to what it actually is: a pagination key for getting under the 70-row cap, worthless as semantics but load-bearing as access. The scraper:

  1. Reads the active season from our database — reusing _get_active_season() (python/scrapers/evf_sync.py:84), which already returns txt_code, dt_start, dt_end, id_season WHERE bool_active = TRUE.
  2. Derives the PZSz season keys that could hold a date in that window, from the calendar years the window touches. For 2026-07-13 … 2027-07-15 that is {2025/2026, 2026/2027, 2027/2028}.
  3. Fetches each Nazwa × season combination, asserting none returns 70.
  4. Unions the rows, deduplicating on the PZSz event id.
  5. Filters by date against our window, discarding whatever PZSz calls the season.

Verified live — the six requested events fall out exactly, and nothing else:

'Puchar Polski senior'      2025/2026 → 13    'Mistrzostwa Polski senior' 2025/2026 →  1
'Puchar Polski senior'      2026/2027 →  6    'Mistrzostwa Polski senior' 2026/2027 →  0
'Puchar Polski senior'      2027/2028 →  0    'Mistrzostwa Polski senior' 2027/2028 →  0

union 20 rows  →  date-filtered to SPWS-2026-2027  →  6 events

This makes the boundary cases right rather than merely lucky. An event PZSz labels 2025/2026 that runs after our season opens is ours; one they label 2026/2027 that runs past our season close is not. The pzsz_season cell is still captured, purely as provenance.

Three measured properties that make this safe

A season key PZSz does not have returns zero, not the unfiltered 70 Confirmed against 2027/2028. Querying a season that does not exist yet is harmless, which is exactly what lets the candidate set run a year ahead of publication. Had an unknown season silently fallen back to unfiltered, this approach would have looked correct while scraping the wrong thing.
Nazwa matches case-insensitively, as a substring So the ASCII-safe values Puchar Polski senior and Mistrzostwa Polski senior are used. That removes the ó percent-encoding trap entirely — a raw ó returns zero rows — while still excluding juniors, whose events read juniorów. Both Seniorów and seniorów casings are caught.
Nazwa alone is not sufficient Puchar Polski seniorów on its own returns the capped 70. The season key is required as pagination even though it is ignored as meaning. Mistrzostwa Polski Seniorów alone returns 10 and is complete, but both series take the same path and the cap assertion covers both.

05Design

1 · Organizer — a migration, not a seed edit

tbl_organizer rows exist only in the PROD seed dumps (supabase/seed_prod_*.sql:14-16); there is no INSERT INTO tbl_organizer in any migration. Two constraints decide the vehicle:

  • Migrations run before the seed dump on CI and db reset, so the insert must be idempotent and survive the seed re-inserting the other three codes.
  • python/pipeline/promote.py resolves id_organizer to PROD by code and raises if unresolved (ADR-081).
Ordering constraint PZSz must exist on CERT and PROD before the first calendar promote runs, or the promote fails outright. The organizer migration is step 1 for this reason, not for tidiness. 
INSERT INTO tbl_organizer (txt_code, txt_name)
VALUES ('PZSz', 'Polski Związek Szermierczy')
ON CONFLICT (txt_code) DO NOTHING;

idx_organizer_code (20250301000001_enums_tables_indexes.sql:169) backs the ON CONFLICT. The name stays Polish: Związek has no clean English equivalent, and the sibling row Stowarzyszenie Polskich Weteranów Szermierki is already stored untranslated.

2 · Event codes

Follows ADR-046 — round number, then lowercase weapon letters, then season. The Roman numeral in the event name carries the round. See §2 for the six planned codes; MPS becomes MPSefs-2026-2027 when announced.

Gender-split rounds A round is occasionally split by gender, and the two halves are separate competitions, not one event over two days — verified on both seasons that show it. Round IV épée 2025/2026 ran men in Gliwice 16–17.05 and women in Warszawa 17.05; the 2024/2025 equivalent ran men in Gliwice 17–18.05 under PIAST GLIWICE and women in Warszawa 11.05 under AZS AWF WARSZAWA — different cities, different organizing clubs, six days apart. Two events, which collide on PPS4e.

The rule is to insert an uppercase gender letter before the weapon letters — PPS4We for women and PPS4Me for men.

W, not the F this codebase would otherwise imply. Event-code weapon letters are English — _WEAPON_LETTERS = {"EPEE": "e", "FOIL": "f", "SABRE": "s"} — while the project's gender letters are M/F (enum_gender_type AS ENUM ('M','F'), and tournament codes read MPW-V0-F-EPEE). Following that convention would give PPS4Fe, one case-fold away from PPS4fe, in a scheme whose trailing lowercase run is the weapon list. F is foil. So the existing gender convention cannot be inherited here, and W is the letter that carries no weapon meaning. The Polish K would dodge the clash too, but sets a Polish gender letter against English weapon letters in one code.

Uppercase also keeps the gender letter clear of the lowercase weapon run, so weaponLetters()'s trailing /[efs]+$/ still resolves E and panelLabel() degrades to a readable PPS4W / PPS4M on the 48px tile. No announced 2026/2027 event exercises this, so it ships with a fail-loud collision guard: two events resolving to one code raise rather than overwrite, mirroring evf_calendar.py's LogicalIntegrityError.

3 · Events are created childless — no tournament rows

tbl_tournament.enum_age_category is NOT NULL over V0..V4, and a senior bracket has no honest value for it. That question belongs to deliverable 2, so this plan creates no tournament rows at all.

This is a supported state, not a workaround. ADR-081 records that the reconciler's "CREATE is childless", and ADR-084 deliberately reads weapons from the code (weaponLetters()) rather than arr_weapons, precisely because that column cannot express "unknown" — 86 of 96 CERT rows sit on its all-three default. Tiles and cards therefore render weapons correctly with zero tournaments present.

5 · Scraper — two modules, mirroring the EVF split

python/scrapers/pzsz_calendar.py — pure parsing and planning, no I/O to our database:

  • season_keys_for_window(dt_start, dt_end) — our window → PZSz pagination keys
  • fetch_series(series, season_key) — the Nazwa + SezonAutocomplete query
  • parse_calendar_html(html) — rows → dicts
  • assert_not_truncated(rows) — raise when exactly 70
  • is_national_senior(row) — Seniorzy (S) ∩ PPS/MPS name, rejecting Świata / Europy / Grand Prix
  • belongs_to_season(row, dt_start, dt_end) — the membership rule; our dates decide
  • parse_round(name) — Roman numeral → int
  • weapon_letters(row) — from the weapons cell
  • normalise_date(raw) — dd.mm.yyyy → ISO, raising on an out-of-range year
  • plan_event_codes(rows, season_code) — codes plus the collision guard

python/scrapers/pzsz_sync.py — the CLI: fetch → filter → plan → diff against CERT → insert/update, with --dry-run for LOCAL parity.

Deliberately not reusing evf_calendar.py Its 1536 lines are EVF-specific pathology — invitation-PDF weapon extraction, slug dedup, future-COMPLETED healing — none of which applies to a clean HTML table. Generalising it now would drag all of that in.
One targeted refactor _management_query and _telegram (python/scrapers/evf_sync.py:51,72) carry the retry-on-429/503 behaviour a scheduled workflow needs; python/tools/_backends.py has no retry and is framed for one-shot tools. Extract both into python/scrapers/_supabase.py and re-point evf_sync at it — behaviour-preserving, and it stops pzsz_sync either duplicating them or importing evf_sync and dragging in the FTL auth chain.

6 · Workflow — a separate workflow, same cron, not a second step

Not a job inside evf-sync.yml. A job there shares one run identity: a single red/green, one re-run button, one set of workflow_dispatch inputs that are EVF-specific (mode, event_code, filter_stale), and a workflow whose name would stop describing what it does. Job-level independence would be real; run-level independence would not — and the run is what an operator actually looks at.

New .github/workflows/pzsz-sync.yml, modelled on evf-sync.yml but much smaller: cron '0 6 * * *', the same minute as evf-sync.yml, plus workflow_dispatch with a --dry-run input.

  • Job 1 sync — scrape → write CERT. permissions: contents: read. No concurrency group; it touches nothing on PROD, so it runs genuinely in parallel with the EVF scrape.
  • Job 2 promote-calendar — python -m python.pipeline.promote --mode calendar, in concurrency: group: prod-write, with if: ${{ !cancelled() }}. That condition is not cosmetic: evf-sync.yml documents at length that without it an upstream failure silently skips the promote, which cost 13 unpromoted events on 14 July 2026.
  • Telegram on failure — the established alert surface, one alert per workflow.
The contention this creates

Concurrency groups are repository-scoped, and cancel-in-progress: false is not enough on its own.

GitHub's documented default is that only one job may be pending per group, and a newly queued job cancels the already-pending one. With evf-sync.yml holding prod-write for promote-calendar-pre, PZSz's promote would sit pending — and EVF's later promote-calendar would cancel it. Silently, because cancelled is not failed and nothing would alert.

The fix is one line on every job in the group: queue: max, which queues up to 100 runs instead of cancelling the pending one. It goes on the new job and on the two promote jobs in evf-sync.yml and the one in promote.yml — the setting is per-job, so protecting only the new job would leave it cancellable by the others.

If queue: max proves unavailable on this runner it fails as a workflow validation error on the first run — loudly, immediately, cheap to detect. The fallback is a 15-minute stagger (45 5 * * *), which costs nothing real.

Why a cancelled or failed promote is survivable anyway

promote --mode calendar is a whole-active-season create/update/delete reconciler keyed on txt_code (ADR-081). It converges everything in CERT, not just the rows the calling workflow scraped. So the two promotes are mutually redundant by construction:

What failsEVF runPZSz runPROD outcome
PZSz scrapegreenred, own alertPZSz rows hold yesterday's state; EVF converges as normal
EVF scrapered, own alertgreenEVF rows hold; PZSz lands
PZSz promotegreenredEVF's promote converges the PZSz rows minutes later
EVF promoteredgreenPZSz's promote converges the EVF rows
both promotesredredtwo alerts; CERT still correct; next run converges

CERT is the source of truth for the calendar and is never left wrong by a promote failure. That is what makes same-minute scheduling safe rather than merely convenient.

The invitation letter — a fill-when-available loop

Every PPS event of 2025/2026 carries a komunikat; none of the six 2026/2027 events carries one yet — their detail pages read Brak komunikatów. The letter is published closer to the event, so the field cannot be filled at first scrape and must be filled later.

That is free from the daily cron. Each run re-visits the detail page of every future PZSz event in the active season and fills url_invitation the first time the section stops being empty. Fill-blank-only: an admin-entered URL is never overwritten, matching the reconciler's existing field-ownership split (ADR-081).

detail page  →  <a href="/test/fileDownload.php?fileId=…" download>Komunikat organizatora…</a>
url_invitation = https://pzszerm.pl/test/fileDownload.php?fileId=…      → HTTP 200, application/pdf
The EVF PDF heuristic does not transfer parse_event_detail_html() finds an invitation by testing href.lower().endswith(".pdf"). The PZSz URL is /test/fileDownload.php?fileId=… — an opaque download endpoint with no extension, so that rule finds nothing. PZSz anchors on the labelled Komunikaty organizatora section instead, which is more reliable than a filename heuristic rather than less.

The venue address — city now, street from the letter

The listing gives a clean city in Miejsce — Poznań, Gdańsk, Szczecin, Konin, Warszawa, Wrocław — with none of the venue-string pollution the EVF scraper wrote into txt_location. The street address appears only inside the komunikat, but does so reliably: 7 of 7 carried one (ul. Siennicka 40B, ul. Grzegorza Przemyka 5, Ul. VII Dwór 7).

So txt_location and txt_country = 'PL' are populated at first scrape; txt_venue_address is populated by the same fill-when-available pass that grabs the letter, parsing the PDF with pypdf — already a dependency of the EVF workflow.

The two fields that do not exist

PPS and MPS have no per-event registration deadline and no per-event registration link. This is the entry model, not a gap in the scrape.

All seven komunikaty say the same thing where a deadline would be — entry is “zgodnie z regulaminem PZS”, per the federation's standing regulations — with the only concrete cutoff being confirmation to the Technical Committee 45 minutes before the start. That is a check-in rule at the venue, not a registration deadline. Three of six contain the phrase Termin zgłoszeń; in every case it resolves to the standing regulation, never to a date.

Nor is there a link to point at. Zero of seven komunikaty reference a registration host (engarde, fencingtimelive, ophardt); the single URL found in any of them was a host club's own homepage. PZSz runs entries through the licence system reached from Licencje / System Sorga, behind pzszerm.pl/logowanie/ — club-mediated and login-walled.

Why we should not populate url_registration anyway url_registration drives a registration affordance on the event card, and a non-empty value plus dt_end is what lights the tile's live-registration dot (ADR-084 §8). Pointing it at a club-officials login would tell a veteran they can enter when in fact they must go through their club. An empty field states the truth; a plausible-looking wrong link does not.

The recommendation is therefore to leave both columns NULL for PZSz events and to carry the entry route as prose the fencer can act on, rather than to synthesise a link. If a per-event entry URL ever appears in a komunikat, the harvesting machinery below picks it up with no schema change.

Reused harvesting machinery

evf_calendar.py already carries the constants this needs, Polish included — _REGISTRATION_HOSTS, _REGISTRATION_KEYWORDS (zgłoszenia), _INVITATION_KEYWORDS (zaproszenie, regulamin) and _DEADLINE_PATTERNS (termin). They move into a shared module alongside _supabase.py rather than being duplicated.

A recorded precedent worth respecting HARVEST_DEADLINE = False in evf_calendar.py:294 disables EVF deadline harvesting, with the reason in the comment: a live hit rate of 0 in 13 against EVF detail pages. Deadline regexes over federation prose have a measured near-zero yield in this project already. PZSz measures 0 in 7. The deadline harvest ships off for PZSz too, behind the same flag, and is turned on only if real phrasings are ever observed.

Storing the PZSz event id

Events gain id_pzsz_event INTEGER, mirroring how EVF events already carry id_evf_calendar_event, id_evf_competition, id_evf_event and txt_evf_slug. It earns its place three times over:

  • Stable identity. PZSz names drift — casing changes between Seniorów and seniorów, and one live row reads mężćzyzn. An id survives a rename; a name-based match would create a duplicate event.
  • The re-check key. The fill-when-available pass needs to know which detail page belongs to which of our rows.
  • Change detection. A row whose id we hold but which vanishes from the listing is a cancellation or a re-key, and should be surfaced rather than silently dropped.

11Deferred: scoring, and its measured blast radius

Recorded now so deliverable 2 starts from facts rather than a fresh investigation.

The rule, as decided PPS and MPS results score with the raw senior placing — 12th of 120 is 12th of 120 — computed by whatever scoring is in force for the active season. Participation is not obligatory, and the ranklist caps how many such results count: best 1 or best 2, to be settled.

The best-N cap needs no new machinery. tbl_scoring_config.json_ranking_rules is per-season JSON already shaped as {"best": N, "types": [...]} — exactly the form {"best": 2, "types": ["PPS", "MPS"]} requires.

Found while scraping — PZSz may host its own results Each tournament has its own page at /zawody/kalendarium-zawodow/turniej/?id=NNNNN, linked from the event, carrying tabs for Lista startowa, Grupy, Ranking Grupowy, Tabela and Klasyfikacja końcowa — a full results platform of their own, with pool-sheet markup already present in the page. The one sampled (id 10520, MPS Warszawa 2025/2026) was empty, so coverage is unverified and this is a lead rather than a finding. If PZSz populates it, deliverable 2 may not need FencingTimeLive for PPS and MPS at all — which would also dissolve the parse_tournament_name() Senior → V0 collision below. Worth measuring across completed events before designing the results path.

Live precedent for exactly this bug PSW was added to the enum and to the scoring function in March 2025 but never to the lifecycle trigger, which still carries only the five original branches. PSW tournaments get a NULL num_multiplier today. Worth fixing in the same pass.

Two further known items

  • tbl_tournament.enum_age_category is NOT NULL over V0..V4. Raw senior placing means one tournament row per weapon × gender with no honest V-cat, so it needs a SENIOR enum member — and fn_age_category's COALESCE(..., t.enum_age_category) fallback (ADR-010) must not then file an unknown-birth-year fencer into a SENIOR ranking that does not exist.
  • parse_tournament_name() (python/tools/scrape_ftl_event_urls.py:289) maps a bracket named Senior to V0, from feedback dated 2 May 2026. On a genuinely senior PZSz event that silently mis-tags every bracket. It must become conditional on the event's type rather than applying globally.

The results path itself needs no new machinery: ADR-029's populate-urls.yml → populate_tournament_urls.py → scrape-tournament.yml chain is organizer-agnostic and works from an admin-entered FTL event URL.
